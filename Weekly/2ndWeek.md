# 3. 문제 발생

## 문제 상황 1 : 로그인/로그아웃 HTTP 메서드 GET으로

### 원인 분석

- 처음에는 서버 상태를 변경하지 않고, 리소스 또한 변경하지 않는다고 여겨 GET으로 정의했음
- 그러나 StackOverflow, 해외 테크 블로그 등을 참고한 결과, GET 메서드를 사용하지 않는다고 함
    - GET으로 접근하기 위해서는 Query String을 통해서 접근해야 하는데, String Query에 아이디와 비밀번호 등 클라이언트의 중요한 정보가 포함되어 있어 보안상 위험하다
    - RESTful 관점에서 POST가 적절하다고 한다. 이유는 GET의 경우 서버의 상태가 변하지 않기 때문에 캐시될 확률이 높다고 한다.

## 문제 상황 2 : 기능 누락

### 원인 분석

- 좋아요는 누르기가 있다면 취소 또한 가능하다는 것을 잊고 있었음
- 댓글 또한 리소스라 추가, 수정, 읽기, 삭제가 가능하지만, 삭제를 정의하지 못했음
- 로그인, 회원가입 2기능의 반대인 로그아웃, 회원 탈퇴 또한 있어야 한다

## 문제 상황 3 : 상태코드 204 응답 본문 작성

### 원인 분석

- 상태 코드 204는 본문 내용을 보낼 필요가 없음
- DELETE를 완료했다는 상태코드로, 리소스 측면에서 DELETE는 참조되는 데이터 마저도 삭제하는 것으로 정의됐기 때문에, 응답 본문에 담아 보낼 내용이 없음
- 그러나 개념 미숙지로 응답 본문에 내용을 채움

## 문제 상황 4 : 응답 본문에 개인정보 포함

### 원인 분석

- 2차 명세서 작성할때 응답 본문에 이메일, 닉네임, 비밀번호 등 클라이언트의 중요한 정보를 포함하여 반환했음
- 서버는 Stateless를 유지해야 하므로, 받은 데이터는 다시 그대로 돌려줘야 한다고 판단해서 클라이언트로부터 받은 정보 + 필요한 정보를 묶어서 응답으로 반환했다.
- 이렇게 하면 당연하게도 보안상 문제가 발생하고, 실제 웹서비스를 이용할 시에 개발자 모드로 확인할 수 있어 해킹 당할 확률이 크다.

# 5. KPT (Keep-Problem-Try)

## Keep

- 원래였다면 조금이라도 막히는게 있다면 GPT를 활용해서 문제를 쉽게 해결했을 것이다. 근데 찰리의 추천대로 GPT 사용 최소화(내가 알고 있는 개념 확인 및 바로잡기 용도로만)해서 Old School한 방식으로 학습을 이어나가고 있다. 확실히 과제를 진행하고 문서를 정리하는데 있어서 작업 시간이 배로 늘었으나, 스스로 자료를 찾고, 더 나아가서 공식 문서와 해외 테크 블로그를 보면서 정리하는데, 노력하는 느낌이 들어서 개인적으로 만족한다
- 과제를 한번 끝냈다고 거기서 끝내는 것이 아니라, 반복적으로 확인하고 실수한걸 캐치하고 바로잡는 활동을 하고 있는데, 이렇게 하는게 확실히 성장에 도움은 되는 것 같다.

## Problem

- 딥다이브 때도 느꼈지만, 핀트를 잘 못 잡는다. 그래서 결국에는 많은 시간을 들여서 자료조사를 하고 정리를 하지만, 질문에 대한 대답은 항상 부족하다. 그리고 정리를 잘 못하고, 남들에 비해 딥다이브의 깊이 또한 깊지 않고, 완벽하게 이해를 못 해서 붙잡다가 시간이 가버리는 경우도 많다. 이 부분은 계속하면 늘곘지만, 당장은 아쉽다. HTTP 내용 정리할때도 위 이유 때문에 힘들었다.
- REST API 명세서를 작성하면서 이게 RESTful한가에 대해서 확신을 못한 채로 과제를 진행했다. REST API 수업 내용을 완벽하게 이해하지 못한게 크게 작용해서, REST API에 대해서 공부한 시간이 과제한 시간보다 더 많다. 그럼에도 완벽하지 않다. 수업때 집중 잘 하고 모르는 내용 있으면 빠르게 해결해야겠다.
