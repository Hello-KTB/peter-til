# 3. 키워드 정리

## 3.1. 멀티 유저 시스템 (Multi-User System)

윈도우는 개인 컴퓨터(Personal Computer)에 사용되는 운영체제로, 개인 컴퓨터에 쓰인다는 것은 사용자가 나 뿐인 싱글 유저 시스템이라는 것이다. 싱글 유저 시스템일 때는 보안 문제에 대해서 신경을 덜 써도 된다.

반면 리눅스는 멀티유저 시스템으로서, 보안에 특히 신경을 써야 합니다. 내 파일 뿐만 아니라 다른 사람의 파일 또한 존재하는데, 내가 다른 사람의 파일을 맘대로 읽고 쓰고 삭제하고 변경하는 일은 일어나선 안 되기 때문이다. 그래서 리눅스가 특히나 보안쪽으로 신경을 많이 쓴 운영체제이다.

### 실제로 궁금했던 점

| 질문 | 답변 요약 |
| --- | --- |
| 왜 다른 사용자의 파일이 안 보이는가? | 디렉토리 격리(`/home/사용자명`)와 권한 시스템이 커널 수준에서 접근을 차단하기 때문 |
| 루트 해킹 시 모든 사용자 파일을 볼 수 있는가? | **가능합니다.** `root`는 모든 권한을 우회하는 마스터키이므로, 탈취 시 파일 열람·감시·삭제까지 가능 |
| 멀티 유저란 전 세계 공유인건가? | 아닙니다. 내 컴퓨터에 설치 후 계정을 부여받은 사람들이 **원격으로 동시 접속**하는 구조입니다 |
| 허락 없이 침입(해킹)도 가능한가? | **가능합니다.** 무차별 대입 공격, 취약점 공격, 사회공학적 해킹이 주요 경로입니다 |

## 3.2. 소유권과 허가권 (Ownership & Permission)

리눅스는 멀티 유저 시스템으로서 동시에 많은 사용자들이 접근 및 사용할 수 있는데, 다수의 사용자가 사용할 수 있다보니 악의적인 사용자가 특정 파일들을 수정하고, 제거하는 문제가 발생할 수 있다.

이러한 문제를 막기 위해서 리눅스 계열의 운영체제에서는 권한을 소유권과 허가권 두 가지로 나눠서 관리를 합니다.

모든 파일과 디렉토리에는 세 종류의 **오너(owner)** 가 할당된다.

### 오너의 종류

| 오너 타입 | 설명 |
| --- | --- |
| **User** | 파일을 만든 소유자 (개인) |
| **Group** | 소유자와 같은 그룹에 속한 사용자 |
| **Other** | User도 아니고 Group에도 속하지 않은 기타 사용자 |

### 권한의 종류

| 권한 | 기호 | 파일에 적용 시 | 디렉토리에 적용 시 |
| --- | --- | --- | --- |
| 읽기 | `r` | 파일 내용 조회 가능 | 디렉토리 내부 목록 조회 가능 |
| 쓰기 | `w` | 파일 내용 수정 가능 | 내부 파일 생성·수정 가능 |
| 실행 | `x` | 파일 실행 가능 | 디렉토리 내부 접근(cd) 가능 |

같은 기호(r, w, x)라도 **파일이냐 디렉토리냐**에 따라 의미가 완전히 달라진다.

### r (읽기)

파일의 `r`은 직관적이다. 파일 안에 담긴 텍스트나 데이터를 열어볼 수 있는 권한이다. `cat`, `less`, `vim` 등으로 내용을 보는 행위가 여기에 해당한다.

디렉토리의 `r`은 **"이 폴더 안에 무엇이 있는지 목록을 볼 수 있는" 권한**이다. `ls` 명령어로 파일 목록을 나열하는 행위가 여기에 해당한다. 단, 목록은 볼 수 있어도 그 안으로 들어가거나 파일을 열 수 있는 것은 아니다.

### w (쓰기)

파일의 `w`는 파일 내용을 수정하거나 덮어쓸 수 있는 권한이다. 단, 파일을 **삭제**하는 것은 파일 자체의 `w`가 아니라 **그 파일이 위치한 디렉토리의 `w`** 로 결정된다. 이 점이 자주 헷갈리는 부분이다.

디렉토리의 `w`는 **"이 폴더 안에서 파일을 만들거나, 이름을 바꾸거나, 삭제할 수 있는" 권한**이다. 파일의 내용 수정과는 무관하고, 폴더 구조를 변경하는 행위 전반을 제어한다.

즉, 어떤 파일을 삭제하려면 그 파일의 권한이 아니라 **부모 디렉토리에 w 권한**이 있어야 한다.

### x (실행)

파일의 `x`는 해당 파일을 프로그램으로서 실행할 수 있는 권한이다. 쉘 스크립트(`.sh`)나 컴파일된 바이너리가 대표적이다. `r`만 있고 `x`가 없으면 내용은 읽을 수 있어도 실행은 되지 않는다.

디렉토리의 `x`는 파일 실행과 전혀 다른 개념으로, **"이 폴더 안으로 들어갈 수 있는" 권한**, 즉 `cd` 명령어로 진입할 수 있는 권한이다. `x` 없이 `r`만 있으면 목록은 보이지만 `cd`로 들어가거나 내부 파일을 열 수 없다. 반대로 `x`만 있고 `r`이 없으면 이름을 정확히 알고 있는 파일에는 직접 접근할 수 있지만 `ls`로 목록은 볼 수 없다.

### 8진수 표기 대응표

| 기호 | 8진수 | 설명 |
| --- | --- | --- |
| `---` | 0 | 권한 없음 |
| `--x` | 1 | 실행만 |
| `-w-` | 2 | 쓰기만 |
| `-wx` | 3 | 쓰기 + 실행 |
| `r--` | 4 | 읽기만 |
| `r-x` | 5 | 읽기 + 실행 |
| `rw-` | 6 | 읽기 + 쓰기 |
| `rwx` | 7 | 읽기 + 쓰기 + 실행 |

### 권한 관련 명령어

| 명령어 | 의미 | 형식 |
| --- | --- | --- |
| `chmod` | 허가권 변경 | `chmod [권한] [파일 또는 디렉터리]` |
| `chown` | 소유자 및 그룹 변경 | `chown [소유자] [파일]` / `chown [소유자]:[그룹] [디렉터리]` |
| `chgrp` | 그룹 소유권만 변경 | `chgrp [그룹] [파일]` |
| `umask` | 기본 허가권 설정 | `umask [마스크값]` |

### chmod — 허가권 변경

```bash
chmod 755 file.sh       # 숫자 방식
chmod u+x file.sh       # 기호 방식: 소유자에게 실행 권한 추가
chmod o-w file.txt      # 기호 방식: 기타 사용자에게서 쓰기 권한 제거
```

### chown — 소유자·그룹 변경

```bash
chown alice file.txt            # 소유자만 alice로 변경
chown alice:developers dir/     # 소유자를 alice, 그룹을 developers로 변경
```

### chgrp — 그룹 소유권만 변경

```bash
chgrp developers file.txt       # 그룹만 developers로 변경
```

> `chown [소유자]:[그룹]` 으로 한 번에 바꿀 수 있어서, 실무에서는 `chgrp`보다 `chown`을 더 많이 사용한다.
> 

### umask — 기본 허가권 설정

새로 생성되는 파일·디렉터리의 **기본 권한을 제한**하는 마스크값이다.

최대 권한에서 umask 값을 뺀 것이 실제 생성 권한이 된다.

| 대상 | 최대 권한 | umask (기본값 022) | 실제 생성 권한 |
| --- | --- | --- | --- |
| 디렉터리 | 777 | 022 | 755 |
| 파일 | 666 | 022 | 644 |

```bash
umask           # 현재 마스크값 확인
umask 022       # 마스크값을 022로 설정
```

### 왜 디렉터리는 777, 파일은 666을 기준으로 하는가?

디렉터리의 최대 권한이 777인 이유는, 디렉터리는 내부 목록을 보거나(`r`) 안으로 이동하려면(`x`) **반드시 실행 권한이 필요**하기 때문이다. 실행 권한 없이는 폴더로서의 기능 자체를 할 수 없으므로 기준점에 `x`가 포함된다.

파일의 최대 권한이 666인 이유는, 일반 문서나 설정 파일은 **실행될 필요가 없기 때문**이다. 아무 파일이나 기본적으로 실행 가능한 상태로 만들면 보안상 위험하므로, 처음부터 `x`를 제외한 666을 기준으로 삼는다.

## 3.4. 특수 권한 (Special Permissions)

!스크린샷 2026-06-12 오전 9.45.03.png

리눅스에는 실제로는 3종류의 권한이 아니라, 4종류의 권한이 있다. 권한 조회시 rwx를 제외한 특이한 권한이 보이기도 하고, 숫자가 4자리인 경우도 있다. 이들이 모두 특수 권한이 적용된 파일이다.

특수 권한이란 예외적인 상황에 대처할 수 있는 권한이며, 기존의 권한 3+3 분류로 해결할 수 없는 특수한 상황이 필요한 경우가 있기 때문에 추가된 기능이다.

하지만 실제로 많은 보안 공격이 이 특수권한을 활용하여 발생하므로, 특수권한은 왠만하면 최소한으로 사용해야 하며 사용에 주의를 요한다.

| 권한 | 기호 | 숫자 | 설명 |
| --- | --- | --- | --- |
| **SUID** | `s` (소유자 실행 비트) | 4xxx | 실행 시 **소유자 권한**으로 임시 승격 |
| **SGID** | `s` (그룹 실행 비트) | 2xxx | 실행 시 **그룹 권한**으로 임시 승격; 디렉토리에 설정 시 공동 작업용 |
| **Sticky Bit** | `t` (other 실행 비트) | 1xxx | 디렉토리 내 파일을 **소유자와 root만** 삭제·변경 가능 (공유 디렉토리 보호) |

### 숫자 방식 예시

```bash
chmod 4755 file   # SUID + rwxr-xr-x
chmod 2755 dir    # SGID + rwxr-xr-x
chmod 1777 /tmp   # Sticky Bit + rwxrwxrwx
```

# 4. 주제로 복귀

## 4.1. 리눅스의 파일 권한 체계가 사용자, 그룹, 기타 사용자 단위로 접근을 제어하는 방식

### 전제 — UID와 GID

리눅스에 로그인하면 커널은 사용자에게 **UID(User ID)** 와 **GID(Group ID)** 를 발급한다. 신분증과 같은 개념으로, 로그아웃할 때까지 항상 가지고 다닌다.

| 식별자 | 설명 |
| --- | --- |
| **UID** | 사용자의 고유 번호 |
| **GID** | 사용자가 속한 그룹의 고유 번호 |

### 접근 제어 판단 흐름

사용자가 파일에 접근을 시도하면 커널은 아래 순서대로 딱 한 단계씩만 판단하고, 해당되는 시점에서 바로 권한을 적용한다. **세 단계 모두를 누적해서 적용하는 것이 아니다.**

```
파일 접근 시도
      ↓
① 나의 UID == 파일 소유자 UID ?
      ↓ YES → User 권한 적용 → 허용 또는 거부
      ↓ NO
② 나의 GID == 파일 소유 GID ?
      ↓ YES → Group 권한 적용 → 허용 또는 거부
      ↓ NO
③ Other 권한 적용 → 허용 또는 거부
```

### 1단계 — 소유자(User) 확인

커널이 현재 사용자의 UID와 파일에 기록된 소유자 UID를 비교한다.
일치하면 **User 권한**을 적용하고 판단을 끝낸다.

### 2단계 — 그룹(Group) 확인

UID가 일치하지 않으면 GID를 비교한다.
나의 GID와 파일의 소유 GID가 일치하면 **Group 권한**만을 적용하고 판단을 끝낸다.

### 3단계 — 기타 사용자(Other) 적용

소유자도, 같은 그룹도 아닐 경우 커널은 자동으로 **Other 권한**을 적용한다.

> **주의:** root는 이 판단 흐름을 완전히 우회한다.
UID가 0인 root는 어떤 권한이 설정되어 있어도 모든 파일에 접근 가능하다.
>

## 4.2. 잘못된 권한 설정이 서버 배포 환경에서 보안 문제나 실행 오류로 이어질 수 있는 사례

## '서버 배포 환경'이란 무엇인가?

쉽게 말해서, 내가 만든 웹사이트나 프로그램을 "전 세계 사용자들이 접속해서 쓸 수 있도록 24시간 켜져 있는 실제 서버로 옮겨서 작동시키는 곳"을 의미합니다.

이 환경은 내가 혼자 쓰는 개인 PC와 몇 가지 차이점이 있습니다.

- **사용자의 다변화:** 내 PC는 나 혼자 쓰지만, 배포 서버에는 **웹 서버 프로그램(Nginx, Apache)**, **데이터베이스(MySQL)**, 그리고 전 세계 서비스 이용자(Others)가 동시에 접속합니다.
- **자동화 시스템:** 개발자가 직접 들어가서 파일을 고치기보다, Jenkins나 GitHub Actions 같은 배포 도구(CI/CD)가 자동으로 코드를 받아와서 실행합니다.

따라서 여기서 권한을 잘못 설정하면, 서비스가 통째로 마비되거나 서비스의 비밀이 전 세계에 털리는 대참사가 일어납니다.

### 사례 1 — 오타로 인한 루트 디렉터리 권한 파괴 (실행 오류)

**상황**

배포 디렉터리 내 파일들의 권한을 일괄 변경하려다 오타가 발생했다.

```bash
# 의도한 명령어 — 현재 디렉터리 내 파일만 변경
sudo chmod 644 ./*

# 실제 입력한 명령어 — 루트(/) 전체 변경
sudo chmod 644 /*
```

**결과**

`/bin`, `/usr/bin` 등 루트 하위의 모든 실행 파일과 하드웨어 제어 파일의 권한이 `644`로 바뀌면서 `x` 비트가 제거된다. 실행 권한이 사라진 바이너리들은 더 이상 실행되지 않아 `ls`, `cd` 같은 기본 명령어조차 `Permission denied`를 반환하며, 최악의 경우 서버가 재부팅 후 정상 기동되지 않는다.

---

### 사례 2 — `chmod 777` 설정으로 인한 설정 파일 노출 (보안 문제)

**상황**

배포 초기에 권한 오류가 계속 발생하자 빠르게 해결하려고 설정 파일에 `777`을 부여했다.

```bash
sudo chmod 777 /var/www/app/config.py
```

**결과**

`config.py`에는 DB 접속 비밀번호, API 키, 시크릿 키 등 민감한 정보가 담겨 있다. `777`은 Other에게도 읽기·쓰기·실행을 모두 허용하므로, 서버에 침투한 공격자나 같은 서버를 쓰는 다른 사용자가 이 파일을 자유롭게 열람하거나 내용을 변조할 수 있다.

**올바른 권한**

```bash
# 소유자만 읽고 쓸 수 있도록
chmod 600 /var/www/app/config.py
```

---

### 사례 3 — SUID 바이너리 악용을 통한 권한 상승 (보안 문제)

**상황**

배포 과정에서 특정 실행 파일에 SUID가 잘못 설정된 채로 서버에 올라갔다. **SUID**란 "이 파일을 실행하는 순간, 실행한 사람이 누구든 **파일 소유자의 권한으로 실행된다**"는 특수 권한이다.

```bash
chmod 4755 /var/www/app/tool   # SUID 설정
```

**결과**

SUID가 설정된 파일은 실행 시 **파일 소유자의 권한으로 동작**한다. 만약 소유자가 root이고 일반 사용자도 실행할 수 있다면, 공격자는 이 파일을 실행하는 순간 root 권한을 획득한다. 특히 `/bin/bash`에 SUID가 설정되면 즉시 root 쉘이 열리는 치명적인 상황이 발생한다.

```bash
# 공격자가 서버에서 SUID 파일을 탐색하는 명령어
find / -perm -4000 -type f 2>/dev/null
```

**올바른 조치**

SUID는 `passwd`처럼 꼭 필요한 시스템 바이너리에만 최소한으로 적용하고,
배포하는 앱 파일에는 절대 설정하지 않는다.

---

### 사례 4 — Sticky Bit 미설정으로 인한 임시 파일 충돌 (실행 오류)

**상황**

여러 사용자(또는 프로세스)가 공유하는 `/tmp` 디렉터리에 Sticky Bit가 설정되지 않았다. **Sticky Bit**는 "이 폴더에서는 **자기가 만든 파일만 삭제할 수 있다**"는 규칙인데, `/tmp`처럼 여러 사람이 공유하는 폴더를 보호하기 위해 존재한다.

```bash
# 잘못된 상태 — Sticky Bit 없음
drwxrwxrwx  /tmp

# 올바른 상태 — Sticky Bit 있음
drwxrwxrwt  /tmp   # 끝의 t가 Sticky Bit
```

**결과**

Sticky Bit가 없으면 `/tmp`에 쓰기 권한이 있는 누구든 다른 사람의 파일을 삭제하거나 덮어쓸 수 있다. 배포된 앱이 `/tmp`에 임시 파일을 만들었다가 다른 프로세스가 이를 삭제하면, 앱이 해당 파일을 찾지 못하고 오류로 종료된다.

---

### 핵심 원칙 — 최소 권한 원칙 (Principle of Least Privilege)

> 필요한 만큼만 권한을 주고, 그 이상은 절대 주지 않는다.
> 

| 잘못된 설정 | 문제 유형 | 올바른 설정 |
| --- | --- | --- |
| `chmod 777` 설정 파일 | 보안 — 정보 노출 | `chmod 600` |
| SUID 설정된 앱 바이너리 | 보안 — 권한 상승 | SUID 제거 |
| `777` cron 스크립트 | 보안 — 백도어 삽입 | `chmod 700` |
| `chmod 644 /*` 오타 | 실행 오류 — 시스템 마비 | 경로 재확인 |
| Sticky Bit 없는 `/tmp` | 실행 오류 — 파일 충돌 | `chmod 1777 /tmp` |
