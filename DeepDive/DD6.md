# 3. 키워드 설명

## 3.1. 가상머신 (Virtual Machine)

> 물리적 하드웨어 시스템에 구축되어 자체 CPU, 메모리, 네트워크 인터페이스 및 스토리지를 갖추고 가상 컴퓨터 시스템으로 작동하는 가상 환경
> 

!VM-Virtualization.width-702.format-webp.webp

각 가상 머신은 자체적인 OS와 리소스(CPU, 메모리, 스토리지, 네트워크 인터페이스)를 가지며, 실제 컴퓨터처럼 독립적인 작업을 수행한다.

### 3.1.1 작동 원리

#### 구성 요소

| 구분 | 설명 |
| --- | --- |
| **호스트** | VM을 실행하는 물리 머신. 호스트 머신 / 호스트 OS / 호스트라고도 부름 |
| **게스트** | 물리 머신의 리소스를 사용하는 VM. 게스트 머신 / 게스트 OS / 게스트라고도 부름 |
| **하이퍼바이저** | CPU·메모리·스토리지를 리소스 풀로 묶어 VM 생성과 관리를 담당하는 소프트웨어 |

#### 작동 흐름

1. 하이퍼바이저가 물리 리소스를 **리소스 풀**로 묶음
2. VM이 리소스를 요청하면 하이퍼바이저가 풀에서 꺼내 해당 VM에 할당
3. 물리 하드웨어는 하이퍼바이저의 스케줄에 따라 **VM의 CPU 명령을 처리**
4. Guest OS 입장에서는 자신이 물리 머신에서 실행되는 것과 **동일하게 인식**

#### 주요 특징

- VM은 **하나의 데이터 파일**로 정의되어, 다른 컴퓨터에서도 동일하게 작동
- Guest OS는 에뮬레이션된 환경에서 실행되지만, 물리 머신의 실시간 OS 환경과 **거의 동일하게 동작**
- 하이퍼바이저가 스케줄을 관리하는 동안에도 **물리 하드웨어는 계속 실행** 중

#### Linux 환경의 하이퍼바이저 종류

| 종류 | 특징 |
| --- | --- |
| **KVM** (Kernel-based Virtual Machine) | Linux 커널에 기본 내장된 하이퍼바이저 |
| **Xen** | 오픈소스 하이퍼바이저 |
| **Microsoft Hyper-V** | Microsoft 제공 하이퍼바이저 |

#### **가상 머신(VM)의 장단점**

| 구분 | 내용 |
| --- | --- |
| **장점** | 격리된 환경 제공 — VM 내 작업이 다른 시스템에 영향을 주지 않음 |
|  | 다양한 OS 지원 — 단일 서버에서 Windows, Mac, Linux 동시 운영 가능 |
|  | 유지/관리 및 자원 활용률 향상 |
| **단점** | VM이 많을수록 성능 안정성 저하 및 실행 속도 감소 |
|  | 각 VM마다 독립적인 OS를 가져 용량 부담 (Windows 기준 약 5GB/개) |

### 3.1.2. 가상화

> 물리적 컴퓨터 리소스를 추상화해서 여러 개의 가상 환경을 만들어내는 기술
> 

가상화는 쉽게 생각해서 하드웨어와 소프트웨어를 분리하는 것이다. 물리 서버 한 대가 있을 때, 가상화 없이는 그 서버에 하나의 OS만 올릴 수 있다. 가상화를 적용하면 동일한 물리 서버 위에 여러 개의 독립된 환경을 만들어 각각 다른 OS와 애플리케이션을 실행할 수 있다.

#### 가상화가 필요한 이유

- 자원 활용 극대화
    - 하나의 물리 서버는 보통 리소스를 100% 활용하지 못한다
    - 가상화로 남는 자원을 여러 VM에 나눠주면 서버 자원 활용률이 크게 올라간다
    - AWS 서비스의 출발도 이와 같다
- 비용 절감
    - 개발/테스트/운영 환경을 물리 서버 없이 논리적으로 분리할 수 있어 비용 절감 효과가 있다
- 가용성 확보
    - 가용성이란 서버와 네트워크 또는 프로그램 등의 다양한 정보 시스템이 정상적으로 사용 가능한 정도
    - 서버 한 대가 망가져도 VM을 다른 서버로 옮겨 계속 운영할 수 있어서 가용성이 높아진다

#### 에뮬레이션 vs 시뮬레이션

| 구분 | 에뮬레이션 (Emulation) | 시뮬레이션 (Simulation) |
| --- | --- | --- |
| **목적** | 다른 시스템의 동작을 **동일하게 재현** | 시스템의 동작을 **모델로 흉내** |
| **정확도** | 실제와 동일하게 작동 (기능적으로 대체 가능) | 근사치로 모방 (실제 대체 불가) |
| **예시** | 닌텐도 DS 게임을 PC에서 그대로 실행 | 비행 시뮬레이터 (실제 비행기 대체 불가) |
| **VM과의 관계** | VM은 하드웨어를 에뮬레이션 — Guest OS 입장에서는 진짜 하드웨어처럼 동작 |  |

**VM이 에뮬레이션인 이유:** Guest OS는 자신이 가상 환경에 있다는 사실을 모른다. 하이퍼바이저가 CPU, 메모리, 디스크를 실제 하드웨어처럼 보이도록 에뮬레이션하기 때문이다.

## 3.2. 컨테이너

> 애플리케이션 코드를 라이브러리 및 종속성과 함께 패키징하는 소프트웨어의 실행 단위
> 

컨테이너는 "어디서나 동일하게 실행되는 앱 상자"다. 앱이 돌아가는 데 필요한 모든 것(코드, 런타임, 라이브러리, 환경 변수, 설정 파일)을 하나의 패키지로 묶는다. 덕분에 개발자 노트북에서 동작하던 앱이 운영 서버에서도 **동일하게** 동작한다.

### 3.2.1. 커널

> 컴퓨터 운영체제의 핵심이 되는 컴퓨터 프로그램으로, 시스템의 모든 것을 완전히 제어한다.
> 

커널은 OS의 가장 핵심적인 부분으로, 하드웨어와 소프트웨어(애플리케이션) 사이의 **중재자** 역할을 한다.

#### 커널의 역할

**① 보안**

커널은 컴퓨터 하드웨어와 프로세스의 보안을 책임진다. 모든 프로세스는 커널을 통해서만 하드웨어에 접근할 수 있기 때문에, 커널이 요청을 검사하고 허용 여부를 결정한다. 악의적인 프로그램이 직접 하드웨어에 접근하는 것을 막는 방어선이다.

**② 자원 관리**

한정된 시스템 자원(CPU, 메모리)을 여러 프로그램에 효율적으로 분배한다. 특히 **스케줄링(Scheduling)** 이란 여러 프로세스 중 어느 프로세스에 CPU를 얼마나 할당할지 결정하는 작업이다.

**③ 추상화**

하드웨어 제조사마다 장치의 동작 방식이 다르다. 커널은 이 복잡성을 숨기고 프로그램에게 일관된 인터페이스(API)를 제공한다. 예를 들어 프린터 제조사가 달라도 프로그램은 같은 방식으로 "인쇄" 명령을 보낼 수 있다. 이를 가능하게 하는 것이 드라이버(Driver)다.

**컨테이너와 커널의 관계:**

컨테이너는 VM과 달리 Guest OS가 없다. 대신 **호스트의 커널을 직접 공유**한다. 이것이 컨테이너가 가볍고 빠른 핵심 이유다. 단, 커널을 공유하기 때문에 Linux 커널 기반 기능에 의존하며, 컨테이너 간 격리는 커널의 **Namespace**와 **cgroups** 기능으로 구현된다.

| 커널 기능 | 역할 |
| --- | --- |
| **Namespace** | 프로세스, 네트워크, 파일시스템 등을 컨테이너별로 분리해서 서로 못 보게 함 |
| **cgroups (Control Groups)** | CPU, 메모리 등 자원 사용량을 컨테이너별로 제한 |

### 3.2.2. 컨테이너 오케스트레이션

> 대규모 애플리케이션을 배포할 수 있도록 컨테이너의 네트워킹 및 관리를 자동화하는 프로세스
> 

컨테이너가 수십 개일 때는 수동으로 관리가 가능하다. 그러나 실제 서비스 환경에서는 수백~수천 개의 컨테이너가 여러 서버에 걸쳐 실행된다. 이를 사람이 직접 관리하는 것은 불가능하다. 오케스트레이션은 이 문제를 해결하기 위한 자동화 계층이다.

#### 필요한 이유

| 상황 | 오케스트레이션 없을 때 | 오케스트레이션 있을 때 |
| --- | --- | --- |
| 컨테이너가 갑자기 죽음 | 수동으로 재시작 | 자동으로 감지하고 재시작 |
| 트래픽이 급증함 | 수동으로 컨테이너 추가 | 자동으로 스케일 아웃 |
| 서버 한 대가 장애남 | 수동으로 다른 서버에 이전 | 자동으로 다른 서버에 재배치 |
| 새 버전 배포 시 무중단 필요 | 복잡한 수작업 | 롤링 업데이트 자동 처리 |

#### Kubernetes (k8s)

> 컨테이너 오케스트레이션의 사실상 표준 플랫폼
> 

`k8s`라는 이름은 'Kubernetes'에서 k와 s 사이의 8글자를 숫자 8로 축약한 것이다.

# 4. 주제로 복귀

## 4.1. 가상머신(VM)과 컨테이너의 구조적 차이

!vm vs container.png

VMware나 Parallels 등의 프로그램을 이용하면 Windows나 Mac에서 다른 OS를 설치하여 사용이 가능한데 이것이 바로 VM이다. 반면 컨테이너는 그보다 훨씬 가볍고 빠른 방식으로 애플리케이션을 격리해서 실행한다. 이 둘은 목표(격리된 실행 환경)는 같지만 구현 방식이 근본적으로 다르다.

**핵심 차이:**

VM은 서버 안에 또 다른 완전한 서버(Guest OS 포함)가 있는 구조다. 부팅 과정도 있고, 여러 프로그램을 설치하는 방식도 물리 서버와 동일하다. 반면 **컨테이너는 Guest OS 없이 호스트 OS를 공유하고 프로세스를 격리하여 실행**한다. 컨테이너가 더 가벼운 이유가 바로 여기에 있다.

원래 컨테이너는 리눅스 커널에서 지원하는 기능들(Namespace, cgroups)로 만들어지기 때문에 기본적으로 Linux 환경을 전제한다. Mac이나 Windows에서 Docker를 실행할 수 있는 것은 내부적으로 경량 Linux VM을 자동으로 띄우고 그 위에서 컨테이너를 기동하기 때문이다.

| 비교 항목 | 가상머신 (VM) | 컨테이너 |
| --- | --- | --- |
| OS 구조 | Guest OS 별도 설치 | Host OS 커널 공유 |
| 격리 수준 | 하드웨어 수준 (강함) | 프로세스 수준 (경량) |
| 크기 | 수 GB | 수십~수백 MB |
| 부팅 시간 | 수십 초 ~ 수 분 | 1초 내외 |
| 성능 오버헤드 | 하이퍼바이저 경유 → 높음 | 커널 직접 처리 → 낮음 |
| OS 다양성 | Windows, Linux 등 자유롭게 선택 | Linux 커널 기반으로 제한 |
| 이식성 | 이미지가 무거워 이동 비용 큼 | 가볍고 어디서나 동일하게 실행 |

## 4.2. 자원 격리·성능·배포 속도 측면에서 컨테이너가 실무적으로 가지는 강점과 한계

### 강점

#### 1. 자원 격리 — 필요한 만큼만, 정밀하게

컨테이너는 커널의 **cgroups** 기능을 통해 각 컨테이너가 사용할 수 있는 CPU와 메모리 상한선을 지정할 수 있다. 이를 통해 특정 컨테이너가 자원을 독점해서 다른 컨테이너에 영향을 주는 것을 방지한다.

VM과의 차이는 **자원 할당의 유연성**에 있다. VM은 처음부터 자원을 고정 할당하는 경향이 강한 반면 컨테이너는 필요에 따라 자원 한도를 동적으로 조정하기 쉽다.

또한 컨테이너는 OS를 공유하기 때문에 **앱당 전체 OS 인스턴스가 필요 없다.** VM에서 Guest OS 하나가 기본적으로 수백 MB ~ 수 GB의 메모리를 차지하는 것과 비교하면, 컨테이너는 앱 자체의 메모리만 쓴다.

#### 2. 성능 — 중간 계층을 제거한다

하이퍼바이저는 여러 Guest OS를 상대해야 하고 하드웨어는 한정된 자원이기 때문에, VM은 구조적으로 성능 오버헤드가 발생한다. 컨테이너는 이 중간 계층을 없애 **네이티브에 가까운 성능**을 낸다. 특히 I/O가 많은 작업(데이터베이스, 파일 처리)에서 차이가 두드러진다.

#### 3. 배포 속도 — 이미지 기반의 즉시 실행

컨테이너의 배포 속도 강점은 두 가지에서 온다.

**① 부팅 시간:** VM은 부팅 과정(BIOS → OS 커널 로드 → 서비스 시작)을 거치는 반면, 컨테이너는 이미 실행 중인 Host OS 커널 위에서 새 프로세스를 시작하는 것과 같다. **수 분 → 수 초 이내**로 줄어든다.

**② 이식성:** 컨테이너 이미지는 앱과 모든 종속성을 포함하므로, 서버 환경을 별도로 구성할 필요가 없다. `docker run` 한 줄로 어느 서버에서나 동일한 환경이 즉시 실행된다.

이 특성은 **CI/CD 파이프라인**과 결합했을 때 강력하다. 코드 변경 → 이미지 빌드 → 자동 배포 흐름이 VM 기반보다 훨씬 빠르게 돌아간다.

#### 4. 마이크로서비스·클라우드 네이티브 아키텍처와의 궁합

모놀리식(Monolithic) 애플리케이션은 하나의 거대한 프로그램이다. 사용자가 몰리면 전체를 통째로 스케일 아웃해야 한다. 마이크로서비스는 기능별로 서비스를 분리해서 **병목이 생기는 부분만** 확장한다. 컨테이너는 이 마이크로서비스 단위와 크기가 맞아떨어진다.

### 한계

#### 1. 격리 수준 — 커널 공유의 양날의 검

컨테이너의 가장 본질적인 한계는 **커널을 공유한다는 점** 자체에서 온다. 각 컨테이너가 Namespace로 서로를 못 보게 막더라도, 결국 같은 커널 위에서 돌아간다.

만약 커널 자체에 취약점이 발견된다면, 이 취약점을 통해 한 컨테이너에서 탈출해 다른 컨테이너나 호스트 시스템에 접근하는 **컨테이너 탈출(Container Escape)** 공격이 가능하다. VM은 Guest OS와 Hypervisor 두 겹의 벽이 있어서 이런 공격이 훨씬 어렵다.

이 때문에 **금융, 의료처럼 높은 보안 격리가 필요한 환경**에서는 VM이나, VM과 컨테이너를 결합한 방식(예: Kata Containers)을 사용하기도 한다.

#### 2. OS 제약 — Linux 종속성

컨테이너는 기본적으로 Linux 커널에 의존한다. Windows 컨테이너가 존재하긴 하지만 Linux 컨테이너 생태계만큼 성숙하지 않았고, Linux 컨테이너를 Windows에서 실행하려면 내부적으로 Linux VM이 필요하다. 특정 OS에 강하게 의존하는 레거시 애플리케이션이라면 컨테이너화가 어렵거나 불가능할 수 있다.

#### 3. 운영 복잡도 — 오케스트레이션 학습 비용

컨테이너 한두 개는 간단하다. 그러나 실제 서비스 환경에서는 수백 개의 컨테이너가 여러 서버에 분산된다. 이를 운영하려면 Kubernetes 같은 오케스트레이션 도구가 필수적인데, k8s는 학습 곡선이 가파르기로 유명하다. 네트워킹, 스토리지, 보안 정책, 모니터링까지 새롭게 익혀야 할 개념이 많다.
