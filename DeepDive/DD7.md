# 3. 키워드 정리

## 3.1. Docker Image

> **Docker 공식 정의**: 컨테이너 이미지는 컨테이너를 실행하는 데 필요한 모든 파일, 바이너리, 라이브러리 및 구성이 포함된 표준화된 패키지이다.
**IBM 정의**: 컨테이너 이미지는 실행 가능한 코드를 담고 있으며 IT 인프라에서 격리된 상태로 작동하는 변경 불가능한 정적 파일이다.
> 

컨테이너는 격리된 프로세스이기 때문에, `실행에 필요한 파일과 구성 정보`를 어디선가 가져와야 하고 이를 다른 환경과 공유할 수 있어야 합니다. 이 역할을 하는 것이 바로 **`컨테이너 이미지`**이다.

### **이미지 원칙**

| 원칙 | 내용 |
| --- | --- |
| 불변성(immutable) | 이미지는 변경할 수 없다. 한 번 생성된 이미지는 수정할 수 없고, 새 이미지를 만들거나 기존 이미지에 변경 사항을 추가하는 것만 가능하다 |
| 레이어 구조 | 컨테이너 이미지는 레이어로 구성된다. 각 레이어는 파일을 추가·제거·수정하는 파일 시스템 변경 사항의 집합이다 |

### **이미지를 사용하는 이유**

| 장점 | 설명 |
| --- | --- |
| 이식성 | Linux, Windows 등 어떤 호스트 OS에서도 실행 가능 → 클라우드, 온프레미스, 로컬 등 다양한 환경에 손쉽게 배포 |
| 배포 속도 | VM과 달리 OS 전체를 가상화하지 않고 애플리케이션 레벨의 격리만 제공하므로 훨씬 가볍고 빠르게 시작 |
| 자원 효율성 | 필요한 자원만 사용하므로 하나의 호스트에서 여러 컨테이너를 효율적으로 동시 운영 가능 |
| 확장성·관리 용이성 | 마이크로서비스 아키텍처로 각 컴포넌트를 독립적으로 확장·관리 가능 |
| 보안 | 컨테이너 간 격리를 통해 취약점이 다른 컨테이너로 확산되는 것을 방지 |

### **1차 키워드**

| 키워드 | 정의 |
| --- | --- |
| 컨테이너 | 코드와 모든 종속성을 패키징하여, 애플리케이션이 한 컴퓨팅 환경에서 다른 환경으로 빠르고 안정적으로 실행될 수 있도록 하는 표준 소프트웨어 단위 |
| 레지스트리 | 컨테이너 이미지를 저장·공유하는 중앙 집중식 저장소. 공개 레지스트리(Docker Hub 등)와 비공개 레지스트리(Amazon ECR, Azure ACR, Google GCR, 또는 Harbor·JFrog Artifactory·GitLab Container Registry 같은 자체 구축형)로 나뉜다 |
| Docker Compose | 여러 컨테이너로 구성된 애플리케이션을 하나의 YAML 파일로 정의하고, 단일 명령으로 서비스·네트워크·볼륨을 생성·관리할 수 있게 해주는 도구. 프로덕션부터 개발, CI 워크플로우까지 전 환경에서 사용 가능하며, 서비스 시작/중지/재구축, 상태 확인, 로그 스트리밍, 일회성 명령 실행 등의 기능을 제공한다 |

## 3.2. 빌드

> 입력 매개변수를 결과 객체로 변환하는 과정
> 

빌드는 개발자가 코드를 작성하는 행위 자체가 아니라, `작성된 코드가 실행 가능한 애플리케이션으로 만들어지기까지의 과정`을 가리킨다. 즉 코드, 필요한 구성 요소, 환경 설정, 외부 라이브러리 등을 모두 컴파일해 실행 가능하거나 사용 가능한 애플리케이션을 만들어내는 과정을 의미한다.

빌드 방식은 크게 **커스텀(custom) 빌드**와 **산업형(industrial) 빌드**로 나눌 수 있는데, 커스텀 빌드는 처음부터 직접 구성해야 해서 설정이 까다로운 반면, 산업형 빌드는 특정 사용 목적에 맞게 미리 구성되어 있어 필요한 유형을 선택해 바로 사용할 수 있다. 어느 쪽을 선택하든 최종적으로는 배포 가능한 프로젝트를 만든다는 목표는 동일하다.

### **빌드 유형**

| 구분 | 특징 |
| --- | --- |
| Full Build (전체 빌드) | 빌드가 실행될 때마다 매번 처음부터 새로운 패키지 애플리케이션을 생성하는 방식이다. 기존에 빌드된 결과물이 있는지와 무관하게 소스 파일을 다시 가져오고, 전체 프로세스를 처음부터 다시 실행하며, 모든 환경을 다시 점검한 뒤 새로 배포한다. 이 때문에 코드 변경량이 많든 적든 빌드에 걸리는 시간은 거의 동일하다 |
| Incremental Build (증분 빌드) | 이미 빌드된 프로젝트가 존재하는지 먼저 확인한 뒤, 변경된 부분만 비교하여 그 변경된 컴포넌트나 소스 파일만 갱신하는 방식이다. 빌드 명령이 실행되어도 전체 프로세스를 처음부터 다시 돌리지 않는다. 따라서 빌드에 걸리는 시간은 소스 파일에서 변경된 양에 따라 달라진다 |

### **빌드 프로세스**

| 단계 | 내용 |
| --- | --- |
| 1. 소스 코드 확보 | 소스 코드를 가져온다 |
| 2. 환경 준비 | 빌드 환경을 준비한다 |
| 3. 의존성 확보 | 필요한 의존성(dependency)을 가져온다 |
| 4. 테스트 | (포함되어 있다면) 테스트를 실행한다 |
| 5. 구성 적용 | 구성(configuration)을 적용한다 |
| 6. 코드 변환 | 소스 코드를 실행 가능한 코드 또는 환경에 맞는 머신 코드로 변환한다 |

## 3.3. 배포

> 소프트웨어 배포는 사용자가 시스템에서 소프트웨어를 사용하거나, 다른 프로그램에서 소프트웨어를 사용할 수 있도록 하는 프로세스
> 

소프트웨어 배포란 애플리케이션을 실제로 사용할 수 있도록 만드는 일련의 과정으로, 릴리스를 준비하는 단계부터 대상 시스템에 설치·구성하는 단계까지를 포함한다. 궁극적인 목표는 개발 환경에 있던 소프트웨어를 프로덕션 환경으로 옮기면서도, 기능과 성능이 사용자의 기대 수준을 충족하도록 하는 것이다.

### **배포가 중요한 이유**

| 이유 | 설명 |
| --- | --- |
| `버그 수정과 성능 개선` | 배포를 통해 업데이트, 버그 수정, 성능 개선 사항을 신속하게 반영할 수 있고, 사용자가 안정적이고 효율적인 버전을 사용하도록 보장한다 |
| `경쟁력과 출시 속도` | 빠르고 효율적인 배포는 제품을 시장에 내놓는 속도를 단축시켜, 변화가 빠른 시장에서 경쟁 우위를 가져다준다 |
| `사용자 경험과 만족도` | 정기적인 업데이트 배포는 사용자에게 최신 개선 사항을 제공하여 만족도를 높이고, 고객 피드백을 신속히 반영할 수 있게 한다 |
| `지속적 개선을 위한 피드백 루프` | 잦은 배포는 사용자가 프로그램과 상호작용하는 방식에 대한 정보를 얻는 피드백 루프를 만들어, 이후 개발과 배포 전략에 반영할 수 있게 한다 |
| `자원 최적화와 비용 절감` | 효율적인 배포 방식은 자원을 절약하고 비용을 낮추는 데도 기여하며, 배포 프로세스를 자동화하면 수작업을 줄이고 오류를 최소화하며 결과의 일관성을 확보할 수 있다 |

### **배포(Deployment) vs 릴리스(Release)**

| 구분 | 배포(Deployment) | 릴리스(Release) |
| --- | --- | --- |
| 정의 | 특정 환경에서 소프트웨어(또는 업데이트)를 사용 가능한 상태로 만드는 과정 | 개발팀 외부의 사용자에게 특정 버전을 공개하는 것 |
| 시점 | 배포되었다고 해서 최종 사용자에게 곧바로 공개되는 것은 아니며, 정기 유지보수의 일환이거나 릴리스에 앞선 사전 단계일 수 있음 | 릴리스되는 시점에 비로소 사용자가 접근 가능해지며, 시점 결정에는 마케팅 일정이나 사용자 기대치 등이 고려됨 |
| 범위 | 소프트웨어를 전달·설치하는 기술적 측면에 초점 | 배포뿐 아니라 문서화, 마케팅, 사용자 커뮤니케이션까지 포함하는 더 넓은 개념 |
| 목표 | 대상 환경에 소프트웨어를 정확하고 효과적으로 배치하는 것 | 품질 기준을 충족하고 사용자에게 가치를 주는 버전을 전달하는 것 |

### **배포 방법론(Methodologies)**

| 방법론 | 설명 |
| --- | --- |
| Continuous Deployment (지속적 배포) | 코드 변경 사항을 자동으로 프로덕션에 반영해, 빠르고 끊김 없는 전달 파이프라인을 유지한다 |
| Continuous Delivery (지속적 전달) | 실제 배포 여부와 무관하게, 소프트웨어가 언제든 배포 가능한 상태를 유지하도록 관리한다 |
| Staged Deployment (단계적 배포) | 소규모 사용자 그룹부터 시작해 점차 넓은 대상으로 확대 배포하며 문제를 단계적으로 발견·해결한다 |
| Blue-Green Deployment | 동일한 프로덕션 환경 두 개(블루/그린)를 운영하며 한쪽만 실제 트래픽을 받도록 하고, 환경 전환 방식으로 업데이트 시 다운타임을 최소화한다 |

### **배포 프로세스(Processes)**

| 단계 | 내용 |
| --- | --- |
| 1. 계획(Planning) | 배포 목표를 정의하고 잠재적 위험을 평가하며, 작업과 책임을 정리한 배포 계획을 수립한다 |
| 2. 빌드(Build) | 코드를 컴파일하여 실행 가능한 패키지(아티팩트, 바이너리, 설치 파일 등)를 생성한다 |
| 3. 테스트(Testing) | 단위·통합·시스템 테스트 등을 통해 다음 단계로 넘어가기 전 문제를 식별하고 수정한다 |
| 4. 스테이징(Staging) | 프로덕션과 유사한 통제된 스테이징 환경에 배포해 추가 검증을 진행한다 |
| 5. 배포(Deployment) | 실제 대상 프로덕션 시스템에 소프트웨어를 배포하며, 규모와 복잡도에 따라 수동 또는 자동화된 방식으로 진행한다 |
| 6. 모니터링(Monitoring) | 배포된 소프트웨어를 지속적으로 관찰하여 문제를 신속히 발견·대응하고, 프로덕션 환경에서 예상대로 동작하는지 확인한다 |

### **배포 베스트 프랙티스**

| 항목 | 설명 |
| --- | --- |
| 자동화 | 반복적이고 실수하기 쉬운 작업을 자동화하여 배포 과정을 단순화하고 휴먼 에러 가능성을 낮춘다 |
| 롤백 계획 | 배포 중 문제가 발생할 경우를 대비해, 이전의 안정적인 상태로 신속히 되돌릴 수 있는 롤백 계획을 마련한다 |
| 환경 일관성(Environment Parity) | 개발·테스트·프로덕션 환경 간 일관성을 유지해 환경 차이로 인한 예기치 않은 동작을 최소화한다 |
| 커뮤니케이션 | 개발, 운영 등 이해관계자 간 명확한 소통 채널을 유지해 배포 상태와 잠재적 문제를 모두가 인지하도록 한다 |
| 테스트 | 배포 전 회귀 테스트를 포함한 철저한 테스트로 기존 기능이 영향받지 않았는지 확인한다 |
| 버전 관리 | 버전 관리 시스템을 사용해 변경 이력을 추적하고 팀원 간 협업을 원활하게 한다 |

**결론**: 소프트웨어 배포는 소프트웨어 개발 생명주기(SDLC)에서 신중한 계획, 테스트, 실행이 요구되는 핵심 단계이며, 최종 사용자에게 신뢰할 수 있고 품질 높은 소프트웨어를 전달하는 데 결정적인 역할을 한다. 베스트 프랙티스를 따르고 적절한 배포 방법론을 활용하면 개발팀은 프로세스를 최적화하고 배포 성공률을 높일 수 있다.

## 3.4. 멀티스테이지 빌드

> 컨테이너 이미지를 만들면서 빌드 등에는 필요하지만 최종 컨테이너 이미지에는 필요 없는 환경을 제거할 수 있도록, 단계를 나누어 기반 이미지를 만드는 방법.
> 

전통적인 빌드 방식에서는 의존성 다운로드, 코드 컴파일, 애플리케이션 패키징 등 모든 빌드 지시어가 하나의 빌드 컨테이너 안에서 순차적으로 실행된다. 문제는 이 과정에서 생긴 레이어들이 그대로 최종 이미지에 남는다는 점인데, 이 때문에 이미지가 불필요하게 무거워지고 보안 위험도 함께 커진다. 멀티스테이지 빌드는 바로 이 문제를 해결하기 위한 방법이다.

멀티스테이지 빌드는 하나의 Dockerfile 안에 여러 개의 단계(stage)를 두고, 각 단계가 서로 다른 역할을 맡도록 구성한다. 마치 빌드의 각 부분을 서로 다른 환경에서 동시에 실행하는 것과 비슷한데, 이렇게 **빌드 환경과 최종 런타임 환경을 분리**하면 `이미지 크기와 공격 표면을 크게 줄일 수 있다`. 특히 빌드에 필요한 의존성이 많은 애플리케이션일수록 효과가 크다.

## 3.5. 베이스 이미지

> 컨테이너를 만들 때 그 위에 모든 것이 쌓이는 **가장 밑바닥의 레이어**로, 애플리케이션 환경의 출발점 역할
> 

운영체제, 런타임 도구, 라이브러리, 의존성 등을 담은 최소한의 사전 구성된 템플릿이라고 볼 수 있으며, Dockerfile의 `FROM` 명령이 바로 이 베이스 이미지를 정의한다. 어떤 베이스 이미지를 고르느냐가 컨테이너의 보안성·크기·성능·유지보수성에 직접적인 영향을 미칩니다.

### **베이스 이미지가 중요한 이유**

베이스 이미지 없이 컨테이너를 만든다는 것은 운영체제부터 라이브러리까지 모든 환경을 직접 조립해야 한다는 뜻이며, 이는 복잡하고 오류가 발생하기 쉬우며 시간도 오래 걸립니다. 베이스 이미지는 이런 환경을 표준화되고 재현 가능한 형태로 제공해, 컨테이너가 어디서 실행되든 일관성을 보장합니다. 구체적으로는 다음 세 가지 특성에 영향을 줍니다.

| 특성 | 영향 |
| --- | --- |
| 크기 | 베이스 이미지가 작을수록 최종 이미지도 작아져, 다운로드가 빨라지고 저장 비용이 줄며 배포 시간도 단축된다 |
| 보안 | 최소한의 구성 요소만 가진 베이스일수록 라이브러리·유틸리티·셸 등 잠재적 취약점의 수가 줄고, 공격 표면도 작아진다 |
| 성능 | 베이스 이미지는 컨테이너의 시작 시간과 CPU·메모리 등 자원 소비량에도 영향을 준다 |

### **대표적인 베이스 이미지 유형**

| 유형 | 특징 |
| --- | --- |
| `scratch` | 파일이 전혀 없는 완전히 빈 이미지다. 애플리케이션에 필요한 바이너리·라이브러리·설정을 전부 직접 추가해야 하지만, 그만큼 완전한 통제력과 최소 크기를 제공한다 |
| Alpine Linux | `musl` libc와 BusyBox 기반으로 약 5~8MB 수준의 매우 작은 크기가 특징이며, `apk` 패키지 매니저를 사용한다. 자원 효율이 뛰어나지만, `glibc` 기반 소프트웨어와의 호환성 문제로 재컴파일이 필요할 수 있고, 일부 표준 도구가 빠져 있으며 쿠버네티스 환경에서 DNS 관련 예외 상황이 보고되기도 한다 |
| Full OS 배포판 (Ubuntu, Debian, CentOS, Red Hat UBI, Rocky Linux, Fedora 등) | `apt`, `yum` 같은 익숙한 패키지 매니저와 폭넓은 사전 설치 도구를 제공한다. 크기는 크지만 호환성이 넓고 의존성 설치가 쉬워, 개발 환경이나 레거시 애플리케이션 마이그레이션에 자주 선택된다 |
| Distroless (Google) | 애플리케이션과 필수 런타임 의존성만 남기고 패키지 매니저, 셸 등은 의도적으로 제외한 보안 특화 이미지로, 공격 표면을 크게 줄여준다. 다만 셸이 없어 디버깅이 어렵다는 단점이 있다 |
| 언어별 공식 이미지 (Python, Node.js, OpenJDK 등) | 특정 언어의 런타임과 컴파일러, 도구를 함께 번들링해 개발 워크플로우를 단순화한다 |

### **올바른 베이스 이미지를 고르는 기준**

| 기준 | 설명 |
| --- | --- |
| 크기 | 저장·전송·배포 속도에 있어 크기 최소화가 얼마나 중요한지 판단한다 (Alpine, `scratch`, Distroless가 대체로 가장 작음) |
| 보안 | 요구되는 보안 수준이 어느 정도인지 확인한다 (구성 요소가 적을수록 취약점도 적음) |
| 호환성과 의존성 | 애플리케이션에 특정 OS 라이브러리(`glibc` 등)나 디버깅 도구가 필요한지 확인한다 |
| 사용 편의성과 익숙함 | 팀이 해당 이미지의 환경과 패키지 매니저에 얼마나 익숙한지 고려한다 |
| 유지보수와 지원 | 누가 이미지를 관리하며, 보안 패치는 얼마나 자주 반영되는지 확인한다 |

### **베이스 이미지 운영 베스트 프랙티스**

| 항목 | 설명 |
| --- | --- |
| 생성 및 초기 구성 | 꼭 필요한 패키지만 설치하고, non-root 사용자를 설정하며, `.dockerignore`로 빌드 컨텍스트를 최소화한다 |
| 유지보수와 업데이트 | 특정 버전으로 고정한 베이스 이미지를 CI/CD 파이프라인에서 자동·주기적으로 재빌드하고, Dockerfile 안에서 `apt-get upgrade` 같은 패키지 업그레이드 명령을 실행하기보다는 업데이트된 베이스 이미지로 다시 빌드하는 방식을 권장한다. 문제 발생 시를 대비한 롤백 전략도 필요하다 |
| 취약점 스캐닝 | Trivy, Clair 같은 도구를 CI/CD에 통합해 이미지 생성·푸시 시점과 레지스트리에 있는 동안 지속적으로 스캔하고, 발견된 취약점은 베이스 이미지나 특정 패키지를 업데이트해 해결한다 |
| 공급망 보안 | 공식 이미지나 신뢰할 수 있는 게시자의 이미지를 사용하고, Docker Content Trust나 Sigstore(`cosign`) 같은 도구로 이미지의 무결성과 출처를 검증하며, SBOM(소프트웨어 구성 명세)을 활용해 구성 요소를 파악한다 |
| 포함/제외 기준 | 최소한의 OS 유틸리티, 필요한 언어 런타임, 필수 라이브러리는 포함하되, 개발 도구는 멀티스테이지 빌드로 분리하고 민감한 정보는 런타임에 주입하는 방식으로 제외한다 |
| 보안 강화와 크기 최소화 | non-root 사용자로 실행, 커널 권한 제한, 읽기 전용 파일시스템 사용, 최소 베이스 이미지·멀티스테이지 빌드 활용, RUN 명령 통합, 불필요한 파일 및 패키지 캐시 제거 등이 함께 권장된다 |

# 4. 주제로 Comeback

## 4.1. 도커 이미지가 커지면 발생하는 문제

컨테이너는 유연성과 확장성 덕분에 애플리케이션 배포 방식으로 널리 자리 잡았지만, 컨테이너 크기가 커지면 배포 시간, 자원 사용량, 확장성, 비용 등에 부정적 영향을 줄 수 있습니다.

### **컨테이너 크기가 커졌을 때의 4가지 영향**

1. **배포 시간(Time to Deploy)**: 컨테이너를 배포하는 데 걸리는 시간이 길어질수록, 애플리케이션을 업데이트하거나 롤백하는 데 걸리는 시간도 함께 늘어납니다.
2. **자원 사용량(Resource Usage)**: 큰 컨테이너는 더 많은 CPU와 메모리를 소비하여 호스트 시스템의 성능에 영향을 줍니다.
3. **확장성(Scalability)**: 컨테이너는 늘어난 트래픽을 감당하기 위해 동일한 컨테이너의 여러 인스턴스를 동시에 띄우는 수평 확장 방식을 전제로 하는데, 컨테이너가 크면 더 많은 자원이 필요해져 확장 자체가 어려워질 수 있습니다.
4. **비용(Cost)**: 더 많은 자원이 필요한 만큼, 애플리케이션 운영 비용도 함께 늘어날 수 있습니다.

### **컨테이너 크기**란**?**

컨테이너 크기는 `컨테이너가 동작하는 데 필요한 메모리와 디스크 공간의 양`을 의미합니다. 컨테이너에 필요한 자원을 관리하는 것은 컨테이너 기반 애플리케이션 배포에서 핵심 이슈 중 하나인데, 작은 이미지는 다운로드·전송이 빨라 더 신속하게 배포될 수 있는 반면, 지나치게 큰 컨테이너는 설치 시간이 길어지고 메모리·CPU 사용량이 늘어나 성능 저하와 비용 상승으로 이어질 수 있습니다. 특히 수백~수천 대 서버에 배포하는 경우라면, 배포 시간을 몇 초만 줄여도 전체적으로는 수십 시간의 절감 효과로 이어질 수 있습니다.

반면 지나치게 큰 컨테이너는 설치 시간이 길어지고 메모리·CPU 사용량이 늘어나 성능 저하와 비용 상승으로 이어질 수 있습니다. 반대로 컨테이너가 너무 작으면 애플리케이션 구동에 필요한 자원 자체가 부족해 오히려 느리고 불안정해질 수 있습니다. 따라서 애플리케이션의 실제 자원 요구사항을 파악해 두 극단 사이에서 적정한 균형점을 찾는 것이 중요합니다.

## 4.2. 최적화 전략: 멀티스테이지 빌드 / 최소 베이스 이미지 / 캐시 활용

### **컨테이너 크기 최적화를 위한 5가지 Best Practice**

1. **`최소 베이스 이미지 사용**:` 예를 들어 Java 웹 애플리케이션을 개발할 때 풀 Linux 배포판 대신 Alpine 같은 경량 베이스 이미지를 사용하면, 컨테이너 크기를 약 1GB에서 400MB 이하로 줄일 수 있습니다.
2. **`의존성 최소화`**: 애플리케이션이 실제로 필요로 하는 라이브러리만 포함시킵니다. 예를 들어 Express와 Mongoose만 필요한 Node.js 앱이라면 그 두 가지만 포함시켜, 약 200MB였던 크기를 50MB 이하로 줄일 수 있습니다.
3. **`불필요한 파일 제거`**: 애플리케이션 동작에 불필요한 임시 파일이나 로그 파일 등을 제거하면 몇 메가바이트 수준이라도 크기를 줄일 수 있습니다.
4. **`멀티스테이지 빌드 사용`**: 빌드 환경과 런타임 환경을 분리해, 최종 이미지에는 런타임에 꼭 필요한 파일만 포함시키는 방식입니다. 예를 들어 바이너리를 컴파일한 뒤 그 결과물만 더 작은 베이스 이미지로 옮기면, 수백MB였던 이미지를 50MB 미만으로 줄일 수 있습니다.
5. **`마이크로서비스로 분리`**: 웹서버, 데이터베이스, 캐시가 한 컨테이너에 모두 들어 있는 모놀리식 구조 대신, 각각을 독립된 컨테이너로 나누면 컨테이너 크기를 줄이면서 확장성도 함께 높일 수 있습니다.

### **예시) Dockerfile과 크기 변화**

**기법 1 — 경량 베이스 이미지 사용**

```docker
# 원본: node:16 (Debian 기반) → 이미지 크기 1.35GB
FROM node:16
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD ["npm", "start"]
```

```docker
# 최적화: node:16-alpine → 이미지 크기 185MB (86.3% 감소)
FROM node:16-alpine
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD ["npm", "start"]
```

Alpine Linux는 최소한의 구성만 담도록 설계된 배포판이라, Debian 기반 이미지보다 훨씬 작다. 애플리케이션 실행에 꼭 필요한 패키지만 포함되어 있다.

**기법 2 — 레이어 캐싱 최적화**

```docker
# 원본: 코드 전체를 먼저 복사한 뒤 설치 → 코드 수정 시에도 매번 npm install 재실행
FROM node:16-alpine
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD ["npm", "start"]
```

```docker
# 최적화: 의존성 파일만 먼저 복사 → 설치 → 이후 소스 코드 복사
# 이미지 크기는 그대로(약 185~206MB)지만, 코드만 바뀌었을 때 재빌드 시간이 약 75% 단축 (예: 7.5초 → 5.9초)
FROM node:16-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["npm", "start"]
```

이 기법은 이미지 크기 자체를 줄이지는 않지만, 애플리케이션 코드만 수정했을 때 `npm install` 레이어의 캐시를 그대로 재사용할 수 있어 빌드 시간을 크게 단축한다.

**기법 3 — 개발 의존성 제거**

```docker
# --only=production으로 개발 의존성(Jest, Nodemon, Supertest 등) 제외
# 이미지 크기 240MB → 170MB (29% 감소)
FROM node:16-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --only=production
COPY . .
EXPOSE 3000
CMD ["npm", "start"]
```

Jest, Nodemon, Supertest 같은 개발용 패키지는 프로덕션 실행에는 필요 없다. `--only=production` 옵션으로 이런 패키지들을 애초에 설치하지 않으면 이미지 크기를 상당히 줄일 수 있다.

**기법 4 — 패키지 매니저 캐시 정리**

```docker
# npm cache clean --force로 설치 후 남는 패키지 매니저 캐시 제거
# 이미지 크기 206MB → 196MB (5% 감소)
FROM node:16-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --only=production && \
    npm cache clean --force
COPY . .
EXPOSE 3000
CMD ["npm", "start"]
```

npm 같은 패키지 매니저는 설치 속도를 높이기 위해 캐시를 남기는데, 이 캐시는 설치가 끝난 뒤에는 불필요하다. 감소 폭 자체는 크지 않지만(약 5%), 적용이 쉬워 기본적으로 넣을 만한 기법이다.

**기법 5 — 멀티스테이지 빌드 적용**

```docker
# 빌드 단계와 실행 단계를 분리(멀티스테이지)해 컴파일된 dist 산출물만 최종 이미지로 복사
# 이미지 크기 360MB → 252MB (30% 감소)

# 빌드 단계
FROM node:16-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# 프로덕션 단계
FROM node:16-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --only=production
COPY --from=builder /app/dist ./dist
EXPOSE 3000
CMD ["node", "dist/index.js"]
```

프로덕션 전용 의존성만 남겨도, 이미지에는 여전히 npm 실행 파일이나 빌드 도구 같은 런타임에 불필요한 구성 요소가 남아 있다. 빌드 환경과 실행 환경을 완전히 분리하면 이런 요소들을 제거할 수 있어, 이번 사례 전체에서 가장 큰 폭(30%)의 단일 개선 효과를 보였다.

**기법 6 — Distroless 베이스 이미지 사용**

```docker
# 프로덕션 단계 베이스를 Alpine → Google distroless로 교체, 필요한 node_modules만 개별 복사
# 이미지 크기 252MB → 163MB (35% 감소) → 최초 1.35GB 대비 최종 약 135MB, 전체 90%대 감소

# 빌드 단계
FROM node:16-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm install
COPY . .
RUN npm run build

# 프로덕션 단계: distroless 사용
FROM gcr.io/distroless/nodejs:16
WORKDIR /app
COPY --from=builder /app/package.json ./package.json
COPY --from=builder /app/node_modules/express ./node_modules/express
COPY --from=builder /app/node_modules/compression ./node_modules/compression
COPY --from=builder /app/node_modules/helmet ./node_modules/helmet
COPY --from=builder /app/node_modules/morgan ./node_modules/morgan
# ... 실제로 필요한 하위 의존성 패키지들을 이런 식으로 개별 복사
COPY --from=builder /app/dist ./dist
EXPOSE 3000
CMD ["dist/index.js"]
```

Alpine조차도 패키지 매니저나 셸 유틸리티처럼, Node.js 애플리케이션 실행에는 필요 없는 구성 요소를 포함하고 있다. Google의 distroless 이미지는 런타임과 그 의존성만 담고 있으며, 셸이나 패키지 매니저, 기본 유닉스 유틸리티조차 없어 매우 가볍고 보안성이 높다. 다만 위 예시처럼 필요한 `node_modules` 하위 패키지를 하나하나 지정해서 복사해야 하는 번거로움이 있다.

### **레이어 수가 성능·보안에 미치는 영향**

| 항목 | 설명 |
| --- | --- |
| 시작 시간 | 레이어가 많을수록 레지스트리에서 각 레이어를 받아 메모리에 로드하는 데 걸리는 시간이 늘어나, 컨테이너 시작이 느려질 수 있다. 특히 작은 레이어가 많을 때 그 오버헤드가 누적되어 체감된다 |
| 디스크 사용량 | 이미지의 각 레이어는 최종 이미지 크기에 더해지므로, 레이어 수가 많으면 그만큼 디스크 사용량도 늘어난다 |
| 캐싱 | 도커는 빌드 속도 향상을 위해 중간 레이어를 캐싱하는데, 이미 캐싱된 레이어를 변경했을 때 재빌드가 이뤄지지 않아 예상과 다른 동작이 나타날 수 있으므로 주의가 필요하다 |
| 보안 | 각 레이어는 잠재적인 공격 표면이 될 수 있으므로, 레이어 수를 최소화하는 것이 컨테이너 보안 강화에도 도움이 된다 |

멀티스테이지 빌드는 가벼운 베이스 이미지에서 시작해 애플리케이션에 꼭 필요한 의존성과 패키지만 단계적으로 추가하는 방식으로, 필요한 구성 요소는 모두 갖추면서도 최종 컨테이너 크기는 최소화할 수 있게 해주는 대표적인 기법이다. 이 외에도 **Kubernetes**와 같은 컨테이너 오케스트레이션 도구의 오토스케일링 기능을 활용하면, 워크로드에 따라 컨테이너를 동적으로 확장·축소해 자원 효율성을 확보하고 불필요한 자원 낭비를 막을 수 있다.

작은 컨테이너의 이점은 빠른 배포와 자원 최적화에 그치지 않는다. 환경 간 이동과 관리가 쉬워지고, 대규모 애플리케이션을 더 작고 독립적으로 배포 가능한 서비스 단위로 나누는 마이크로서비스 아키텍처 구현에도 유리하다.

**결론**: 현대적인 애플리케이션을 배포하는 데 있어 컨테이너 크기를 줄이는 일은 매우 중요하며, 이를 통해 배포 속도를 높이고 자원 사용을 줄이며 안정적이고 효율적인 애플리케이션 운영을 보장할 수 있다. 소규모 비즈니스 시스템이든 작은 애플리케이션이든, 컨테이너 크기 최적화에 시간을 투자할 가치는 충분하다.

# 5. 흥미로웠던 반박 관점

여기까지의 정리대로 따라가면 "이미지가 크면 나쁘다 → 그러니 작게 만들어야 한다"는 흐름이 자연스러워 보인다. 그런데 한 블로그에서 이 통념의 **근거 자체**를 반박하고 있어서 흥미로웠다.

### 우리가 당연하게 여기던 두 가지 전제

이 블로그는 실무에서 흔히 듣는 두 가지 주장을 정면으로 겨냥한다.

1. "이미지가 작으면 디스크 공간을 덜 차지한다."
2. "이미지가 크면 업로드/다운로드에 시간이 오래 걸린다."

앞서 4장에서 다룬 FullStack 블로그의 논리도 결국 "크기가 작을수록 좋다"는 이 전제 위에 서 있는데, Semaphore 블로그는 두 전제 모두 **일반적으로는 사실이 아니다**라고 주장합니다.

### 어떤 부분에서 반박하는가

**반박 1 — "이미지가 작으면 디스크를 덜 차지한다"는 착각**

도커 이미지는 여러 레이어로 이루어져 있고, 서로 다른 이미지끼리 동일한 레이어를 **공유**할 수 있습니다. 그래서 이미지 크기와 실제 디스크 사용량은 생각만큼 직접적으로 비례하지 않습니다.

이를 보여주기 위해 1GB 이미지(레이어 20MB + 980MB)를 태그만 다른 10개의 이미지가 있다고 가정한 두 가지 케이스를 비교합니다.

- **큰 레이어(980MB)를 공유**하고 작은 레이어(20MB)만 이미지마다 다르다면 → 전체 디스크 사용량은 `980 + (20×10) = 1,180MB`, 이미지당 약 118MB(보고되는 이미지 크기의 11.8%)에 불과합니다.
- 반대로 **작은 레이어(20MB)만 공유**하고 큰 레이어(980MB)가 이미지마다 다르다면 → 전체 사용량은 `20 + (980×10) = 9,820MB`, 이미지당 약 982MB(이미지 크기의 98.2%)에 달합니다.

즉, 실제 디스크 사용량을 좌우하는 것은 "이미지 전체 크기"나 "베이스 이미지 크기"가 아니라 **자주 바뀌는(변경 빈도가 높은) 레이어의 크기**입니다. 베이스 이미지를 줄이는 노력은 디스크 절감 효과가 거의 없으며, 오히려 그만큼 기능이 줄어드는 대가를 치를 수 있다고 지적합니다.

**반박 2 — "큰 이미지는 업로드가 오래 걸린다"는 착각**

도커 이미지를 push/pull할 때는 레이어 단위로 전송되며, 대상 위치에 이미 존재하는 레이어는 다시 전송되지 않습니다. 따라서 실제 전송량은 이미지 전체 크기가 아니라 **아직 존재하지 않는(즉 새로 바뀐) 레이어들의 합**과 같습니다. 첫 전송에서만 전체 크기의 부담을 지고, 이후에는 자주 바뀌는 레이어만 주고받으면 됩니다.

다만 CI/CD 환경처럼 컴퓨팅 자원이 매번 새로 생성되어 캐시가 유지되지 않는 경우에는, 파이프라인 단계마다 이미지 전체를 다시 받아야 하는 예외적인 비효율이 발생할 수 있으며, 이는 자체 레지스트리를 갖춘 CI/CD 도구로 레이어 캐싱을 활용해 완화할 수 있다고 제안합니다.

### 이 블로그가 진짜 하고 싶은 주장

"이미지 크기는 중요하지 않다"가 아니라, **크기가 중요한 진짜 이유가 다르다**는 것이다.

- 관리하기 쉬운 이미지를 만들려면 베이스 이미지나 전체 크기를 줄이는 데 집중할 게 아니라, **Dockerfile을 어떻게 설계하느냐**가 핵심이다.
- 변경 빈도가 낮은 것(의존성 설치 등)을 먼저, 변경 빈도가 높은 것(프로젝트 코드)을 나중에 레이어로 쌓아야 자주 바뀌는 레이어의 크기를 최소화할 수 있다.
- 아래처럼 프로젝트 코드를 이미지 상단에서 통째로 복사하는 구조는, 코드가 조금만 바뀌어도 그 위의 모든 레이어가 매번 다시 만들어지는 "무거운" 이미지가 되므로 지양해야 할 안티패턴으로 제시된다.

```docker
FROM whatever:latest

COPY . ./
...
```

- 결과적으로 이미지가 작아야 좋다는 결론 자체에는 동의하지만, 그 이유는 디스크·전송 효율이 아니라 **공격 표면(attack surface) 축소**와 같은 보안적 이유에 있다고 못박습니다. 이미지가 잘 설계되어 있다면(자주 바뀌는 레이어가 작다면), 최초 한 번의 큰 전송 비용은 이후 반복되는 배포 과정에서 충분히 상쇄된다는 것이 이 블로그의 최종 입장이다.

# 6. 결론

전반적인 자료 조사 결과 "이미지를 작게 만드는 것 자체"가 중요하다는건 엄연한 사실이지만, 반박 관점도 함께 보면 어떤 것에 포커싱을 해야하는지 더 정밀해진다.

- `작게 만들어라`는 여전히 유효 — 최소 베이스 이미지, 불필요한 의존성 제거, 멀티스테이지 빌드, 마이크로서비스 분리는 실제로 배포 시간과 자원 사용량을 줄여줍니다.
- 다만 `왜 작게 만들어야 하는가`에 대한 답은 다시 생각해볼 필요가 있습니다. 디스크 사용량이나 전송 시간은 이미지 전체 크기가 아니라 **Dockerfile 안에서 얼마나 자주 바뀌는 레이어를 잘 분리했는지**에 더 크게 좌우됩니다. 즉 베이스 이미지를 줄이는 것보다, 의존성 설치처럼 잘 안 바뀌는 레이어를 앞에 두고 코드처럼 자주 바뀌는 레이어를 뒤에 두는 **레이어 순서 설계**가 실질적인 캐시 재사용률과 배포 효율에 더 직접적인 영향을 준다.

두 글을 종합하면, 실무에서 가장 균형 잡힌 접근은 다음과 같이 정리할 수 있다.

> **베이스 이미지·의존성·불필요 파일을 줄이고 멀티스테이지 빌드로 런타임 이미지 자체를 가볍게 만들되, Dockerfile 내부에서는 변경이 잦은 레이어(프로젝트 코드)를 최대한 나중에 배치해 캐시 재사용률을 극대화하는 것(Semaphore)이 함께 이뤄져야, 배포 속도·자원 효율·보안(공격 표면 축소)이라는 세 가지 목표를 모두 달성할 수 있다.**
> 

즉 "이미지를 얼마나 작게 만들 것인가"뿐 아니라 "그 이미지를 어떤 순서로 쌓을 것인가"까지 함께 고려하는 것이 실무적인 결론입니다.
