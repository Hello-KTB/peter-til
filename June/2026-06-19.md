# 2. 키워드 정리

## 2-1. 대규모 이벤트

대규모 이벤트란 예시를 통해서 확인할 수 있듯이 평소와는 다르게 트래픽이 몰리는 이벤트라고 저는 이해했습니다. 대규모 이벤트가 발생했다는건 대규모 트래픽이 발생했다는 것과 같다고 해석할 수 있습니다.

### 이벤트 유형 구분

| 유형 | 예시 | 특징 |
| --- | --- | --- |
| 자연 발생형 | 티켓팅, 쇼핑몰 세일 | 예측 가능한 시간대, 정상 사용자 요청 |
| 악의적 공격형 | DDoS 공격 | 예측 불가, 봇/좀비PC 등 비정상 요청 |

DDoS는 티켓팅/세일과 트래픽 급증이라는 결과는 같지만, **의도성과 요청 출처**가 다르기 때문에 완화 전략도 일부 달라집니다.

---

### 트래픽

> 특정 시점에 네트워크를 통해 이동하는 데이터의 양.
> 

위와 같이 특정 시점에 네트워크를 통해 이동하는 데이터의 양이 트래픽이고, 해당 시점에 네트워크를 통해 이동하는 데이터의 양이 많은게 대규모 트래픽이다.

### 대규모 트래픽 기준

**요청 수(RPS, Request Per Second)**

- 소규모 : 초당 100 ~ 1,000 RPS
- 중규모 : 초당 1,000 ~ 10,000 RPS
- 대규모 : 초당 10,000 RPS 이상

**동시 연결 수**

- 일반적으로 10,000 ~ 100,000 이상의 동시 연결이 대규모로 간주

**트래픽 데이터 전송량**

- 초당 몇 MB 또는 GB의 데이터를 전송하는지
- 동영상 스트리밍 서비스 → 초당 수백 MB의 데이터를 전송할 수 있다

**사용자 수**

- 초당 수천 명의 사용자가 동시에 서비스를 이용할 경우 대규모로 간주

---

### 패킷

> 네트워크에서 데이터를 주고받을 때 사용되는 데이터 조각
> 

**구성**

- 헤더(Header) : 패킷에 대한 메타정보 (패킷 길이, 번호, 네트워크 프로토콜, 수신자 및 발신자의 IP주소 등)
- 페이로드(Payload) : 수신자가 요청한 데이터
- 트레일러(Trailer) : 패킷의 끝을 나타내기 때문에 여러 패킷의 경계를 뚜렷하게 알리는 역할을 하고, 오류 검출 역할 또한 한다.

**왜 필요한가?**

데이터를 하나로 보낼 경우

- 전송 과정 중 오류 발생시 전체 데이터 손실 위험
- 손실된 데이터는 재전송해야 하기 때문에 시간이 오래 소요되고 네트워크 자원 낭비
- 네트워크를 사용하는 모든 사용자의 속도 저하

데이터를 작은 용량의 패킷으로 나누어서 보낼 경우

- 패킷을 여러 서버로 분산 가능 → **로드밸런싱, CDN과 연결되는 핵심 원리**
- 특정 네트워크에 부담되지 않음
- 트래픽을 균일하게 분배할 수 있음
- 여러 서버를 사용하기 때문에 데이터 전송을 병렬로 처리하기 용이
- 데이터 전송 시간을 줄임으로써 보다 나은 UX 제공
- 데이터가 손실되어도, 해당 패킷만 재전송하면 되기 때문에 효율적

---

### 지터

> 네트워크에서 데이터 패킷의 전송 지연 시간이 변동하는 현상
> 

이상적인 상황에서라면 일정한 간격으로 전달되어야 하지만, 네트워크 혼잡, 라우터 처리 시간, 링크 상태 등에 의해 지연 시간이 일정하지 않게 된다.

**왜 중요한가?**

- 화상통화, 라이브 스트리밍처럼 **실시간성이 중요한 서비스**에서 지터가 크면 영상이 끊기거나 음성이 뭉개지는 현상 발생
- 대규모 이벤트 상황에서 네트워크 혼잡이 심해질수록 지터도 함께 악화됨

**주요 원인**

- 네트워크 혼잡 : 대역폭이 초과되거나 과다한 트래픽으로 인해 데이터 전송 지연이 불규칙하게 발생
- 라우터/스위치 처리 지연 : 라우터나 스위치가 처리해야 할 패킷이 많아지면 대기 시간이 발생
- 경로 변경 : 데이터 패킷이 다른 경로로 전송되면서 전송 시간이 달라짐
- 패킷 손실 : 손실된 패킷의 재전송 또는 복구로 인해 데이터 지연 증가

**종류**

- 전송 지연 지터 (Transmission Jitter) : 송신과 수신 간 패킷 전달 간격이 달라지는 현상
- 큐잉 지터 (Queuing Jitter) : 네트워크 장치에서 대기 중인 패킷이 처리 순서에 따라 지연이 발생하는 현상
- 패킷 지터 (Packet Jitter) : 각 패킷의 전송 시간 변동으로 인해 수신 간격이 불규칙해지는 현상

---

### 패킷 손실

> 네트워크를 통한 전송 중에 하나 이상의 데이터 패킷이 목적지에 도달하지 못하는 것
> 
1. **목적지에 도착하지 못하는 경우:** 이 경우 패킷이 네트워크 전송 중에 사라져서 목적지에 도달하지 않는 상황을 의미합니다. 패킷이 네트워크의 경로 중간에 사라진다면, 해당 패킷의 데이터는 목적지에 도달하지 못하게 되어서 데이터의 일부 또는 전체가 손실됩니다.
    - **네트워크 혼잡:** 네트워크가 많은 트래픽으로 인해 혼잡한 경우, 패킷이 큐에서 기다리다가 버려질 수 있습니다.
    - **패킷 중계 장비 오류:** 패킷 중계 장비(라우터, 스위치 등)의 오류로 인해 패킷이 손실될 수 있습니다.
    - **신호 간섭:** 무선 네트워크에서는 주변 전파 간섭이나 신호 감도가 낮아서 패킷이 손실될 수 있습니다.
2. **도착했으나 내용이 이상한 경우:** 패킷이 목적지에 도착했지만, 그 내용이 왜곡되었거나 손상된 경우를 말합니다. 이런 경우에는 데이터의 무결성이 위배되어 패킷의 내용이 올바르지 않을 수 있습니다.
    - **데이터 손상:** 패킷 전송 중에 데이터가 손상되거나 왜곡될 수 있습니다. 이는 전파 간섭이나 전송 오류로 인해 발생할 수 있습니다.
    - **암호화/복호화 오류:** 데이터가 암호화되어 전송되는 경우, 복호화 과정에서 오류가 발생하면 데이터가 이상하게 보일 수 있습니다.
    - **데이터 변조:** 중간에 악의적인 공격자가 패킷의 내용을 조작하는 경우, 패킷의 데이터가 변경될 수 있습니다.

## 2-2. 네트워크 병목 현상 (Network Bottleneck)

> 네트워크나 시스템의 특정 지점에서 대역폭, 처리량 등이 제한되어 전체 성능을 저하시키는 현상
> 

네트워크 병목 현상은 네트워크 용량의 한계로 인해 데이터 전송 속도가 현저히 저하되는 지점을 말합니다.

### 핵심 용어

- **대역폭 (Bandwidth)** : 주어진 경로를 통해 데이터를 전송할 수 있는 최대 속도
- **토폴로지 (Topology)** : 네트워크 내 노드와 연결의 물리적·논리적 배열. 장치 간 데이터가 흐르는 방식을 결정한다.

### 토폴로지와 병목 현상의 관계

네트워크의 구조(스타, 링, 메쉬 등)에 따라 데이터 흐름 경로가 다르기 때문에, 특정 노드나 연결부가 병목 현상을 유발할 가능성이 있다.

예시: **스타(Star) 토폴로지**에서는 모든 장치가 중앙 허브를 통해 통신하기 때문에, 허브 하나에 트래픽이 집중되면 전체 네트워크가 느려지는 병목이 발생한다.

### 주요 원인

- 대역폭 제한
- 네트워크 혼잡
- 하드웨어 제약 사항
- 비효율적인 네트워크 설계
- 지연 시간
- 소프트웨어 문제

### 병목 현상으로 인한 영향

- 생산성 감소
- 지연 시간 증가
- 패킷 손실
- 사용자 불만족

### 병목 현상 식별법

- **네트워크 모니터링 도구** : Wireshark, PRTG Network Monitor, SolarWinds 등으로 트래픽 및 성능 지표를 지속적으로 모니터링
- **성능 테스트** : iperf, PingPlotter 등으로 네트워크 속도 및 지연 시간 측정
- **네트워크 트래픽 분석** : 패킷 분석 도구를 사용하여 네트워크를 통해 흐르는 데이터 패킷 검사
- **하드웨어 활용도 분석** : 네트워크 장치의 CPU 및 메모리 사용량 확인
- **경로 분석** : traceroute 도구를 사용하여 데이터 이동 경로 분석

# 3. 완화 전략

## 3-1. 인프라/아키텍처 레벨

### 대역폭 업그레이드

현재 필요한 대역폭 평가 후 DSL에서 광섬유로 전환하는 등 빠른 속도의 연결로 업그레이드

### 서비스 품질(QoS, Quality of Service) 구현

라우터 및 스위치의 QoS 설정을 활용하여 VoIP 또는 비디오 스트리밍과 같은 특정 유형의 트래픽 우선순위 지정

### 네트워크 설계 최적화

VLAN을 사용하여 네트워크를 분할하는 등 효율성을 높이기 위해 네트워크 아키텍처 검토 및 재설계

### 네트워크 세분화

네트워크를 더 작고 관리하기 쉬운 부분으로 나누어 혼잡을 줄이고 성능 향상

### 로드밸런서 (Load Balancer)

라운드로빈 DNS 또는 전용 로드밸런서와 같은 기술을 활용하여 여러 서버에 트래픽을 고르게 분산

---

## 3-2. 애플리케이션/서비스 레벨

### Rate Limiting (레이트 리미팅)

> 네트워크 트래픽을 제한하는 전략으로, 특정 시간 내에 특정 작업을 반복할 수 있는 횟수에 제한을 두는 것
> 

### 구현 알고리즘

| 알고리즘 | 동작 원리 | 적합한 상황 |
| --- | --- | --- |
| Token Bucket | 버킷에 일정 속도로 토큰이 채워지고, 요청마다 토큰을 소모. 토큰이 없으면 요청 거부. 버킷이 가득 차면 토큰은 더 이상 쌓이지 않음 | 버스트 트래픽을 일정 범위 내에서 허용해야 하는 경우 |
| Leaky Bucket | 요청이 FIFO 큐에 쌓이고, 일정한 속도로만 처리됨. 큐가 가득 차면 새 요청은 버려짐 | 처리율을 엄격하게 일정하게 유지해야 하는 경우 |
| Fixed Window | 시간을 고정 단위(예: 1분)로 나누고 각 윈도우마다 요청 수를 카운트. 한계 초과 시 거부 | 구현이 단순해야 하는 경우. 단, 윈도우 경계 시점에 요청이 몰리는 버스트 문제가 있음 |
| Sliding Window | 각 요청의 타임스탬프를 기록하고, 현재 시간 기준 윈도우 내 요청 수를 계산. Fixed Window의 버스트 문제를 해결 | 정밀한 제어가 필요한 경우. 단, 타임스탬프 저장으로 메모리 사용량이 높음 |

### 적용 단위

- **IP별** : 특정 IP에서 너무 많은 요청이 올 때 차단. 구현이 단순하지만, 봇넷처럼 여러 IP를 쓰는 공격은 우회 가능
- **사용자(계정)별** : 로그인한 사용자 기준으로 제한. 로그인 무차별 대입 공격 방어에 효과적. IP+사용자 조합으로 사용하면 우회 가능성이 낮아짐
- **API 엔드포인트별** : API 호출 횟수 자체를 제한. 서버 리소스 보호 및 남용 방지, DDoS성 API 공격 방어에 활용

### DDoS 방어에서의 역할

레이트 리미팅은 DDoS 공격 시 비정상적으로 높은 요청 빈도를 가진 IP나 계정을 자동으로 차단함으로써 서버가 정상 사용자의 요청을 처리할 여력을 유지하도록 돕는다. 다만 수많은 IP에서 분산 공격하는 경우엔 IP 기반 레이트 리미팅만으로는 한계가 있으며, Anycast나 CDN과 같은 전략과 함께 사용하는 것이 효과적이다.

---

### CDN (Content Delivery Network)

> 최종 사용자와 가까운 곳에 컨텐츠를 캐싱하는 지리적으로 분산된 서버 네트워크 시스템
> 

전 세계에 분산된 서버 네트워크로, 사용자에게 빠르고 효율적으로 컨텐츠를 전달하기 위해 만들어졌습니다. 이 네트워크는 웹페이지, 비디오, 이미지 등의 정적 컨텐츠를 사용자와 물리적으로 가까운 위치에서 제공하여 로딩 시간을 단축시키고, 서버 과부하를 방지합니다.

### 동작 원리

CDN은 세 종류의 서버로 구성됩니다.

- **오리진 서버** : 웹사이트의 원본 컨텐츠를 저장하는 중앙 서버. 운영자가 직접 관리
- **엣지 서버** : 전 세계 곳곳에 위치한 분산 서버. 오리진 서버의 컨텐츠를 캐싱하고, CDN 공급업체가 관리
- **DNS 서버** : 사용자의 요청을 가장 가까운 엣지 서버로 라우팅하는 역할

**요청 흐름**

1. 사용자가 컨텐츠를 요청하면, DNS 서버가 사용자 위치 기준 가장 가까운 엣지 서버의 IP를 반환
2. 엣지 서버에 해당 컨텐츠가 캐싱되어 있으면 즉시 응답 (캐시 히트)
3. 캐시가 없거나 만료됐으면 오리진 서버에서 최신 컨텐츠를 가져온 뒤 사용자에게 전달하고 캐시에 저장

### 정적 콘텐츠 vs 동적 콘텐츠

- **정적 콘텐츠 (이미지, CSS, JS 등)** : 내용이 변하지 않으므로 엣지 서버에 캐싱하기 적합. CDN이 가장 효과적으로 작동하는 영역
- **동적 콘텐츠 (실시간 재고, 좌석 현황 등)** : 요청마다 최신 데이터가 필요하므로 캐싱이 어려움. 캐싱된 데이터를 그대로 보여주면 "이미 매진된 좌석이 남아있는 것처럼" 표시되는 문제 발생 → 캐시 무효화 전략이 필수

### 캐싱과의 관계

CDN은 캐싱을 핵심 메커니즘으로 활용한다. 엣지 서버에 캐시된 컨텐츠를 제공함으로써 오리진 서버까지 요청이 도달하지 않아도 되기 때문에, 오리진 서버의 부하를 크게 줄여준다. 즉, CDN은 캐시 레이어 중 "CDN 캐시(엣지 서버)" 레이어를 담당한다. → 캐싱 섹션의 레이어 구조 참고

### 실제 사례

- **Cloudflare** : 전 세계 300개 이상의 데이터센터를 보유한 CDN 및 보안 서비스. DDoS 방어 기능도 함께 제공하여 레이트 리미팅, Anycast와 통합 운용이 가능
- **Akamai** : 세계 최초의 상용 CDN 중 하나로, 대규모 미디어 스트리밍 및 엔터프라이즈 서비스에 많이 사용됨

### Anycast

> 들어오는 요청을 다양한 위치 또는 노드로 라우팅할 수 있는 네트워크 주소 지정 및 라우팅 방법
> 

### Unicast vs Anycast 비교

|  | Unicast | Anycast |
| --- | --- | --- |
| 목적지 | 하나의 특정 서버 | 동일한 IP를 공유하는 여러 서버 중 하나 |
| 라우팅 방식 | 고정된 경로로 특정 서버에 전달 | 라우터가 네트워크 상 가장 가까운 서버로 자동 전달 |
| 적합한 상황 | 특정 서버와의 1:1 통신이 필요한 경우 | 지리적으로 분산된 서비스에서 응답 속도와 가용성을 높여야 하는 경우 |

### DDoS 트래픽 분산에 효과적인 이유

DDoS 공격은 단일 서버에 트래픽을 집중시켜 마비시키는 방식이다. Anycast를 사용하면 공격 트래픽도 여러 노드에 자동으로 분산되기 때문에, 특정 서버 한 곳이 공격 트래픽을 모두 감당하지 않아도 된다. 전체 네트워크 용량으로 공격을 흡수하는 구조여서 대규모 DDoS에 효과적이다.

### CDN과 함께 쓰이는 방식

CDN 공급업체(예: Cloudflare)는 전 세계 엣지 서버 네트워크에 Anycast를 적용한다. 사용자가 CDN의 IP로 요청을 보내면 Anycast가 가장 가까운 엣지 서버로 라우팅하고, 해당 엣지 서버가 캐싱된 컨텐츠를 응답하는 방식이다. 결과적으로 응답 속도 단축 + 오리진 서버 부하 감소 + DDoS 분산 방어를 동시에 달성한다.

### 캐싱 (Caching)

> 파일 복사본을 캐시 또는 임시 저장 위치에 저장하여 보다 빠르게 액세스할 수 있도록 하는 프로세스
> 

### 캐시 레이어 구조

```
요청 흐름
사용자 → [브라우저 캐시] → [CDN 캐시] → [애플리케이션 캐시(Redis 등)] → [DB 캐시] → 원본 DB
         (캐시 히트 시 즉시 응답, 미스 시 다음 레이어로 전달)
```

| 레이어 | 위치 | 특징 |
| --- | --- | --- |
| 브라우저 캐시 | 클라이언트(사용자 기기) | 이미지, CSS, JS 등을 로컬에 저장. 재방문 시 서버 요청 없이 즉시 로드. 만료 시간(TTL)으로 갱신 주기 제어 |
| CDN 캐시 | 엣지 서버 (지역 분산) | 오리진 서버 대신 가까운 엣지 서버에서 응답. 오리진 트래픽 대폭 감소 |
| 애플리케이션 캐시 | 서버 메모리 (Redis, Memcached 등) | DB 조회 결과나 연산 결과를 메모리에 저장. DB보다 훨씬 빠른 응답 속도 |
| DB 캐시 | DB 앞단 (쿼리 캐시 등) | 동일한 쿼리의 결과를 캐싱하여 DB 부하 감소. DB 자체 캐시 또는 별도 캐시 레이어로 구현 |

### 캐시 히트율 (Cache Hit Rate)

> 전체 요청 중 캐시에서 직접 응답된 요청의 비율
> 

캐시 히트율이 높을수록 오리진 서버나 DB까지 요청이 도달하는 빈도가 줄어들기 때문에, 응답 속도가 빨라지고 서버 부하가 낮아진다. 대규모 이벤트 상황에서 히트율이 높으면 트래픽이 폭증해도 오리진 서버가 버틸 수 있는 구조가 만들어진다.

- **히트율 높음** → 오리진 서버 요청 감소 → 병목 완화
- **히트율 낮음** → 대부분의 요청이 오리진까지 도달 → 병목 악화

### 캐시 무효화 (Cache Invalidation) 문제

> 원본 데이터가 변경됐을 때 캐시된 오래된 데이터를 제거하거나 갱신하는 프로세스
> 

캐싱은 성능을 높이지만, **데이터의 실시간성이 중요한 상황에서는 오히려 문제가 된다.**

예시: 티켓팅 서비스에서 잔여 좌석 수를 CDN이나 애플리케이션 캐시에 저장해두면, 실제로는 매진됐더라도 캐시 만료 전까지 "잔여 좌석 있음"으로 표시될 수 있다. 사용자가 결제를 시도할 때서야 실패가 발생하므로 UX에 악영향을 준다.

**대응 전략**

- TTL(Time To Live)을 짧게 설정하여 캐시 갱신 주기를 빠르게 유지
- 데이터 변경 시 캐시를 즉시 삭제(Purge)하는 이벤트 기반 무효화 적용
- 실시간성이 필요한 데이터는 캐싱 대상에서 제외하고 오리진에서 직접 조회

# 4. 주제로 복귀

## 4-1. 대규모 이벤트 상황에서 발생하는 네트워크 병목 현상 설명

대규모 이벤트는 크게 두 가지 유형으로 나뉘지만, 공통적으로 대규모 트래픽이 발생한다는 점에서 같습니다. 지금 진행하고 있는 무신사 무진장 세일, 인기 그룹 티켓팅, 게임 이벤트처럼 특정 시간에 자연적으로 트래픽이 몰리는 **자연 발생형**이 있고, 시스템을 마비시킬 목적으로 봇/좀비 PC를 동원해 의도적으로 트래픽을 폭증시키는 **DDoS 공격**이 있습니다. 의도 여부와 관계없이 결과적으로 네트워크에 감당하기 어려운 수준의 트래픽이 집중된다는 공통점이 있습니다.

이렇게 트래픽이 급증하면 네트워크 병목 현상이 발생합니다. 트래픽 폭증으로 인해 네트워크 대역폭이 초과되면 데이터 패킷이 라우터나 스위치의 큐에 쌓이기 시작하고, 큐가 가득 차면 패킷이 드롭(손실)됩니다. 패킷 손실은 재전송을 유발하여 지연을 더욱 악화시키고, 결국 특정 지점에서 데이터 흐름이 현저히 느려지거나 완전히 막히는 병목 현상으로 이어집니다. 특히 모든 요청이 단일 오리진 서버로 집중되는 구조에서는 서버 자체의 처리 용량도 한계에 부딪혀 응답 불가 상태까지 발생할 수 있습니다.

## 4-2. 이를 완화하기 위한 전략 서술

### 문제 지점

병목의 핵심 원인은 두 가지다. 하나는 **단일 오리진 서버로의 트래픽 집중**이고, 다른 하나는 **처리 가능한 요청 수를 초과하는 비정상적 요청 폭증**이다. 이 두 지점을 각각 또는 함께 해결하는 방향으로 완화를 합니다.

### CDN — 오리진 서버 집중 완화

CDN은 전 세계에 분산된 엣지 서버가 오리진 서버의 컨텐츠를 캐싱하여, 사용자 요청이 오리진까지 도달하지 않아도 응답할 수 있게 한다. 대규모 이벤트 상황에서 오리진 서버로 몰리는 요청의 상당수를 엣지 서버에서 흡수함으로써 오리진의 부하를 크게 줄인다.

무신사 세일처럼 이미지, 상품 목록 페이지 등 **정적 컨텐츠 요청이 많은 경우**에 특히 효과적이다. 다만, 실시간 재고나 좌석 현황 같은 동적 컨텐츠는 캐싱이 어려워 CDN만으로는 한계가 있다.

### 캐싱 — 반복 요청 처리 부하 감소

캐싱은 한 번 처리한 데이터를 임시 저장해두고 동일한 요청에 재사용하는 전략이다. 브라우저 캐시 → CDN 캐시 → 애플리케이션 캐시(Redis) → DB 캐시 순서로 레이어가 구성되어 있으며, 앞단 레이어에서 응답이 완료될수록 오리진 서버와 DB의 부하가 줄어든다.

캐시 히트율이 높을수록 병목 완화 효과가 크다. 단, 티켓팅 잔여 좌석처럼 **실시간성이 중요한 데이터**는 캐시된 값이 실제와 달라지는 문제가 생기므로, TTL을 짧게 설정하거나 데이터 변경 시 즉시 캐시를 무효화하는 전략이 함께 적용되어야 한다.

### Anycast — 트래픽의 지리적 분산

Anycast는 동일한 IP 주소를 여러 노드에서 BGP로 동시에 광고하여, 요청이 자동으로 가장 가까운 노드로 라우팅되도록 하는 방식이다. 단일 서버가 모든 트래픽을 받는 대신 전 세계 노드가 분산해서 처리하기 때문에, 특정 지점에서의 병목을 구조적으로 방지한다.

DDoS 공격에서는 공격 트래픽 역시 여러 노드로 분산되므로, 전체 네트워크 용량으로 공격을 흡수할 수 있다. CDN과 결합하면 응답 속도 단축 + 오리진 부하 감소 + DDoS 분산 방어를 동시에 달성한다.

### Rate Limiting — 비정상 요청 차단

Rate Limiting은 단위 시간당 요청 수에 제한을 두어 특정 IP, 사용자, API 엔드포인트에서 과도한 요청이 서버에 도달하지 못하도록 막는다. DDoS 공격처럼 비정상적으로 높은 빈도의 요청을 조기에 차단함으로써 서버가 정상 사용자의 요청을 처리할 여력을 유지하도록 돕는다.

다만 수많은 IP에서 분산 공격하는 경우엔 IP 기반 Rate Limiting만으로는 한계가 있어, CDN이나 Anycast와 함께 사용하는 것이 효과적이다.

### 전략 조합의 중요성

각 전략은 단독으로 쓰이기보다 **조합**할 때 더 강력하다. 예를 들어 Anycast + CDN 조합은 지리적 분산과 캐싱을 동시에 처리하고, Rate Limiting + CDN 조합은 비정상 요청을 걸러내면서 정상 요청은 빠르게 응답한다. Cloudflare는 이 전략들을 통합적으로 제공하는 대표적인 서비스로, CDN·Anycast·Rate Limiting·DDoS 방어를 하나의 플랫폼에서 운용할 수 있다.
