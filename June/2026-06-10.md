# 1. 공유자원

> 여러 사용자나 프로세스, 스레드가 동시에 접근하거나 사용하는 시스템 내의 자원
> 

## 왜 사용하는가?

운영체제에서 CPU, 메모리, 파일, 네트워크 같은 자원은 무한하지 않다. 모든 프로세스가 각자 별도의 자원을 요청하면 자원이 금방 소진된다. 그래서 하나의 자원을 여러 작업이 공유해서 사용한다

| 이유 | 설명 |
| --- | --- |
| 메모리 절약 | 프로세스 3개가 각각 100MB → 300MB / 공유하면 → 100MB |
| 데이터 일관성 유지 | 공유 데이터를 사용하면 데이터가 일관적으로 유지됨 |
| 프로세스 간 협업 | 여러 기능(로그인, 주문, 결제 등)이 "사용자 정보"라는 공유 자원으로 협업 가능 |

대표적인 공유 자원: 메모리, 파일, 데이터베이스, 네트워크 소켓, 전역 변수

## 발생할 수 있는 문제점

- 동시에 공유자원을 수정하면 문제가 생길 수 있다
- 서로 다른 프로세스가 동일한 자원에 동시에 접근하는 것을 **경쟁 상태(Race Condition)** 라고 한다

# 2. 임계영역

> 공유 자원에 접근하는 프로그램 코드의 일부분으로, 동시에 여러 프로세스나 스레드가 접근하면 문제가 생길 수 있는 구간
> 

| 구분 | 공유 자원 | 임계 영역 |
| --- | --- | --- |
| 의미 | 스레드/프로세스가 함께 사용하는 대상 | 공유 자원에 접근하는 코드 블록 |
| 예시 | `balance`, 파일, 메모리, DB row, 큐 | `balance`를 읽고 수정하고 저장하는 코드 |
| 보호 대상 | 자원 자체 | 자원을 다루는 위험한 코드 |
| 구분하는 질문 | "무엇을 함께 쓰는가?" | "어디에서 충돌이 발생할 수 있는가?" |

```java
int balance = 1000; // 공유 자원

void withdraw(int amount) {
    // 임계영역 시작
    int temp = balance;   // Read
    temp += amount;       // Modify
    balance = temp;       // Write
    // 임계영역 끝
}
```

## 왜 임계영역을 분리해서 사용하나?

공유 자원 전체를 보호하는 것보다 임계 영역만 보호하면 더 효율적으로 시스템 자원을 관리할 수 있다

| 이유 | 설명 |
| --- | --- |
| 데이터 무결성 유지 | 여러 스레드가 동시에 같은 데이터를 수정해도 데이터가 깨지지 않도록 |
| 경합 조건 방지 | 실행 순서에 따라 결과가 달라지는 문제를 막기 위해 |
| 예측 가능한 프로그램 실행 | 같은 입력에 대해 항상 같은 결과가 나오도록 |
| 시스템 안정성 확보 | 멀티스레드 환경에서 데이터 손상, 중복/누락 처리를 줄이기 위해 |

## 임계영역에서 발생하는 문제들

**1. 경합 조건 (Race Condition)**

- 실행 순서에 따라 결과가 달라지는 문제
    - 예시) Lost Update

**2. 데이터 무결성 문제**

- 데이터가 논리적으로 맞지 않는 상태가 되는 문제

**3. 교착 상태 (Deadlock)**

- 여러 스레드가 서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상태
- 실무에서도 자주 발생하며, 특정 임계영역에 두 스레드가 특정 순서로 들어올 때만 발생하기 때문에 재현이 어렵다

## 임계영역 문제를 해결하기 위한 3가지 조건

| 조건 | 설명 | 예시 |
| --- | --- | --- |
| 상호 배제 (Mutual Exclusion) | 한 프로세스가 임계 영역에 있으면 다른 프로세스는 들어갈 수 없음 | "한 번에 한 명만 들어가기" |
| 진행 (Progress) | 임계 영역이 비어 있고 들어가려는 프로세스가 있으면 누군가는 들어가야 함 | "비어 있는데 아무도 못 들어가는 상황 없어야 함" |
| 유한 대기 (Bounded Waiting) | 특정 프로세스가 무한히 기다리지 않아야 함 | "계속 새치기당하면 안 됨" |

# 3. 동기화

> 여러 프로세스 또는 스레드가 공유 자원에 동시에 접근할 때 발생할 수 있는 충돌이나 데이터 무결성 문제를 방지하고, 올바른 `순서와 조정을 보장`하는 메커니즘
> 

한 줄 요약: 임계 영역에서 발생 가능한 문제를 방지하고자 프로세스나 스레드의 **접근 순서를 조정**하는 기술

| 해결 원리 | 설명 |
| --- | --- |
| 동시에 들어가지 못하게 한다 | 한 스레드가 임계 영역에 있으면 다른 스레드는 기다리게 한다 |
| 작업이 끝나면 반드시 나오게 한다 | 락을 잡은 스레드는 작업 후 반드시 락을 해제해야 한다 |
| 무한정 기다리지 않게 한다 | 특정 스레드가 계속 밀려나지 않도록 보장해야 한다 |
| 필요한 구간만 보호한다 | 임계 영역을 너무 넓게 잡으면 성능이 떨어진다 |

## 동기화 방법

**1. Lock / Mutex 사용**

- 공유 자원에 들어가기 전에 "잠금"을 획득하고, 작업 후에 "잠금"을 해제하는 방식

**2. 세마포어 (Semaphore)**

- 락은 임계 영역에 한 명만 들어갈 수 있지만, 세마포어는 임계 영역에 들어갈 수 있는 입장권의 개수가 정해져 있다

**3. Atomic 연산**

- 읽기 → 수정 → 저장 연산을 하나의 쪼갤 수 없는 연산처럼 처리하는 방식

**4. 트랜잭션**

**5. 임계 영역을 작게 유지 (성능 개선)**

- 락을 너무 넓게 잡으면 하나의 스레드가 락을 보유하는 시간이 길어져 처리량이 감소한다

## 실무에서의 동기화

**백엔드 개발자 관점**

운영체제 레벨에서 락을 직접 사용하지는 않지만, 이미 동기화 개념을 쓰고 있다

| 상황 | 동기화 방법 |
| --- | --- |
| 재고 차감, 쿠폰 발급 | DB 트랜잭션 (Row Lock) |
| 결제 처리 | 트랜잭션 (DB + 코드 레벨 비즈니스 로직) |
| 포인트 적립 | AtomicInteger, 트랜잭션 |
| 메시지 큐 (Pub-Sub) | Consumer Lock |
| 캐시 갱신 | CAS, TTL, 분산락 |

**인프라 엔지니어 관점**

코드의 임계영역이 아니라 **공유 리소스의 경합** 관점으로 바라본다

- 커널 내부 락 → 여러 CPU가 커널 자료구조를 동시에 수정하지 못하도록
- 파일 시스템 → 여러 프로세스가 동일 파일을 동시에 수정하지 못하도록 (MVCC)
- 데이터베이스 운영 → 락 경합, 데드락, 트랜잭션 대기 분석
- 쿠버네티스 → 여러 컨트롤러가 리소스 상태를 갱신할 때

# 4. 락

> 하나의 스레드나 프로세스가 자원을 점유할 경우 다른 스레드/프로세스가 해당 자원에 접근하지 못하도록 제어하는 기법
> 

락은 **공유 자원 앞에 걸어두는 자물쇠**

| 개념 | 설명 |
| --- | --- |
| 공유 자원 | 여러 스레드나 프로세스가 함께 사용하는 대상 |
| 임계 영역 | 공유 자원에 접근하는 위험한 코드 구간 |
| 락 | 임계 영역에 한 번에 하나의 스레드만 들어가게 만드는 도구 |

## 락의 기본 동작

```
1. 락 요청
2. 락 획득 (락이 비어 있으면 획득)
3. 임계 영역 실행
4. 다른 스레드 대기
5. 락 해제
6. 다음 스레드 진입
```

## 락의 종류

### 1. 스핀락 (Spin Lock)

- 락이 풀릴 때까지 계속 확인하면서 기다리는 락
- 스레드가 잠들지 않고 반복 확인한다 (Busy-waiting)
- 백엔드 개발에서는 거의 쓸 일이 없고, 운영체제 커널/런타임/저수준 라이브러리에서 사용한다

| 장점 | 단점 |
| --- | --- |
| 락이 아주 빨리 풀리면 빠르게 진입 가능 | 기다리는 동안 CPU를 계속 사용 |
| 컨텍스트 스위칭 비용이 없음 | 락 대기 시간이 길면 비효율적 |
| 커널 내부나 짧은 임계 영역에 적합 | 단일 CPU 환경에서 특히 비효율적 |

### 2. 낙관적 락 (Optimistic Lock)

- 충돌이 거의 없다고 "가정"하고, 작업을 먼저 하고 마지막에 충돌 여부를 검사하는 방식

| 구분 | 설명 |
| --- | --- |
| 기본 가정 | 충돌이 자주 발생하지 않을 것이다 |
| 동작 방식 | 먼저 읽고 수정한 뒤, 저장 시점에 버전이나 값이 바뀌었는지 검사 |
| 충돌 발생 시 | 롤백하거나 재시도 |
| 적합한 상황 | 읽기가 많고 쓰기가 적은 시스템 |
| 대표 예시 | DB version 컬럼, CAS, 분산 환경의 상태 갱신 |

### 3. 뮤텍스 (Mutex)

- 한 번에 하나의 스레드만 자원에 접근하게 하는 대표적인 락
- Mutual Exclusion(상호 배제)의 약자. 소유권 개념이 있으며, **락을 획득한 스레드만 락을 해제할 수 있다**

| 핵심 | 설명 |
| --- | --- |
| 상호 배제 | 한 번에 하나의 스레드만 임계 영역에 들어갈 수 있다 |
| 소유권 | 락을 획득한 스레드가 "현재 소유자"가 된다 |
| 해제 권한 | 락을 획득한 스레드만 락을 해제할 수 있다 |

**뮤텍스 내부 구조**

| 내부 정보 | 의미 |
| --- | --- |
| Lock State | 현재 뮤텍스가 잠겨 있는지, 풀려 있는지 |
| Owner Thread | 현재 뮤텍스를 획득한 스레드가 누구인지 |
| Wait Queue | 뮤텍스를 얻지 못해 기다리는 스레드 목록 |
| Policy | 대기 스레드 중 누구를 깨울지 정하는 방식 |

**대기 큐 정책**

| 방식 | 설명 |
| --- | --- |
| FIFO | 먼저 기다린 스레드가 먼저 깨어남 |
| Priority | 우선순위가 높은 스레드가 먼저 깨어남 |
| 경쟁 방식 | 깨어난 스레드들이 다시 락 획득 경쟁 |
| Fair Lock | 대기 순서를 비교적 엄격하게 지킴 |
| Non-fair Lock | 새로 온 스레드가 먼저 락을 가져갈 수도 있음 |

```java
Lock lock = new ReentrantLock();

public void update() {
    lock.lock();
    try {
        // 임계 영역
    } finally {
        lock.unlock();
    }
}
```

**조건 변수와 함께 사용하기**

단순 상호 배제 외에 "특정 조건을 만족할 때까지 기다려야 하는" 상황에서는 조건 변수를 함께 사용한다

```java
// 큐가 비어있을 때 CPU를 낭비하지 않고 대기
while (queue.isEmpty()) {
    notEmpty.await(); // 잠든다
}
// 큐에 데이터가 들어오면 notEmpty.signal()로 깨어남

// 뮤텍스 = 공유 자원 접근 권한 관리
// 조건 변수 = 특정 조건 충족 여부 관리
```

**장단점**

| 장점 | 단점 |
| --- | --- |
| 데이터 무결성 보장 | 병렬성 감소 |
| 사용 방식이 직관적 (lock → 작업 → unlock) | 컨텍스트 스위칭 오버헤드 |
| 운영체제/언어 기본 제공 | 데드락 위험 |
| CPU 낭비 감소 (스핀락과 달리 스레드를 잠들게 할 수 있음) | 락 미해제 시 무한 대기 발생 |
| 임계 영역 보호에 적합 | 우선순위 역전 가능성 |

### 4. 리드-라이트 락 (Read-Write Lock)

- 읽기는 여러 명이 동시에 허용하고, 쓰기는 한 명만 허용하는 락
- 읽기가 많고 쓰기가 적은 시스템에서 뮤텍스보다 성능이 좋다

| 상황 | 허용 여부 |
| --- | --- |
| Reader + Reader | 가능 |
| Reader + Writer | 불가능 |
| Writer + Writer | 불가능 |

**대기 순서 정책**

- Writer 우선 정책: 라이터가 들어오면 더 이상 리더를 받지 않고 라이터가 먼저 권한 획득
- Reader 우선 정책: 라이터가 대기 중이어도 계속 리더를 받아줌 → Writer 기아 발생 가능

**사용 예시**

| 상황 | 설명 |
| --- | --- |
| 캐시 조회 | 읽기는 많고 갱신은 적은 경우 |
| 설정 정보 조회 | 대부분 읽고 가끔 수정하는 경우 |
| 파일 시스템 메타데이터 | 조회는 많고 변경은 제한적인 경우 |

**장단점**

| 장점 | 단점 |
| --- | --- |
| 읽기 요청이 많은 시스템에서 성능 향상 | 구현이 뮤텍스보다 복잡 |
| Reader는 동시에 접근 가능 | Writer/Reader 기아 상태 가능 |
| Writer는 독점 접근으로 데이터 무결성 보장 | Read Lock에서 Write Lock 업그레이드 시 데드락 위험 |

## 자주 헷갈리는 것들

| 질문 | 답 |
| --- | --- |
| 공유 자원 = 임계 영역? | 아니다. 공유 자원은 대상, 임계 영역은 그걸 수정하는 코드 블록 |
| 모든 공유 자원 접근이 임계 영역? | 아니다. 읽기만 한다면 임계 영역이 아닐 수 있다 |
| 락을 많이 걸면 안전해지나? | 안전하지만 성능이 나빠진다. 락의 범위를 제한해야 한다 |
| 락을 쓰면 다 해결되나? | 아니다. 데드락, 성능저하, 기아 상태, 락 누락, 락 범위 오류 문제가 남는다 |

## 실무 팁

1. 임계 영역은 작게 잡아야 한다
2. 락은 잡으면 무조건 `finally`에서 해제해라
3. 여러 락이 필요하면 항상 같은 순서로 획득해라 (항상 A → B 순서 유지)
4. 데이터베이스에서 Unique, Transaction을 적극적으로 활용해라
5. 분산 환경(서버 여러 대)에서는 로컬 락만으로는 부족하다 → DB Lock, Redis 기반 분산락 사용
