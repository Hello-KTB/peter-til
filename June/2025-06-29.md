# 1. DevOps

## 핵심 개념

> 개발(Development)과 운영(Operations)의 협업을 통해 소프트웨어 배포 속도와 안정성을 함께 높이는 문화 및 방법론
> 

더 자주 배포하는 것 자체가 목표가 아니다. 작은 변경을 더 빠르게 검증하고, 안전하게 배포하고, 문제가 생기면 복구할 수 있는 환경을 만드는 것이 목표다.

## 개발팀 vs 운영팀

| 구분 | 원하는 것 |
| --- | --- |
| 개발팀 | 기능을 빠르게 만들고, 빨리 배포하고 싶다 |
| 운영팀 | 서비스를 안정적으로 서빙하고, 장애 위험 때문에 배포는 최대한 적고 안전하게 하고 싶다 |

## DevOps가 등장한 이유 (기존 분리 방식의 문제)

| 문제 | 내용 |
| --- | --- |
| 배포 지연 | 개발팀은 완료 즉시 배포 원함 / 운영팀은 배포 일정(예: 7월 1일)에 맞춰 야근하며 릴리즈 → 배포 덩어리가 커지고, 테스트·안정화가 어려워짐. 운영팀 입장에선 배포가 잦을수록 서비스가 불안정해진다고 봄 |
| 수동 작업 | 개발팀은 운영 서버 접속 불가(위험). 운영팀이 서버 접속 → 파일 복사 → 명령어 → 설정 수정 → 배포 실행을 손으로 처리 |
| 환경 차이 | 개발 서버 ↔ 운영 서버의 자바 버전, 라이브러리 버전 불일치 |
| 책임 차이 | 배포 후 장애 발생 시 코드 문제인지 서버 문제인지 책임 소재가 불명확 |

→ 개발과 운영이 분리되어 생기는 **소통 지연, 배포 지연, 수작업 문제**를 줄이기 위해 DevOps가 만들어졌다.

## DevOps의 핵심 목표

| DevOps가 추구하는 것 | 의미 |
| --- | --- |
| 빠른 전달 | 기능 수정이 사용자에게 도달하는 시간을 줄임 |
| 안정적인 배포 | 배포가 장애의 큰 원인이 되지 않도록 만듦 |
| 자동화 | 반복되는 빌드·테스트·배포 작업을 줄임 |
| 공동 책임 | 개발과 운영이 서비스 품질을 함께 책임짐 |
| 빠른 피드백 | 장애와 성능 문제를 관찰하고 개선에 반영 |
| 지속적 개선 | 한 번 구축하고 끝내지 않고 계속 개선 |

# 2. Docker

## 핵심 개념

> Docker는 애플리케이션 실행에 필요한 모든 요소(코드, 라이브러리, 설정 등)를 하나로 묶어, 어떤 컴퓨터에서든 동일하게 실행되도록 도와주는 도구
> 
> 
> 코드는 깃으로 공유했지만, **실행하는 사람마다 환경이 달랐다.** Spring 서버 하나를 실행하는 데도 자바 버전, Gradle 버전, 라이브러리 버전, OS 패키지, 환경 변수, 포트 설정, DB 주소, 파일 권한, 실행 명령어 등 변수가 너무 많았다.
> 
> 스프링 컨테이너에서 `killall` 같은 명령이 나와도 MySQL의 PID를 모르기 때문에 전파되지 않는다. 즉 프로세스를 분리하면 장애 영향이 훨씬 덜 간다.
> 

## 도커 이전에 발생한 문제들

| 구분 | 개발자 컴퓨터 | 운영 서버 |
| --- | --- | --- |
| 자바 | 21 | 17 |
| DB | MySQL 8.0 | MySQL 6 |
| 패키지 매니저 | brew 등 | apt (`apt-get install`) |
| 포트 | 모두 열려 있음 | 방화벽 → 보안 그룹 → 프로세스 단계로 제한 |
- 패키지 매니저(`brew` ↔ `apt`) 차이로 설치되는 버전이 다름. MySQL 7·8 버전 차이로 작성한 쿼리가 동작하지 않을 수도 있다.
- "내 컴퓨터에서는 됐는데..." → 수동으로 환경을 설정하면 서버 3대까지는 버틸 수 있어도, 30대를 세팅하는 순간 감당이 안 된다.

## 기존 해결 방식 — 가상 머신(VM)

VM은 하이퍼바이저를 통해 **서비스마다 독립적인 OS를 제공**하는 방식이다.

| 구분 | 내용 |
| --- | --- |
| 장점 | 서비스별로 강하게 분리(OS를 다르게 사용 가능), 한 VM의 장애가 다른 VM으로 잘 전파되지 않음 |
| 단점 | 앱 하나 실행에도 항상 전체 OS 실행 필요 (운영체제 + 시스템 프로세스 + 커널 자원 + 부팅 과정). 서비스가 많아지면 자원 사용량과 관리 비용이 커짐 |

## 도커 — 앱만 분리하자

> 도커는 운영체제 전체를 여러 개 만드는 대신, 하나의 운영체제 위에서 애플리케이션 실행 환경만 분리한다.
> 

OS를 복사하지 말고, 앱 + 파일 + 라이브러리 정도만 묶어서 실행하자는 발상.

| 비교 | 가상 머신 | Docker 컨테이너 |
| --- | --- | --- |
| 격리 대상 | 운영체제 전체 | 애플리케이션 프로세스 |
| Guest OS | VM마다 필요 | 컨테이너마다 없음 |
| 커널 | VM마다 독립 | 호스트 Linux 커널 공유 |
| 실행 속도 | OS 부팅 필요 | 프로세스 실행에 가까움 |
| 자원 사용량 | 상대적으로 큼 | 상대적으로 작음 |
| 주 용도 | 서버 단위 격리 | 애플리케이션 단위 배포·실행 |

## 도커의 동작 흐름

> 도커는 실행 환경을 "이미지"로 표준화하고, 컨테이너로 실행하고, 레지스트리로 배포한다.
> 

```
Dockerfile = 붕어빵 레시피   → 실행 환경을 만드는 코드(설명서)
Image      = 붕어빵 틀       → 실행 환경이 포함된 읽기 전용 배포 패키지
Container  = 구워진 붕어빵    → 이미지를 실제 실행한 격리된 프로세스
```

# 3. 🔥 도커는 어떻게 격리하는가 (핵심)

## 핵심 개념

> 컨테이너는 별도의 컴퓨터가 아니라, 하나의 컴퓨터에서 "보이는 환경"과 "사용 가능한 자원"을 제한한 프로세스다.
> 

EC2도 실제로는 하드웨어 장비를 공유받는 것이듯, 컨테이너는 하나의 호스트 OS를 나눠 쓰면서 서로에 대해 격리되어 있다.

| 구성 요소 | 역할 |
| --- | --- |
| 커널(Kernel) | 애플리케이션이 CPU·메모리·디스크·네트워크를 쓰도록 실제로 처리해주는 운영체제의 핵심 |
| Namespace | 컨테이너마다 서로 다른 프로세스·네트워크·파일시스템이 있는 것처럼 보이게 함 |
| cgroups | 컨테이너별로 CPU·메모리·프로세스 수 등을 얼마나 쓸지 제한하고 측정함 |

## 커널(Kernel)

> 애플리케이션 ↔ 하드웨어 사이에서 CPU·메모리·네트워크·디스크 자원을 관리하는 운영체제의 핵심 프로그램
> 

| 영역 | 예시 | 역할 |
| --- | --- | --- |
| 사용자 공간(User Space) | Java, Python, Nginx, MySQL, `bash`, `ls` | 우리가 직접 실행하는 프로그램 영역 |
| 커널 공간(Kernel Space) | Linux Kernel | 하드웨어 제어와 자원 관리 |
| 하드웨어 | CPU, 메모리, 디스크, 네트워크 카드 | 실제 물리 자원 |
- 애플리케이션은 디스크에 직접 접근하지 못하고, 반드시 커널에게 **시스템 콜**로 요청한다.
- **도커 컨테이너 안에는 커널이 없다.** 이미지 안에는 자바 런타임·jar·라이브러리만 있고, 호스트 OS 커널을 공유한다. 그래서 Guest OS 전체를 부팅하는 VM보다 훨씬 가볍다.

## Namespace

> 컨테이너마다 "프로세스, 네트워크, 파일시스템"이 독립적으로 존재하는 것처럼 보이게 만드는 Linux 커널 기능
> 

하나의 전역 자원을 분리된 자원처럼 사용할 수 있게 한다. 같은 서버에서 실행되어도 다른 네임스페이스면 분리된다. (네임스페이스가 없으면 모든 프로세스가 같은 프로세스 목록·네트워크 인터페이스·파일시스템 구조·hostname·사용자 체계를 본다.)

| 종류 | 분리 대상 |
| --- | --- |
| PID Namespace | 프로세스 목록 — 컨테이너가 자기 안의 프로세스만 보도록 분리 |
| Network Namespace | 컨테이너별 독립 IP·포트·라우팅 테이블·네트워크 인터페이스(eth0)·DNS |
| Mount Namespace | 파일시스템 분리 |

**PID Namespace 예시**

```
Spring Boot 컨테이너          MySQL 컨테이너
PID 1  java -jar app.jar     PID 1  mysqld
PID 25 worker-thread         PID 31 mysql-worker
PID 40 shell
```

## cgroups

> 여러 프로세스를 하나의 그룹으로 묶고, 그 그룹의 CPU·메모리·I/O·프로세스 수 사용량을 제한·측정하는 Linux 커널 기능
> 

Namespace가 다른 컨테이너를 "안 보이게" 했더라도, 호스트 OS의 자원은 공유한다. 제한이 없으면:

```
MySQL 컨테이너가 메모리 7GB 사용
→ Spring Boot 컨테이너가 쓸 메모리 부족
→ 서버 전체 성능 저하 또는 OOM 발생
```

## Namespace vs cgroups

| 구분 | Namespace | cgroups |
| --- | --- | --- |
| 핵심 질문 | 무엇이 보이는가? | 얼마나 사용할 수 있는가? |
| 주요 목적 | 격리 | 자원 제어 |
| 프로세스 목록 | 다른 컨테이너 프로세스를 안 보이게 함 | 프로세스 개수 제한 가능 |
| 네트워크 | 컨테이너별 IP·포트·라우팅 분리 | 네트워크 사용량 측정·일부 제어 |
| 파일시스템 | 컨테이너별 루트 파일시스템처럼 보이게 함 | 직접 분리는 하지 않음 |
| CPU·메모리 | 분리하지 않음 | CPU·메모리 사용량 제한 |
| 대표 비유 | 각 팀에 다른 사무실을 보여줌 | 각 팀의 전기·회의실 사용량을 제한 |

# 4. 실무에서의 도커 활용

> 애플리케이션 → Dockerfile → Image → Registry 저장 → 서버에서 이미지를 다운받아 컨테이너로 실행
> 
1. **로컬 개발 환경 통일** — 6명 팀이 MySQL·Redis·RabbitMQ·Spring·Java·라이브러리를 각자 다른 설정으로 깔지 않고, 컨테이너로 환경을 통일한다.
2. **초기 프로젝트의 단일 EC2** — EC2 하나에 여러 서비스를 컨테이너로 띄운다.
3. **배포 과정** — 소스 코드를 복사하지 않고, 빌드된 도커 이미지를 서버에 전달해서 사용한다.
4. **컨테이너 여러 개 → Docker Compose** — 앱이 하나면 `docker run`이면 충분하지만, Nginx·Redis·MySQL·Spring처럼 여러 개를 매번 환경 변수·옵션과 함께 실행하기 번거로우므로 Docker Compose로 묶는다.

# 5. 도커 사용 시 꼭 지켜야 하는 원칙

| # | 원칙 | 이유 / 대응 |
| --- | --- | --- |
| 1 | 이미지에 비밀번호를 넣지 않는다 | Dockerfile에 DB 비밀번호·API Key를 적으면 이미지 내부에 그대로 노출됨(레지스트리에서 습득 가능). → AWS Secret Manager나 Vault에 넣고 `${...}` 변수로 참조 |
| 2 | `latest` 태그만 쓰지 않는다 | `spring-app:latest`만 쓰면 디버깅 시 어떤 버전에서 에러가 났는지 모름. 운영 배포는 `v1.0` 등 버전 명시 필수 |
| 3 | 컨테이너 안에 데이터를 영구 저장하지 않는다 | 컨테이너 종료 시 내부 데이터 삭제가 기본. 영속이 필요하면 Docker Volume과 함께 사용 |
| 4 | 한 컨테이너에 핵심 역할 하나만 | Nginx+Spring+MySQL을 한 컨테이너에 넣으면 배포·확장·장애 분석이 어려움. 프로세스 여러 개가 들어가도 동작은 하지만, 관리·책임 분리 원칙을 따른다 |
| 5 | 로그를 컨테이너 밖에서도 볼 수 있게 한다 | 로그는 프로세스에서 발생 → 기본적으론 컨테이너에 접속해야 보임. 컨테이너 100개 운영 중 500 에러를 추적하려면 CloudWatch·Loki·Datadog 등으로 외부에 로그를 모은다 (옵저빌리티) |

# 6. Dockerfile

## 핵심 개념

> 도커 이미지를 생성하기 위한 명령어 및 설정이 담긴 텍스트 기반 스크립트 파일 (실행 환경 설명서 / 배포 설계서)
> 

"애플리케이션 실행에 필요한 환경과 절차를 코드로 적어서, 누구나 같은 이미지를 만들 수 있게 하는 것." 도커만 쓰면 컨테이너 만들 때마다 환경 변수를 직접 기입해야 하는데, 그 수동 과정을 파일에 적어두는 것이 Dockerfile이다.

## 위치

보통 프로젝트 최상위 경로에 둔다.

```
my-spring-project/
├── Dockerfile
├── .dockerignore
├── build.gradle
├── settings.gradle
├── gradlew
├── gradle/
├── src/
└── build/
```

## 핵심 명령어

| 명령어 | 질문 | 역할 |
| --- | --- | --- |
| `FROM` | 어디서 시작하는가? | 기반 Image 선택 |
| `WORKDIR` | 어디에서 작업하는가? | 컨테이너 내부 기본 작업 폴더 설정 |
| `COPY` | 어떤 파일을 넣는가? | 로컬 파일을 Image 내부로 복사 |
| `RUN` | Image를 만들 때 무엇을 실행하는가? | 패키지 설치·빌드 등 수행 |
| `EXPOSE` | 앱은 어느 포트를 쓰는가? | 컨테이너가 사용하는 포트를 문서화 |
| `CMD` / `ENTRYPOINT` | 컨테이너 시작 시 무엇을 실행하는가? | 기본 실행 명령 지정 |

### FROM — 어디서 시작할 것인가

누군가 만들어둔 베이스 이미지(자바 런타임, ubuntu, nginx 등)에서 시작하는 게 일반적이다.

- **멀티 스테이지 빌드**: FROM은 한 번만 쓰는 게 아니다. 빌드용/실행용 이미지를 분리 — 빌드 이미지는 `FROM JDK`, 실행 이미지는 `FROM JRE`.

### WORKDIR — 작업 폴더 지정

```docker
WORKDIR /app
COPY app.jar app.jar   // 로컬 app.jar → 이미지 내부 /app/app.jar 로 복사
```

### COPY — 프로젝트 파일을 이미지 안으로

```docker
COPY /build/libs/my-app.jar app.jar
```

### RUN — 이미지를 만드는 중에 실행

```docker
RUN chmod +x gradlew
RUN ./gradlew bootJar --no-daemon
```

| 구분 | 실행 시점 |
| --- | --- |
| `RUN` | `docker build` 중 (이미지를 만들 때) |
| `CMD` / `ENTRYPOINT` | `docker run`으로 Container 시작 시 |

### EXPOSE — 사용 포트 문서화

```docker
EXPOSE 8080
```

`EXPOSE`는 호스트의 포트를 실제로 열어주지 않는다. 실제 포트 매핑은 실행 시 `docker run -p 8080:80 my-spring`.

### CMD + ENTRYPOINT

```docker
ENTRYPOINT ["java", "-jar", "app.jar"]   // 컨테이너가 반드시 실행할 주 프로그램(고정)
CMD ["--spring.profiles.active=prod"]    // 기본 인자/옵션(실행 시 변경 가능)
// 결과: java -jar app.jar --spring.profiles.active=prod
```

| 명령어 | 역할 |
| --- | --- |
| `ENTRYPOINT` | 컨테이너가 항상 실행할 주 프로그램 명령어(고정). `--entrypoint` 옵션으로만 변경 |
| `CMD` | 기본 명령/기본 옵션. `docker run` 시 인자로 쉽게 변경 가능 |

**구분 기준: "무엇을 고정하고, 무엇을 실행 시 바꾸게 할 것인가"**

- 하나만 쓰는 경우: 실행 명령이 단순할 때 (`ENTRYPOINT`만 또는 `CMD`만)
- 병행하는 경우(실무 케이스): 실행 프로그램은 고정(ENTRYPOINT), 옵션만 쉽게 변경(CMD)
    
    ```
    docker run my-app                  → java -jar app.jar --spring.profile.active=proddocker run my-app ...dev로 변경      → java -jar app.jar --spring.profile.active=dev
    ```
    
- `CMD`만 쓰는 경우: ENTRYPOINT를 굳이 고정하지 않고, 완전히 다른 명령(`java -jar` ↔ `javac`)을 실행하고 싶을 때


## 🔥 Dockerfile과 이미지 레이어

> 도커 이미지는 하나의 거대한 파일이 아니다. 베이스 이미지에서 시작해 **이전 상태에서 바뀐 파일만 한 겹씩 쌓아** 만든 실행 환경이다.
> 

도커는 이전 빌드에서 변경되지 않은 단계는 그대로 **재사용(캐싱)** 한다. (자바 레이어 / 라이브러리 레이어 / jar 레이어 / 환경변수 레이어처럼 단계가 나뉜다.) 투명 필름을 겹쳐 보면 완성된 코드가 보이는 것과 같다.

그래서 **명령어 순서가 중요하다.**

```docker
# ❌ 소스 한 줄만 바꿔도 COPY . . 가 바뀌어 npm install 다시 실행
COPY . .
RUN npm install

# ✅ package.json 먼저 복사 → 소스만 바뀌면 install 레이어 캐시 재사용
COPY package.json ./
RUN npm install
COPY index.js ./
```

```

build
node_modules
*.log         # 과거 로그
.env / .env.* # 비밀번호·API Key 노출 위험
```

- 무엇을 만드나? Docker Image

# 7. Docker Image

## 핵심 개념

> Docker Image는 애플리케이션 실행에 필요한 파일을 여러 개의 읽기 전용 레이어로 쌓아 만든 실행 환경의 스냅샷이다.
> 

Dockerfile이 "이미지를 어떻게 만들지"에 대한 설계라면, 도커가 그 내용(COPY, RUN, CMD…)을 읽고 빌드해 Layer가 쌓인 하나의 이미지를 만들어낸다. 컨테이너는 그 이미지를 기반으로 실행된다.

## 레이어

> Layer는 전체 파일시스템 복사본이 아니라, 이전 레이어와 비교해 추가·수정·삭제된 파일의 차이(diff)를 저장한 단위다.
> 

전체 파일을 매번 새로 복사하지 않고 바뀐 파일만 새 레이어에 기록 → 캐싱에 유리.

**레이어는 폴더가 아니다.** 레이어마다 `/app`, `/etc`, `/usr`가 통째로 있는 게 아니라, 이전 상태에서 새로 추가·변경된 파일만 기록된다.

```
Layer 1: /usr/bin/sh, /etc/passwd, /bin/ls
Layer 2: /usr/bin/java, /usr/lib/jvm/...
Layer 3: /app/my-api.jar
```

## OverlayFS

> OverlayFS는 여러 개의 읽기 전용 Image Layer를 겹쳐, 애플리케이션이 하나의 완성된 파일시스템처럼 사용할 수 있게 하는 Linux 파일시스템 기능이다.
> 

여러 레이어로 나뉘어 있어도 컨테이너 안에서는 하나의 완성된 트리로 보인다.

```
/
├── app/app.jar
├── bin
├── etc
├── usr/bin/java
└── var
```

## 이미지 실습

```bash
docker pull nginx:latest          # 이미지 다운로드
docker images   /  docker image ls  # 받은 이미지 확인

docker run -d --name my-nginx -p 8080:80 nginx   # 컨테이너 실행
docker ps                                         # 확인

docker exec -it my-nginx sh       # 컨테이너 내부 진입
# 경량화로 내부 명령어가 없을 수 있음 → apt-get update && apt-get install nano
# /usr/share/nginx/html/index.html 수정  (※ 8주차 과제에서 별도 제출)
```

# 8. Container

## 핵심 개념

> Docker Container는 Docker Image를 바탕으로 실제 애플리케이션 프로세스를 실행한 격리된 실행 단위다. (호스트 OS 커널 위에서 실행되는 격리된 프로세스)
> 

## 컨테이너가 필요한 이유

이미지는 공통 "실행 환경"을 제공하고, 컨테이너는 실제 환경에 맞는 이름·포트·환경 변수를 적용해 실행한다. 같은 스프링 앱 이미지라도:

| 환경 | DB 주소 | 포트 |
| --- | --- | --- |
| 개발 | 개발 DB | 8080 |
| 테스트 | 테스트 DB | 8081 |
| 운영 | 운영 DB | 80 / 443 |

## 컨테이너 실행 과정

`docker run`은 (1) 새 컨테이너 생성 + (2) 실행을 합친 것 (`docker create` + `docker start`).

```
docker run 실행 시
1. registry(이미지 저장소)에서 해당 이미지 확인
2. 없으면 외부 저장소에서 pull 시도
3. 컨테이너 생성
4. 실행 변수 적용 (--name, -p 등)
5. 메인 프로세스 실행, -d 로 실행 상태 유지
6. 메인 프로세스 종료 시 컨테이너 중지
```

## 컨테이너 생명주기

`Created → Running → Exited → Removed`

- **컨테이너는 메인 프로세스가 끝나면 중지된다.** (`docker run hello-world` 후 `docker ps`로 확인) 서버 프로세스는 `d`로 백그라운드 유지.
- 도커는 종료돼도 삭제되지 않는다. 컨테이너·볼륨·이미지가 남음. EC2에서 배포를 100번 하면 이미지(300MB~)가 쌓여 30GB가 될 수도 있다.

## 중지 ≠ 삭제

| 명령어 | 결과 |
| --- | --- |
| `docker stop` | 컨테이너를 멈춘다 |
| `docker start` | 멈춘 기존 컨테이너를 다시 실행 |
| `docker rm` | 컨테이너 자체를 삭제 |
| `docker run` | 새 컨테이너 생성 + 실행 |
| `docker rmi` | 이미지를 삭제 |

## Image vs Container

| 구분 | Image | Container |
| --- | --- | --- |
| 역할 | 실행 환경을 담은 템플릿 | Image를 실제 실행한 단위 |
| 상태 | 읽기 전용 | 실행·중지·삭제 가능 |
| 생성 방법 | `docker build`, `docker pull` | `docker run`, `docker create` |
| 변경 | 직접 수정 안 함 | 실행 중 파일 생성·수정 가능 |
| 예시 | `nginx:1.27` | `nginx-web` |
| 개수 관계 | 하나의 Image로 | 여러 Container 생성 가능 |

## 명령어 모음

| 목적 | 명령어 |
| --- | --- |
| 실행 중 컨테이너 확인 | `docker ps` |
| 전체(종료 포함) 확인 | `docker ps -a` |
| 새 컨테이너 생성·실행 | `docker run ...` |
| 기존 컨테이너 시작 | `docker start <이름>` |
| 컨테이너 중지 | `docker stop <이름>` |
| 컨테이너 재시작 | `docker restart <이름>` |
| 로그 확인 | `docker logs <이름>` |
| 실시간 로그 | `docker logs -f <이름>` |
| 내부 명령 실행 | `docker exec -it <이름> sh` |
| 자원 사용량 | `docker stats` |
| 컨테이너 삭제 | `docker rm <이름>` |

> 우분투 계열은 `sh`는 기본 제공이지만 `bash`는 없을 수 있다. 컨테이너는 기본적으로 경량화를 지향한다.
> 

## 실무적으로 컨테이너 다루기

1. **이름을 붙여라** — 컨테이너 수가 많으면 ID(`fdf3059133f5`)로만 부르게 됨. `-name=was-spring`을 줘야 `docker stop was-spring`처럼 다룰 수 있다.
2. **`docker run`을 반복하지 마라** — run은 기존 컨테이너를 찾아 실행하는 게 아니라 **매번 새 컨테이너를 만든다.** 항상 `docker ps -a`로 확인하고, 안전하게는 `create & start`(= run)를 분리해서 사용.
3. **운영 컨테이너는 직접 수정하지 마라** — `docker exec`로 들어가 파일/설정을 고치는 건 Thin(R/W) layer를 수정하는 것. 변경이 필요하면 이미지를 새로 빌드해 컨테이너를 다시 만든다.
4. **RUNNING ≠ 정상** — `docker ps`에서 RUNNING이어도 프로세스가 실행 중일 뿐 서비스 정상을 보장하진 않는다. `docker ps -a` + `docker logs -f` + `docker stats`로 확인.
5. **재시작 정책 고려** — 서버는 언제든 재부팅될 수 있으므로 컨테이너의 행동을 미리 지정.
(참고: docs.docker.com/engine/containers/start-containers-automatically)
    
    ```bash
    docker run -d --restart unless-stopped --name api-server my-api:1.0
    ```

# 9. 전체 정리

| 개념 | 핵심 |
| --- | --- |
| Docker | "내 컴퓨터에선 되는데 여기선 왜 안 돼?"라는 환경 차이를 좁히려고 등장. 실행에 필요한 모든 걸 묶어 "이미지"로 전달 |
| Dockerfile | 애플리케이션 실행 환경을 만드는 코드 설명서 |
| Image | 애플리케이션 + 실행 환경이 담긴 읽기 전용 배포 패키지 |
| Container | 이미지를 실제 실행한 격리된 프로세스 |
| Namespace | 프로세스·네트워크·파일시스템을 분리된 것처럼 보이게 하는 커널 기능 (무엇이 보이는가) |
| cgroups | 컨테이너별 CPU·RAM 등 자원 사용량을 제한·측정하는 커널 기능 (얼마나 쓰는가) |
| Kernel | 컨테이너 안엔 없음. 호스트 OS 커널을 공유 → VM보다 가벼움 |
| 도커는 기술? | Container라는 기술을 쓰기 쉽게 만든 "서비스"의 이름 |
