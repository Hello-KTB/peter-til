# 1. ElastiCache

> AWS가 관리해주는 인메모리 캐시 서비스로, 자주 조회하는 데이터를 메모리에 저장해 응답 속도를 높이고 DB 부하를 줄인다.
> 

데이터베이스만으로 서비스하면 인기글 조회처럼 반복적인 요청이 몰릴 때 IOPS 한계에 부딪히고 MySQL 자체가 병목 구간이 된다. ElastiCache는 원본 데이터를 매번 다시 조회하지 않도록 자주 사용하는 데이터를 빠르게 꺼낼 수 있게 임시 저장하는 캐시 계층을 제공한다.

## 캐시가 메모리에 저장되는 이유

캐시는 자주 접근되고 빠른 속도가 필요하기 때문에 디스크가 아닌 RAM에 저장한다. 디스크 기반의 RDS와 메모리 기반의 ElastiCache는 역할이 다르다.

| 구분 | RDS | ElastiCache |
| --- | --- | --- |
| 핵심 역할 | 영구 데이터 저장 | 빠른 반복 조회 |
| 저장 위치 | 디스크 중심 | 메모리 중심 |
| 데이터 성격 | 원본 데이터 | 임시 복사본 또는 빠른 상태 데이터 |
| 정합성 | 강하게 관리 | TTL·무효화 전략 필요 |
| 대표 사례 | 회원, 주문, 결제, 게시글 | 인기 목록, 세션, 랭킹, API 제한 |

## 캐시 사용 패턴 — Cache-Aside

애플리케이션이 먼저 캐시를 조회하고, 캐시에 없을 때만 DB를 조회한 뒤 캐시에 저장하는 방식이다.

- **Cache Hit**: 캐시에 데이터가 있는 경우 바로 응답
- **Cache Miss**: 캐시에 데이터가 없으면 RDS에서 조회 후 응답하면서 캐시에 저장

## TTL (Time To Live)

캐시 데이터가 자동으로 만료되기까지의 시간이다.

```
Key = post::1::likeCount
Value = 10
TTL = 300s
```

TTL이 필요한 이유는 두 가지다. 첫째, 캐시는 메모리라는 제한된 자원을 사용한다. 둘째, 캐시 데이터는 정합성을 보장하지 않으므로 오래 남아 있으면 최신 데이터와 달라질 수 있다.

| TTL 설정 | 결과 |
| --- | --- |
| 너무 짧은 경우 (예: 10s) | 캐시 미스가 많아져 RDBMS 조회가 빈번해지고 캐시 효과가 줄어듦 |
| 너무 긴 경우 (예: 3600s) | 오래된 데이터가 노출되어 사용자 경험이 깨질 수 있음 |

```
자주 바뀌는 데이터       → 짧은 TTL 검토
거의 바뀌지 않는 데이터  → 긴 TTL 검토
즉시 최신 값이 필요한 데이터 → TTL만 믿지 말고 캐시 삭제 또는 갱신 필요
```

## 캐시 무효화 전략

> 원본 데이터가 변경되었을 때, 기존 캐시 값을 삭제하거나 수정하는 작업
> 

## 주요 엔진

| 엔진 | 특징 | 대표 활용 |
| --- | --- | --- |
| Valkey | Redis OSS 호환 계열의 인메모리 저장소 | 캐시, 세션, 랭킹, Pub/Sub |
| Redis OSS | 다양한 자료구조와 기능 제공 | 캐시, 세션, 분산 락, 실시간 기능 |
| Memcached | 단순하고 가벼운 분산 키-값 캐시 | 단순 조회 캐시 |

Redis·Valkey는 String, Hash, List, Set, Sorted Set, Stream, Pub/Sub 같은 다양한 자료구조를 지원하기 때문에 세션 스토어, 인기 검색어, API Limiter, 분산 락, 실시간 채팅 등 단순 K-V로 해결되지 않는 목적에도 활용한다. Memcached는 단순 캐시 목적에 적합하다.

## 고가용성 구성

| 구성 | 설명 |
| --- | --- |
| Replica | 고가용성과 읽기 확장을 위해 복제본 구성 |
| Multi AZ | 가용 영역 장애 시 Replica 승격으로 가용성 향상 |
| Shard | 키를 분산 저장하여 저장 용량과 쓰기 처리량 확장 |

## 캐시 사용 시 주의해야 할 문제

**1. 캐시는 원본 데이터가 아니다**

캐시는 인메모리라 Redis가 꺼지거나 TTL이 끝나면 데이터가 사라진다. 캐시에만 의존하는 구조를 만들면 안 되고, Cache Miss 시 반드시 영구 저장소를 조회하는 fallback 로직을 추가해야 한다.

**2. 캐시 스탬피드**

동일한 TTL을 가진 키가 동시에 대량으로 만료되면 그 순간 모든 요청이 RDBMS로 폭증하면서 응답 지연과 서비스 불안정이 발생한다. 실무에서는 TTL에 임의 값을 더해 만료 시점을 분산한다.

```
기본 TTL: 300초
실제 TTL: 300초 + 0~30초 랜덤 값
```

**3. 메모리 부족 현상**

캐시 메모리가 가득 차면 새로운 캐시가 저장되지 않는다. Eviction 정책을 설정해 메모리 부족 시 오래되거나 덜 사용된 키를 자동으로 제거하도록 구성해야 한다.

## ElastiCache 정리

| 항목 | 설명 |
| --- | --- |
| ElastiCache | AWS 관리형 인메모리 캐시 서비스 |
| 주요 엔진 | Valkey, Redis OSS, Memcached |
| 핵심 목적 | 반복 조회를 빠르게 처리하고 RDS 부하 감소 |
| 저장 위치 | 메모리(RAM) |
| 대표 패턴 | Cache-Aside |
| Cache Hit | 캐시에 데이터가 있어 빠르게 응답 |
| Cache Miss | DB에서 조회한 후 캐시에 저장 |
| TTL | 캐시 데이터 자동 만료 시간 |
| 캐시 무효화 | 원본 변경 시 기존 캐시 삭제 또는 갱신 |
| 주요 활용 | 게시글 캐시, 세션, 인증번호, 랭킹, Rate Limiting |
| Multi-AZ | 캐시 노드 장애 시 Replica 승격으로 가용성 향상 |
| Replica | 고가용성과 읽기 확장 |
| Shard | 저장 용량·쓰기 처리량 확장 |

# 2. ELB (Elastic Load Balancer)

> ELB는 사용자의 요청을 여러 서버에 나누어 전달하고, 장애 난 서버는 자동으로 제외하여 서비스가 느려지거나 멈추는 일을 줄여주는 AWS 관리형 로드 밸런서 서비스다.
> 

서버 한 대로 운영하면 사용자가 몰릴 때 응답이 느려지고, 서버 장애 시 서비스 전체가 중단된다. 서버를 여러 대로 늘리더라도 요청 분산 없이는 특정 서버에만 트래픽이 몰리거나 장애 서버로 요청이 계속 전달되는 문제가 생긴다.

## ELB가 해결하는 방식

사용자는 ELB로 접속을 요청하고, ELB는 연결된 리소스 중 건강하고 트래픽이 적은 서버에 요청을 분산해 전달한다.

| ELB의 역할 | 설명 |
| --- | --- |
| 요청 분산 | 여러 서버에 요청을 나누어 전달 |
| 장애 서버 제외 | 응답하지 않는 서버에는 새 요청을 보내지 않음 |
| 단일 진입점 제공 | 사용자는 하나의 도메인 또는 주소로 접속 |
| 서버 확장 지원 | 서버가 늘어나도 ELB가 새 서버에 요청 분산 |
| HTTPS 처리 | 인증서를 연결해 HTTPS 요청을 받을 수 있음 |
| 요청 분기 | URL 경로·도메인 등에 따라 다른 서버 그룹으로 전달 가능 |

## 헬스 체크

ELB는 아래 경로를 주기적으로 요청해 서버 상태를 확인하고, 정상 응답이 오는 서버에만 트래픽을 전달한다.

```
GET /actuator/health

정상 응답:
{
  "status": "UP"
}
```

## ELB 구조

**1. Load Balancer** — 사용자가 접속하는 입구. Route53으로 도메인을 LB에 연결해 사용한다.

**2. Listener** — ELB가 특정 포트에서 요청을 기다리는 입구다.

| Listener | 의미 |
| --- | --- |
| HTTP : 80 | 일반 웹 요청을 받는 입구 |
| HTTPS : 443 | 암호화된 웹 요청을 받는 입구 |

사용자는 HTTPS로 안전하게 전달하고, ALB는 서버 내부에 HTTP로 요청을 전달한다.

**3. Rule** — 요청을 어디로 보낼지 정하는 규칙이다.

| 요청 조건 | 전달 대상 |
| --- | --- |
| `/api/*` | API 서버 Target Group |
| `/admin/*` | 관리자 서버 Target Group |
| `/socket/*` | WebSocket 서버 Target Group |
| 그 외 요청 | 프론트엔드 서버 Target Group |

**4. Target Group** — 실제 요청을 처리할 서버들의 묶음이다.

| 항목 | 예시 |
| --- | --- |
| 대상 유형 | EC2 인스턴스 |
| 프로토콜 | HTTP |
| 포트 | 8080 |
| Health Check 경로 | `/actuator/health` |
| 성공 코드 | 200 |
| 등록 대상 | EC2 서버 1, 2, 3 |

## ELB 종류

| 종류 | 주로 다루는 트래픽 | 대표 사용 사례 |
| --- | --- | --- |
| ALB | HTTP, HTTPS | 웹 서비스, Spring Boot API, 마이크로서비스 |
| NLB | TCP, TLS, UDP, QUIC | 게임 서버, TCP 서비스, 초저지연 서비스 |
| GWLB | 네트워크 보안 장비 트래픽 | 방화벽, IDS/IPS, 보안 어플라이언스 |
| CLB | 이전 세대 로드 밸런서 | 기존 레거시 시스템 |

웹 서비스·REST API에는 ALB를, TCP·UDP처럼 HTTP가 아닌 경우에는 NLB를 검토한다. ALB는 L7 응용 계층에서 URL 경로, 도메인, 헤더 조건을 기준으로 요청을 분기할 수 있다.

## 보안 그룹 구성

ELB를 구성할 때는 애플리케이션 서버를 인터넷에 직접 노출하지 않는다.

**ALB 보안 그룹**

| 방향 | 포트 | 허용 대상 |
| --- | --- | --- |
| Inbound | 80 | 인터넷 사용자 |
| Inbound | 443 | 인터넷 사용자 |
| Outbound | 8080 | 애플리케이션 EC2 보안 그룹 |

**애플리케이션 보안 그룹**

| 방향 | 포트 | 허용 대상 |
| --- | --- | --- |
| Inbound | 8080 | ALB 보안 그룹 |
| Inbound | 22 | 관리자 고정 IP 또는 Bastion |
| Outbound | 3306 | RDS 보안 그룹 |

애플리케이션 보안 그룹의 8080 포트를 `0.0.0.0/0`으로 열어서는 안 된다.

## HTTPS 처리

실무에서는 HTTPS SSL 처리를 애플리케이션 서버가 아니라 ALB에서 담당한다. ACM을 통해 인증서를 발급받아 ALB에 연결한다.

| 장점 | 설명 |
| --- | --- |
| 인증서 중앙 관리 | EC2마다 인증서를 설치할 필요 없음 |
| 서버 확장 편리 | 서버가 늘어도 인증서를 복제할 필요 없음 |
| 자동 갱신 활용 | ACM 인증서와 연동 가능 |
| 애플리케이션 단순화 | Spring Boot의 TLS 설정 부담 감소 |

## ELB 정리

| 개념 | 핵심 |
| --- | --- |
| ELB | 여러 서버에 요청을 분산하는 AWS 서비스 |
| ALB | HTTP/HTTPS 웹 서비스에 주로 사용하는 로드 밸런서 |
| Listener | ELB가 요청을 받는 포트와 프로토콜 |
| Rule | 요청을 어디로 보낼지 결정하는 규칙 |
| Target Group | 실제 요청을 처리하는 서버 묶음 |
| Health Check | 정상 서버에게만 요청을 보내기 위한 상태 확인 |

# 3. CloudFront

> 전 세계에 분산된 서버 네트워크(CDN)를 통해 사용자에게 콘텐츠를 빠르고 안전하게 전달하는 AWS CDN 서비스
> 

정적 웹 페이지, 이미지, 영상은 S3에, 백엔드 API는 ALB → EC2에서 제공하는 구조는 초기에는 잘 동작한다. 그러나 사용자가 많아지거나 서버와 거리가 멀어지면 네트워크 왕복 시간이 길어지고, 동일한 파일에 대한 요청이 원본 서버에 집중되면서 부하와 비용이 증가한다.

## CDN과 CloudFront

> CDN (Content Delivery Network): 여러 지역에 콘텐츠 전달 서버를 분산 배치해 사용자와 가까운 서버에서 콘텐츠를 내려받도록 하는 방식
> 

CloudFront는 AWS에서 제공하는 CDN 서비스다. 사용자와 원본 서버 사이에 캐시 계층(엣지 로케이션)을 두어 원본까지 요청하지 않고 근처 서버에서 데이터를 받아올 수 있게 한다. 엣지 로케이션은 자주 요청되는 콘텐츠의 복사본을 잠시 보관하는 AWS의 분산 네트워크 거점이다.

## CloudFront 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| Distribution | CloudFront 배포 단위. 어떤 원본과 캐시 정책을 사용할지 정의 |
| Viewer | CloudFront에 요청하는 사용자 또는 브라우저 |
| Edge Location | 사용자 가까이에서 캐시된 콘텐츠를 전달하는 위치 |
| Origin | 원본 콘텐츠가 실제 저장된 위치 |
| Cache Behavior | 어떤 경로를 어떤 원본으로 보내고 어떻게 캐시할지 정하는 규칙 |
| Cache Policy | 캐시 키와 TTL 등 캐시 동작을 결정하는 정책 |
| OAC | S3 원본에 CloudFront만 접근하도록 제한하는 기능 |

## Cache Behavior

URL 경로에 따라 어떤 원본으로 요청을 보내고 캐시를 어떻게 적용할지 정하는 규칙이다.

| 요청 경로 | Origin | 캐시 전략 |
| --- | --- | --- |
| `/images/*` | S3 | 길게 캐시 |
| `/assets/*` | S3 | 길게 캐시 |
| `/api/*` | ALB | 짧게 캐시 또는 캐시 비활성화 |
| `/` | S3 | HTML 특성에 맞게 짧게 캐시 |

HTML 파일은 변경 주기가 뚜렷하기 때문에 배포 스크립트에 캐시 무효화 코드를 함께 넣는다.

## 콘텐츠별 캐시 전략

| 콘텐츠 종류 | 예시 | 권장 캐시 전략 |
| --- | --- | --- |
| 변경이 거의 없는 정적 파일 | 로고, 폰트, 라이브러리 파일 | 길게 캐시 |
| 빌드 결과물 | `app.8f3a2.js`, `main.2c4d.css` | 매우 길게 캐시 |
| 일반 이미지 | 프로필 이미지, 게시글 이미지 | 변경 빈도에 맞춰 캐시 |
| HTML | `index.html` | 짧게 캐시 |
| 로그인·결제·개인 정보 API | `/api/me`, `/api/orders` | 기본적으로 캐시하지 않음 |
| 공개 조회 API | 상품 목록, 공지 목록 | 조건부로 짧게 캐시 가능 |

## CloudFront vs ELB

둘 다 사용자 요청 앞단에 위치하지만 해결하려는 문제가 다르다.

| 구분 | CloudFront | ALB |
| --- | --- | --- |
| 핵심 목적 | 콘텐츠 캐싱과 글로벌 전송 가속 | 여러 서버에 요청 분산 |
| 주요 위치 | 사용자와 원본 사이의 글로벌 엣지 | AWS 리전 내부의 애플리케이션 앞단 |
| 대표 대상 | 이미지, CSS, JS, 영상, 정적 파일 | EC2, ECS, 컨테이너, API 서버 |
| 캐시 | 핵심 기능 | 핵심 기능 아님 |
| Health Check | Origin 장애 대응 기능은 가능 | Target 서버 상태 확인이 핵심 |
| 대표 구조 | CloudFront → S3 | ALB → EC2/ECS |
| 함께 사용 | CloudFront → ALB → EC2/ECS | CloudFront의 Origin으로 사용 가능 |

## 실무 구조 예시

**1. 정적 웹사이트**

S3에 Vite, Vue, React 등 프론트엔드 빌드 파일을 저장하고, CloudFront로 콘텐츠를 캐싱한다. Route53에서 CloudFront 배포에 도메인을 연결한다.

**2. 이미지 업로드 서비스**

사용자가 이미지를 업로드하면 백엔드가 S3에 저장하고, DB에는 S3 원본 주소 대신 CloudFront URL 또는 객체 키를 저장한다. 프론트엔드는 CloudFront 주소로 이미지를 요청하며 CloudFront가 캐싱을 처리한다.

## CloudFront 정리

| 개념 | 핵심 |
| --- | --- |
| CloudFront | AWS의 CDN 서비스 |
| CDN | 사용자 가까운 위치에서 콘텐츠를 전달하는 분산 네트워크 |
| Origin | 콘텐츠 원본 위치 |
| Edge Location | 콘텐츠를 캐시하고 사용자에게 전달하는 위치 |
| Cache Behavior | URL 경로별 Origin·캐시 규칙 |

CloudFront는 파일을 저장하는 서비스가 아니라, 원본 콘텐츠를 사용자 가까이에서 빠르게 전달하고 원본 서버의 반복 요청을 줄이기 위해 사용한다.
