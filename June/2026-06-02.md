## 1. 값 타입과 임베디드 매핑

JPA에는 세 가지 값 타입이 있다

### 기본 값 타입

> 단일 값(예: 이름, 나이, 금액)으로만 의미를 가지는 데이터를 엔티티의 필드로 직접 정의해 테이블 컬럼에 저장하는 방식
> 
- 자바 기본형(`int`, `long`, `double`), 래퍼 클래스(`Integer`, `Long` 등), 문자열 타입(`String`)
- ID 값은 보통 래퍼 클래스를 쓰는 것이 일반적임
    - 객체가 먼저 생성되어야 DB에 올라감
    - 기본형 `long`과 래퍼 클래스 `Long`의 차이는 `null` 허용 여부다
    - 기본형 `long`은 `null`이 불가능하기 때문에 에러가 발생함

### 임베디드 값 타입

> 두 개 이상의 값을 하나의 객체로 묶어 엔티티에 포함시켜 사용하는, 재사용 가능한 값 타입
> 
- 테이블 구조에는 변화를 주지 않음
- 엔티티 구조만 더 객체 지향적으로 보이게 함
- 코드 재사용성을 높임

### 컬렉션 값 타입

> 엔티티에 직접 연관되지 않는 여러 개의 값을 리스트나 세트 형태로 저장하기 위한 타입
> 
- 객체 지향적으로 표현하기 위해 사용함
- 여러 개의 단순 값을 별도 엔티티 없이 테이블에 분리 저장하기 위해 사용함

## 2. JPQL (Java Persistence Query Language)

> 엔티티 객체를 대상으로 데이터를 조회하거나 조작할 수 있도록 제공되는 객체 지향 쿼리 언어
> 

JPA는 객체 중심으로 설계되어 SQL처럼 자유롭게 테이블과 컬럼을 다루기 어려움

- 단일 엔티티 관리는 가능함
- 복잡한 관계식, 조인, 조건 등은 처리하기 어려움

이 문제를 해결하는 두 가지 접근:

**JPA를 통한 데이터 핸들링**

- 엔티티와 연관 엔티티를 순차적으로 조회함
- 단순한 작업도 여러 과정을 거쳐야 함
- 메모리 부담이 크고, 그렇게까지 할 필요가 없음

**JPQL 사용**

- DB 레벨에서 데이터를 처리하므로 성능상 유리함

### 특징

- SQL이 아닌 엔티티 중심의 쿼리 언어다 (DB 테이블이 아닌 엔티티 기준으로 쿼리 진행)
- 엔티티 모델을 기준으로, JPA 구현체가 사용하는 DB에 맞게 SQL문을 작성한다(데이터베이스 문법에 종속되지 않음)

### 사용법

- 엔티티를 기반으로 쿼리를 작성
- 엔티티에 별칭이 필요

엔티티 매니저를 통해 쿼리를 실행함

| 메서드 | 설명 |
| --- | --- |
| `createQuery` | 쿼리 생성 |
| `getResultList` | 여러 결과 가져오기 |
| `getSingleResult` | 결과 하나만 가져오기 |
| `executeUpdate` | 수정, 삭제 실행 |

**파라미터 바인딩** — 쿼리 내에 변수를 넣기 위한 방식

- 위치 기반
- 이름 기반

**경로 표현식**

- 묵시적 조인
    - `join` 키워드 없이 경로만 표현해서 조인하는 방식
    - 항상 내부 조인
- 명시적 조인
    - `join` 키워드로 조인을 직접 선언
    - 조인 구조가 명확하고 성능 최적화에 용이
    - JPQL에서 조인을 선택한다면 명시적 조인을 권장

**Projection** — 엔티티 전체가 아닌 필요한 필드를 선택해서 조회하는 방식

- 엔티티 타입 : `select` 절에 엔티티 타입을 지정 → 엔티티 전체 컬럼을 가져옴
- 임베디드 타입 : `select` 절에 엔티티에 포함된 임베디드 타입을 지정
- 스칼라 타입 : `select` 절에 숫자, 문자열, 날짜 같은 단순 값을 지정해 특정 컬럼만 조회
- DTO
    - `select`에서 필요한 필드를 지정
    - 필드 수와 타입이 정확히 일치하는 DTO 생성자를 이용
    - 조회 시점에 바로 DTO로 매핑

**Paging** — 대량의 데이터를 한 번에 가져오지 않고, 일정 단위(페이지)로 나누어 조회하는 처리 방식

- `setFirstResult()` — 조회 시작 위치 지정
- `setMaxResults()` — 가져올 데이터 개수 지정
- DB에 종속적인 페이징 문법(`LIMIT`, `OFFSET` 등)을 JPA가 각 DB에 맞게 변환해줌

### N+1 문제

연관 엔티티를 조회할 때, 처음 1번의 쿼리로 N개의 결과를 가져온 뒤, 각 결과의 연관 엔티티를 가져오기 위해 추가로 N번의 쿼리가 더 실행되는 문제

- 원인
    - 지연 로딩(`LAZY`) 설정 시, 연관 엔티티에 실제로 접근하는 순간마다 쿼리가 추가 발생
    - 즉시 로딩(`EAGER`) 설정 시에도, 조회된 각 엔티티마다 연관 엔티티 조회 쿼리가 별도로 나가 동일하게 발생
    - 결과적으로 쿼리 1번 + 추가 N번 = 총 N+1번의 쿼리가 실행되어 성능 저하

해결 방법:

- **Fetch Join** — JPQL에서 연관 엔티티를 한 번에 가져오기
    - 조인을 통해 연관 엔티티까지 한 번의 쿼리로 조회하여 N+1 문제 해결
    - 필요한 데이터를 미리 로딩
    - 한계
        - 컬렉션 fetch-join 시 페이징이 불가능 (메모리에서 페이징하게 되어 위험)
        - 필요 이상의 데이터가 들어올 수 있음
        - 둘 이상의 컬렉션을 동시에 페치 조인할 수 없음

## 3. Spring Data JPA

JPQL에서 사용하는 쿼리가 반복되기 때문에 이를 해결하기 위해 탄생했다

반복적인 CRUD 코드 없이 인터페이스만으로 리포지토리를 구현하여 개발 생산성과 유지 보수 효율을 높임

### 특징

- `JpaRepository`를 상속하면 기본 CRUD를 자동 제공
- 메서드 이름만으로 쿼리 생성이 가능
- 반복적인 CRUD가 자동 생성
- 내부적으로 순수 JPA를 사용

### 기본 사용법

**리포지토리**

- 새로운 리포지토리를 `interface`로 생성
- `JpaRepository<엔티티, ID>`로 상속
- 기본 CRUD를 제공받음

**쿼리 메서드** — 리포지토리 인터페이스의 메서드 이름을 기반으로 JPQL 쿼리를 자동 생성하는 기능

- 리포지토리 내 메서드 이름으로 JPQL 자동 생성
- 코드 가독성, 생산성 향상
- 메서드 이름만으로 실행될 쿼리 이해 가능

**`@Query`**

- 사용 이유 : 메서드 이름만으로 표현하기 어려운 복잡한 조건, 조인, 집계 처리를 위해
- 쿼리를 직접 작성해서 성능 개선 가능

**`@EntityGraph`** — 특정 엔티티 조회 시 함께 로딩할 연관 엔티티를 지정

- 사용 이유 : 반복 쿼리가 발생하는 N+1 문제 방지, 연관 데이터를 한 번에 조회하기 위해

**`Pageable`** — Spring Data JPA에서 페이징과 정렬을 손쉽게 처리할 수 있도록 제공하는 객체

**사용자 정의 리포지토리** — 기본 제공 기능으로 구현할 수 없는 복잡한 쿼리나 로직을 직접 구현하기 위해 커스텀 메서드를 추가한 리포지토리

- 자동화로 만들기 어려운 복잡한 로직을 구현할 때 사용
- 사용 방법
    1. 커스텀 인터페이스 만들기 (필요한 기능 선언, 필요한 메서드 작성)
    2. 구현 클래스 작성
    3. 레포지토리에 상속 → Spring Data JPA를 사용하면서 커스텀 기능도 함께 사용 가능

## 4. QueryDSL

> 자바 코드로 JPQL이나 SQL을 직접 작성하지 않고, 메서드 호출과 객체 지향 문법을 이용해 쿼리를 표현할 수 있도록 해주는 객체 지향 쿼리 라이브러리
> 

### 탄생 배경

**JPQL 사용 시**

- 문자열 내에 JPQL 쿼리를 작성
- 빌드 시 에러를 발견하기 어려움
- 오타 시 런타임 에러
- 엔티티 변경 시 에러 발생

**동적 쿼리에서 JPQL 사용 시**

- 조건에 따라 문자열을 추가
- 문자열을 이어 붙임
- 오타 시 런타임 에러
- IDE에서 자동 완성이 어려움

**JPQL의 직접 사용 또는 `@Query`에서 사용할 때의 문제**

- 문자열 기반 → IDE 자동 완성 지원 안 함
- 조건이 많아지면 코드 가독성 저하
- 동적 쿼리 사용 불가 또는 어려움

### JPQL vs QueryDSL

| JPQL | QueryDSL |
| --- | --- |
| 문자열로 쿼리 작성 | 자바 코드로 쿼리 작성 (타입 안전) |
| 수동 바인딩 | 메서드 체인으로 바인딩 (`u.name.eq`) |
| 동적 문자열 분기 복잡 | 동적 조건을 객체 조립하듯이 구성 |
| 필드명 변경 시 런타임 오류 | Q클래스 기반으로 컴파일 타임에 검증 |
| 조건이 많아지면 읽기 어려움 | 도메인 필드가 그대로 드러나 직관적 |
| IDE에서 에러 파악 어려움 | IDE 자동 완성 등 활용 가능 |
| 동일 조건이면 동일 성능 | 성능 동일 (둘 다 JPQL → SQL로 전환) |

### QueryDSL로 얻는 이점

- 타입 안전한 쿼리 가능
- 동적 쿼리 최적화
- 문법 오류 발견이 쉬움
- 복잡한 조건식 표현이 쉬움
- 코드 재사용성이 높음

### Q클래스

빌드 시 QueryDSL의 메타 모델 클래스가 엔티티들을 Q클래스로 생성함

### 기본 사용법

- `JPAQueryFactory`와 함께 사용함

### 기본 문법

**SELECT**

- `select(entity)` — SELECT 절
- `from(entity)` — FROM 절
- `where(조건)` — WHERE 절
- `fetch()` — 실행 후 결과 반환

**조건 조합**

- 여러 조건을 콤마로 나열하면 AND 조건
- `or(...)`를 사용하면 OR 조건도 가능

**정렬과 페이징**

- `orderBy(조건)` — 정렬
- `offset()` — 페이징 시작 위치
- `limit()` — 가져올 개수

**조인**

- `join(entity)` — `join` 메서드로 연관 엔티티 조인 가능

**집계 함수**

- `count()` — 개수 카운트
- `max()` — 최대값
- `avg()` — 평균값

### BooleanBuilder

QueryDSL에서 여러 조건을 조립하거나 동적으로 추가해 `where` 절을 구성할 수 있도록 도와주는 조건 빌더 객체

### Where 다중 파라미터

QueryDSL에서 `where()` 절에 여러 조건 메서드를 파라미터로 전달해, `null`인 조건은 자동으로 제외하는 동적 쿼리 작성 방식

- 조건을 메서드로 분리
- `titleEq`, `authEq`, `statusEq`처럼 간결하게 나열
- `null` 조건은 자동으로 무시
- 별도로 조건 메서드들을 만들어서 써야 하는 번거로움 존재

## 5. 어떤 때에 어떤 걸 써야 하나?

### Spring Data JPA (1순위)

- 기본적인 CRUD
- 추가적인 쿼리가 필요하면 → 쿼리 메서드 검토
- 커스텀 인터페이스 → 내부적으로 쿼리를 쓰기 때문에 차라리 QueryDSL 사용
- `@Query`는 일반적으로 고려하지 않음 → 주로 배치 프로그램에서 사용
    - 배치 쿼리는 단발성이고, 복잡하며 트랜잭션이 걸림
    - 대량 데이터를 한 번에 수정/삭제하는 벌크 연산(`@Modifying`)에 적합
    - 영속성 컨텍스트를 거치지 않고 DB에 직접 반영되므로, 실행 후 컨텍스트 초기화에 주의해야 함
- 웬만한 건 다 여기서 해결하려고 함

### QueryDSL (2순위)

- 타입이 안정적
- 런타임 환경에 가지 않더라도 에러를 바로 확인 가능
- 일반적인 복잡한 쿼리는 여기서 진행
- Q클래스가 타입의 변화도 알아서 맞춰줌

### JPA

- 엔티티 매니저를 직접 다루는 경우는 없음

### JPQL

- Spring Data JPA의 `@Query`나 QueryDSL을 통해 간접적으로 활용되며, 직접 작성하는 경우는 드묾
- 문자열 기반이라 타입 안전성이 없고, 오타·필드 변경이 런타임 에러로 이어짐
- 동적 쿼리 작성이 까다로워, 복잡한 쿼리는 QueryDSL로 대체하는 추세
