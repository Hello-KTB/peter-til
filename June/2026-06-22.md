# VPC (Virtual Private Cloud)

> 공용 클라우드 환경에서 사용자에게 독립된 가상 네트워크를 제공하는 서비스
> 

AWS 안에 논리적으로 분리된 나만의 가상 네트워크로, IP 대역, 서브넷, 라우팅, 보안 규칙을 직접 설정할 수 있다.

## VPC를 사용하는 이유

> 서버와 데이터베이스를 무작정 인터넷에 연결하지 않고, 서비스별 통신 경로와 접근 범위를 통제하기 위해 사용한다.
> 

VPC 없이 구성하면 웹 서버, DB, 캐시 서버 등이 외부 인터넷에 그대로 노출된다.
VPC를 사용하면 서비스별로 네트워크를 나누고, 트래픽이 지나가는 경로를 제어하며, 사용자가 접근할 수 있는 자원을 제한할 수 있다.

**접근 흐름 예시:**

- 사용자는 Domain으로 접근
- 퍼블릭 서브넷에 LB, Web Server 배치
- LB, WS는 WAS에만 접근 가능
- WAS만 DB에 접근 가능

## VPC 구성 요소

| 구성 요소 | 정의 및 역할 | 일반 네트워크 비교 예시 |
| --- | --- | --- |
| VPC | 클라우드 환경에서 논리적으로 격리된 가상 네트워크 | 사내 전체 네트워크 환경 |
| 서브넷 (Subnet) | VPC 내의 IP 주소 범위를 나눠 생성한 논리적 네트워크 단위 | LAN의 하위 네트워크 (세그먼트) |
| 퍼블릭 서브넷 | 인터넷과 연결되어 외부 접근이 가능한 서브넷 | 인터넷 접근 가능한 DMZ 또는 외부망|
| 프라이빗 서브넷 | 인터넷과 직접 연결되지 않고, 내부 통신만 가능한 서브넷 | 사내의 인터넷 접근이 제한된 내부망 |
| 라우팅 테이블 | 서브넷 간 또는 인터넷과의 데이터 흐름을 결정하는 라우팅 규칙 목록 | 네트워크 라우터의 라우팅 테이블 |
| 인터넷 게이트웨이(IGW) | VPC와 인터넷 간의 연결을 지원하는 게이트웨이 장치 | LAN과 WAN 사이의 인터넷 연결 라우터 |
| NAT 게이트웨이 | 프라이빗 서브넷에서 인터넷으로의 아웃바운드 연결을 지원하는 장치 | 내부망에서 외부 인터넷 연결 시 사용하는 NAT 장비 |
| 보안 그룹 | 인스턴스 수준에서 트래픽 접근을 제어하는 상태 저장형 방화벽 | 개별 서버에 설정된 방화벽 규칙 |
| 네트워크 ACL | 서브넷 전체의 트래픽을 제어하는 상태 비저장형 접근제어 규칙 집합 | 서브넷 전체에 적용된 방화벽 규칙 |
* DMZ: 내부망과 외부망 사이에 위치해, 외부에서 접근 가능한 서버만 두고 내부망은 보호하는 중간 구역

## VPC 구성 시 주의 사항

1. **퍼블릭 IP 과금 주의** — EC2가 중지 상태이면 할당된 퍼블릭 IP에 대해 별도 과금이 발생한다
2. **내부 서비스에 퍼블릭 IP 할당 금지** — RDS, ElastiCache에 퍼블릭 IP를 부여하고 퍼블릭 서브넷에 올리는 것은 심각한 보안 문제다
3. **SSH 포트 0.0.0.0/0 오픈 금지** — pem 키가 있더라도 전체 인터넷에 SSH 포트를 열어두는 것은 위험하다
4. **VPC 설계 선행** — 어떤 구성 요소(WAS, DB, WS, Cache)를 어디에 배치할지 미리 설계해야 한다
5. **NAT Gateway 비용 주의** — 네트워크 통신량 기반으로 과금되므로, 컨테이너 이미지 다운로드, Git clone, S3 전송 등을 NAT를 통해 처리하면 비용이 급증할 수 있다

# IAM (Identity and Access Management)

> AWS 리소스에 대한 사용자 인증과 권한 관리를 제공하는 서비스
> 

"누가 AWS 리소스에 접근할 수 있는가"와 "어떤 작업을 할 수 있는가"에 답한다.

| 구분 | 질문 | IAM이 하는 일 |
| --- | --- | --- |
| 인증 | 당신은 누구인가? | 사용자, 역할, 로그인 방식, MFA 확인 |
| 인가 | 당신은 무엇을 할 수 있는가? | AWS 서비스·리소스·API별 권한 확인 |

## IAM을 사용하는 이유

> 실무에서는 다양한 역할의 작업자(개발자, 네트워크 엔지니어, 재무팀 등)가 함께 작업한다. 모두에게 동일한 권한을 부여하면 심각한 보안 위험이 생긴다. IAM을 통해 역할별로 필요한 권한만 분리해 부여한다.
> 

## 최소 권한 원칙

필요한 작업을 수행할 때 필요한 최소한의 권한만 부여하는 보안 원칙.

- 권한은 넓게 열고 나중에 줄이는 것보다
- 처음에 최소한으로만 할당하고, 필요할 때 검토 후 확장하는 것이 안전하다

## IAM 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| Root User | AWS 계정을 처음 만들 때 생성되는 최고 관리자 |
| User | AWS에 접근하는 개별 사용자 |
| Group | 여러 사용자에게 공통 권한을 부여하는 묶음 |
| Role | 특정 사용자나 AWS 서비스가 임시로 맡는 권한 |
| Policy | 허용·거부할 작업을 정의한 권한 규칙 |
| MFA | 로그인 시 비밀번호 외에 추가 인증 요구 |

**자주 사용하는 그룹 예시:**

| 그룹 | 권한 예시 |
| --- | --- |
| Developers | 개발 계정의 EC2, CloudWatch, S3 일부 접근 |
| Operators | 배포·모니터링·장애 대응 권한 |
| ReadOnlyAuditors | 리소스 조회만 허용 |
| BillingAdmins | 비용·결제 관련 설정 접근 |

## Policy

AWS에서 어떤 작업을 허용하거나 거부할지 정하는 규칙. 4가지 요소로 구성된다.

| 요소 | 의미 |
| --- | --- |
| Effect | 허용(`Allow`) 또는 거부(`Deny`) |
| Action | 어떤 AWS API 작업을 대상으로 할지 |
| Resource | 어떤 AWS 리소스에 적용할지 |
| Condition | 어떤 조건에서만 적용할지 |

## Role

> IAM 유저나 AWS 서비스가 특정 권한을 "임시로" 빌려서 사용할 수 있게 하는 권한 묶음
> 
- Policy들을 묶어 Role을 만들고, 필요한 서비스나 사용자에게 할당한다
- 예: `BackendFileUploader` Role에 S3 업로드 권한과 조회 권한 Policy를 연결

# 보안 그룹

> 클라우드 환경에서 인스턴스에 대한 네트워크 트래픽을 제어하는 가상 방화벽
> 

누가, 어떤 포트로, 이 리소스에 접근할 수 있는지를 정의한다.

### 보안 그룹을 사용하는 이유

> 서버를 인터넷에 무작정 노출하지 않고, 필요한 대상에게만 필요한 통신만 허용하기 위해서
> 

기본적으로 인바운드 규칙이 없으면 모든 인바운드 트래픽은 차단되며, 필요한 규칙을 추가해야만 트래픽이 허용된다.

| 트래픽 방향 | 설명 | 예시 |
| --- | --- | --- |
| 인바운드 | 외부에서 내 리소스로 들어오는 트래픽 | 인터넷 → ALB, ALB → WAS |
| 아웃바운드 | 내부에서 외부로 나가는 트래픽 | WAS → 외부 OAuth, 3rd Party API |

### 보안 그룹의 특징

**1. 상태 저장형(Stateful) 방화벽**

- 한 번 허용된 요청의 응답은 반대 방향 규칙을 별도로 작성하지 않아도 자동으로 허용된다.

**2. Allow만 가능하며, Deny는 불가**

- 허용 규칙이 없으면 기본적으로 차단된다
- 특정 IP나 국가를 명시적으로 차단하려면 Network ACL, WAF 등 별도 수단을 사용해야 한다

**3. 하나의 리소스에 여러 보안 그룹 연결 가능**

- 실무에서는 역할별로 보안 그룹을 나누고 필요한 리소스에 조합해 사용한다.

### 보안 그룹 구성 항목

| 항목 | 의미 | 예시 |
| --- | --- | --- |
| Type | 서비스 유형 | SSH, HTTP, HTTPS, MySQL |
| Protocol | 통신 규약 | TCP, UDP, ICMP |
| Port Range | 허용할 포트 범위 | 22, 443, 3306 |
| Source | 인바운드 출발지 | `203.0.113.10/32`, `sg-alb` |
| Destination | 아웃바운드 목적지 | `0.0.0.0/0`, `sg-db` |

### 보안 그룹 참조

소스로 IP 대역 대신 다른 보안 그룹을 지정할 수 있다.
EC2가 오토 스케일링으로 IP가 변경되어도 통신 규칙을 유지할 수 있으며, 어떤 역할의 서비스가 접근하는지 명확하게 파악할 수 있다.

**역할별 보안 그룹 구성 예시:**

| 보안 그룹 | 인바운드 허용 | Source |
| --- | --- | --- |
| `sg-alb` | HTTPS 443 | `0.0.0.0/0` |
| `sg-app` | TCP 8080 | `sg-alb` |
| `sg-db` | MySQL 3306 | `sg-app` |
| `sg-redis` | TCP 6379 | `sg-app` |

# Route 53

> 사람이 읽는 도메인 주소를 서버나 AWS 서비스의 주소로 연결하고, 상황에 따라 어느 서비스로 보낼지 결정하는 DNS 서비스
> 

**DNS 기본 흐름:**

1. 브라우저에서 `example.com` 접속 시도
2. DNS에 해당 도메인의 IP 주소 질의
3. DNS가 IP 반환
4. 브라우저가 해당 IP로 요청

Route 53은 이 도메인 요청을 어디로 보낼지 결정하는 DNS 역할을 담당한다.

### 도메인 등록과 DNS 관리는 다르다

- 도메인 등록 기관: 가비아, 후이즈, Cloudflare 등
- DNS 호스팅 서비스: 도메인을 어디로 연결할지 관리 (Route 53, 가비아 DNS 등)

가비아에서 도메인을 구매했더라도 DNS 관리는 Route 53으로 할 수 있다.

### Hosted Zone

> 특정 도메인과 서브 도메인에 대한 DNS 레코드를 보관하고 관리하는 공간
> 

| 구분 | 조회 가능 범위 | 사용 목적 | 예시 |
| --- | --- | --- | --- |
| Public Hosted Zone | 인터넷 전체 | 공개 웹사이트, 공개 API | `www.example.com` |
| Private Hosted Zone | 연결된 VPC 내부 | 내부 DB, 사내 API | `db.internal.example.com` |

Private Hosted Zone은 DB 등의 내부 서비스 주소를 도메인으로 관리할 때 유용하다. IP가 변경되더라도 애플리케이션 설정에서 도메인만 사용하면 된다.

### 주요 DNS 레코드

| 레코드 | 역할 | 예시 |
| --- | --- | --- |
| A | 도메인 → IPv4 주소 | `example.com → 203.0.113.10` |
| AAAA | 도메인 → IPv6 주소 | `example.com → 2001:db8::1` |
| CNAME | 도메인 → 다른 도메인 | `www → example.com` |
| Alias | Route 53 전용 AWS 리소스 연결 | `example.com → ALB` |
| MX | 메일 서버 지정 | `example.com → mail.example.com` |
| TXT | 텍스트 기반 인증·정책 | SPF, DKIM, ACM 검증 |
| NS | DNS 담당 네임서버 | Route 53 네임서버 |

**CNAME 주의 사항:** DNS 규칙상 최상위 도메인(`example.com`)에는 CNAME을 사용할 수 없다. 서브 도메인(`www.example.com`)에는 사용 가능하다.

**Alias 레코드:** ALB, CloudFront, NLB, API Gateway, S3 엔드포인트 등 AWS 리소스에 도메인을 직접 연결할 때 사용한다. ALB는 고정 IP를 보장하지 않기 때문에 A 레코드 대신 Alias를 사용해야 한다.

### 라우팅 정책

| 정책 | 설명 | 사용 사례 |
| --- | --- | --- |
| Simple | 하나의 도메인 → 하나의 대상 | 기본 연결 |
| Weighted | 비율대로 여러 대상에 분산 | 카나리 배포, 무중단 배포 |
| Failover | 주 서버 장애 시 부 서버로 전환 | DR(재해 복구) 구성 |
| Latency | 지연 시간이 가장 낮은 리전으로 연결 | 글로벌 서비스 |
| Geolocation | 사용자 IP 기반 가장 가까운 리전으로 연결 | 지역별 서비스 분리 |

# EC2 (Elastic Compute Cloud)

### 하이퍼바이저와 가상화

**하이퍼바이저:** 물리 서버 한 대에서 CPU, 메모리, 디스크, 네트워크 등의 자원을 여러 개의 가상 컴퓨터가 나눠 사용하고 서로를 격리해주는 소프트웨어 계층.

물리 서버를 고객 한 명에게만 빌려주면 남는 자원이 생기는데, 하이퍼바이저를 통해 OS 수준까지 격리하여 여러 고객에게 나눠줄 수 있다.

| 역할 | 설명 |
| --- | --- |
| CPU 분배 | 어떤 EC2가 언제 CPU를 사용할지 조정 |
| 메모리 분리 | 각 EC2가 자기 메모리만 사용하는 것처럼 보이게 함 |
| 가상 장치 제공 | 가상 디스크, 가상 네트워크 카드 등 제공 |
| 격리 | 다른 고객 EC2의 메모리·프로세스·디스크에 접근 차단 |

**가상화 비교:**

| 방식 | 격리 수준 |
| --- | --- |
| 하이퍼바이저 | OS 수준까지 격리 |
| 컨테이너 | OS 하드웨어는 공유, Application 레벨만 격리 |

### EC2를 배우는 이유

EC2는 AWS에서 가장 기초적인 컴퓨팅 자원이다. 범용적이고 자유로운 구성이 가능하며, 운영체제를 격리시켜서 빌리는 방식이기 때문에 서버를 직접 다루는 모든 영역(애플리케이션, 네트워크, 운영체제, 보안, 스토리지, 모니터링)을 직접 배울 수 있다.

RDS, ECS, EKS 등 여러 AWS 관리형 서비스는 결국 EC2 위에서 특정 작업을 자동화해주는 것이다. EC2를 이해하면 이러한 파생 서비스도 원리를 이해하기가 쉽다.

### 핵심 구성 요소

### 1. AMI (Amazon Machine Image)

서버를 만드는 템플릿. 운영체제와 초기 소프트웨어 구성이 포함된 서버 이미지.

실무에서는 매번 서버 생성 시 반복해야 하는 설정(JDK 설치, Docker 설치, Git clone, 빌드 등)을 미리 구워놓은 Custom AMI를 만들어 반복 배포와 오토 스케일링에 활용한다.

### 2. 인스턴스 타입

CPU와 메모리 조합으로 정의된 성능 단위. 예: `t3.medium` = vCPU 2개, RAM 2GB.

| 계열 | 특징 | 대표 사용 사례 |
| --- | --- | --- |
| T | 평소 낮은 CPU, 순간적 증가 가능 | 개발 서버, 소규모 웹 서버 |
| M | CPU·메모리 균형형 | 일반 백엔드, API 서버 |
| C | CPU 중심 | 배치 작업, 인코딩 |
| R | 메모리 중심 | 캐시, 대용량 JVM, 메모리 집약 DB |
| G/P | GPU 중심 | AI 추론, 머신러닝, 그래픽 처리 |
| I/D | 고성능 로컬 스토리지 | 고성능 데이터 처리 |

실무에서는 부하 테스트를 통해 서비스의 트래픽 패턴과 CPU/RAM 사용률을 측정한 뒤 인스턴스 타입을 결정한다.

### 3. EBS (Elastic Block Store)

EC2에 연결되는 영구 블록 스토리지. 가상의 하드디스크.

EC2는 가상화된 컴퓨팅 자원이므로, 데이터는 별도의 스토리지인 EBS에 저장된다.
EBS는 EC2와 독립적이므로, EC2를 중지하거나 교체해도 EBS를 분리해 다른 EC2에 재연결할 수 있다.

| 상황 | EC2 | EBS |
| --- | --- | --- |
| 인스턴스 실행 | 서버 실행 | 디스크 사용 |
| 인스턴스 중지 | CPU·메모리 사용 중단 | EBS는 계속 존재 |
| 인스턴스 종료 | 서버 삭제 | 삭제 정책에 따라 EBS도 삭제 가능 |

### 4. 네트워크

EC2는 반드시 VPC 내 서브넷 안에 배치된다.
퍼블릭 서브넷의 EC2에 외부 접속이 되려면 아래 세 조건이 모두 충족되어야 한다.

- 퍼블릭 IP 할당
- 서브넷이 IGW에 연결
- 보안 그룹에서 외부 요청 허용

### 실무에서 EC2를 잘 사용하는 방법

1. **태그 강제** — Name, Environment, Service, Owner, CostCenter, ManagedBy 등의 태그를 일관되게 붙인다
2. **중요 파일은 EC2에 저장하지 않는다** — EC2는 삭제될 수 있으므로 파일은 S3 등 별도 스토리지에 관리한다
3. **SSH로 직접 파일을 수정하지 않는다** — 서버가 여러 대인 환경에서는 수동으로 각각 접속해 파일을 수정하는 것이 불가능하므로 배포 스크립트를 통해 관리한다
4. **장애를 전제로 구성한다** — EC2는 언제든 장애가 발생할 수 있다. 이를 감지하고 대응하는 구성을 처음부터 포함시켜야 한다

## 인프라 구성 작업 순서

1. **서비스 명세 확인** — 어떤 서비스인지, 어디에 부하가 걸리는지, 중요 데이터는 무엇인지 파악 (API Docs, 기획서 검토)
2. **필요한 구성 요소 파악** — DB, 세션 스토어, 웹 서버, WAS, 이미지 저장, 로깅, 메트릭 트래킹 필요 여부 판단
3. **구성 요소 확정** — 구체적인 기술 스택 결정 (예: MariaDB, Nginx, S3, CloudFront)
4. **노출도 설정** — 어떤 리소스를 공개/일부 공개/비공개로 할지 결정
5. **트래픽 목표 설정** — 얼마나 많은 트래픽을 감당해야 하는지, 어느 레이어에서 부하를 받을지 결정 (모든 아키텍처가 항상 대규모 트래픽을 견딜 필요는 없다)
6. **실행** — VPC 설계, 네트워킹 설정, DB, 인스턴스 순서로 구성
