# 1. EFS (Elastic File System)

> AWS에서 제공하는 관리형 네트워크 파일 시스템으로, 용량 설정 없이 자동으로 확장·축소되며 여러 EC2 인스턴스가 동시에 공유할 수 있다
> 

파일을 서버 로컬 디스크(EBS)에만 저장하면 EC2가 한 대일 때는 문제가 없지만, 두 대 이상이 되는 순간 공통 파일 관리 문제가 생긴다. EFS는 이 문제를 해결하는 공유 네트워크 파일 시스템이다.

## 사용 이유

| 사용 이유 | 설명 |
| --- | --- |
| 다중 인스턴스 공유 | 여러 EC2가 같은 파일을 동시에 읽고 쓸 수 있음 |
| 자동 확장 | 파일이 늘어도 별도 증설 작업 없이 용량이 자동으로 늘어남 |
| 공통 파일 관리 | .env, 인증서 키 등 여러 서버에서 동일하게 써야 하는 파일 관리 |
| 고가용성 | Regional EFS 사용 시 여러 AZ에 데이터를 중복 저장해 내결함성 확보 |
| 컨테이너 환경 | 쿠버네티스 등 여러 컨테이너가 같은 영속 볼륨을 공유해야 할 때 |

## 마운트(Mount)란?

> 외부 파일 시스템을 서버의 특정 디렉토리에 연결해서, 로컬 폴더처럼 사용하는 작업
> 

EFS는 외부 네트워크 저장소이기 때문에 EC2에서 사용하려면 반드시 마운트 과정이 필요하다. USB를 꽂으면 D드라이브로 연결되는 것처럼, EC2의 `/efs` 폴더에 EFS를 연결하면 로컬 폴더처럼 사용할 수 있다.

비유: EFS = 공용 창고 / Mount Target = 창고로 들어가는 출입구 / EC2 = 창고를 사용하는 직원

## EFS 구성 요소

| 구성 요소 | 설명 |
| --- | --- |
| 파일 시스템 | 파일을 저장하고 폴더를 구성하는 핵심 리소스 |
| Mount Target | VPC 내에서 EC2가 EFS에 접속하기 위한 네트워크 진입점. 각 AZ에 하나씩 생성 |
| Security Group | EC2 ↔ EFS 간 통신을 허용하기 위한 방화벽 규칙 (TCP 2049 포트) |
| Access Point | EFS 내 특정 디렉토리에 대한 접근을 제한하는 논리적 진입점 |

## 성능 모드

| 모드 | 특징 | 추천 상황 |
| --- | --- | --- |
| General Purpose | 낮은 지연 시간 중심 | 일반 웹 서비스, CMS, 홈 디렉터리 (기본 권장) |
| Max I/O | 높은 병렬 처리 중심 | 매우 많은 클라이언트가 동시에 접근하는 특수 상황 |

## Throughput 모드

| 모드 | 특징 |
| --- | --- |
| Elastic | 사용량에 따라 처리량을 자동으로 늘리고 줄임 (도입 초기 권장) |
| Bursting | 파일 시스템 크기와 버스트 크레딧 특성을 활용 |
| Provisioned | 필요한 처리량을 직접 지정 |

## EFS vs EBS vs S3

| 구분 | EBS | EFS | S3 |
| --- | --- | --- | --- |
| 저장 방식 | 블록 스토리지 | 파일 스토리지 | 객체 스토리지 |
| 접근 방식 | EC2 디스크처럼 연결 | 여러 서버에서 마운트 | API / SDK / HTTP |
| 다중 EC2 접근 | 일반적으로 제한적 | 가능 | 가능 (파일 시스템 방식 아님) |
| 자동 확장 | 용량 증설 작업 필요 | 자동 확장 | 자동 확장 |
| 파일 시스템 명령어 | 가능 | 가능 | 불가 |
| 대표 사용처 | EC2 OS, DB 디스크 | 공유 업로드 폴더, 환경변수 | 이미지, 동영상, 백업, 로그 |

## 실무 적용 시 주의사항

- **모든 파일 저장소로 사용하지 않는다.** 비용이 상대적으로 비싸므로 공유 파일 시스템이 꼭 필요할 때만 선택한다.
- **DB 디렉토리에는 사용하지 않는다.** MySQL, PostgreSQL 등은 낮은 지연 시간 IOPS가 필요하므로 EBS를 권장한다.
- **NFS 포트(TCP 2049)를 인터넷에 절대 열면 안 된다.** VPC 내부 통신에만 사용해야 한다.
- **백업 전략을 별도로 설계해야 한다.** RDS와 달리 자동 백업이 기본 제공되지 않으므로 AWS Backup 정책을 직접 설정해야 한다.

# 2. S3 (Simple Storage Service)

> 이미지, 동영상, 백업 파일, 로그처럼 많은 파일을 객체(Object) 단위로 저장하고, HTTP 또는 AWS SDK를 통해 접근할 수 있게 해주는 객체 스토리지 서비스
> 

파일을 서버 디스크에 저장하면 EC2가 교체될 때 사라지고, 용량이 고정되어 있으며, 외부에서 URL로 직접 접근하기 어렵다. S3는 이 문제들을 모두 해결하는 관리형 객체 스토리지다.

## 객체 스토리지란?

S3에서는 파일을 단순한 파일이 아니라 아래 정보를 모두 포함한 '객체(Object)'로 저장한다.

| 구성 요소 | 설명 |
| --- | --- |
| Bucket | 객체가 저장되는 최상위 저장 공간 (폴더와 유사한 개념) |
| Key | 버킷 안에서 객체를 구분하는 고유한 이름 (경로처럼 보이지만 실제로는 하나의 문자열) |
| Value | 실제 파일 데이터 (이미지 바이너리, 텍스트 등) |
| Metadata | Content-Type, 생성 시각, 사용자 정의 태그 등 파일의 속성 정보 |
| Version ID | 버전 관리 활성화 시 객체 버전 식별자 |

S3는 내부적으로 Key-Value 구조로 저장된다. 콘솔에서 폴더처럼 보이는 것은 Key에 `/`를 포함시켜 시각적으로 계층 구조처럼 표현한 것이며, 실제 파일 시스템의 디렉토리가 아니다.

## EC2와 S3를 연동하는 두 가지 방식

**1. 백엔드가 업로드를 직접 처리하는 방식**

사용자 → 백엔드 서버 → S3 순서로 파일이 전달된다. 포맷 검사, 사이즈 제한, 리사이징 등 전처리를 수행할 수 있어 보안적으로 안전하지만, 대용량 파일이 백엔드 서버의 네트워크 자원을 소비한다.

**2. Presigned URL 방식**

| 단계 | 설명 |
| --- | --- |
| 1 | 클라이언트가 백엔드 서버에 업로드 URL 요청 |
| 2 | 백엔드 서버가 시간 제한이 있는 Presigned URL 생성 후 반환 |
| 3 | 클라이언트가 Presigned URL로 S3에 직접 업로드 |

| 구분 | 내용 |
| --- | --- |
| 장점 | 백엔드 서버가 대용량 파일을 직접 받지 않아 EC2 네트워크 비용 절감 |
| 장점 | 업로드 가능 시간, 파일 경로, 권한을 시간 제한으로 통제 가능 |
| 단점 | 파일 검증을 클라이언트에게 맡겨야 하므로 보안상 취약 |
| 단점 | 파일 압축·형 변환 결과가 클라이언트 환경마다 달라 일관성이 낮다 |

## 주요 기능

**Versioning** — 같은 Key로 파일을 다시 올려도 이전 버전을 보관한다. 실수로 삭제하거나 덮어쓴 경우에도 복구할 수 있으나, 버전이 쌓이면 저장 비용이 증가하므로 Lifecycle과 함께 설계해야 한다.

**Lifecycle Rule** — 오래된 객체를 더 저렴하고 느린 스토리지 클래스로 자동 이동시킨다. (예: 생성 후 30일 → Standard-IA, 90일 → Glacier)

## 스토리지 클래스

| 스토리지 클래스 | 대표 사용처 |
| --- | --- |
| S3 Standard | 자주 사용하는 이미지, 서비스 애플리케이션 파일 |
| S3 Intelligent-Tiering | 접근 패턴이 예측하기 어려운 파일 |
| S3 Standard-IA | 가끔 읽는 백업 파일 |
| S3 One Zone-IA | AZ 장애를 허용할 수 있는 재생성 가능 데이터 |
| Glacier Instant Retrieval | 거의 안 쓰지만 빠른 조회가 필요한 데이터 |
| Glacier Flexible Retrieval | 장기 보관 백업 |
| Glacier Deep Archive | 매우 장기 보관, 가장 저렴한 아카이브 |

## S3 보안 관리

S3는 VPC 외부의 AWS 공용 네트워크에 위치한다. EC2/RDS처럼 보안 그룹을 적용할 수 없으며, 대신 아래 방법으로 접근을 제어한다.

- **기본 설정은 비공개(Private):** AWS는 신규 버킷을 모두 비공개로 생성한다.
- **버킷 정책(Bucket Policy):** 특정 IP, IAM Role, 서비스에 대한 접근 허용/차단을 JSON으로 작성한다.
- **IAM Role:** EC2에 IAM Role을 연결하고 필요한 S3 권한만 부여하는 방식이 운영 환경에서 권장된다.
- **VPC 엔드포인트:** 인터넷망을 거치지 않고 내부망으로 S3에 안전하게 접근하려면 Gateway Endpoint를 사용한다.

# 3. RDS (Relational Database Service)

> AWS에서 제공하는 관리형 관계형 데이터베이스 서비스로, DB 설치·운영·백업·패치를 자동으로 처리해준다.
> 

EC2에 직접 MySQL을 설치하면 백업, 패치, 모니터링, 장애 복구를 모두 직접 관리해야 한다. RDS는 이 운영 부담을 AWS가 대신 처리해주는 서비스다.

## 주요 특징

| 특징 | 설명 |
| --- | --- |
| 자동 백업 | 설정한 보존 기간 동안 자동으로 스냅샷 생성 |
| 자동 패치 | OS 및 DB 엔진 보안 패치를 자동으로 적용 |
| 모니터링 | CloudWatch와 연동해 CPU, 연결 수, 스토리지 등을 실시간 확인 |
| 스케일 업 | 인스턴스 타입을 변경해 CPU/메모리를 손쉽게 확장 |
| Multi-AZ | 다른 가용 영역에 예비 DB를 두어 장애 시 자동 전환 |
| Read Replica | 읽기 전용 복제본을 생성해 읽기 트래픽 분산 |

## Read Replica vs Multi-AZ

| 구분 | Read Replica | Multi-AZ |
| --- | --- | --- |
| 목적 | 읽기 성능 향상 (부하 분산) | 고가용성 (장애 복구) |
| 평소 사용 여부 | 읽기 요청을 실제로 처리 | 숨겨두고 대기 상태 유지 |
| 장애 시 자동 승격 | 자동 승격되지 않음 | 자동으로 메인 DB로 전환 (Failover) |
| 데이터 동기화 | 비동기 복제 | 동기 복제 |

실제 서비스는 읽기 요청이 70~80% 이상을 차지하기 때문에, Read Replica로 읽기 트래픽을 분산하고 Multi-AZ로 장애 대비를 동시에 설계하는 것이 일반적이다.

# 4. 개인 질문 & 답변 정리

## EFS 관련

**Q. EBS만 있으면 되는데 굳이 EFS를 써야 하는 상황이 언제인가?**

EC2가 한 대일 때는 EBS로 충분하다. EFS가 필요해지는 순간은 EC2가 두 대 이상으로 늘어날 때다. Auto Scaling으로 인스턴스가 동적으로 늘어나는 환경에서 모든 인스턴스가 동일한 `.env` 파일이나 업로드된 이미지를 봐야 한다면, EBS는 한 인스턴스에만 붙기 때문에 EFS가 유일한 해결책이 된다.

**Q. EFS와 S3 둘 다 여러 서버에서 접근 가능한데, 차이가 무엇인가?**

접근 방식이 근본적으로 다르다. EFS는 리눅스 파일 시스템처럼 마운트해서 `ls`, `touch`, `cat` 같은 명령어로 사용할 수 있다. S3는 마운트 개념이 없고 AWS SDK나 HTTP API를 통해서만 접근한다. 기존 코드가 로컬 파일 시스템처럼 파일을 다룬다면 EFS를, 파일을 업로드·다운로드하는 형태로 다룬다면 S3를 선택한다.

**Q. EFS는 왜 DB 디렉토리로 쓰면 안 되는가?**

DB는 초당 수천~수만 번의 I/O가 발생하고 지연 시간이 매우 낮아야 한다. EFS는 네트워크를 경유하기 때문에 로컬 디스크(EBS)보다 지연 시간이 길다. MySQL, PostgreSQL 같은 DB를 EFS 위에서 운영하면 성능이 급격히 저하되고 트랜잭션이 불안정해진다.

## S3 관련

**Q. S3는 외부에서 이미지를 제공하는 역할도 하는데, 왜 기본이 비공개(Private)인가?**

S3는 퍼블릭 이미지 서버로도 쓰이지만, 훨씬 많은 경우 신분증 사본, DB 백업 파일, 서버 로그처럼 절대 외부에 노출되면 안 되는 데이터를 저장한다. AWS가 기본을 비공개로 설정하는 이유는 실수로 민감한 파일을 공개하는 사고를 방지하기 위해서다. 외부 공개가 필요한 파일만 명시적으로 허용하는 방식이 안전하다.

**Q. S3가 Key-Value 구조라면 NoSQL DB처럼 사용할 수 있지 않나?**

구조는 비슷해 보이지만 용도와 성능이 완전히 다르다. DynamoDB 같은 NoSQL DB는 수 밀리초 안에 수십만 건의 소규모 데이터를 처리하도록 설계됐다. S3는 대용량 파일을 안전하게 보관하는 스토리지로, 텍스트 파일 하나를 읽는 데도 네트워크를 거쳐 100~200ms 이상 걸린다. 자주 읽고 써야 하는 데이터에는 적합하지 않다.

**Q. Presigned URL은 유효 시간이 지나면 어떻게 되는가? 이미 다운로드 중이면 끊기나?**

유효 시간은 요청(접속)을 시작할 수 있는 시간이다. 유효 시간 안에 다운로드를 시작했다면, 이미 진행 중인 전송은 끊기지 않는다. 유효 시간이 지난 뒤 새로 접속을 시도하면 403 오류가 반환된다.

**Q. 클라이언트가 S3에서 파일을 검색할 때 내부 흐름은 어떻게 되는가?**

클라이언트는 S3에 직접 검색 요청을 보내지 않는다. 일반적인 흐름은 다음과 같다. 클라이언트가 백엔드 서버에 조건을 포함한 API 요청을 보내면, 백엔드 서버가 RDS나 DynamoDB에서 메타데이터와 S3 Key를 조회한다. 이후 해당 Key로 Presigned URL을 생성해 클라이언트에 반환하고, 클라이언트는 그 URL로 S3에서 직접 파일을 받아온다. 대규모 로그 분석이 필요한 경우에는 백엔드 서버가 AWS SDK를 통해 Athena나 S3 Select로 S3 내부를 직접 쿼리하기도 한다.

## RDS 관련

**Q. Read Replica와 Multi-AZ를 둘 다 써야 하는 이유가 무엇인가?**

역할이 다르기 때문에 하나로 대체할 수 없다. Read Replica는 평소에 읽기 요청을 실제로 처리해 성능을 높인다. Multi-AZ는 평소에 아무 일도 하지 않다가 메인 DB가 장애를 일으켰을 때만 자동으로 역할을 인수한다. 성능은 Read Replica가, 장애 복구는 Multi-AZ가 담당하는 구조다.

**Q. RDS를 쓰면 EC2에 직접 MySQL을 설치하는 것보다 항상 나은가?**

대부분의 경우 그렇지만, 비용이 더 비싸고 설정 자유도가 낮다는 단점이 있다. 트래픽이 매우 적은 초기 서비스나, 특수한 DB 설정이 필요한 경우에는 EC2 직접 설치가 합리적일 수 있다. 다만 서비스가 성장해 백업·복구·가용성이 중요해지는 시점부터는 RDS의 관리 편의성이 비용 차이를 압도한다.
