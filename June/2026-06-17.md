# 1. Proxy

> 클라이언트와 서버 사이에서 중계자 역할을 하는 네트워크 장치
> 

데이터 요청·응답 과정을 제어하는 네트워크 장치 또는 소프트웨어를 의미한다.

프록시 없이 클라이언트와 서버가 직접 연결되면 구조는 단순해지지만, 보안·로깅·캐싱·접근 제어 같은 기능을 중간에서 처리하기 어렵다.

## 사용 이유

| 사용 이유 | 설명 |
| --- | --- |
| 보안 강화 | 클라이언트와 서버의 직접 연결을 줄이고, 요청을 검사하거나 차단 |
| 트래픽 최적화 | 캐싱, 압축, 로드 밸런싱 등으로 성능 개선 |
| 접근 제어 | 허용된 사용자나 IP만 특정 서비스에 접근하게 함 |
| 로깅/감시 | 누가 어떤 요청을 했는지 기록 |
| 익명성 | 클라이언트의 실제 IP나 서버의 실제 IP를 숨김 |
| 정책 적용 | 회사나 학교 네트워크에서 접근 가능한 사이트 제한 |

## Proxy의 종류

"누구를 대신하는가?"에 따라 프록시의 종류가 결정된다.

| 유형 | 누구의 대리자인가? | 대표 목적 |
| --- | --- | --- |
| Forward Proxy | 클라이언트의 대리자 | 클라이언트 보호, 우회, 익명성, 사내 정책 적용 |
| Reverse Proxy | 서버의 대리자 | 서버 보호, 로드 밸런싱, SSL 처리, 캐싱 |

## Forward Proxy

> 클라이언트 대신 외부 서버에 요청을 보내는 프록시
> 

클라이언트가 외부 서버에 직접 요청하지 않고, 요청을 프록시에 전달하면 프록시가 서버로 요청을 전달하는 방식이다. 응답도 프록시가 받아 클라이언트에게 전달한다.

| 단계 | 설명 |
| --- | --- |
| 1 | 클라이언트가 Forward Proxy로 요청 |
| 2 | Forward Proxy가 목적지 서버로 요청 전달 |
| 3 | 서버는 Proxy에게 응답 |
| 4 | Proxy가 클라이언트에게 응답 반환 |

### 사용 예시

| 예시 | 설명 |
| --- | --- |
| 회사 인터넷 프록시 | 직원들의 외부 사이트 접근을 통제하고 로그 기록 |
| 학교 네트워크 프록시 | 특정 사이트 접근 제한 |
| 캐싱 프록시 | 자주 요청하는 파일이나 페이지를 저장해 속도 개선 |
| 익명 프록시 | 클라이언트의 실제 IP를 숨김 |
| 제한 우회 | 특정 네트워크 제한을 우회하는 데 사용 |

## Reverse Proxy

> 서버 대신 클라이언트 요청을 먼저 받아 처리하는 프록시
> 

서버의 대리 역할을 하며, 서버 보호와 네트워크 최적화에 중점을 두는 프록시다.

| 단계 | 설명 |
| --- | --- |
| 1 | 클라이언트 요청이 Reverse Proxy에 도착 |
| 2 | Reverse Proxy가 규칙 검사, 라우팅, 인증, 캐싱 등을 수행 |
| 3 | 정상 요청을 백엔드 서버로 전달 |
| 4 | 백엔드 서버의 응답을 받아 클라이언트에게 반환 |

### 주요 기능

| 기능 | 설명 |
| --- | --- |
| 보안 강화 | 서버의 IP 주소를 숨기고, DDoS 공격 및 악성 요청을 차단 |
| SSL/TLS 처리 | HTTPS 트래픽을 처리하여 데이터 전송을 암호화 |
| 로드 밸런싱 | 다수의 서버에 트래픽을 분산시켜 서버 과부하를 방지 |
| 캐싱 | 반복적인 요청 데이터를 저장하여 서버 부하를 줄이고 응답 속도 향상 |
| 요청 라우팅 | `/api`는 API 서버, `/static`은 정적 파일 서버로 전달 |

### 대표 예시

Nginx, HAProxy, Envoy, CloudFront, API Gateway, ALB

## Forward Proxy vs Reverse Proxy

| 구분 | Forward Proxy | Reverse Proxy |
| --- | --- | --- |
| 누구의 대리자냐? | 클라이언트 | 서버 |
| 위치 | 클라이언트 쪽 | 서버 앞쪽 |
| 클라이언트가 아는 대상 | 프록시를 명시적으로 설정하는 경우 많음 | 보통 서비스 주소만 알고 프록시는 의식하지 못함 |
| 서버가 보는 요청자 | 프록시 | 프록시 |
| 주요 목적 | 클라이언트 보호, 접근 제어, 우회, 익명성 | 서버 보호, 로드밸런싱, SSL 처리, 캐싱 |
| 대표 예시 | 회사 인터넷 프록시, 캐싱 프록시 | Nginx, ALB, API Gateway, CDN |

# 2. VPN

> 공용 인터넷 위에 암호화된 가상 터널을 만들어, 멀리 떨어진 사용자나 네트워크를 사설망처럼 안전하게 연결하는 기술
> 

## 사용 이유

**1. 원격지에서 내부망을 안전하게 사용해야 할 때**

회사 내부에 있는 서비스들(DB, WAS, 사내 Git 서버 등)은 외부에서 접근이 불가능하다. 재택근무나 출장 시 외부 네트워크에서 사내망에 접근하기 위해 VPN을 사용한다.

**2. 보안성 강화**

카페나 공항 같은 공용망에서 통신할 때, VPN 터널링으로 내용을 암호화하면 외부에서는 목적지나 내용을 볼 수 없다.

**3. 떨어진 사설망들을 하나의 사설망처럼 묶을 때**

본사와 지사, 또는 IDC와 클라우드 서버(AWS)처럼 물리적으로 떨어진 네트워크를 하나의 사설망처럼 연결할 수 있다.

## 핵심 구성 요소

| 구성 요소 | 설명 |
| --- | --- |
| VPN Client | 사용자의 PC나 스마트폰에서 VPN 연결을 시작하는 프로그램 |
| VPN Server | VPN 접속을 받아 인증하고 터널을 만들어주는 서버 |
| VPN Tunnel | 클라이언트와 서버 사이의 암호화된 가상 통로 |
| 인증 정보 | 계정, 비밀번호, 인증서, MFA 등 사용자 확인 수단 |
| 암호화 키 | 데이터를 암호화하고 복호화하기 위한 키 |
| 가상 IP | VPN 연결 후 클라이언트에게 할당되는 내부망용 IP |
| 라우팅 정책 | 어떤 트래픽을 VPN으로 보낼지 결정하는 설정 |

## 터널링이란?

원본 패킷을 다른 프로토콜로 감싸서 보내는 방식이다. 외부에서 보면 "VPN 서버로 암호화된 데이터가 가고 있다"는 것만 보이고, 실제로 어느 서버에 어떤 요청을 하는지는 보이지 않는다.

## VPN 연결 방식

**Full Tunnel** — 모든 트래픽을 항상 VPN으로 보내는 방식

**Split Tunnel** — 사내망에 가야 하는 트래픽만 VPN으로 보내고, 나머지는 일반 인터넷으로 내보내는 방식

## 실무 활용 예시

- 재택 근무자가 사내 Git, DB에 접속할 때
- Bastion Server(Jump Server)를 통해 운영 DB에 접근할 때
- 어드민 페이지를 외부에서 접속해야 할 때
- IDC와 AWS 같은 퍼블릭 클라우드를 LAN처럼 연결할 때

# 3. CIDR

> 라우팅할 때 트래픽 경로를 명확하게 지정하기 위해 네트워크 범위를 구분하는 주소 표준
> 

기존 클래스 기반 IP 주소 체계를 극복하고자 만들어졌으며, IP 주소 공간을 효율적으로 사용하고 라우팅 테이블의 크기를 줄이기 위해 사용한다.

## IP 주소의 구성

IP 주소는 네트워크 영역과 호스트 영역 두 가지 정보로 나뉜다.

| 구분 | 의미 |
| --- | --- |
| 네트워크 영역 | 이 IP가 어느 네트워크에 속해 있는지 |
| 호스트 영역 | 그 네트워크 안에서 몇 번 장치인지 |

## 네트워크와 호스트 영역을 나누는 이유

나누지 않으면 라우터가 42억 개의 IP 주소 경로를 전부 외우고 있어야 한다. 네트워크 영역으로 묶으면 라우터는 동네 단위로만 경로를 알고 있으면 된다.

## 서브넷 마스크와 프리픽스

어디까지가 네트워크 영역인지를 표현하기 위해 슬래시 뒤의 숫자(프리픽스)를 사용한다.

```
192.168.1.10 / 24
→ 앞 24비트: 네트워크 영역
→ 나머지 8비트: 호스트 영역
```

AND 연산으로 네트워크 주소를 구할 수 있다.

```
IP:   11000000.10101000.00000001.00001010  (192.168.1.10)
마스크: 11111111.11111111.11111111.00000000  (/24)
결과:  11000000.10101000.00000001.00000000  (192.168.1.0) ← 네트워크 주소
```

## 호스트 수 계산

```
호스트 비트 수 = 32 - 프리픽스
사용 가능 호스트 수 = 2^(호스트 비트 수) - 2
```

2를 빼는 이유는 네트워크 주소(.0)와 브로드캐스트 주소(.255)를 호스트에 사용할 수 없기 때문이다.

| CIDR | 호스트 비트 | 사용 가능 호스트 수 |
| --- | --- | --- |
| /16 | 16 | 65,534개 |
| /24 | 8 | 254개 |
| /26 | 6 | 62개 |
| /30 | 2 | 2개 |
| /32 | 0 | 단일 IP 1개 |
