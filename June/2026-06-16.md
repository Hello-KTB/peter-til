# 1. Inline
<img width="489" height="134" alt="image" src="https://github.com/user-attachments/assets/fdae70e4-aa01-4be2-aadc-a3ef6b2f8c6f" />

> 네트워크 상의 데이터 패킷이 반드시 해당 장치를 통과하도록 설계된 네트워크 구조
> 

모든 요청은 반드시 거쳐야 하는 통로로, 트래픽의 흐름에 직접 개입하여 제어하고 관리한다.

트래픽이 목적지에 도달하기 전 허용, 차단, 필터링과 같은 작업을 수행한다.

네트워크 장비를 이해할 때는 장비의 기능만큼이나 **트래픽 흐름상 이 장비가 어디에 놓이는지**가 중요하다.

```
사용자 → 인터넷 → 서버             # 보안 장비 없음

사용자 → 인터넷 → 보안장비 → 서버  # Inline 구조
```

보안 장비가 사용자와 서버 사이 길목에 위치하고, 모든 요청이 항상 반드시 이 장비를 지나야 한다면 **Inline 방식**이다.

인라인 방식은 "네트워크의 검문소" 역할을 한다. 목적지에 가려면 항상 검문소를 거치는 것처럼.

## 특징

**1. 반드시 지나간다**

- 강제성을 가진다
- 우회 없이 무조건 거쳐야 목적지에 도달할 수 있다

**2. 트래픽을 직접 제어한다**

- 반드시 지나가기 때문에 아래와 같은 판단을 수행한다
    - 이 요청이 정상인가?
    - 이 IP는 차단 대상인가?
    - 이 포트는 허용되었나?
    - 이 요청은 너무 많이 들어오고 있지 않나?
    - 패턴이 악성 패턴인가?
- 판단 결과에 따라 트래픽을 통과, 드롭, 다른 곳으로 우회시키는 등 직접 제어한다

| 처리 방식 | 의미 |
| --- | --- |
| 허용 | 정상 트래픽을 통과시킴 |
| 차단 | 위험하거나 정책에 맞지 않는 트래픽을 버림 |
| 필터링 | 특정 조건에 따라 트래픽을 제한하거나 조정 |
| 수정 | 필요하면 헤더나 요청 정보를 변경 |
| 기록 | 트래픽 로그를 남김 |

## 왜 사용하는가?

**1. 실시간 보안 적용**

- 인라인 장비 자체가 보안 적용에 유리하다
- 악성 요청을 서버 도달 전에 막을 수 있다

**2. 트래픽 제어**

- IP 기반 차단
- 포트 기반 제어 (예: 22번 SSH는 사내망에서만)
- 프로토콜 제어 (HTTPS, DNS)
- Rate Limit
- 접근 제어 (예: /admin은 사내망에서만)

**3. 서버 보호**

- 인라인 장비가 서버 앞에 위치하면 모든 요청을 서버가 처리하지 않아도 된다

```
악성 요청 → 인라인 장비 처리 (서버까지 안 감)
정상 요청 → 인라인 장비 → 서버
```

이러한 구조를 **Reverse Proxy**라고 부른다**.**

강제성이라는 특징 때문에 보안에 효과적이며, 트래픽을 직접 제어하기 때문에 조건에 맞는 트래픽만 서버에 도달시킬 수 있다.

## 대표적인 인라인 장비

| 장치 | 설명 |
| --- | --- |
| 공유기(Router) | 네트워크 트래픽을 경유하며 기본적인 데이터 흐름 관리 수행 |
| 방화벽(Firewall) | 네트워크를 통과하는 트래픽을 규칙에 따라 허용하거나 차단 |
| 네트워크 스위치 | 내부 네트워크의 트래픽을 특정 조건에 따라 라우팅 |
| 침입 방지 시스템(IPS) | 악성 트래픽을 실시간으로 탐지하고 즉각 차단 |
| 로드밸런서 | 들어오는 요청을 여러 서버에 분배 |
| WAF (Web Application Firewall) | 웹 애플리케이션 레벨의 공격 차단 |

## 장점

| 장점 | 설명 |
| --- | --- |
| 강제성 | 모든 트래픽이 반드시 장비를 지나감 |
| 실시간 차단 | 악성 요청을 서버 도달 전에 막을 수 있음 |
| 정책 적용 확실함 | 우회 경로가 없으면 보안 정책이 강하게 적용됨 |
| 로그 확보 | 통과/차단 트래픽을 기록할 수 있음 |
| 서버 보호 | 백엔드 서버가 직접 공격 트래픽을 받지 않도록 보호 |

## **단점**

1. **병목 현상** — 트래픽이 급격히 증가하면 인라인 장비에서 처리 지연 발생 가능
2. **단일 장애지점 (SPOF)** — 인라인 장비에 문제 발생 시 전체 네트워크 다운
3. **잘못된 정책의 위험** — 규칙을 잘못 만들면 정상 트래픽도 전부 차단될 수 있다

**장애 극복 방법**

| 방법 | 설명 |
| --- | --- |
| 이중화 | Inline 장비를 2대 이상 구성 |
| Failover | 장애 발생 시 대기 장비로 자동 전환 |
| Bypass Mode | 장비 장애 시 트래픽을 우회 통과시킴 |
| 로드밸런싱 | 여러 장비로 검사 부하 분산 |
| 정책 테스트 | 운영 반영 전 탐지 모드나 테스트 환경에서 검증 |
| 모니터링 | 지연, 차단 수, 에러율, CPU/메모리 감시 |

# 2. Out of Path
<img width="730" height="209" alt="image (3)" src="https://github.com/user-attachments/assets/91096ab1-7661-437b-8fc8-615de981fdd9" />

> 네트워크 경로에서 데이터를 실시간으로 처리하지 않고, 트래픽을 복사하거나 분석용으로 수집하여 별도 장치에서 처리하는 네트워크 구조
> 

트래픽을 복사하거나 미러링해서 분석 장치에서 데이터를 처리한다. 트래픽 흐름에 직접적인 영향을 주지 않으면서 실시간으로 네트워크 상태를 모니터링하거나 보안 위협을 탐지할 수 있다.

```
실제 흐름:  Client → 스위치 → Server    (원본, 영향 없음)
                       ↓ 복사
                    분석 장비            (복사본만 분석)
```

## 왜 사용하는가?

**1. 서비스 트래픽에 영향을 주지 않는다**

- Out of Path는 트래픽 경로 밖에서 동작한다
- Inline과 달리 분석 장치가 고장나도 실제 처리 흐름에는 영향을 주지 않는다

**2. 모니터링을 안정적으로**

- 원본이 아닌 복사본을 보기 때문에 모니터링을 안정적으로 수행할 수 있다

**3. 탐지와 분석에 집중**

- 장비들도 역할이 분리되어 있다. Out of Path 장비는 탐지에 집중한다

```
이상 트래픽 발견
→ 로그 저장
→ 알림 발생
→ 관리자 확인
→ 필요한 조치 수행
```

- Inline은 "이 트래픽 이상하네 → 즉시 차단"
- Out of Path는 "이 트래픽 이상해 → 로그 저장, 관리자에게 알림"

## 특징

| 특징 | 설명 |
| --- | --- |
| 경로 외부 동작 | 실제 트래픽 경로 밖에서 복사본을 분석 |
| 비간섭성 | 원본 트래픽 흐름에 직접 개입하지 않음 |
| 탐지 중심 | 차단보다는 탐지, 분석, 알림, 기록에 적합 |
| 서비스 안정성 | 분석 장비 장애가 서비스 전체 장애로 이어질 가능성이 낮음 |
| 확장성 | 분석 장비를 추가하거나 교체하기 비교적 쉬움 |
| 직접 차단 한계 | 원본 트래픽이 이미 지나가기 때문에 즉시 차단은 제한적 |

## Inline vs Out of Path

| 구분 | Inline | Out-of-Path |
| --- | --- | --- |
| 위치 | 실제 트래픽 경로 위 | 실제 트래픽 경로 밖 |
| 원본 트래픽 처리 | 직접 통과시킴 | 복사본을 분석 |
| 차단 능력 | 직접 차단 가능 | 직접 차단은 제한적 |
| 서비스 영향 | 장비 장애 시 서비스 영향 큼 | 분석 장비 장애 시 서비스 영향 작음 |
| 주요 목적 | 제어, 차단, 필터링 | 탐지, 분석, 모니터링 |
| 대표 장비 | 방화벽, IPS, WAF, 로드밸런서 | IDS, SIEM, Zeek, Wireshark, Flow Logs |
| 비유 | 도로 위 검문소 | 도로 옆 CCTV |

# 3. Wireshark

> 내 컴퓨터나 네트워크 인터페이스를 지나가는 패킷을 캡처하고 분석하는 네트워크 프로토콜 분석 도구
> 

네트워크 통신은 눈에 보이지 않지만, 브라우저 하나를 접속해도 내부적으로는 상당히 많은 일이 일어난다.

```
브라우저 접속
→ DNS 조회 → TCP 연결 → TLS Handshake → HTTP 요청 → 서버 응답
```

Wireshark는 이 보이지 않는 네트워크의 흐름을 눈으로 볼 수 있게 해주는 도구다.

## 캡처

캡처는 **네트워크 인터페이스를 흐르는 패킷을 복사해서 저장하는 행위**다.

NIC는 기본적으로 자신의 MAC 주소로 오는 패킷만 OS에 전달하고 나머지는 버린다.

Wireshark는 NIC를 Promiscuous Mode로 전환해서, 자신에게 오는 것이 아닌 패킷도 포함해 지나가는 패킷을 복사한다.

## Wireshark로 볼 수 있는 것들

| 확인할 수 있는 것 | 예시 |
| --- | --- |
| DNS 조회 | 도메인이 어떤 IP로 해석되는지 |
| TCP 연결 | 3-way handshake가 성공하는지 |
| 재전송 | 네트워크 손실로 재전송이 발생하는지 |
| TLS Handshake | HTTPS 연결이 어디서 실패하는지 |
| HTTP 요청 | 평문 HTTP 요청/응답 내용 |
| 포트 통신 | 특정 포트로 패킷이 실제로 나가는지 |
| 응답 지연 | 요청 후 응답까지 시간이 얼마나 걸리는지 |

## 필터

모든 패킷을 다 보려고 하면 너무 많아서 원하는 패킷을 찾기 어렵다.

필터를 통해 내가 보고 싶은 패킷만 골라본다.

### Capture Filter — 캡처 전에 적용

캡처 자체를 특정 패킷만 수행한다.

한 번 걸러진 패킷은 다시 볼 수 없으므로 신중하게 설정해야 한다.

**BPF(Berkeley Packet Filter) 문법을 사용한다.** Display Filter와 문법이 다르다.

| 목적 | Capture Filter 문법 |
| --- | --- |
| 특정 IP만 | `host 142.250.196.78` |
| 특정 포트만 | `port 443` |
| HTTP + HTTPS만 | `port 80 or port 443` |
| DNS만 | `port 53` |
| 특정 IP의 443만 | `host 142.250.196.78 and port 443` |
| 특정 IP 제외 | `not host 192.168.0.1` |
| 특정 대역만 | `net 192.168.0.0/24` |

### Display Filter — 캡처 후에 적용

캡처된 것들 중에서 어떤 패킷을 보여줄지 결정한다.

필터를 잘못 걸어도 나중에 수정해서 다시 볼 수 있어 유연하다.

# 4. 오늘 학습 중 궁금했던 점

## Wireshark를 Out of Path 구조라고 볼 수 있나?

그렇다. Wireshark는 Out of Path 구조의 대표적인 예다.

근거는 세 가지다. 첫째, 원본 패킷의 경로에 끼어들지 않는다. 패킷은 원래 목적지로 그대로 흘러가고 Wireshark는 복사본만 받는다. 둘째, NIC를 Promiscuous Mode로 전환해 복사한다. 원래 NIC는 자신의 MAC 주소로 오는 패킷만 올리고 나머지는 버리는데, Wireshark는 이 모드를 바꿔 지나가는 모든 패킷을 복사해 버퍼에 쌓는다. 셋째, 읽기 전용이다. Wireshark로는 패킷을 차단하거나 수정할 수 없고 분석·탐지만 가능하다.

같은 Out of Path인 IDS와 비교하면, IDS는 복사본을 받아 자동으로 위협을 탐지하고 알람을 발생시키는 반면 Wireshark는 사람이 직접 눈으로 분석한다. 둘 다 Out of Path지만 Wireshark는 더 수동적인 도구다.

## 캡처란 정확히 무엇을 의미하는 건가?

캡처는 네트워크 인터페이스를 흐르는 패킷을 복사해서 저장하는 행위다.

NIC는 기본적으로 자신의 MAC 주소로 오는 패킷만 OS에 전달하고 나머지는 버린다. Wireshark는 NIC를 Promiscuous Mode로 전환해서 지나가는 모든 패킷을 복사한다. 원본 흐름을 방해하지 않고 지나가는 걸 몰래 복사해 보는 것이다. 복사된 데이터는 `.pcap` 파일로 저장해 나중에 불러와서 다시 분석할 수 있다.

## WiFi(en0)로 접속하면 보이는 패킷들이 전부 실시간으로 교환되고 있는 패킷들인가?

그렇다. 전부 실시간이다. 단, 범위가 있다.

en0는 내 맥의 Wi-Fi 인터페이스다. 여기서 캡처되는 패킷은 내 컴퓨터가 보내는 패킷과 내 컴퓨터가 받는 패킷이다. 같은 Wi-Fi의 다른 기기 패킷은 기본적으로 보이지 않는다.

처음에 엄청난 양의 패킷이 흘러가는 이유는 내 컴퓨터가 생각보다 훨씬 많은 백그라운드 통신을 하고 있기 때문이다. iCloud 동기화, Spotlight, 각종 앱 heartbeat, mDNS, ARP 등이 끊임없이 오가고 있다.

## 패킷 분석이면 네트워크 계층에서 일어나는 일들만 분석 가능한 건가?

아니다. Wireshark는 OSI 전 계층을 동시에 분석한다.

"패킷"이라는 단어가 3계층(네트워크 계층)의 데이터 단위이긴 하지만, Wireshark에서 "패킷"은 관용적으로 캡처된 하나의 프레임 전체를 의미한다. 하나의 캡처 항목을 클릭하면 아래처럼 모든 계층이 펼쳐진다.

```
[Frame]              ← L2 — MAC 주소
[Ethernet II]        ← L2
[Internet Protocol]  ← L3 — IP 주소, TTL
[TCP / UDP]          ← L4 — 포트 번호, 시퀀스 번호
[HTTP / DNS / TLS]   ← L7 — 실제 요청/응답 데이터
```

즉, 하나의 패킷을 캡처하면 그 안에 담긴 모든 계층의 정보가 함께 보인다.

## Capture Filter에 도메인명만 입력하면 해당 도메인 패킷만 필터링되는 건가?

아니다. Capture Filter에서 도메인명 직접 입력은 불가능하다.

Capture Filter는 NIC 레벨에서 동작한다. 이 단계의 패킷 안에는 이미 도메인명이 없고 IP 주소만 담겨 있다. 브라우저가 google.com에 접속하려 할 때 이미 DNS를 통해 IP로 변환한 뒤 패킷을 만들기 때문이다.

```
브라우저: "google.com 접속"
    ↓
DNS 조회: google.com → 142.250.196.78  ← 이 시점에 도메인이 IP로 변환됨
    ↓
패킷 생성: dst: 142.250.196.78 / port: 443  ← 도메인명 없음
    ↓
NIC 레벨  ← Capture Filter가 작동하는 곳
```

해결 방법은 먼저 터미널에서 IP를 확인한 뒤 그 IP를 필터에 입력하는 것이다.

```bash
nslookup google.com   # IP 확인
```

```
host 142.250.196.78   # Capture Filter에 IP 입력
```

Display Filter 단계에서는 응용 계층까지 파싱된 상태이므로 도메인명으로 필터링이 가능하다.

```
http.host contains "google.com"
tls.handshake.extensions_server_name contains "google.com"
```
