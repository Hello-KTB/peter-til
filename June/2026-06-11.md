# 교착 상태 (Deadlock)

> 두 개 이상의 프로세스나 스레드가 자원을 점유한 채 서로가 필요로 하는 자원을 기다리며 무한히 대기하는 상태
> 


## 왜 알아야 하는가?

| 이유 | 설명 |
| --- | --- |
| 시스템 안정성 확보 | 교착 상태는 일부 프로세스나 스레드를 무한 대기 상태로 만들어 전체 시스템의 응답성을 저하시킨다. 대형 서버에서 발생하면 서비스 전체가 중단될 수 있다. |
| 효율적인 자원 관리 | 자원의 비효율적인 점유 및 대기는 CPU, 메모리, DB 커넥션 등의 낭비를 초래한다. 예방하면 동시 사용자 처리량을 높일 수 있다. |
| 복잡한 분산 환경에서의 신뢰성 확보 | 분산 시스템에서는 자원이 여러 노드에 분산되어 있어 교착 상태가 발생하기 쉽다. 이를 방지하면 시스템 간의 신뢰성과 성능을 높일 수 있다. |

참고

- 교착 상태는 가시성이 나쁜 에러다
- 예외가 발생하는 것이 아니라 그냥 멈추기 때문에, 단순 성능 문제처럼 보일 수 있다


## 교착 상태 발생 조건 4가지

4가지 조건이 **모두** 충족되어야 교착 상태가 발생한다. 하나라도 깨지면 교착 상태는 발생하지 않는다.

| 조건 | 설명 |
| --- | --- |
| 상호 배제 (Mutual Exclusion) | 자원은 한 번에 하나의 프로세스만 사용할 수 있음 |
| 점유와 대기 (Hold and Wait) | 프로세스가 하나의 자원을 점유한 상태에서 다른 자원을 기다림 |
| 비선점 (No Preemption) | 점유된 자원은 강제로 빼앗길 수 없음 |
| 순환 대기 (Circular Wait) | 프로세스들이 자원을 서로 기다리며 순환 구조를 형성함 |


## 해결 및 예방 방법

| 방법 | 설명 |
| --- | --- |
| 자원 요청 순서 통일 | 모든 스레드가 같은 순서로 락을 획득하게 하여 순환 대기를 방지한다 |
| 타임아웃 설정 | 일정 시간 안에 락을 얻지 못하면 포기하고 재시도한다 |
| 우선순위 기반 자원 할당 | 교착 가능성이 있으면 한 트랜잭션을 롤백하고 자원을 반환한다 |
| 락 범위 최소화 | 락을 잡고 있는 시간을 최대한 줄인다 |


## 교착 상태 코드 예시 (Java)

```java
// 교착 상태 발생: 두 스레드가 서로 다른 순서로 락 획득
Thread thread1 = new Thread(() -> {
    synchronized (lockA) {          // lockA 획득 후
        synchronized (lockB) { }    // lockB 대기
    }
});

Thread thread2 = new Thread(() -> {
    synchronized (lockB) {          // lockB 획득 후
        synchronized (lockA) { }    // lockA 대기 → 교착!
    }
});
```

```java
// 해결: 두 스레드가 같은 순서로 락 획득
Thread thread1 = new Thread(() -> {
    synchronized (lockA) {
        synchronized (lockB) { }
    }
});

Thread thread2 = new Thread(() -> {
    synchronized (lockA) {          // 순서를 lockA → lockB 로 통일
        synchronized (lockB) { }
    }
});
```

# 기아 상태 (Starvation)

> 운영체제에서 특정 프로세스나 스레드가 자원을 장시간 할당받지 못하여 실행되지 못하는 상태
> 


## 왜 알아야 하는가?

공정한 스케줄링과 시스템 자원 분배를 보장하기 위해서. 기아 상태는 "내 차례가 계속 오지 않는 문제"다.


## 해결 방법

| 해결 방법 | 설명 | 예시 |
| --- | --- | --- |
| Aging (에이징) 기법 | 대기 시간이 길어질수록 우선순위를 점진적으로 증가시켜 실행 기회를 보장 | 10초마다 우선순위 1단계 증가 |
| 타임 슬라이스 (Round Robin) | 각 프로세스에게 일정한 CPU 실행 시간을 부여하여 모든 프로세스가 최소한의 실행 시간을 보장 | 모든 프로세스에 10ms씩 CPU 할당 |
| 최대 대기 시간 설정 | 특정 프로세스가 일정 시간 이상 대기하면 강제로 실행 기회를 부여 | 30초 이상 대기 시 CPU 강제 할당 |

참고

- 공정한 락(Fair Lock)은 오래 기다린 스레드가 먼저 락을 얻도록 보장하지만, 누가 언제 도착했는지 추적하는 비용이 발생한
- 불공정 락은 더 저렴하게 운영되지만 기아 상태의 원인이 될 수 있다


## 교착 상태 vs 기아 상태

| 구분 | 교착 상태 (Deadlock) | 기아 상태 (Starvation) |
| --- | --- | --- |
| 정의 | 둘 이상의 프로세스가 서로 상대가 점유한 자원을 기다려 무한 대기에 빠지는 상황 | 하나의 프로세스가 자원을 얻지 못하고 계속 대기하는 상태 |
| 발생 원인 | 상호배제·점유대기·비선점·순환대기 4가지 조건이 동시 충족 | 우선순위 스케줄링 등에서 낮은 우선순위 작업이 계속 밀려 자원을 할당받지 못함 |
| 특징 | 관련 프로세스들이 **서로** 대기하므로 전체가 멈춤 | 특정 프로세스만 **일방적으로** 무한 대기 |
| 해결 기법 | 자원 할당 순서 준수, 타임아웃, 롤백 | Aging, 타임 슬라이스 보장 (Round Robin) |

# 세마포어 (Semaphore)

> 공유 자원에 접근할 수 있는 "허가권(permit)"의 개수를 관리하는 동기화 방법
> 


## 왜 알아야 하는가?

| 이유 | 설명 |
| --- | --- |
| 효율적인 자원 관리 | 한정된 자원(DB 커넥션, 스레드 등)이 동시에 너무 많은 작업에 의해 사용되면 장애나 성능 저하가 발생한다. 세마포어로 동시 접근 수를 제한한다. |
| 병렬 처리 제어 | 경쟁 상태를 방지하고 데이터 무결성을 유지할 수 있다. |
| 상황에 맞는 도구 선택 | DB 커넥션 풀, 스레드 풀, API 호출 제한 등 실무 문제를 해결하는 데 직접 활용된다. |


## 핵심 개념

| 개념 | 설명 |
| --- | --- |
| S | 현재 공유 자원에 접근할 수 있는 허가권의 수 |
| P | 세마포어 값을 감소시킴. S > 0이면 접근 허용, S = 0이면 대기 |
| V | 세마포어 값을 증가시킴. 대기 중인 스레드가 있으면 하나를 깨움 |

```java
semaphore.acquire(); // P(wait): 허가권 획득
try {
    // 공유 자원 사용
} finally {
    semaphore.release(); // V(signal): 허가권 반환
}
```


## 종류

| 구분 | 이진 세마포어 (Binary Semaphore) | 카운팅 세마포어 (Counting Semaphore) |
| --- | --- | --- |
| 값의 범위 | 0 또는 1 | 0 이상의 정수 |
| 사용 목적 | 단일 자원 보호 | 다중 자원 접근 제어 |
| 예시 | 단일 파일 접근, 단일 디바이스 제어 | DB 커넥션 풀, 네트워크 포트 제한, 병렬 처리 작업 수 제어 |
| 특징 | 뮤텍스와 유사하지만 소유권 개념이 없음 | 사용 가능한 자원의 수를 카운트하여 관리 |


## 뮤텍스 vs 세마포어

| 구분 | 뮤텍스 | 세마포어 |
| --- | --- | --- |
| 핵심 목적 | 하나의 자원에 대한 배타적 접근 | N개의 허가권으로 동시 접근 수 제한 |
| 값 | 잠김 / 열림 | 0 이상의 정수 |
| 소유권 | 락을 획득한 스레드가 해제 | permit 반환 개념이며 소유권이 약함 |
| 비유 | 화장실 열쇠 1개 | 식당 입장권 N장 |
| 대표 예시 | 계좌 잔액 수정, 공유 변수 수정 | DB 커넥션 풀, API rate limit |


## 주의할 점

| 항목 | 설명 |
| --- | --- |
| permit 반환 누락 | `acquire` 후 `release`를 누락하면 허가권이 고갈되어 모든 스레드가 대기 상태에 빠진다. 반드시 `finally` 블록에서 반환할 것 |
| 무한 대기 | S = 0인 상태가 지속되면 대기 스레드가 영원히 깨어나지 못한다. 타임아웃과 함께 사용을 고려한다. |
| 잘못된 permit 수 설정 | permit 수가 너무 많으면 자원 보호 효과가 없고, 너무 적으면 처리량이 떨어진다. 실제 자원 한계에 맞게 설정해야 한다. |
