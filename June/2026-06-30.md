# 1. Portainer

## 핵심 개념

> Docker와 Kubernetes 같은 컨테이너 환경을 웹 기반 GUI로 손쉽게 관리할 수 있도록 해주는 관리 도구
> 
> 
> Docker는 기본적으로 `docker ps`, `docker logs`, `docker restart`, `docker exec -it` 같은 CLI 명령으로 동작한다. CLI는 잘 동작하고 자동화에도 편하지만, 운영자가 컨테이너를 여러 개 관리하기 시작하면 한계가 드러난다.
> 

## 왜 필요한가 (CLI만 쓸 때의 문제)

| 문제 | 상황 | 결과 |
| --- | --- | --- |
| 상태 파악이 어려움 | 컨테이너가 많아지면 `docker ps`, `docker logs`를 반복 실행 | 현재 서비스 상태를 한눈에 보기 어려움 |
| 명령어 실수 | 컨테이너 이름·포트·볼륨·네트워크를 잘못 지정 | 잘못된 컨테이너 삭제·재시작 가능 |
| 운영 접근성이 낮음 | CLI 경험이 적은 팀원도 운영 작업이 필요 | 운영 업무가 특정 인력에게 집중 |
| 여러 서버 관리가 불편함 | EC2가 여러 대이고 각각 Docker 설치 | 서버마다 SSH 접속 후 별도 명령 실행 |
| 설정이 눈에 안 보임 | 볼륨·네트워크·환경 변수·포트 설정이 분산 | 장애 원인 파악이 느려짐 |

## Portainer의 동작 방식

- Docker Engine + API, Portainer Agent를 통해 Docker의 연결 상태를 읽고, Docker 명령어를 대신 실행한다.
- GUI 기반으로 **버튼 클릭 → Docker 명령어로 전환**해서 전달한다.
- Portainer는 Docker를 대체하는 것이 **아니라**, Docker를 GUI 기반으로 쉽게 사용하게 해주는 도구다.

## Portainer 기능

| 기능 | 설명 | Docker CLI 대응 |
| --- | --- | --- |
| 컨테이너 조회 | 실행·중지·종료 상태 확인 | `docker ps -a` |
| 시작·중지·재시작 | 버튼으로 컨테이너 제어 | `docker start`, `stop`, `restart` |
| 로그 확인 | 브라우저에서 로그 조회 | `docker logs -f` |
| 콘솔 접속 | 컨테이너 내부 셸 접속 | `docker exec -it` |
| 이미지 관리 | 조회·Pull·삭제 | `docker images`, `pull`, `rmi` |
| 볼륨 관리 | 생성·연결·조회 | `docker volume ...` |
| 네트워크 관리 | 연결 상태 확인 | `docker network ...` |
| Stack 관리 | Compose 기반 서비스를 화면에서 배포 | `docker compose up -d` |
| 자원 상태 확인 | CPU·메모리·네트워크·I/O 사용량 | `docker stats`, `top` |

## Docker Desktop vs Portainer

둘 다 Docker를 GUI로 관리하는 툴이지만, Docker Desktop은 로컬에서, Portainer는 서버 환경에서 관리한다.

| 구분 | Docker Desktop | Portainer |
| --- | --- | --- |
| 주 목적 | 개인 로컬 개발 환경 | 서버·운영 환경 관리 |
| 주 설치 위치 | 개발자 개인 PC | EC2, 온프레미스, 클라우드 VM |
| 관리 범위 | 보통 내 PC의 Docker | 여러 Docker 서버, Swarm, Kubernetes |
| 주요 사용자 | 개인 개발자 | 개발팀, 운영팀, DevOps |
| 핵심 가치 | 개발 편의성 | 운영 가시성, 원격 관리, 표준화 |
| 대표 상황 | 로컬 앱 실행·테스트 | EC2 컨테이너 상태 확인·재시작·로그 분석 |

## Portainer 구조

| 구성 요소 | 역할 |
| --- | --- |
| **Portainer Server** | 웹 UI와 관리 기능을 제공하는 중심 서버 |
| **Docker Engine** | 실제 컨테이너·이미지·볼륨·네트워크를 실행·관리하는 엔진 |
| **Portainer Agent** | 원격 Docker 서버의 정보를 Portainer Server에 제공 |
| **Edge Agent** | 외부에서 직접 접근하기 어려운 원격 환경을 관리할 때 사용 |

## 설치 전 알아야 하는 개념

### Docker Socket

리눅스에서 Docker CLI는 Docker 데몬과 통신해야 하며, 그 경로가 아래다.

```bash
/var/run/docker.sock
```

- 실제로는 Docker API와 통신하기 위한 소켓이다.
- Portainer 컨테이너에서 EC2의 Docker Socket을 연결하면, Portainer가 해당 Docker Engine을 제어할 수 있다.

### 🔥 보안적으로 위험할 수 있다

Docker Socket으로 연결되면 Portainer가 해당 Docker Engine을 강력하게 제어할 수 있다.

- 컨테이너 생성·중지·삭제
- 호스트 디렉터리 마운트
- 민감한 환경 변수 조회 가능성
- Docker Engine 설치 서버에 큰 권한으로 접근 가능

> **🔥 중요 🔥** Portainer 컨테이너는 절대로 외부 인터넷에 노출하면 안 된다. 항상 네트워크 접속 가능 영역을 줄여놓아야 한다.
> 
> - Private subnet (VPN을 통해서만 접근)
> - 특정 IP 대역에서만 접근 허용

## 실무에서 언제 사용하는가

### 1. 운영 가시성 확보

장애가 발생하면 가장 먼저 "지금 어떤 컨테이너가 죽어있는가"를 봐야 한다. Portainer로 확인할 수 있는 것:

- 컨테이너 실행 중 / 중지 / 삭제 상태
- 최근 재시작 여부 (문제 컨테이너는 재시작 시도 횟수가 비정상적으로 높다)
- 컨테이너가 사용 중인 이미지 버전 (예: 백엔드 이미지 1.0.0 vs 1.0.1)
- CPU·RAM 자원 사용량

### 2. 개발자–DevOps 협업

Portainer는 Docker를 보기 쉽게 만들어준다. 개발자는 코드를 만들고 CI/CD 파이프라인을 돌려 테스트를 통과시키고, DevOps 팀은 실제 배포가 안정적으로 되는지를 확인한다.

### 3. 소규모 운영

대형 중앙 집중 로그·메트릭 수집 툴은 무겁고 관리가 까다롭다. EC2를 심플하게 운영할 때는 Grafana 같은 대시보드까지는 무거우니, 간단하게 Portainer로 설정한다.

## 주의사항

1. **GUI에서 바꾸면 실제로 변경된다** — "안 쓰는 이미지네, 그냥 지우지 뭐"가 실제 삭제로 이어진다.
2. **보안 사항 준수** — Private subnet, VPN/Bastion Host, Admin 계정 공유 관리.
3. **RBAC 접근 제어** — 사용자별 권한 관리(예: 누구는 조회만, 누구는 로그만). 삭제 사고 시 책임 소재를 위해서도 권한 분리가 필요하다.

## Portainer 정리

| 구분 | 핵심 |
| --- | --- |
| 역할 | Docker를 관리하는 GUI, 컨테이너 운영 툴 |
| 관리 대상 | Container, Image, Volume, Network |
| 장점 | 가시성, 분산된 로그 집중화, 버튼으로 간단한 제어 |
| 주의사항 | Docker Socket 권한이 매우 강함, 인터넷에 노출 금지 |
| 실무 활용 | 장애 확인, 컨테이너 재시작, 소규모 서버 운영 |

# 2. Volume

## 핵심 개념

> 컨테이너 간 데이터 공유 및 영속성을 제공하기 위해, 호스트 파일 시스템에 생성되는 독립적인 저장소
> 
> 
> 컨테이너는 비영속적이다. 컨테이너 내부에 데이터를 저장하면 컨테이너를 삭제할 때 함께 사라진다.
> 

## 컨테이너 안에 파일을 저장하면 어떻게 될까

```bash
# 데이터 영속성이 필요한 컨테이너 생성
docker run -d --name mysql-test mysql:8.0
# 컨테이너 내부 경로 /var/lib/mysql 에 데이터 저장

docker rm mysql-test
# 컨테이너 내부 저장 공간도 함께 삭제된다
```

중지·시작까지는 데이터가 살아있지만, 컨테이너를 삭제하면 데이터도 같이 사라진다.

## 왜 이렇게 되는가

- 컨테이너는 이미지 위에 **쓰기 가능한 임시 레이어**를 얹어서 동작한다.
- 실행 중 만든·수정한 파일은 "이미지"가 아니라 컨테이너의 읽기·쓰기 레이어에 저장된다.
- 이 쓰기 레이어가 **컨테이너 생명 주기에 묶여 있다.**

| 상황 | 데이터 |
| --- | --- |
| 컨테이너 실행 중 | 내부 변경 사항 유지 |
| stop | 컨테이너가 남아 있으면 데이터도 남음 |
| start | 기존 컨테이너라면 데이터 유지 |
| rm | 쓰기 레이어도 삭제 |
| 새 컨테이너 생성 | 이전 컨테이너 데이터는 이어지지 않음 |

## 왜 이런 구조로 만들었나

이 비영속 구조는 의도된 것이다. 컨테이너를 빠르게 만들고 버릴 수 있어야 하기 때문이다.

| 목적 | 설명 |
| --- | --- |
| 빠른 생성 | 컨테이너를 빠르게 만들 수 있어야 함 |
| 빠른 삭제 | 필요 없으면 쉽게 제거 가능 |
| 동일한 실행 환경 | 이미지로부터 같은 환경을 재현 |
| 일회성 실행 가능 | 테스트·배치·임시 작업에 적합 |
| 배포 단순화 | 서버마다 설치하지 않고 이미지로 실행 |

애플리케이션 실행 환경에는 매우 좋다. 백엔드 컨테이너에 문제가 생기면 아래처럼 지우고 다시 띄우면 된다.

```bash
docker rm -f backend
docker run -d --name=backend backend:1.3.1
```

## Volume이 해결하는 방법

> 컨테이너 내부에 데이터를 쓰지 않고, 컨테이너 외부(Host OS)에 데이터를 작성한다.
> 

`/var/lib/mysql`에 저장하는 것처럼 보이지만, 실제 데이터는 Host OS의 Docker Volume에 저장된다. 그래서 컨테이너를 삭제하고 다시 만들어도 볼륨은 호스트 OS에 그대로 남아 있다.

```bash
docker run -v mysql-data:/var/lib/mysql mysql:8.3
```

| 부분 | 의미 |
| --- | --- |
| `mysql-data` | Docker Volume 이름 |
| `/var/lib/mysql` | 컨테이너 내부 경로 |
| `:` | 왼쪽 저장소를 오른쪽 경로에 연결 |

## Volume 사용 이유

| 사용 이유 | 설명 |
| --- | --- |
| 데이터 영속성 | 컨테이너를 삭제·재생성해도 데이터 유지 |
| 재배포 안전성 | 새 컨테이너를 띄워도 기존 데이터 재사용 |
| 데이터 공유 | 여러 컨테이너가 같은 데이터 공유 가능 |
| 저장 위치 관리 | 호스트 경로를 직접 지정하지 않아도 Docker가 관리 |
| 운영 안정성 | DB·업로드 파일·설정 등 중요 데이터 보호 |

## 기본 사용 방법

```bash
# 볼륨 생성
docker volume create mysql-data

# 볼륨 목록
docker volume ls

# 볼륨 내부 정보
docker volume inspect mysql-data

# 볼륨 컨테이너 연결
docker run -d \
  --name mysql-test \
  -e MYSQL_ROOT_PASSWORD=1234 \
  -v mysql-data:/var/lib/mysql \
  mysql:8.0
```

## 현업에서 언제 사용하나

1. **데이터베이스 컨테이너** — 영속성이 필요하므로 (MySQL, Redis 등)
2. **파일 업로드 임시 폴더** — EC2 내부 WAS 컨테이너 여러 개가 공용으로 보는 업로드 임시 저장 폴더
3. **설정 파일 마운트** — Nginx 설정, Spring env 파일
4. **로그 보관** — 컨테이너 로그는 기본적으로 내부에 생성되어, 컨테이너 삭제 시 함께 지워진다. 오류로 컨테이너가 삭제될 때 로그가 사라지는 것을 방지

## Volume 정리

| 구분 | 핵심 |
| --- | --- |
| 무엇 | 호스트 파일 시스템에 생성되는 독립 저장소 |
| 왜 필요 | 컨테이너 쓰기 레이어는 생명 주기에 묶여 있어 비영속적 |
| 해결 방식 | 데이터를 컨테이너 외부(Host OS)에 저장 |
| 주요 용도 | DB, 업로드 임시 폴더, 설정 파일, 로그 보관 |
