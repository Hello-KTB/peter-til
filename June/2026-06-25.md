# 1. AWS Lambda

## 핵심 개념

> 서버를 직접 관리하지 않고 코드만 실행할 수 있는 **서버리스** 컴퓨팅 서비스
> 

서버리스라고 해서 서버가 없는 건 아니다. 서버 운영의 상당 부분을 AWS가 대신 책임지는 방식이다.

## EC2 vs Lambda

| 구분 | EC2 | Lambda |
| --- | --- | --- |
| 실행 방식 | 서버를 항상 켜두고 요청 처리 | 이벤트 발생 시에만 실행 |
| 과금 방식 | 시간 단위 (요청 없어도 과금) | 실행 시간만큼만 과금 |
| 상태 관리 | 디스크/파일 관리 용이 | 실행 환경이 사라지면 상태도 사라짐 |
| 확장성 | 직접 설정 필요 | 자동 확장 |

## 이벤트 트리거 종류

| 이벤트 소스 | Lambda 사용 예시 |
| --- | --- |
| API Gateway | HTTP API 요청 처리 |
| S3 | 이미지 업로드 후 썸네일 생성 |
| EventBridge | 매일 오전 9시 정기 작업 |
| SQS | 비동기 메시지 처리 |
| DynamoDB Streams | 데이터 변경 감지 후 후속 처리 |
| CloudWatch Alarm | 장애 발생 시 자동 복구 작업 |

## Lambda 실행 순서

1. **이벤트 발생** — API Gateway, S3 업로드 등
2. **실행 환경(Execution Environment) 준비** — 메모리/CPU 자원, Runtime, 함수 코드, /tmp 임시 저장소, 환경변수 포함
3. **Init 단계** — 함수 코드 + Lambda Layer 다운로드 → Runtime 초기화 → 핸들러 바깥 코드 초기화
4. **Invoke 단계** — 핸들러 함수 실행

## Cold Start vs Warm Start

- **Cold Start**: 새 실행 환경을 만들고 Init 단계까지 수행 → 처리 시간이 상대적으로 길다
- **Warm Start**: 기존 실행 환경 재사용, Init 단계 생략 → 응답 시간이 짧다
- 실행 환경을 오래 유지하면 그만큼 과금되기 때문에, **Warmup(헬스체크 요청)**으로 환경을 살려두는 방식을 사용하기도 한다

## Lambda가 적합한 use case

1. **파일 업로드 처리** — S3 업로드 트리거 → 썸네일 생성, 포맷 변환, 바이러스 검사
2. **예약 작업 (배치)** — 매일 새벽 임시 데이터 삭제, 매주 리포트 생성
3. **비동기 작업 처리** — 주문 생성 후 이메일/슬랙 알림, 통계 갱신 등
4. **극초기 서비스 API** — 트래픽이 거의 없을 때 EC2 대신 사용 가능

## Lambda 설정 주요 항목

| 항목 | 범위 / 기본값 | 참고 |
| --- | --- | --- |
| 메모리 | 128MB ~ 10GB | 메모리 늘리면 CPU도 자동 증가 |
| 타임아웃 | 기본 3초, 최대 900초(15분) | 작업 특성에 맞게 반드시 설정 |

## 실무 주의사항

- **SRP 원칙** — 함수 하나에 하나의 역할만. 독립적인 실패와 처리가 필요한 단위로 분리
- **Cold Start 대응** — 가벼운 런타임(Node.js/Python) 사용, Provisioned Concurrency, 헬스체크 유지
- **동시성 문제** — 람다가 RDS에 직접 연결하면 커넥션이 폭발할 수 있음 → 중간에 큐를 두어 동시 실행 수를 제한
- **15분 제한** — 대용량 배치, 웹소켓, 장시간 실행 작업에는 부적합
- **모든 백엔드를 Lambda로 만들면 안 됨** — DB 연결을 지속적으로 유지해야 하는 API, 복잡한 가입 프로세스 등은 EC2가 더 적합

## 핵심 개념 정리

| 개념 | 설명 |
| --- | --- |
| Lambda | 이벤트가 발생할 때 코드를 실행하는 서버리스 컴퓨팅 서비스 |
| Serverless | 서버가 없는 것이 아니라 서버 운영을 AWS가 대신하는 방식 |
| Trigger | Lambda를 실행시키는 이벤트 소스 |
| Handler | 이벤트를 받아 실제 로직을 처리하는 함수 |
| Cold Start | 새 실행 환경 초기화로 첫 요청이 느려질 수 있는 현상 |
| Concurrency | 동시에 실행되는 Lambda 수 (계정 기본 한도 1,000개) |
| `/tmp` | 임시 저장소이며 영구 저장소가 아님 |

# 2. CloudWatch

## 핵심 개념

> CloudWatch의 목적은 그래프를 보는 것이 아니다.
**"장애를 더 빨리 발견하고 복구하기 위해서"** — 서비스의 안정성을 높이는 것
> 

CloudWatch 없이는 사용자 리포트가 올라온 뒤에야 문제를 인지하게 된다. CloudWatch는 그 전에 먼저 감지하는 것이 목표다.

## CloudWatch 핵심 기능

| 기능 | 역할 | 예시 |
| --- | --- | --- |
| Metrics | 시간에 따른 숫자 지표 확인 | CPU, 요청 수, 오류 수 |
| Logs | 시스템과 애플리케이션 기록 저장 | Spring ERROR 로그, Nginx 로그 |
| Alarms | 조건 충족 시 알림 또는 자동 대응 | CPU 80% 초과 시 이메일 |
| Dashboards | 여러 지표를 한 화면에서 확인 | EC2·ALB·RDS 상태 한눈에 보기 |
| Logs Insights | 로그를 쿼리로 검색·분석 | 5xx 오류가 많은 API 찾기 |

## Metrics — 자주 보는 지표

| 서비스 | 메트릭 | 의미 |
| --- | --- | --- |
| EC2 | `CPUUtilization` | CPU 사용률 |
| EC2 | `StatusCheckFailed` | 인스턴스/네트워크 상태 문제 |
| ALB | `HTTPCode_Target_5XX_Count` | 백엔드 서버 5xx 오류 |
| ALB | `TargetResponseTime` | 백엔드 응답 시간 |
| ALB | `HealthyHostCount` | 정상 Target 수 |
| RDS | `DatabaseConnections` | DB 연결 수 |
| RDS | `FreeStorageSpace` | 남은 DB 스토리지 |
| ElastiCache | `CacheHits` / `CacheMisses` | 캐시 효율 |

## Logs

메트릭은 "문제가 발생했다"는 것을 알려주고, 로그는 "왜 발생했는지"를 기록한다. CloudWatch Logs는 여러 EC2 인스턴스의 로그를 **중앙 집중화**해서 한 곳에서 확인할 수 있게 한다.

## Alarms

알람은 단순한 이상 감지가 아니다. **"지금 당장 사람이 대응하지 않으면 큰일 나는" 상황에만 울려야 한다.** 알람이 자주 울리면 무감각해지기 때문에 임계값 설정에 신중해야 한다.

# 3. Observability (옵저빌리티)

## 모니터링 vs 옵저빌리티

| 구분 | 설명 |
| --- | --- |
| 모니터링 | 미리 예상한 문제를 기준값으로 감지 ("CPU 80% 넘으면 알림") |
| 옵저빌리티 | 예상하지 못한 문제도 데이터로 원인을 추론할 수 있는 능력 |

## 옵저빌리티의 3가지 축

| 데이터 | 핵심 질문 | 대표 예시 |
| --- | --- | --- |
| Metrics | 지금 상태가 어떤가? | CPU, 오류율, 요청 수, 응답 시간 |
| Logs | 어떤 일이 발생했는가? | Exception, 에러 메시지, 요청 로그 |
| Traces | 어디에서 시간이 오래 걸렸는가? | API → DB → 외부 API 호출 시간 |

## Trace 예시

사용자가 "주문이 느리다"고 느낄 때, 메트릭만으로는 원인을 알 수 없다. Trace를 통해 병목 지점을 특정할 수 있다.

```
전체 요청: 3.2초
├─ Spring Boot 처리: 100ms
├─ RDS 쿼리: 20ms
└─ 외부 결제 API 호출: 3000ms  ← 원인
```

Trace ID를 요청마다 부여하면, 여러 서비스를 거치는 요청도 하나의 흐름으로 추적할 수 있다.

## 실무에서 옵저빌리티 높이기

**1. 로그를 구조화한다 (JSON 형식)**

```json
{
  "timestamp": "2026-06-25T10:12:20+09:00",
  "level": "ERROR",
  "service": "community-api",
  "traceId": "ab12cd34",
  "path": "/api/posts",
  "status": 500,
  "message": "Database connection timeout"
}
```

**2. 핵심 API의 응답 시간과 오류율을 수집한다**

모든 API를 처음부터 수집할 필요는 없다. 회원가입, 결제, 게시글 작성 등 서비스 핵심 기능부터 시작한다.

## 옵저빌리티가 높다는 기준

아래 질문에 데이터로 답할 수 있으면 옵저빌리티가 높은 것이다.

- 지금 서비스는 정상인가?
- 어떤 기능이 실패하고 있는가?
- 언제부터 문제가 시작됐는가?
- 어느 서버 또는 API가 문제인가?
- DB, Redis, 외부 API 중 어디가 병목인가?
- 최근 배포와 관련이 있는가?

## 핵심 개념 정리

| 개념 | 핵심 |
| --- | --- |
| CloudWatch | AWS 운영 상태를 확인하고 대응하는 서비스 |
| Metrics | CPU, 요청 수, 오류율 같은 숫자 지표 |
| Logs | 오류와 사건의 상세 기록 |
| Alarms | 기준 초과 시 알림과 자동 대응 |
| Dashboard | 여러 지표를 한 화면에서 확인 |
| Observability | 메트릭·로그·트레이스로 시스템 원인을 추론하는 능력 |
| CloudWatch Agent | EC2 내부 메모리·디스크·로그 수집 |
| CloudTrail | AWS 작업 이력과 감사 기록 |
