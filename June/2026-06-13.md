# 1. 필터

**서블릿**: 자바를 사용해 웹 페이지를 동적으로 생성하는 프로그램

**서블릿 컨테이너**: 서블릿을 담아두고 관리하는 주체. 라이프 사이클 관리 등의 역할 담당

**디스패처 서블릿**: 스프링 Web MVC의 핵심으로, 개발자가 구현 로직에만 집중할 수 있게 해줌

---

### 필터란?

> 서블릿 컨테이너가 디스패처 서블릿으로 요청을 전달하기 전/후, URL 패턴에 맞는 모든 요청에 대해 부가 처리를 수행하는 객체
> 

**특징**

- 서블릿, 정적 컨텐츠에 대한 요청/응답을 필터링하는 객체
- 서블릿 컨테이너(톰캣 등)가 제공하는 기능
- 스프링 프레임워크와 무관하게 동작 가능
- 필터 체인으로 구성됨

**주요 용도**

- 공통 보안, 인증/인가
- 모든 요청에 대한 로깅, 감사
- 이미지·데이터 압축 및 문자열 인코딩
- 스프링과 분리되어야 하는 기능

---

### Filter 인터페이스 메서드

| 메서드 | 설명 |
| --- | --- |
| `init()` | 필터 객체 초기화. 웹 컨테이너에 의해 1회 호출 |
| `doFilter()` | URL 패턴에 맞는 요청이 디스패처 서블릿에 전달되기 전 실행. `filterChain.doFilter()`로 다음 필터 호출 |
| `destroy()` | 필터 객체 제거 및 자원 반환. 웹 컨테이너에 의해 1회 호출, 이후 `doFilter()`에 의해 처리되지 않음 |

---

### 필터 체인

- 서블릿 컨테이너가 관리하는 필터들의 연결 구조
- 디스패처 서블릿 도달 전, 필요한 여러 필터를 순차적으로 거치도록 함
- 필터 등록 순서에 따라 처리 순서 결정
- 각 필터에서 `doFilter()` 호출로 다음 필터 전달

## 2. 인터셉터

> 디스패처 서블릿이 컨트롤러를 호출하기 전/후에 개입하는 스프링 제공 기술
> 

**특징**

- 스프링이 제공하는 기술
- 스프링 컨텍스트에서 동작
- 스프링 예외 처리 지원
- 요청과 응답을 참조, 가공 가능 (직접 조작은 불가)

**주요 용도**

- 세부적인 보안, 인증/인가
- API 호출에 대한 로깅, 감사
- 컨트롤러로 넘겨주는 정보 가공

---

### HandlerInterceptor 메서드

| 메서드 | 설명 |
| --- | --- |
| `preHandle()` | 컨트롤러 호출 전 실행. 반환 타입 `boolean` — `true`면 다음 단계 진행, `false`면 작업 중단 |
| `postHandle()` | 컨트롤러 호출 후 실행. 컨트롤러 하위에서 예외 발생 시 호출되지 않음 |
| `afterCompletion()` | 모든 작업 완료 후 실행. 예외 발생 여부와 관계없이 반드시 호출됨 |

---

## 3. 필터 vs 인터셉터 비교

| 구분 | 필터 | 인터셉터 |
| --- | --- | --- |
| 관리 주체 | 서블릿 컨테이너 | 스프링 컨테이너 |
| 스프링 예외 처리 | 불가 | 가능 |
| Req/Res 객체 조작 | 가능 | 불가 |
| 주요 용도 | 공통 보안 및 인증/인가, 전체 요청 로깅, 인코딩·압축 | 세부 인증/인가, API 로깅, 컨트롤러 데이터 가공 |

### 필터 vs 인터셉터 vs AOP 한 줄 정리

- **필터**: 전역 로직 (인코딩, XSS 필터링 등)
- **인터셉터**: 컨트롤러 관련 로직 (요청별 공통 데이터 주입 등)
- **AOP**: 스프링 빈 메서드 관련 로직 (트랜잭션 등)

## 4. 스프링 예외 처리

### try-catch

- 단순한 프로그램에서는 적합
- 백엔드 서비스에서는 지양
    - 코드 중복
    - 가독성 저하
    - 유지보수 어려움
    - 예외 처리 흐름 불명확

---

### BasicErrorController

- 예외 발생 시 기본으로 호출되는 컨트롤러 (별도 설정 없을 때)
- 에러 요청을 다시 WAS에 전달
- JSON으로 응답하나 `timestamp`, `status`, `error` 등 클라이언트에게 유용하지 않은 정보 포함
- 유의미한 에러 응답 전달이 어려움

---

### @ResponseStatus

- 에러 HTTP 상태를 변경하는 어노테이션
- 사용 위치: Exception 클래스, `@ExceptionHandler`와 함께, `@RestControllerAdvice`와 함께
- **한계점**
    - 에러 응답 내용 수정이 어려움
    - 예외 클래스와 강하게 결합
    - 외부에서 정의한 Exception 클래스에는 사용 불가

---

### ResponseStatusException

스프링 5에서 추가된 예외 응답 클래스. `HttpStatus`와 함께 선택적으로 reason, cause 추가 가능

**장점**

- 예외 처리를 빠르게 적용 가능
- `HttpStatus` 설정으로 예외 클래스와의 결합도 낮음
- 불필요한 예외 클래스를 많이 만들지 않아도 됨

**한계점**

- 직접 예외 처리 코드를 작성해야 함
- 일관된 예외 처리가 어려움
- 예외 처리 코드 중복 발생

---

### @ExceptionHandler

매우 유연하게 에러 처리 가능

**사용 가능 위치**

- 컨트롤러 메서드
- `@ControllerAdvice` / `@RestControllerAdvice`가 있는 클래스의 메서드

**특징**

- `@ResponseStatus`와 결합 가능
- 에러 응답을 자유롭게 구성 가능 (code, message, errors 등)
- 컨트롤러 내부에서 사용 시, 특정 컨트롤러에서만 발생하는 예외 처리 가능
- 단, 여러 컨트롤러에 분산되면 예외 처리 코드 중복 발생

---

### @RestControllerAdvice (권장)

`@ExceptionHandler`를 전역으로 적용하기 위한 방법. `@ControllerAdvice` + `@ResponseBody`

**이점**

- 하나의 클래스로 모든 컨트롤러의 예외를 전역 처리
- 일관성 있는 에러 응답 전달 가능
- 별도의 try-catch 없이 코드 가독성 향상

**주의사항**

- 프로젝트당 하나의 `ControllerAdvice`로 관리 권장
- 직접 구현한 Exception 클래스는 한 곳에서 관리

## 5. 파일 처리

### 이미지 업로드 시나리오

- 이미지 파일을 업로드한다
- 업로드된 이미지 파일에 접근한다

---

### 개략적 설계

**지원 파일 형태**

- `jpg`, `png`, `webp` 지원
- 고용량 파일 및 기타 이미지 형식은 미지원
- 파일 크기 제한: 10MB

**압축 및 변환 전략**

지원 파일은 모두 `jpg`와 `webp` 두 가지 포맷으로 변환 후 저장. 브라우저가 webp를 지원하면 webp, 아니면 jpg 제공

| 유형 | 압축률 |
| --- | --- |
| 프로필 사진 | 60% |
| 게시글 원본 | 20% |
| 게시글 썸네일 | 60% |

**데이터 저장**

- 파일 자체: 스토리지(로컬 또는 클라우드)에 저장
- 파일 메타데이터: RDB의 `images` 테이블에 저장
    - 저장 항목: 스토리지 접근 경로, 썸네일 접근 경로, 생성일, 활성 여부
    - 비활성 이미지는 배치 프로그램으로 주기적 삭제

**처리 흐름**

```
클라이언트 → Web Server → WAS → Storage (파일 저장)
                              ↕
                              DB (파일 정보 저장)
```

---

### 코드 책임 설계

```
controller/
  └─ ImageController     : 이미지 전달받는 외부 API 컨트롤러
service/
  ├─ ImageService        : 비즈니스 로직 (DB + 파일 서비스 호출)
  ├─ FileService         : 파일 저장/로드 책임 (인터페이스)
  └─ ImageProcessor      : 변환/압축 책임
repository/
  └─ ImageRepository     : DB 접근
domain/
  └─ ImageEntity         : 이미지 메타정보 (파일명, 타입, 경로 등)
```

> 클래스 단일 책임 원칙: 각 클래스는 하나의 명확한 책임만 가진다.
> 

**FileService 인터페이스 구조**

파일 기능은 스토리지에 의존적이지 않아야 한다. 향후 클라우드 확장을 고려해 인터페이스로 추상화.

```
FileService (인터페이스)
    ├─ LocalFileService   : 로컬 파일 저장
    └─ CloudFileService   : 클라우드 파일 저장
```

**전체 처리 흐름**

```
ImageController → ImageService → LocalFileService
                       ↓
                 ImageProcessor
                       ↓
               ImageRepository → DB
```

## 6. 고아 이미지 (Orphan Image)

더 이상 애플리케이션에서 참조하지 않지만 스토리지에는 여전히 남아 있는 데이터

**문제점**

- 불필요한 저장 공간 차지
- 스토리지 비용 증가
- 장기적인 시스템 관리 혼란 유발
