# 1. Spring & Spring Boot

> Spring : 자바 애플리케이션에서 객체 생성과 의존성 관리를 자동화해 구조를 단순하고 유연하게 만드는 프레임워크

Spring Boot : 스프링 애플리케이션을 빠르고 쉽게 개발할 수 있도록 설정과 배포를 자동화한 프레임워크
> 

## Spring의 주요 특징

- AOP : 공통 관심사와 비즈니스 로직 분리
- IoC / DI : 제어 역전, 의존성 주입
- POJO : 자바로만 이루어져 있는 프레임워크
- Bean : 스프링 프레임워크에서 관리하는 객체

## Spring Boot 핵심 기능

- Auto_Configuratoin : 클래스패스에 있는 라이브러리와 의존성을 바탕으로 개발자가 설정해야 할 수 많은 초기 Bean과 설정을 알아서 구성해 주는 메커니늠
- Starter Dependencies : 특정 기술을 구현하는 데 필요한 라이브러리들을 모아둔 그룹
- Embedded Server : 외부 WAS를 따로 띄울 필요 없이 자체 내장된 서버로 동작

## 왜 탄생했나?

- 기본 프로젝트는 설정이 복잡했음
- 의존성 관리와 배포를 쉽게 하기 위해 탄생

# 2. Annotation

> Annotation : 자바 코드에 메타데이터를 추가해, 컴파일러나 런타임에 특정 동작을 지시하거나 정보를 제공하는 표기 방법
> 
- 실행 로직을 갖지 않고, 프로그램 의미를 직접 바꾸지 않음
- 컴파일, 런타임 때 메타데이터가 읽혀져서 활용됨

## 왜 어노테이션을 써야 하는가?

1. 설정이 응집됨 : 기존에는 XML에 설정을 따로 작성했지만, @Entity @Id 처럼 코드와 설정이 한 곳에 모임
2. 정적, 동적 검증이 자동화 : 안 쓸 경우, if문으로 직접적으로 해야 함. 

코드와 매핑 정보를 한 곳에서 관리해 가독성과 유지보수성을 높이고, 컴파일 시점에 오류를 검출해 안정성을 확보하기 위해서

# 3. ORM

> 자바의 객체와 데이터베이스 테이블을 자동으로 연결하고 변환해, 객체 지향 코드로 데이터를 조작할 수 있게 해주는 기술
> 

## 왜 사용하는가?

- SQL 중심으로 작성 → 비즈니스 로직보다 SQL 매핑과 최적화에 더 신경쓰게됨
- ORM 이 중간에서 객체와 테이블 연결
- 객체지향과 RDB 간 간극을 줄임 → 설계의 일관성과 코드의 생산성 높아짐

## 객체지향 vs RDB

| 구분 | 객체 지향 | RDB |
| --- | --- | --- |
| 상속과 다형성 | 클래스 상속 지원 | 상속 개념 없음 |
| 연관관계 | 참조가 단방향 | 참조가 양방향 |
| 데이터 탐색 범위 | 그래프 탐색 | SQL에 따라 데이터 탐지 넓게 가능 |

# 4. JPA

> 자바 객체와 관계형 데이터베이스를 매핑하고, 객체 단위로 데이터를 저장조회할 수 있게 해주는 표준 ORM 인터페이스
> 
- JDBC를 직접 사용하지 않고도 객체를 데이터베이스에 저장하고 불러올 수 있도록 돕는 중간 계층 역할
- 객체를 JPA에게 전달시, JPA가 엔티티 구조 분석 후 필요한 SQL을 자동으로 생성

## JPA 동작 과정

개발자가 엔티티 전달 → JPA가 구조 분석 →  맞춤형 SQL 자동 생성 → JDBC로 실행

# 5. Entity

> 데이터베이스 테이블과 1:1로 매핑되어 데이터를 객체 형태로 표현하는 자바 클래스
> 

## 왜 사용하는가?

- DB 테이블은 값을 저장하는 구조 제공, BUT 데이터의 의미나 사용 규칙 못 담음
- 엔티티 클래스는 필드와 함께 데이터 제약, 연관관계, 비즈니스 로직을 한 곳에 모아둘 수 있음 → 수정 범위 줄어듦
- 엔티티는 DB의 한 행을 명확히 표현 → 객체지향적인 설계와 DB 구조 사이의 연결 고리가 됨
- 엔티티 명확히 정의 → 애플리케이션 전반의 구조가 안정적이고 일관성 있게 유지됨

## 기본 형식

```java
import jakarta.persistence.*;

@Entity
public class 클래스명 {
	
		// 필드 선언
		// ex) private Long id;
		
		protected 클래스명() {}
}
```

# 6. DTO

> 계층 간 데이터 전달을 위해 사용하는, 값만 담는 전용 객체
> 
- Getter/Setter, 생성자만 포함하고, 비즈니스 로직이나 DB 접근 기능은 전혀 가지지 않음
    - 데이터 구조 단순해짐
    - 유지보수성과 확장성 높아짐

## 왜 사용하는가?

엔티티의 내부 구조나 민감 정보를 외부에 노출하지 않고, 필요한 데이터만 안전하고 명확하게 전달하기 위해서이다.

- 전달이 필요한 데이터만 선별하여 담음
    - 외부로 나가는 데이터의 범위를 명확히 제어할 수 있음
- 데이터  형식과 구조를 상황에 맞게 변환 or 가공
    - API 요청/응답 스펙을 유연하게 설계 가능
- 계층 간 결합도 낮춤
- 장기적으로 유지보수성과 확장성 크게 높여줌

## DTO 제작 시 주의사항

- 비즈니스 로직 배제
- 소통 규격화

# 7. @Id

> 엔티티의 식별자를 지정해주는 기본 키 매핑 어노테이션
> 

## 기본 키 할당 방식

- 직접 할당 (@Id)
- 자동 생성 (@GeneratedValue)

## 사용 이유

- JPA는 엔티티 영속성 컨텍스 관리
    - 엔티티 식별을 위해 기본 키 필요
- 동일한 엔티티 여러번 조회시 동일한 인스턴스로 인식
- 변경 감지, 1차 캐시 관리, 병합 등의 기능을 정확하게 수행 가능

## 기본 키 생성 전략

1. **IDENTITY**
    - DB의 AUTO_INCREMENT를 사용하여 기본 키 생성
    - DB에 실제 삽입 후 ID를 받아옴 → **쓰기 지연 불가**, 배치 처리에 불리
2. **SEQUENCE**
    - DB에 존재하는 시퀀스 오브젝트를 이용해 기본 키 값을 생성
    - 쓰기 지연 가능, allocationSize로 미리 번호 묶음을 가져와 성능 최적화
3. **TABLE**
    - 키 생성 전용 테이블을 만들어 시퀀스 동작 흉내
    - DB 종류 상관없이 적용 → 이식성 측면에서 유리
    - 키 생성 테이블에 잠금이 발생
    - 조회, 갱신을 위한 추가 I/O가 필요 → 성능 저하 발생 가능
4. **AUTO**
    - JPA가 데이터베이스 방언을 기준으로 적절한 키 생성 방식을 자동 매핑해 주는 방법
    - MySQL → IDENTITY, Oracle/PostgreSQL → SEQUENCE

# 8. 영속성 컨텍스트

> JPA가 엔티티 객체를 관리하며, 동일 트랜잭션 내에서 변경 사항을 추적하고 자동으로 데이터베이스와 동기화하는 메모리 상의 저장소
> 
- 애플리케이션 내부 메모리에 존재
- 트랜잭션이 끝날 때까지 엔티티 상태 보관

## 왜 사용하는가?

JPA가 언제 데이터를 저장, 변경, 조회하는지 정확히 이해하고, 예측 가능한 데이터 처리와 오류 없는 트랜잭션 관리를 하기 위해서

## 영속성 컨텍스트에 따른 엔티티의 생명주기 상태

| **상태** | **설명** |
| --- | --- |
| **비영속 (new / transient)** | 영속성 컨텍스트와 전혀 관계가 없는 상태입니다.
`new`로 객체를 생성했지만 EntityManager를 통해 관리되지 않는 경우가 여기에 해당합니다. |
| **영속 (managed)** | 엔티티가 영속성 컨텍스트에 등록되어 관리되는 상태입니다.
`em.persist(entity)`를 호출하면 이 상태가 되며, 트랜잭션 커밋 시 데이터베이스와 동기화됩니다. |
| **준영속 (detached)** | 한 번 영속 상태였던 엔티티가 영속성 컨텍스트에서 분리된 상태입니다.
`em.detach(entity)` 또는 `em.clear()`를 호출하거나 `em.close()`로 EntityManager를 종료하면 해당 상태가 됩니다. |
| **삭제 (removed)** | 엔티티가 영속성 컨텍스트에서 삭제된 상태입니다.
`em.remove(entity)` 호출 시 이 상태가 되며, 트랜잭션 커밋 시 데이터베이스에서도 삭제됩니다. |

### 핵심 특징

- 1차 캐시
- 쓰기 지연
- 변경 감지

# 9. 연관관계 매핑

> 엔티티 객체 간의 관계를 설정하여, 객체지향적으로 연결된 데이터 구조를 정의하고 관리할 수 있도록 해주는 매핑 구조
> 

## 단방향 연결 관계

- 한 엔티티에서만 다른 엔티티를 참조해 관계를 맺는 방식
- 어노테이션 : @OneToOne, @ManyToOne
- 참조를 가진 쪽은 반대편 접근이 가능하지만, 반대편은 접근 불가

## 양방향 연결 관계

- 한 엔티티에가 서로를 참조하는 관계
- 어노테이션 : @OneToMany, @ManyToMany
- 두 엔티티가 서로 참조해 양쪽 모두에서 탐색 가능

# 10. Proxy와 지연 로딩

> Proxy : JPA에서 지연 로딩을 사용할 때 실제 엔티티 대신 먼저 생성되어, 데이터가 필요한 순간에 실제 조회를 지연시키는 가짜 객체

지연 로딩 : 필요한 시점에 연관된 객체의 데이터를 불러오는 것
> 
- 실제 엔티티를 즉시 DB에서 조회하지 않고, 엔티티와 동일한 모양의 프록시 클래스 먼저 생성해 반환
- 필드 접근 시점까지 조회를 미루는 역할 수행
- 한번 초기화되면 계속 실제 엔티티에 위임
- 원본 데이터로 변환하지 않고, 끝까지 프록시 객체로 남음

## 왜 사용하는가?

연관된 엔티티를 실제로 사용할 때까지 조회를 미뤄, 초기 쿼리 수를 줄이고 성능을 최적화하기 위해서이다.

프록시는 최소한의 정보(식별자)만 가진 가짜 객체를 먼저 반환하고, 실제 데이터가 필요한 시점에만 데이터베이스를 조회한다.
