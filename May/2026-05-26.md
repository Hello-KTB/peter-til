# 1. 데이터베이스

## 1-1. 등장 배경

### 천공카드

초기에는 데이터를 기록하기 위해 **`천공카드`**를 활용함

> 구멍의 위치로 데이터를 입력 및 저장하는 구멍 뚫린 종이 카드
> 

그러나 많은 단점 존재

- 수정이 어려움
- 데이터 처리가 느림
- 종이 재질이기 때문에 쉽게 훼손

### 파일 시스템

보조기억장치에 데이터를 파일 단위로 묶어서 저장하고 관리함

그러나 단점이 분명했음

- 데이터 기록 중복
- 보안과 권한 관리 부족
- OS 호환성 이슈
- 파일 탐색 어려움

### 데이터베이스

위 문제들을 해결하기 위해 DB가 만들어짐

DB는 아래와 같은 장점이 있음

- 중앙 집중 관리
- 데이터 중복 최소화
- 인덱스를 활용한 효율적 검색
- 무결성 보장
- 보안 강화
- 호환성 향상

## 1-2. 데이터베이스 및 SQL

### Database(DB)

> 통합 및 관리되는 데이터들의 집합
> 

### 관계형 데이터베이스 (RDB)

> 데이터를 테이블의 형태로 저장하고, 테이블 간의 관계를 ***정의***하여 데이터를 관리하는 데이터베이스 시스템
> 
- 테이블 기반 구조
- 행(Row)과 열(Column)
- 테이블 간 관계(Relation)

### RDBMS

- 데이터베이스 관리 시스템의 역할
- MySQL, PostgreSQL 등

### SQL

> 데이터베이스와 소통하는 언어
> 
- DDL(Data Definition Language)
    - DB의 구조를 생성, 수정, 삭제하는 언어
    - 종류 : CREATE, ALTER, DROP, TRUNCATE
- DML(Data Manipulation Language)
    - 테이블 안에 실제 데이터를 검색, 삽입, 수정, 삭제할 때 사용하는 언어
    - 종류 : SELECT, INSERT, UPDATE, DELETE
- DCL(Data Control Language)
    - 사용자의 권한을 부여하거나 회수하고, 데이터의 보안과 무결성을 제어하는 언어
    - 종류 : GRANT, REVOKE, COMMIT, ROLLBACK

# 2. 인덱스(Index)

> 데이터베이스 분야에 있어 테이블에 대한 조회 동작의 속도를 높여주는 자료 구조
> 

### 인덱스를 사용하는 이유

- 조회 속도를 향상시키기 위해서
- 시스템의 부하를 줄여서 시스템 전체에 대한 성능에 긍정적인 영향을 주기 위해서

---

## 2-1. Hash Index

> 해시 함수를 기반으로 인덱스 엔트리를 저장한 인덱스
> 

#### 특징

- 해시 버킷 : 해시 함수를 통해 얻은 해시값에 따라 데이터를 분류하여 저장하는 그룹 또는 공간
- 해시 함수 값을 버킷 번호로 사용

#### 장단점

- 조회 속도 빠름
- 메모리 접근 효율적

단점

- 해시 값 충돌 가능성 있음
    - 체이닝 기법을 통해 해결

## 2-2. Tree Index

>

#### 장단점

- 빠른 탐색
- 삽입/삭제 효율
- 범위 검색 가능

## 2-3. BST, B-Tree, B+Tree

## Binary Search Tree

> 
> 
> 
> 다음과 같은 속성이 있는 자료구조
> 
> - 각 노드에 값이 있다
> - 값들은 정렬된 순서가 있다
> - 노드의 왼쪽 서브트리에는 그 노드의 값보다 작은 값들, 오른쪽 서브트리에는 그 노드의 값보다 큰 값들을 지닌 노드들로 이루어져 있다.
> - 좌우 하위 트리는 각각이 다시 이진 탐색 트리여야 한다.

### BST 장단점

장점

- 입력 시 값에 따라 곧바로 위치가 지정되기 때문에, 데이터 검색 속도가 빠르다

단점

- 최악의 경우에 한 쪽으로만 이어질 수 있다
- 그럴 경우, 이진 탐색 트리의 성능이 매우 저하될 수 있음

## B-Tree

<img width="500" height="139" alt="btree" src="https://github.com/user-attachments/assets/73612ef3-3204-40f2-89d4-fbd18235e927" />

> DB와 파일 시스템에서 대량의 데이터를 효율적으로 검색하기 위해 설계된 트리 자료 구조
> 
- 하나의 노드가 여러 개의 키와 자식 노드를 가질 수 있음
- 모든 리프 노드는 같은 깊이에 위치하도록 유지되어, 트리의 높이가 자동으로 규형을 이룸
- 이 구조 덕분에 검색, 삽입, 연산이 항상 시간 복잡도 O(log n))을 유지함.
- 특히 디스크 기반 시스템에서 트리 높이를 최소화하여 I/O 횟수를 줄이는데 최적화된 구조

### 키

- 내부 노드
    - 실제 데이터가 아닌 경계 키
    - 자식 노드가 담당하는 값의 범위를 나누는 역할
    - 탐색 시 어느 자식 노드로 내려갈지 결정하는 기준값
- 리프 노드 (마지막 층)
    - 실제 인덱싱 대상 키
    - 데이터 레코드를 직접 가리킴
    - 정렬된 상태로 저장되어 범위 검색에 유리

### B-Tree 장단점

장점

- 중간 노드에서 바로 데이터를 찾을 수 있어 단일 검색 속도 빠름
- 메모리 사용 효율 높음
- 작은 데이터셋이나 메모리 기반 구조에 작헙

단점

- 리프 노드들이 연결되어 있지 않아 범위 검색 비효율적

## B+Tree

<img width="1121" height="516" alt="b+tree" src="https://github.com/user-attachments/assets/adcce920-aa86-4e20-8f5e-3709aca51495" />

> 키(Key)를 기준으로 레코드를 식별하며, **데이터의 삽입·검색·삭제를 효율적으로 수행하면서 항상 정렬된 상태를 유지**하도록 설계된 트리 자료 구조
> 
- **MySQL InnoDB 스토리지 엔진에서 인덱스를 관리하기 위해 사용**
- **여러 계층으로 구성된 동적 인덱스 구조로,** 각 인덱스 세그먼트(일반적으로 페이지 또는 노드라고 부름)는 **일정 범위의 키들을 저장**하며 트리 전체의 균형을 유지함
- 오늘날 RDB는 거의 모두 B+Tree 기반 인덱스 사용

### B+Tree 장단점

장점

- 범위 검색 / 순차 탐색 최적화
- 내부 노드에 더 많은 키 저장 가능
- 대규모 데이터디스크 기반(DB, 파일 시스템 인덱스) 최적

단점

- 항상 리프까지 내려가야 하므로 단일 검색 속도는 B 트리보다 불리

## B-Tree vs B+Tree

| 구분 | B-Tree | B+Tree |
| --- | --- | --- |
| 데이터 저장 | 모든 노드(내부+리프)에 데이터 저장 | 내부 노드는 키만 저장, 데이터는 리프 노드에만 저장 |
| 단일 조회 | 중간 노드에서도 바로 조회 가능 → 단일 조회 빠름 | 항상 리프까지 내려가야 함 → 단일 조회는 B-Tree보다 느림 |
| 범위 검색 / 순차 접근 | 리프 노드 간 연결이 없어 비효율적 | 리프 노드가 연결 리스트로 이어져 있어 범위 검색 최적화 |
| 트리 높이 | 같은 크기의 노드에 저장할 수 있는 키 수가 적음 → 트리 높이 상대적으로 큼 | 내부 노드에 더 많은 키 저장 가능 → 트리 높이 낮음 |
| I/O 효율성 | 메모리 기반 소규모 데이터에 적합 | 디스크 페이지 단위 I/O 최적화 → 디스크 기반 환경에 유리 |
| 적합한 환경 | 작은 데이터셋, 메모리 기반, 단일 검색 위주 | 대규모 데이터셋, 디스크 기반 DB·파일 시스템 (사실상 표준) |

### 왜 DB는 B+트리를 쓸까?

1. 범위 검색과 순차 접근에 최적화 / 디스크 페이지와 잘 맞는 구조
    1. B-Tree는 리프 노드들이 연결돼 있지 않아서 범위 검색 시 키마다 별도 탐색이 필요
    2. 반면, B+Tree는 리프 노드가 연결 리스트로 이어져 있어, `WHERE id BETWEEN 10 AND 100` 같은 쿼리를 처리할 때 시작점만 찾으면 순차적으로 데이터를 빠르게 읽을 수 있음
    3. 또한 데이터가 리프 노드에 모여 있고 연속적으로 배치되므로, DB가 디스크 페이지 단위로 데이터를 읽을 때 인접 데이터까지 한 번에 가져올 수 있어 I/O 효율이 높음
2. 트리 높이는 줄여 디스크 I/O 최소화
    1. B-Tree는 내부 노드에도 데이터를 저장해야 하므로, 같은 페이지 크기에서는 담을 수 있는 키 개수가 적음
    2. B+Tree는 내부 노드에 키만 저장하기 때문에 더 많은 키를 넣을 수 있고, 결과적으로 트리의 높이가 낮아짐
    3. 트리 높이가 낮아진다는건 곧 디스크 접근 횟수가 줄어든다는 뜻이므로 DB 성능에 큰 이점이 됨
3. SQL 쿼리 패턴과 잘 맞음
    1. `ORDER BY`, `GROUP BY`는 인덱스 정렬 상태를 그대로 활용할 수 있음
    2. `JOIN`에서는 정렬된 키를 활용해 `Merge Join` 같은 최적화가 가능함
    3. B-Tree는 이런 활용도가 떨어지기 때문에, 실제 SQL 실행 계획에서 인덱스 효율성이 낮음
4. 대규모 데이터셋에 강함
    1. 수백만-수억 건 이상의 데이터셋에서는 단건 조회보다 범위 검색, 정렬, 조인이 훨씬 더 자주 발생함
    2. B+Tree는 이러한 워크로드에 맞춰 설계돼 있기 때문에 대규모 디스크 기반 DB 환경에서 사실상 표준이 되었음

# 3. Full Text Index

> 텍스트 검색에서 컴퓨터에 저장된 문서 또는 전문 데이터베이스를 검색하는 기법
> 

문서에 포함된 모든 텍스트를 분석해 각 단어가 어떤 문서와 어떤 위치에 나타나는지를 기록함

이렇게 해서 만들어진 Index를 통해 사용자가 검색 쿼리를 입력했을 때, 빠르고 정확하게 원하는 정보를 찾아낼 수 있음

---

## 3-1. Parser

> **문장을 검색 가능한 단위로 잘게 나눠주는 엔진(도구)**
> 

### Stopword Parser

> 공백, 문장 부호(쉼표, 마침표)를 기준으로 분리하는 파서
> 
- 영어권은 단어들의 나열이기 때문에 잘 작동함
- 한글은 어절, 조사 등 문법적인 규칙 때문에 동작이 제대로 안 됨

### N-gram Parser

> 지정된 글자 수 만큼 자르는 파서
> 
- 한글 한전 stopword보다 성능은 좋음
- 인덱스가 엄청 커지는 단점 존재 → 메모리/디스크 많이 먹음
- 의미 없는 결과 발생 가능

### MeCab

> 문장의 의미 단위(형태소)로 분리하는 파서
> 
- 노이즈 감소
- N-gram보다 인덱스가 가벼워짐 → 효율적
- 동의어 처리 어려움
- 문맥 이해 부족
- 형태소 분석 자체가 무거워서 대용량 트래픽 비용 증가

### 한글의 검색 엔진 필요성

- Full Text Index만으로는 한국어 검색 성능이 안 좋음
- Elastic Search와 같은 검색 엔진을 별도로 사용해서 성능 높이는게 좋음
    - DB는 저장 담당, 검색엔진은 검색 담당

### Full Text Index의 한계

- 작업 자체가 무거움 (글 하나 insert 되어도 글 인덱스 업데이트까지 많은 작업 추가로 발생)
- 전문 검색엔진 수준이 못됨

# 4. 트랜잭션(Transaction)

> **데이터베이스의 상태를 변화시키는 더 이상 쪼갤 수 없는 논리적 작업의 단위**
> 

### 트랜잭션 사용 이유

- 데이터베이스의 무결성과 일관성 보장
- 여러 작업을 하나의 논리적인 작업 단위로 묶어서 처리하기 위해서

## 4-1. ACID

### Atomicity (원자성)

> 트랜잭션이 데이터베이스에 모두 반영되던가, 아니면 전혀 반영되지 않아야 한다는 것 (All Or Nothing)
> 

### Consistency (일관성)

> 트랜잭션의 작업 처리 결과가 항상 일관성이 있어야 한다는 것
> 

### Isolation (고립성)

> 어떤 하나의 트랜잭션이라도, 다른 트랜잭션의 연산에 끼어들 수 없다는 점을 가리킴
> 

### Durability (지속성)

> 트랜잭션 성공적으로 완료시, 결과는 영구적으로 반영되어야 한다는 점
>
