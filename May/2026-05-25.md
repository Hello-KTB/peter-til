## REST API란 무엇인가

### 웹의 탄생 (1991)

팀 버너스리에 의해 WWW 탄생. 핵심 질문은 **"어떻게 인터넷에서 정보를 공유할 것인가?"** 였고, 정보들을 하이퍼텍스트로 연결하는 방식으로 해결했다.

- 표현 형식: HTML
- 식별자: URI
- 전송 방법: HTTP

---

### REST의 탄생 (1994–2000)

로이 필딩은 HTTP/1.0 작업에 참여하면서 고민했다. **"어떻게 하면 웹을 망가뜨리지 않고 HTTP를 개선할 수 있을까?"**

이 고민의 해결책이 HTTP Object Model이었고, 이것이 REST로 발전했다.

- 1998년 마이크로소프트 재단에서 발표
- 2000년 박사 논문으로 공식 정의

---

### API의 역사

마이크로소프트가 XML-RPC(1998)를 발표했고, 이후 SOAP으로 발전했다.

- **Salesforce API**: 인터넷 최초의 공개 API, SOAP 활용
- **Flickr API (2004.8)**: SOAP과 REST 두 방식 모두 제공

### SOAP vs REST 비교

| 구분 | SOAP | REST |
| --- | --- | --- |
| 복잡도 | 복잡하다 | 단순하다 |
| 규칙 | 규칙 많음 | 규칙 적음 |
| 난이도 | 어렵다 | 쉽다 |

결과적으로 REST API 사용률이 증가하고 SOAP API 사용률이 감소했다.

- 2006년, AWS가 자사 API 사용량의 85%가 REST임을 밝힘
- 2010년, Salesforce.com REST API 추가

---

### 그런데, 그것이 정말 REST인가?

### 로이 필딩의 비판

- **CMIS (2008)**: REST 바인딩을 지원한다고 했으나, 로이 필딩 왈 "No REST in CMIS"
- **Microsoft REST API Guidelines (2016)**: 로이 필딩 왈 "REST API 아님. HTTP API"

로이 필딩의 주장:

> REST API는 hypertext-driven이어야 한다.
REST API를 위한 최고의 버저닝 전략은 버저닝을 안 하는 것이다.
> 

---

### REST의 정의

- **REST**: 분산 하이퍼미디어 시스템(예: 웹)을 위한 아키텍처 스타일
- **아키텍처 스타일**: 제약조건들의 집합
- **REST API**: REST 아키텍처 스타일을 따르는 API

### REST를 구성하는 6가지 스타일

1. Client-Server
2. Stateless
3. Cache
4. **Uniform Interface**
5. Layered System
6. Code-on-Demand *(optional)*

---

### Uniform Interface의 4가지 제약조건

1. Identification of Resources
2. Manipulation of Resources through Representations
3. **Self-descriptive Messages**
4. **HATEOAS** (Hypermedia as the Engine of Application State)

> 1, 2번은 대부분 잘 지켜지고 있지만, <u>3, 4번은 오늘날 자칭 REST API라고 불리는 것들의 대부분이 만족하지 못하고 있다.</u>
> 

---

### Self-descriptive Messages

메시지를 내용만으로 온전히 해석할 수 있어야 한다.

```http
# 목적지가 없어 self-descriptive하지 못한 예시
GET / HTTP/1.1

# Host 추가 → self-descriptive 만족
GET / HTTP/1.1
Host: www.example.org

# Content-Type 없음 → 어떤 문법인지 알 수 없음
HTTP/1.1 200 OK

[{"op": "remove", "path": "/a/b/c"}]

# Content-Type 추가했지만 op, path의 의미를 알 수 없음
HTTP/1.1 200 OK
Content-Type: application/json

[{"op": "remove", "path": "/a/b/c"}]

# 명세를 참조할 수 있도록 media type 지정 → self-descriptive 만족
HTTP/1.1 200 OK
Content-Type: application/json-patch+json

[{"op": "remove", "path": "/a/b/c"}]
```

---

### HATEOAS

<u>애플리케이션의 상태는 Hyperlink를 이용해 전이되어야 한다.</u>

html

```html
<!-- HTML → HATEOAS 만족 (하이퍼링크를 통해 다음 상태로 전이 가능) -->
HTTP/1.1 200 OK
Content-Type: text/html

<html>
  <body><a href="/test">test</a></body>
</html>
```

json

```http
// JSON + Link 헤더 → HATEOAS 만족
HTTP/1.1 200 OK
Content-Type: application/json
Link: </articles/1>; rel="previous", </articles/3>; rel="next"

{
  "title": "The second article",
  "contents": "blah blah..."
}
```

### 왜 Uniform Interface가 필요한가?

### 독립적 진화

- 서버와 클라이언트가 각각 독립적으로 진화한다
- 서버의 기능이 변경되어도 클라이언트를 업데이트할 필요가 없다
- REST를 만들게 된 계기: *"How do I improve HTTP without breaking the Web."*

### 웹이 독립적으로 진화할 수 있는 이유

W3C, IETF, 브라우저 개발자들의 엄청난 노력 덕분이다.

- HTML5 첫 초안에서 권고안까지 **6년**
- HTTP/1.1 명세 개정판 작업에 **7년** (하위 호환성을 깨뜨리지 않기 위해)

### 상호운용성에 대한 집착

- `Referer` — 오타지만 고치지 않음
- `charset` — 잘못 지은 이름이지만 고치지 않음
- HTTP 상태코드 418 — 포기함 (I'm a teapot)
- HTTP/0.9 — 아직도 지원함 (Chrome, Firefox)

> 이 모든 것이 웹이 깨지는 것을 방지하기 위한 선택이다.
> 

---

### REST는 성공했는가?

**REST 자체는 성공했다.** 웹은 독립적으로 진화하고 있다.

**그러나 REST API는?**

오늘날 스스로 REST API라고 부르는 API들의 대부분이 REST 아키텍처 스타일을 따르지 않는다.

> 로이 필딩: REST API는 <u>하이퍼텍스트를 포함한 self-descriptive한 메시지의 uniform interface를 통해 리소스에 접근하는 API</u>여야 한다.
> 

---

### HTML vs JSON: 왜 API는 REST가 잘 안 되나?

|  | 흔한 웹페이지 | HTTP API |
| --- | --- | --- |
| 프로토콜 | HTTP | HTTP |
| 커뮤니케이션 | 사람-기계 | 기계-기계 |
| 미디어 타입 | HTML | JSON |

|  | HTML | JSON |
| --- | --- | --- |
| 하이퍼링크 | 지원 (a 태그 등) | 정의되어 있지 않음 |
| Self-descriptive | 만족 (HTML 명세) | 불완전 |
- HTML은 self-descriptive **성공**, HATEOAS **성공**
- JSON은 self-descriptive **실패**, HATEOAS **실패**

### REST API로 개선하는 방법

### Self-descriptive 해결

**방법 1. Custom Media Type**

json

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.todos+json
```

미디어 타입을 직접 정의하고 IANA에 등록한다. 명세에 필드 의미를 정의하면 해석 가능해진다.

- 단점: 매번 media type을 새로 정의해야 한다

**방법 2. Profile Link Relation**

json

```http
HTTP/1.1 200 OK
Content-Type: application/json
Link: <https://example.org/docs/todos>; rel="profile"
```

- 단점: 클라이언트가 Link 헤더(RFC 5988)와 profile(RFC 6906)을 이해해야 하며, Content Negotiation 불가

---

### HATEOAS 해결

**방법 1. 데이터에 링크 포함**

json

```http
[
  {"link": "https://example.org/todos/1", "title": "회사 가기"},
  {"link": "https://example.org/todos/2", "title": "집에 가기"}
]
```

또는 JSON 하이퍼링크 명세(JSON API, HAL, UBER, Siren 등)를 활용한다.

**방법 2. HTTP 헤더 활용**

json

```http
HTTP/1.1 204 No Content
Location: /todos/1
Link: </todos/>; rel="collection"
```

> 데이터와 헤더 모두 활용하는 것이 좋다.
> 

---

### 결론

- 오늘날 대부분의 REST API는 사실 REST를 따르지 않고 있다
- 특히 **Self-descriptive**와 **HATEOAS**를 잘 만족하지 못한다
- REST는 긴 시간에 걸쳐 진화하는 웹 애플리케이션을 위한 것이다
- <u>REST를 따를 것인지는 API를 설계하는 이들이 스스로 판단해야 한다</u>

### REST API를 구현하려면

- **Self-descriptive**: custom media type 또는 profile link relation으로 해결
- **HATEOAS**: HTTP 헤더나 본문에 링크를 담아 해결

### 선택지

1. REST API를 구현하고 REST API라고 부른다 *(도전)*
2. REST API 구현을 포기하고 HTTP API라고 부른다
3. REST API가 아니지만 REST API라고 부른다 *(현재 대부분의 상태)*

> 로이 필딩: "시스템 전체를 통제할 수 있거나, 진화에 관심이 없다면 REST에 대해 따지느라 시간을 낭비하지 마라."
>
