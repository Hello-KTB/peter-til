# 1. 동시성 제어

<img width="797" height="164" alt="image" src="https://github.com/user-attachments/assets/4fd463d8-ca5f-4636-b633-4f296ca6b5fc" />

> 여러 사용자가 동시에 데이터베이스에 접근할때 발생할 수 있는 문제를 방지하고, 데이터의 일관성과 무결성을 유지하기 위한 기술
> 

## 왜 필요한가?

클라이언트가 많은 환경에서는 여러 요청이 동시에 들어올 수도 있는데, 그 중에서도 같은 데이터에 접근하고자 하는 요청도 여러 개 있을 수 있다. 이러한 경우에서도 데이터의 일관성과 무결성을 보장하기 위해서는 동시성 제어가 필요하다.

* 일관성(consistency)이란 데이터베이스가 트랜잭션 전후에도 항상 정의된 규칙을 만족하는 상태를 유지하는 것을 의미합니다.

* 무결성(integrity)은 데이터가 정확하고 신뢰할 수 있는 상태를 유지하는 것을 의미합니다.

## Locking 메커니즘

데이터베이스는 동시성 제어를 위해서 락(Lock), 트랜잭션, 격리 수준, MVCC 등 여러 메커니즘을 제공하는데, 그 중 락이 데이터 접근을 제한하는 가장 직관적인 수단이다.

락에는 두가지 종류가 있는데, 비관적 락과 낙관적 락이 있다. 둘을 나누는 기준은 충돌 발생 가능성 가정이다.

### 비관적 락

> 동시에 충돌이 발생할 가능성이 높다고 가정하고, 데이터를 사용하기 전에 먼저 락을 걸어 다른 트랜잭션의 접근을 제한하는 방식
> 
- 충돌은 반드시 발생할 수 있으므로, 미리 차단해야 한다는 관점에서 동작
- 데이터를 읽는 시점에 락 설정을 통해 다른 트랜잭션의 수정이나 접근 차단
    - 데이터 무결성 강하게 보장
    - 락 대기 시간 증가와 동시성 저하 발생
- RDBMS에서 주로 사용됨
- 정확성과 일관성이 무엇보다 중요한 데이터에 적용

장단점

| **장점** | **단점** |
| --- | --- |
| 데이터 무결성과 일관성을 강하게 보장합니다. | 동시성이 저하될 수 있습니다. |
| 충돌을 사전에 차단합니다. | 락 대기 및 데드락 발생 가능성이 있습니다. |
| 정합성이 중요한 작업에 적합합니다. | 트랜잭션 처리량이 감소할 수 있습니다. |

### 낙관적 락

> 동시에 데이터 충돌이 발생할 가능성이 낮다고 가정하고, 데이터를 미리 잠그지 않은 채 작업을 진행한 뒤 최종 업데이트 시점에 충돌 여부를 검증하는 방식
> 
- 락을 미리 설정하지 않음
    - 시스템의 동시성을 높이는 데 유리
- 버전 컬럼 또는 조건 비교를 통해 업데이트 시점에 ‘내가 읽은 데이터가 아직 유효한지’ 확인
- 충돌 발생 시 UPDATE 실패, 애플리케이션을 이를 감지해 재시도 또는 실패 처리로 대응
- RDBMS에서도 널리 사용되며, DB의 원자적 UPDATE 연산을 기반으로 동작

장단점

| **장점** | **단점** |
| --- | --- |
| 높은 동시성과 성능을 제공합니다. | 충돌 시 재시도 또는 실패 처리가 필요합니다. |
| 락 대기가 없습니다. | 충돌이 잦으면 비효율적입니다. |
| 읽기 위주의 환경에 적합합니다. | 구현 로직이 필요합니다 |

# 2. OAuth

> 사용자가 자신의 정보에 대한 접근 권한을 안전하게 타사 애플리케이션에 부여할 수 있게 하는 개방형 표준 프로토콜
> 

사용자(유저)의 비밀번호를 제 3자 애플케이션(서비스)에 제공하지 않고도, 사용자가 자신의 리소스에 대한 접근 권한을 안전하게 부여할 수 있도록 한다.

## 왜 필요한가?

OAuth는 사용자 비밀번호를 노출하지 않고도, 애플리케이션이 사용자의 데이터에 안전하게 접근할 수 있도록 도와준다. 

OAuth가 없다면, 클라이언트(애플리케이션)가 사용자의 아이디와 비밀번호를 직접 받아서 리소스 서버에 요청하는 방식을 쓸 수 있다. 그러나 이 경우 사용자의 자격증명을 클라이언트가 직접 취급하게 되므로, 자격증명 유출에 대한 책임이 클라이언트에게 생기고 보안 위험도 커진다. 이는 사용자도, 서비스 제공자도 원하지 않는 구조다.
