## Web

<aside>
💡

위키백과

인터넷에 연결된 컴퓨터를 통해 사람들이 정보를 공유할 수 있는 전 세계적인 정보 공유 시스템

</aside>

### 개요

웹은 정보를 주고 받는 시스템으로, 정보를 요청하는 주체는 클라이언트, 요청에 대한 응답을 하는 주체는 서버이다.

### 탄생 배경

팀 버너스리 CERN에서 근무하던 중, “정보를 자유롭게 공유할 수 있는 시스템”이 필요하다고 판단해 World Wide Web을 개발

**나의 한줄 요약** : 누구나 정보를 공유하고 접근할 수 있는 공간

## 서버 (Server)

<aside>
💡

위키독스

클라이언트의 요청을 받아 데이터를 처리하고 응답을 반환하는 컴퓨터

</aside>

### 개요

클라이언트는 고객(정확히는 고객이 다루는 프로그램 또는 디바이스)으로 서버에 자원을 요청한다. 서버는 네트워크를 통해서 클라이언트에게 서비스나 자원을 제공하는 컴퓨터 시스템이나 프로그램이다.

### 핵심 역할과 특징

- 수동적 대기, 응답
- 비즈니스 로직, 데이터 처리
- 중앙 집중식 자원 관리 + 보안

### 왜 클라이언트-서버로 나눴을까?

- 초기에는 중앙 컴퓨터가 둘의 역할을 했지만
    - 가격이 비쌌고, 중앙에 요청이 몰릴시 병목 현상이 심해졌음
- 성능 좋은 개인용 컴퓨터 보급
    - 일부 작업을 개인 컴퓨터에 위임

### 위 구조로 얻은 것

- 비용 절감
- 향상된 사용자 경험
- 확장 용이해짐
- 유지보수

나의 한줄 요약 : 클라이언트의 요청을 처리하는 디바이스 또는 소프트웨어

## HTTP (Hyper Text Transfer Protocol)

<aside>
💡

AWS

클라이언트와 서버 간 통신을 위한 통신 규칙 세트 또는 프로토콜

</aside>

하이퍼 텍스트 : 글을 뛰어넘는 구조화된 텍스트 (이미지, 링크 등)

### 왜 사용하는가?

- 사람마다 방법이 달라서, 너무 많은 표현 방식으로 인해 해석이 힘듬
- 이러한 이유들로 규칙이 필요했음
- (비유) 바디랭귀지로도 소통은 가능하나, 사람마다 바디랭귀는 다름. 이러한 문제를 해소하기 위해 언어라는 규칙을 만들었고, 그 중 전 세계적으로 가장 표준화된 언어는 영어이다.
- 전세계에서 하이퍼텍스트 전송 규칙을 만듬
- 규칙만 지키면, 환경이 달라도 통신이 가능
    - OS를 따지지 않고 통신

### 사용법

클라이언트측에서 서버측으로 URL(경로)을 전송

나의 한줄 요약 : 일반적인 텍스트가 아닌 텍스트(파일, 링크 등)을 전송하기 위해 사용하는 통신 규약

## HTTP Request Method

<aside>
💡

MDN

**클라이언트(웹 브라우저 등)가 웹 서버에 데이터를 요청하거나 작업을 수행하기 위해 보내는 핵심 명령어**

</aside>

| **HTTP Method** | **역할 (의미)** | **데이터 위치** | **CRUD 매핑** | **실제 예시** |
| --- | --- | --- | --- | --- |
| **`GET`** | 데이터를 **조회(가져오기)** | URL (쿼리 스트링) | **C**RUD (Read) | 뉴스 기사 읽기, 검색창 검색 |
| **`POST`** | 새로운 데이터를 **생성(등록)** | Message Body | **C**RUD (Create) | 회원가입, 게시글 작성, 결제 |
| **`PUT`** | 기존 데이터를 **전체 수정(대체)** | Message Body | CR**U**D (Update) | 프로필 정보 전체 수정 |
| **`PATCH`** | 기존 데이터의 **일부만 수정** | Message Body | CR**U**D (Update) | 비밀번호만 변경, 닉네임만 변경 |
| **`DELETE`** | 데이터를 **삭제** | URL 또는 Body | CRU**D** (Delete) | 회원 탈퇴, 게시글 삭제 |

나의 한줄 요약 : 클라이언트 기준에서 서버로 보내는 요청으로, 종류는 GET, POST, PATCH,  DELETE, PUT이 있다.

## Path Variable

<aside>
💡

교재

경로 부분에 포함되어 있는, 특정 자원을 식별하는 변수

</aside>

Path Variable : 특정 자원을 식별하고자 사용하는 변수

| **분류** | **Query String (질의 문자열)** | **Path Variable (경로 변수)** |
| --- | --- | --- |
| **일반 명사 (직역)** | **문의하는 줄 (의문의 줄)**
• Query: 문의, 의문
• String: 끈, 줄 | **길 변수 (계획 변수)**
• Path: 길, 경로
• Variable: 변수 |
| **고유 명사 (뜻)** | 클라이언트가 웹 페이지에 대한 **추가 정보**를 서버에 전달하기 위해 URL 끝에 붙이는 문자열 | URL **경로 자체에 변수 값을 포함**시켜, 특정 자원(리소스)을 식별하는 변수 |
| **사용 목적** | 데이터의 **검색, 필터링, 정렬, 페이지네이션** | 특정 데이터의 **위치를 특정하고 식별** |
| **사용 방법** | URL 끝에 `?`를 붙이고 `key=value` 형태 전달 | URL 경로 중간이나 끝에 `{변수값}`을 그대로 포함 |

## RESTful API

<aside>
💡

AWS
두 컴퓨터 시스템이 인터넷을 통해 정보를 안전하게 교환하기 위해 사용하는 인터페이스

</aside>

#### REST란?

> Representational State Transfer(REST)는 API 작동 방식에 대한 조건을 부과하는 소프트웨어 아키텍처
> 

#### RESTful 하다란?

REST 아키텍처의 설계 원칙과 규칙을 올바르게 지켜서 설계한 상태를 ‘RESTful 하다’라고 표현한다.

#### REST 아키텍처 원칙

- 균일한 인터페이스
- 무상태
- 계층화 시스템
- 캐시 가능성
- 온디맨드 코드

#### RESTful API 사용 이점

- 확장성
- 유연성
- 독립성

#### RESTful API 작동 방식

1. 클라이언트가 서버에 요청을 전송. 클라이언트가 API 문서에 따라 서버가 이해하는 방식으로 요청 형식 지정
2. 서버가 클라이언트를 인증하고 해당 요청을 수행할 수 있는 권한이 클라이언트에 있는지 확인
3. 서버가 요청을 수신하고 내부적으로 처리
4. 서버가 클라이언트에 응답을 반환. 응답에는 요청이 성공했는지 여부를 클라이언트에 알려주는 정보가 포함됨. 응답에는 클라이언트가 요청한 모든 정보도 포함됨.

#### RESTful API 클라이언트 요청 포함 요소

- 고유 리소스 식별자
    - URL을 통해 리소스 식별
- 메서드
    - 주로 GET, POST, PUT, DELETE 사용
- HTTP 헤더
    - 데이터
    - 파라미터

#### RESTful API 서버 응답 포함 요소

- 상태 표시줄
    - 200: 일반 성공 응답
    - 201: POST 메서드 성공 응답
    - 400: 서버가 처리할 수 없는 잘못된 요청
    - 404: 리소스를 찾을 수 없음
- 메시지 본문
- 헤더

나의 한줄 정리 

- RESTful API : HTTP를 기반으로 자원의 이름과 상태를 표현하여 클라이언트가 서버에게 요청하는 통신 규약
- 사용 이유 : 개발자 간 일관된 규칙을 지킴으로써 요청을 이해하기 위해서.
