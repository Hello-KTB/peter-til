# 1. 쿠키와 세션

## 1-1. HTTP 특징

### a. Stateless

> 이전 상태를 보존하지 않음
> 

위 정의 그대로, 서버에서 클라이언트의 상태를 보존하지 않고, 매번 요청마다 

#### 왜 HTTP는 Stateless인가?

위 의문을 해결하기 위해서는 Stateful에 대해서도 알아야 한다.

**stateful** : stateless의 반대말로, 이전 상태를 가지고 있다.

즉, 서버에서 클라이언트의 상태 정보를 저장하고 있다는 것을 의미한다.

→ But, 만약 해당 서버가 멈추거나 여러 이유로 해당 서버를 못 쓰게 되어 다른 서버를 사용한다면?

- 새로운 서버는 이전 서버에서 가지고 있던 상태값 없음
- 또 상태 정보를 줘야 하는 번거로움 발생

→ And, 하나의 서버가 수많은 클라이언트가 몰리면

- 처리하는데 한계가 생김
- 서버 메모리는 한계가 존재
- 위와 같은 문제 해결을 위해, 실무에서는 Redis에 상태 데이터 저장

#### Stateless 특징

- 서버는 단순히 요청이 오면 응답을 보내는 역할만 수행
    - 상태 관리는 전적으로 클라이언트 책임
- 서버가 바뀌어도 응답에 문제 없음

#### Stateless 장단점

장점

- 서버 부하 줄어듬
- 서버 확장 용이

단점

- 클라이언트 요청에 더 많은 데이터가 소모됨

### b. Connectionless

> 클라이언트가 서버에 요청을 하고 응답을 받으면 연결을 끊음
> 

#### 왜 Connectionless 인가?

- HTTP는 기본적으로 불특정 다수와 통신이 가능하도록 설계된 프로토콜
- 서버가 다수의 클라이언트들의 상태 또는 연결을 계속 유지
    - 리소스 낭비가 심해짐

따라서 **상태 또는 연결을 유지하지 않는 대신에, 더 많은 연결을 할 수 있도록 설계함. 이 특성이 Connectionless이다.**

#### Connectionless 장단점

장점

- 서버의 자원을 효율적으로 사용 가능

단점

- TCP 3 way handshake를 매번 해야 함
    - 시간이 더 걸림
    - 최근에는 HTTP 지속 연결로 해결

위 Stateless와 Connectionless의 단점으로 인해 로그인을 했음에도 url path를 바꿔가며 페이지 이동시 계속 로그인해야 함

위와 같이 HTTP의 Stateless와 Connectionless를 해결하기 위 등장한 게 쿠키와 세션이다.

## 1-2. 인증·인가

### a. 인증

> 다중 사용자 시스템이나 네트워크에서, 사용자의 신원을 확인하는 보안 절차
> 

인증은 “넌 누구?”라는 질문에 답하는게 인증이다. 즉 사용자를 검증하는 과정이다.

#### 생성과 저장 과정

1. 사용자가 자격 증명(비번, OTP, 생체 정보)을 입력
2. 시스템이 자격 증명을 확인
3. 유효한 경우, 사용자는 성공적으로 인증됨

### b. 인가

> 사용자와 제작자 사이에 프로그램 사용이나 특허 제작 권한을 주고받는 계약
> 

#### 작동 방식

1. 시스템은 사용자의 역할 또는 권한 확인
2. 리소스에 대한 접근 권한 부요 혹은 거부
3. 사용자가 허용된 작업만 수행할 수 있도록 보장

### c. 인증·인가의 차이점은?

|  | 인증 | 인가 |
| --- | --- | --- |
| 기능 | 자격 증명 확인 | 권한 허가/거부 |
| 진행 방식 | 비밀번호, 생체인식, 일회용 핀 또는 앱 | 보안 팀에서 관리하는 설정 사용 |
| 사용자가 볼 수 있는가? | 예 | 아니오 |
| 사용자가 직접 변결할 수 있는가? | 부분적으로 가능 | 불가능 |
| 데이터 전송 | ID 토큰 사용 | 액세스 토큰 사용 |

## 1-3. 쿠키

> 인터넷 사용자가 웹 사이트를 방문할 경우 사이트가 사용하고 있는 서버를 통해 인터넷 사용자의 컴퓨터에 설치되는 작은 기록 정보 파일
> 

쿠키는 Key-Value 형식의 문자열 덩어리이다.

### a. 쿠키의 생성과 저장 과정

<img width="571" height="428" alt="쿠키" src="https://github.com/user-attachments/assets/bee78140-b46d-4f65-be48-a32b2b076e10" />

1. 브라우저(클라이언트)가 서버에 요청(접속)을 보냄
2. 서버는 클라이언트의 요청에 대한 응답을 작성할 때, 클라이언트 측에 저장하고 싶은 정보를 응답 헤더의 Set-Cookie에 담음
3. 이후 해당 클라이언트는 요청을 보낼 때마다, 매번 저장된 쿠키를 요청 헤더의 Cookie에 담아 보냄.
4. 서버는 쿠키에 담긴 정보를 바탕으로 해당 요청의 클라이언트가 누군지 식별하거나 정보를 바탕으로 추천 광고를 띄우거나 함

### b. 쿠키 방식의 한계

- 보안에 취약함
    - 요청 시 쿠키의 값을 그대로 보내기 때문에 유출 및 조작 당할 위험 존재
- 용량 제한이 있음
    - 많은 정보를 담을 수 없음
- 웹 브라우저마다 쿠키에 대한 지원 형태가 다름
    - 브라우저간 공유 불가능
- 쿠키 사이즈가 커질수록 네트워크 부하가 심해짐

## 1-4. 세션

> 컴퓨터 프로세스들 사이에서, 서로를 인식한 후 데이터 송수신을 마칠 때까지의 기간
> 

쿠키의 보안적 이슈를 해결하기 위해 클라이언트의 민감한 인증 정보를 서버 측에 저장하고 관리함

### a. 정보 저장 공간

- 서버의 메모리
- 서버의 로컬 파일
- 데이터베이스

### b. 세션의 생성과 저장 과정

<img width="640" height="479" alt="세션" src="https://github.com/user-attachments/assets/7f9e9e47-1922-4ee7-b394-746306ec4e22" />

1. 유저가 웹사이트에서 로그인하면 Session이 서버 메모리 (혹은 DB) 상에 저장됨
    - 이때 Session을 식별하기 위한 Session ID를 기준으로 정보를 저장함
2. 서버에서 보낸 Response header의 Set-Cookie의 Session Id를 브라우저의 쿠키에 저장함
3. 브라우저는 해당 사이트에 대한 모든 Request에 Session Id를 header cookie에 담아 전송함
4. 서버는 클라이언트가 보낸 Session Id와 서버 메모리로 관리하고 있는 Session Id를 비교하여 인증을 수행하여 Response를 보냄

### c. 세션 방식의 한계

- 해커가 세션 ID 탈취
    - 클라이언트인척 위장 가능
- 서버에서 세션 저장소를 사용
    - 요청이 많아지면 서버 부하 심해짐
 
# 2. 프레임워크와 라이브러리

## 2-1. 프레임워크

> 기본적인 기능들을 제공해 개발자가 기능을 구현하는데 집중할 수 있도록 도와주는 골조
> 

간단 요약 : 개발을 위한 구조와 규칙을 제공해 개발 과정을 단순화시켜주는 도구

### a. 왜 사용하는가?

일관성을 지키기 위해서

- 프레임워크 내에서는 정의된 규칙과 패턴을 따름
    - 코드가 일관됨
    - 유지보수하기 쉬운 구조 갖추기 가능

### b. 장점

- 개발 과정이 빨라짐
- 일관된 코드 작성 가능
- 코드 재사용성

## 2-2. 라이브러리

> 소프트웨어를 개발할 때 컴퓨터 프로그램이 사용하는 비휘발성 자원의 모임
> 

간단 요약 : 개발자가 필요한 기능을 호출 해 기능을 사용할 수 있는 코드의 집합

### a. 왜 사용하는가?

전문성을 위해서

- 라이브러리는 특정 분야에서 전문적인 기능을 제공
    - 활용하면 해당 분야의 전문 지식 없이도 고품질의 기능을 구현할 수 있음

### b. 장점

- 복잡한 작업 간단하게 처리
- 개발 과정 간소화
- 프로젝트 질 향상
- 특정 분야의 전문 지식 효과적으로 활용 가능케 함

## 2-3. API

> 애플리케이션과 애플리케이션이 서로 통신할 수 있도록 정의한 명세서
> 

교재에는 위와 같이 정의가 돼있는데, 위 정의는 API보다는 API 규격(사양)이라고 한다. 

API는 Application Programming Interface의 약자로 컴퓨터나 컴퓨터 프로그램 사이의 연결이다. 일종의 소프트웨어 인터페이스이다. 

### a. 왜 사용하는가?

‘서로 다른 시스템이나 애플리케이션 간에 데이터를 교환하고 기능을 공유하기 위해서’라고 교재에 나와있습니다.

즉, 다른 애플리케이션과 정보를 주고 받기 위해서입니다.

### b. API를 통해 얻는 이점

- 애플리케이션 간의 유연성과 통합성 향상
- 효율성 향상
- 비용 절감
- 보안성 강화
- 확장성
