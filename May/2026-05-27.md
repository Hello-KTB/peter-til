# HTTP 자격 증명 헤더
> 클라이언트와 서버 간의 인증 과정에서 사용자의 자격을 확인하기 위해 사용하는 헤더
> 

**용어 정리** 

헤더(Header) : 웹 브라우저와 서버 간의 통신 메시지에서 메타데이터(데이터에 대한 데이터)를 담고 있는 부분

## HTTP는 어떻게 인증하는가?

HTTP는 기본적으로 Stateless 프로토콜이다

- 매 요청마다 이전 요청을 기억하지 못함
- 매 요청마다 내가 누구인지 증명해야 함
- 보호가 필요한 리소스에 접그하기 위해서는 반드기 인증 과정이 필요함

이러한 인증 과정은 HTTP 헤더를 통해 이루어짐 (규격은 RFC에 정의되어 있음)

### 핵심 헤더

#### WWW-Authenticate

> 서버가 클라이언트에게 보내는 Response Header
> 

“이 리소스는 보호된 구역이니 인증이 필요합니다“라는 의미를 지니고 있고, 상태코드 401과 함께 전송됨

#### Authorization

> 클라이언트가 서버에게 보내는 Request Header
> 

“여기 내 신분증!”라는 의미를 지니고 있고, 실제 인증 정보를 담아서 서버로 보냄

## HTTP 인증 방식

### Basic Authentication (기본 인증)

> id와 pw를 `id:pw` 형태로 합친 뒤 Base64로 인코딩해서 헤더에 담음
> 
- Base64는 암호화가 아닌 인코딩
    - 누구든 디코딩하면 원문을 볼 수 있음
    - 그러므로 HTTPS(TLS) 환경에서만 사용해야 함

#### 장단점

**장점**

- 구현이 매우 단순함
    - 토이 프로젝트, 내부용 API에 적합

**단점**

- 매 요청마다 서버가 DB에서 id/pw를 조회하고 검증해야 함
    - 트래픽이 몰릴 경우 병목 현상 발생

### Digest Authentication

> Basic인증의 문제(매 요청마다 헤더에 중요 정보를 담아 보냄)를 개선한 방식으로, 비밀번호 대신 해시값을 보냄
> 
- 비밀번호가 노출되지 않음
    - Basic 보다는 안전
- 매 요청마다 서버가 Nonce를 생성 및 저장하고 해시 검증을 반복해야한다는 부담이 남아 있음

**용어 정리**

- Nonce : 서버가 클라이언트에게 발급하는 일회성 난수
- Realm : 서버가 관리하는 보안 공간의 범위를 나타내는 문자열

#### 동작 과정

1. 클라이언트가 보호된 리소스를 요청
2. 서버가 401 응답과 함께 `Nonce`, `Realm`을 클라이언트에게 전송
3. 클라이언트는 `비밀번호+Nonce+Realm`을 해시 함수로 변환해 Authorization 헤더에 담아 재요청
4. 서버는 동일한 방식으로 해시값을 계산해 비교하여 인증 완료

#### 장단점

**장점**

- 비밀번호가 노출되지 않음
    - Basic 보다는 안전

**단점**

- 매 요청마다 서버가 Nonce를 생성 및 저장하고 해시 검증을 반복해야한다는 부담이 남아 있음

### Bearer

> 서버는 토큰을 제시한 사람이 진짜 본인인지 따지지 않고, 토큰이 위조되지 않았으면 유효한 것으로 간주
> 

#### 장단점

**장점**

- 비밀번호가 최초 1회만 전송되어 보호됨
- 쿠키 기반 세션 인증은 브라우저에서만 잘 작동하고 도메인이 달라지면 깨지는 문제가 있었지만, 토큰 방식은 모바일 앱, SPA, 크로스 도메인 환경 모두에서 동작함
- 쿠키 기반 인증에서 발생하는 CSRF 공격에 대한 노출이 줄어듬

**단점**

- 토큰은 클라이언트 책임이기 때문에, 탈취당하면 위험함
    - 그래서 HTTPS 통신을 기본 전제
    - 일반적으로 유효기간을 짧게 설정
    - 민감도 높은 서비스일수록 더 짧게 설정
- 저장 위치에 따른 보안 취약점
    - 브라우저의 스토리지에 저장하면 XSS 공격으로 탈취 가능
    - 쿠키에 저장하면 CSRF 공격에 취약해짐

## JWT 필요성

일반적인 Bearer 토큰은 불투명 토큰

- 토큰 자체에 아무 의미 없는 무작위 문자열 → 서버는 이 토큰의 유효성 확인을 위해 반드시 DB 조회를 해야함
- 사용자가 많아지만, 매 요청마다 테이블 조회
    - DB 부하 문제 발생

이러한 문제를 해결하는 것이 `JWT(JSON Web Token)`이다. 토큰 문자열 자체에 유저 정보가 담겨 있고, 서버는 DB를 조회하지 않고 토큰의 서명만 검증해 위조 여부를 판단할 수 있음

# JWT

> 애플리케이션 간의 정보 교환을 위해 설계된, 정보를 JSON 형식으로 포함하는 자체 포함형(compact and self-contained) 토큰
> 

불투명 토큰의 한계를 돌파하기 위해 등장한 개방형 웹 표준(RFC 7519)이다.

토큰 안에 유저 정보를 직접 담고, 위변조 여부까지 토큰 스스로 증명할 수 있게 만들어 서버가 DB를 조회하지 않아도 되게 하는 것이 목적이다

**비유**

- 불투명 토큰 = 아무 글자나 적힌 티켓
- JWT = 관리자의 홀로그램 서명까지 찍힌 티켓

서버 입장에서 서명만 검증하면 내용의 위변조 여부를 즉시 알 수 있음

### Header

> 토큰의 타입과 서명에 사용한 알고리즘 정보를 담음
> 
- 헤더에 담긴 내용은 Base64로 인코딩됨

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### Payload

> 실제로 전달할 정보를 담는 영역
> 
- 이 영역 또한 Base64로 인코딩함
    - 누구나 디코딩해서 볼 수 있음
    - 그러므로 비밀번호, 주민등록번호, 카드 번호와 같은 민감 정보는 절대 넣어서는 안됨

```json
{
  "userId": 10,
  "email": "void@startupcode.kr",
  "username": "void",
  "role": "admin",
  "iat": 1609239023,
  "exp": 1609242623
}
```

### Signature

> 위변조 검증을 위한 핵심 영역
> 

해커가 페이로드 수정시 서명값이 달라짐 → 서버는 서명 검증만으로 위변조를 즉시 탐지할 수 있음

비밀 키는 서버만 보유하므로, 공격자는 유효한 서명을 새로 만들 수 없음

## 왜 JWT를 써야 하는가?

### 장단점

**장점**

- 완전한 무상태성과 확장성
    - Basic, Digest 인증은 매 요청마다 서버가 DB 조회해야함
    - JWT는 토큰 안에 인증•인가에 필요한 정보가 모두 담겨 있음
        - 서버는 CPU로 서명 검증만 수행하면 됨
        - 이러한 특징으로 Redis와 같은 공유 저장소 필요 없이 서버를 늘릴 수 있음
- DB 조회 횟수 대폭 감소
    - 기존 방식들은 DB를 거쳐야 하는 병목이 존재헀음
        - 데이터가 HDD 같은 느린 저장 장치에 쓰이기 때문
    - JWT는 이러한 병목을 제거함

**단점**

- 토큰 무효화가 어려움
    - JWT는 발급되는 순간 클라이언트가 보관하고, 서버는 상태를 들고 있지 않음
        - 특정 토큰을 만료시키는 것이 어려움
    - 위 문제를 해결하기 위해 실무에서는 Access Token과 Refresh Token을 도입
        - Access Token은 유효기간을 짧게 설정
        - Refresh Token은 유효기간을 길게 설정
- 네트워크 대역폭 낭비
    - 페이로드에 담기는 정보가 많을수록 토큰이 길어짐
    - 매 API 요청마다 수 KB짜리 토큰을 주고받음
        - 동시 접속자가 많은 서비스에서는 대역폭 낭비가 심해짐

### Access Token 과 Refresh Token

Access Token의 유효기간을 길게 설정 → 사용자 입장에선 편리하지만, 탈취시 오랫동안 악용 가능

Access Token의 유효기간을 짧게 설정 → 안전하지만, 사용자가 재로그인을 자주해야 하는 불편이 있음

위와 같이 보안성과 편의성은 반비례적인 관계를 가짐

위와 같은 딜레마를 해결하기 위해 Access Token과 Refresh Token을 같이 사용하는 방법을 실무에서 주로 적용함

| 구분 | Access Token | Refresh Token |
| --- | --- | --- |
| 역할 | API 접근용 출입증 | Access Token 재발급용 인증서 |
| 유효기간 | 짧게 설정(15~30분) | 길게 설정(2주~1달) |
| 저장 위치 | 메모리 또는 로컬 스토리지 또는 쿠키 | 서버측 Redis 또는 쿠키 |
| 전송 빈도 | 매 API 요청마다 | Access Token 만료 시에만 |

### RTR (Refresh Token Rotation)

> Refresh Token 마저 탈취당하면 장기간 악용될 수 있다는 문제를 해결하는 기법
> 

Refresh Token을 한번 사용하면 즉시 폐기하고 새것으로 교체

<img width="847" height="461" alt="rtr" src="https://github.com/user-attachments/assets/5ff50b28-6b2b-41dc-bc75-3c469f335d90" />

이미 사용된 토큰으로 재발급 요청이 들어오면, 서버는 이를 탈취된 것으로 간주하고 해당 유저의 모든 Refresh Token을 일괄 폐기한다. 해커가 발급받은 R2도 이 시점에 함께 무효화됨

# 레이어드 아키텍처

> 시스템을 책임과 변경 이유에 따라 여러 계층으로 분리해, 각 계층이 정해진 역할만 수행하도록 구성하는 구조
> 
- 각 계층이 서로 독립적으로 구성되어 있음
    - 그러므로, 한 계층의 변경이 다른 계층에 영향을 주지 않게 설계 가능

용어 정리

계층 : 각 계층이 맡는 역할의 범위와 책임의 경계

## 사용 이유

웹 요청 처리, 비즈니스 로직, 데이터 접근을 분리해 변경 범위를 국소화하고 테스트·유지보수·확장을 안정적으로 수행하기 위해서이다

### 장단점

**장점**

- 코드의 재사용성 및 유지보수성
- 변화에 유연하게 대처
- 테스트 용이성

**단점**

- 오버헤드
- 복잡성


## 역할 구분

Layered Architecture는 **Controller, Service, Repository를 역할 기준으로 분리하고, 요청 흐름이 상위 계층에서 하위 계층으로만 내려가도록 코드를 구성**하는 방식으로 사용한다.

### Controller

> 요청을 받아 처리 흐름을 처리하는 계층
> 
- UI와 상호작용하는 레이어
- 직접적인 비즈니스 로직을 수행하는 것이 아닌 사용자의 요청을 받아오고 결과를 응답하는 역할

### Service

> 비즈니스 처리를 담당하는 계층
> 
- 애플리케이션의 핵심 비즈니스 규칙과 로직을 처리

### Repository

> 데이터 접근을 담당하는 계층
> 
- 데이터베이스나 다른 저장 매체와 상호작용하는 레이어
- 실제로 데이터의 CRUD 작업을 처리

DTO : 계층 간의 데이터 전달을 위해 사용하는 객체
