# 1. 스프링 MVC

## 1-1. Spring Web MVC

> **서블릿(Servlet) API를 기반으로 구축된 강력한 웹 프레임워크**로, 모델-뷰-컨트롤러(MVC) 아키텍처를 사용하여 유연하고 분리된 웹 애플리케이션 개발을 지원
> 

### MVC 패턴

> Model View Controller의 약자로, 소프트웨어를 세 가지 역할로 나누어 개발하는 디자인 패턴
> 
- Model : 데이터와 비즈니스 로직 관리
- View : 사용자에게 보여지는 화면 담당
- Controller : 클라이언트의 요청 처리, 모델과 뷰 연결

MVC 패턴 1

- JSP 파일 하나에 모델, 뷰, 컨트롤러의 역할 모두 포함
    - 유지보수 어려움

MVC 패턴 2

- JSP와 서블릿 분리
    - JSP는 뷰를 담당
    - 서블릿은 컨트롤러 담당
    - 코드 역할 명확화
    - 유지보수성 높아짐

스프링MVC

- MVC 2 기반
- 디스패치 서블릿 도입
    - 개발자가 비즈니스 로직에만 집중할 수 있도록 함

### 왜 사용하는가?

- 서블릿, JSP
    - 서블릿 : 클라이언트의 요청을 처리하고, 응답을 생성하는 자바 클래스
    - JSP : HTML과 자바 코드를 혼합하여 작성할 수 있는 파일
    - JSP는 서블릿의 동작을 간소화하여, 개발자가 HTML과 자바 코드를 쉽게 작성할 수 있도록 함
    - JSP와 서블릿은 서로 보완적인 관계
- 한계
    - 비즈니스 로직, 뷰 렌더링을 모두 맡음
        - 코드 방대해짐
        - 유지보수 어려워짐
- 해결책
    - 역할을 분리 → MVC 패턴 적용

## 1-2. DispatcherServlet

> 클라이언트로부터 들어오는 모든 HTTP 요청을 가장 먼저 받아 공통 작업을 처리하고, 적합한 컨트롤러(Handler)로 요청을 위임하며, 응답을 반환하는 중앙 서블릿
> 

비유하자면 디스패처 서블릿은 안내 데스크 역할이다. 클라이언트의 요청이 들어오면 안내 데스크에서 요청을 접수하여, 해당 요청을 처리할 담당를 찾고 작업을 넘깁니다. 이후 부서에서 처리된 클라이언트의 요청을 다시 클라이언트에게 주는 역할을 한다고 생각하면 편하다.

### 왜 이러한 구조인가?

Spring MVC 이전의 전통적인 Servlet 기반 웹 애플리케이션에서는 요청마다 개별 Servlet이 존재했다.

- /login → LoginServlet
- /board → BoardServlet
- /user → UserServlet

이 방식의 문제점은 다음과 같다.

- 공통 로직(인증, 인코딩, 예외 처리)이 중복
- 요청 흐름이 분산되어 관리가 어려움
- 확장성과 유지보수성이 떨어짐

이 문제를 해결하기 위해 Spring MVC는 Front Controller 패턴을 도입했고, 그 역할을 수행하는 객체가 바로 DispatcherServlet이다.

DispatcherServlet은 클라이언트의 요청을 먼저 받기 위해 Spring MVC의 가장 앞단에 위치한다.

# 2. HTTPS

## 2-1. HTTPS

> HTTP의 전송 계층에 인증과 암호화를 적용해 보안을 강화시킨 통신 규약
> 

쉽게 생각하면 HTTP의 보안 강화 버전이다

### 등장 배경

#### 문제점

- HTTP 자체는 암호화되지 않은 텍스트로 통신
    - 중간에 누군가 통신내용 가로채기
    - 정보 탈취

HTTP 자체는 암호화되지 않은 상태로, 클라이언트에서 보낸 정보 그래도 서버로 가는데, 이럴 경우 위에 나열한 문제들이 발생한다

#### 해결책

HTTP 통신에 신뢰성과 무결성을 아래와 같은 방법으로 추가하자

- 서로 신뢰할 수 있음을 증명하는 인증서 사용
- 통신 내용은 SSL(Secure Socket Layer) 또는 TSL(Transport Layer Security)이라는 프로토콜로 암호화

### 작동 방식

- HTTPS 웹 사이트는 독립된 인증 기관(CA)에서 SSL/TLS 인증서를 획득해야 함
- 이러한 웹 사이트는 신뢰를 구축하기 위해 데이터를 교환하기 전에 브라우저와 인증서를 공유함
- SSL 인증서는 암호화 정보도 포함하므로 서버와 웹 브라우저는 암호화된 데이터나 스크램블된 데이터를 교환할 수 있습니다

프로세스 진행 방식

1. 사용자 브라우저의 주소 표시줄에 *https://* URL 형식을 입력하여 HTTPS 웹 사이트를 방문합니다.
2. 브라우저는 서버의 SSL 인증서를 요청하여 사이트의 신뢰성을 검증하려고 시도합니다.
3. 서버는 퍼블릭 키가 포함된 SSL 인증서를 회신으로 전송합니다.
4. 웹 사이트의 SSL 인증서는 서버 아이덴티티를 증명합니다. 브라우저에서 인증되면, 브라우저가 퍼블릭 키를 사용하여 비밀 세션 키가 포함된 메시지를 암호화하고 전송합니다.
5. 웹 서버는 프라이빗 키를 사용하여 메시지를 해독하고 세션 키를 검색합니다. 그런 다음, 세션 키를 암호화하고 브라우저에 승인 메시지를 전송합니다.
6. 이제 브라우저와 웹 서버 모두 동일한 세션 키를 사용하여 메시지를 안전하게 교환하도록 전환합니다.

### HTTPS 인증 절차

#### **인증서 발급 과정**

1. 서버측에서 준비
    - 서버는 암호화 알고리즘(RSA, ECDSA 등)을 사용하여 개인키 생성함
    - 이 키는 절대 외부에 노출 안 되며, 서버에 안전하게 보관
    - 개인키는 나중에 클라이언트와의 암호화 통신에서 메시지를 복호화하는데 사용
2. CSR**(Certificate Signing Request)** 생성
    - 서버는 인증 기관(CA)에 제출한 인증서 서명 요청(CSR)을 생성함
    - CSR에는 다음과 같은 정보 포함
        - 도메인 이름 : 인증서가 보호할 웹사이트 주소
        - 조직 정보 : 회사명, 부서명 등
        - 위치 정보 : 국가, 도시, 주소 등
        - 공개키 : 개인키와 쌍을 이루는 공개키
    - CSR은 서버의 개인키로 서명되어 생성
3. CA에 CSR 제출
    - 서버 관리자는 생성된 CSR을 신뢰할 수 있는지 인증기관(CA)에 제출함
    - 여기에는 Verisign, DigiCert, Let’s Encrypt 등의 상용 또는 무료 인증 기관 포함
    - 제출 과정에서 도메인 소유권 증명과 같은 추가 정보가 요구될 수 있음

#### 인증 기관(CA)에서의 처리

1. 신원 확인 및 검증
    - CA는 CSR을 받은 후 신청자의 신원을 확인하는 검증 과정 수행함
    - 검증 수준은 인증서 종류에 따라 다름
        - DV(Domain Validation): 도메인 소유권만 확인 (이메일, DNS 레코드, 특정 파일 업로드 등으로 검증)
        - OV(Organization Validation): 조직의 실재 여부 및 도메인 소유권 확인
        - EV(Extended Validation): 가장 엄격한 수준의 조직 검증 (법적 서류 필요)
2. 인증서 생성
    - 검증이 완료되면 CA는 SSL/TLS 인증서 생성함
    - 인증서에는 다음 정보 포함
        - 서버의 공개키
        - 도메인 이름
        - 인증서 발급자 정보
        - 인증서 유효 기간
        - 인증서 일련번호
        - CA의 디지털 서명 : CA의 개인키로 인증서 내용을 서명
    - 이 디지털 서명은 인증서의 신뢰성과 무결성을 보장하는 핵심 요소
3. 인증서 전달
    - 생성된 인증서는 서버 관리자에게 전달됨
    - 종종 중간 인증서도 함께 제공됨
4. 서버에 인증서 설치
    - 서버 관리자는 받은 인증서를 웹 서버에 설치함
    - 이때 개인키와 함께 설정되어야 함
    - 필요한 경우 중간 인증서도 함께 설치하여 인증 체인 완성

#### 인증서 검증 과정 (HTTPS 연결 시)

1. 클라이언트와 서버 간의 초기 통신
    
    (1) 클라이언트의 HTTPS 연결 요청
    
    - 사용자가 브라우저에서 HTTPS 웹사이트에 접속 시도
    - 브라이저는 서버에 보안 연결을 요청
    
    (2) 서버의 인증서 제공
    
    - 서버는 자신의 SSL/TLS 인증서를 클라이언트에게 전송함
    - 필요에 따라 중간 인증서도 함께 전송됨
2. 클라이언트의 인증서 검증
    
    (3) 인증서 검증 단계
    
    - 클라이언트(브라우저)는 받은 인증서를 다음과 같은 방법으로 검증
    1. 인증서 유효성 확인
        - 만료 여부 : 현재 날짜가 인증서의 유효 기간 내인지 확인
        - 도메인 일치 여부 : 인증서의 도메인 이름이 접속한 웹사이트 주소와 일치하는지 확인
        - 해지 여부 : CRL(Certificate Revocation List) 또는 OCSP(Online Certificate Status Protocol)를 통해 인증서가 해지되지 않았는지 확인
    2. 발급자(CA) 신뢰성 확인
        - 인증 체인(Certificate Chain) 검증 : 서버 인증서 → 중간 인증서 → 루트 인증서로 이어지는 체인 확인
        - 루트 인증서 확인 : 인증 체인의 루트 인증서가 브라우저/OS의 “신뢰할 수 있는 루트 인증서” 저장소에 있는지 확인
    3. 인증서 무결성 확인
        - 디지털 서명 검증 : CA의 공개키를 사용하여 인증서의 디지털 서명을 검증
        - 이 과정에서 인증서가 변조되지 않았음을 확인
3. 검증 결과에 따른 처리
    
    (4) 검증 결과에 따른 분기
    
    - 5A. 검증 성공 시
        - 브라우저는 서버와 안전한 HTTPS 연결을 수립함
        - 주소창에 자물쇠 아이콘 등으로 안전한 연결임을 표시함
        - 이후 SSL/TLS 핸드셰이크를 계속 진행하여 암호화된 통신을 시작
    - 5B. 검증 실패 시
        - 브라우저는 보안 경고를 표시함
        - 사용자에게 연결이 안전하지 않을 수 있다는 경고와 함께 계속 진행할지 물어봄
        - 실패 이유는 여러가지
            - 자체 서명된 인증서 사용
            - 만료된 인증서
            - 도메인 불일치
            - 신뢰할 수 없는 CA
            - 인증서 해지
            - 인증 체인 불완전

    - 위의 그림에서 나와있는 정보 외에 아래의 내용 추가
    - 만약 이전에 SSL 핸드 셰이크가 완료된 상태라면, 그때 생성된 세션 아이디(session ID)

2. 서버: 웹서버는 1번에 응답하면서 아래 정보를 클라이언트에 제공함 (server hello 단계)

- 서버의 공개키가 담긴 SSL인증서. 인증서는 CA의 비밀키로 암호화되어 발급된 상태
- 클라이언트 인증서 요청(선택사항)

3. 클라이언트: 브라우저는 서버의 SSL 인증서가 올바른지 확인

- 대부분 브라우저에는 공신력있는 CA들의 정보와 CA가 만든 공개키가 이미 설치되어 있다. 내장된 CA공개키로 암호화된 인증서를 복호화하고 정상적으로 복호화된다면 CA가 발급한 것이 증명된다. 이 과정에서 오류가 난다면 브라우저 경고를 보낸다.

4. 클라이언트: 브라우저는 자신이 생성한 난수와 서버의 난수를 사용하여 premaaster secret을 만듦

- 웹 서버 인증서에 딸려온 웹 사이트의 공개키로 이것을 암호화하여 서버로 전송한다.

5. 서버: 서버는 사이트의 비밀키로, 브라우저가 보낸 premaster secret 값을 복호화힘

- 복호화한 값을 master secret 값으로 저장한다. 이것을 사용하여 방금 브라우저와 만들어진 연결에 고유한 값을 부여하기 위한 세션키를 생성한다. 세션 키는 대칭키 암호화에 사용할 키이다. 이것으로 브라우저와 서버 사이에 주고받는 데이터를 암호화하고 복호화한다.

6. 서버 and 클라이언트: SSL 핸드셰이크를 종료하고 HTTPS 통신을 시작

- 브라우저와 서버는 SSL 핸드셰이크가 정상적으로 완료되었따. 이제는 웹 상에서 데이터를 세션키를 사용해 암호화/복호화하며, https 프로토콜을 통해 주고받을 수 있다. https 통신이 완료되는 시점에서 서로에게 공유된 세션 키를 폐기한다. 만약 세션이 아직 유지되고 있다면 브라우저는 SSL핸드셰이크 요청이 아닌 세션 ID만 서버에게 알려주면 된다.
- SSL 인증서에는 대칭키 방식과 공개키 방식 두 개 모두 사용하며, 모든 웹 콘텐츠의 전달을 공개키 방식으로 한다면 웹 서버와 브라우저에 많은 부담이 된다. -> **SSL 핸드셰이크 단계까지는 공개키 방식, 그 이후의 HTTPS 통신은 대칭키 방식을 사용한다.**

### 왜 HTTP < HTTPS 인가?

#### HTTPS 장점

- 보안
    - 모든 데이터를 암호화 형태로 전송
    - 제3가자 중간에서 가로챌 수 없음
- 권위
    - 검색 엔진은 HTTPS의 우선순위를 HTTP보다 더 높게 지정
        - HTTP의 신뢰성이 더 낮게 때문
    - 고객도 HTTP보다 HTTPS 선호

### HTTP와 HTTPS

|  | HTTP | HTTPS |
| --- | --- | --- |
| 본말 | Hypertext Transfer Protocol | Hypertext Transfer Protocol Secure |
| 기본 프로토콜 | HTTP/1과 HTTP/2는 TCP/IP를 사용합니다. HTTP/3은 QUIC 프로토콜을 사용합니다. | HTTP 요청 및 응답을 추가로 암호화하기 위해 SSL/TLS와 함께 HTTP/2 사용 |
| 포트 | 기본 포트 80 | 기본 포트 443 |
| 용도 | 이전 텍스트 기반 웹 사이트 | 모든 최신 웹 사이트 |
| 보안 | 추가 보안 기능 없음 | 퍼블릭 키 암호화에 SSL 인증서 사용 |
| 장점 | 인터넷을 통한 통신 지원 | 웹 사이트에 대한 권위, 신뢰성 및 검색 엔진 순위 개선 |

## 2-2. 대칭키

> 암호화, 복호화에 사용하는 키가 동일
> 

대칭키 암호화 방식은 암호화와 복호화에 같은 키를 사용하는 알고리즘

#### 장단점

장점

- 구현이 용이함
- 데이터를 암호화하기 위한 연산이 빨라 대용량 데이터 암호화에 적합
- 기밀성 제공
- 속도가 빠름

단점

- 강한 보안을 위해 키를 주기적으로 교환해주는 것이 좋음
- 키 탈취 및 관리가 어려움
- 무결성 지원이 부분적으로만 가능
- 부인 방지 기능을 제공하지 못함

---

## 2-3. 비대칭키

> 암호화, 복호화에 사용하는 키가 서로 다름
> 

비대칭키 암호화 방식은 암호화, 복호화할 때 서로 다른 키로 사용하는 암호화 알고리즘이다.

개인키로 암호화 → 공개키로 복호화

공개키로 암호화 → 개인키로 복호화

#### 장단점

장점

- 키 분배 및 키 관리 용이
- 기밀성, 무결성 지원
- 부인 방지 기능 제공
- 암호학적 문제 해결

단점

- 상대적으로 키의 길이가 김
- 속도가 느림
