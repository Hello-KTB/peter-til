# 1. OOP

## OOP (Object Oriented Programming)

> 객체 지향적 프로그래밍
> 

많은 객체(Object)들이 모여서 상호 협력하면서 데이터를 처리하는 방식의 프로그래밍 설계 방법

→ 프로그램을 묶음 단위로 잘게 쪼개서, 추후에 가져다 쓰기 편하게 만들어 놓은 프로그래밍 방식

### 왜 중요한가?

- 절차 지향 프로그래밍 : 함수를 이용해서 작은 부품을 만들고 이것을 결합해서 더 큰 프로그램을 만들어가는 테크닉
- But, 기술이 발전됨에 따라, 더 복잡한 애플리케이션에 대한 수요 증가
    - 절차지향 프로그래밍 한계 드러나기 시작
        - 유지보수 어렵고 복잡해짐

위와 같은 문제를 해결하기 위해 OOP 등장

### OOP 특징

- 추상화 : 복잡한 사물이나 개념에서 공통된 핵심만 추출하여 단순하게 모델링하는 것
- 캡슐화 : 객체의 데이터와 기능을 하나로 묶고, 내부 구현을 숨겨 외부의 접근을 통제(보호)하는 것
- 상속 : 부모(상위) 클래스의 속성과 기능을 자식(하위) 클래스가 물려받아 코드 중복을 줄이고 재사용하는 것
- 다형성 : 같은 부모에게서 상속받았지만 자식 클래스마다 다르게 동작하게 만드는 성질

### 객체지향 vs 절차지향

|  | **Procedural (절차지향)** | **Object-Oriented (객체지향)** |
| --- | --- | --- |
| **핵심 질문** | "어떤 **순서**로 실행할 것인가?" | "**누구**에게 이 일을 맡길 것인가?" |
| **코드 구성** | 데이터와 함수가 분리됨 | 데이터와 행동이 객체로 묶임 |
| **변경 영향** | 로직 변경 시 연쇄 수정 발생 (폭탄) | 객체 내부만 수정 (영향 국소화) |

# 2. SOLID

## SOLID

> 객체지향 설계에서 지켜줘야 할 5개의 소프트웨어 개발 원칙
> 

유지보수성과 확장성을 높이기 위해 만든 다섯 가지 핵심 원칙이다.

위 5가지 원칙들은 서로 독립된 개별적인 개념이 아니라, 서로 개념적으로 연관되어 있다. 원칙끼리 서로가 서로를 이용하기도 하고 포함하기도 한다.

### 왜 중요한가?

- 객체지향 프로그래밍 기술 면접 단골 질문
- 앞으로 배울 디자인 패턴들이 SOLID 원칙에 입각해서 만들어진 것이기 때문

### 얻는 것

- 코드 확장
- 유지 보수 관리 쉬워짐
- 불필요한 복잡성 제거
- 리팩토링 시간 줄임 → 개발의 생산성 높아짐

## SRP (Single Resposibility Principle)

> 클래스(객체)는 단 하나의 책임만 가져야 한다
> 
- 책임 → 하나의 ‘기능 담당’
    - 하나의 클래스는 하나의 기능을 담당하여 하나의 책임을 수행
- 만일 하나의 클래스에 기능이 여러 개 있음
    - 기능 변경 일어날 시, 수정 코드 많아짐
- SRP 적용
    - 한 책임의 변경으로부터 다른 책임의 변경으로의 연쇄작용 극복
- 결국 프로그램의 유지보수성을 높이기 위한 설계 기법
- 책임의 범위는 정해져 있지 않음
    - 어떤 프로그램을 개발하는지, 개발자의 생각은 어떤지에 따라 달라질 수 있음
        - SRP에는 100% 해답은 없음

## OCP (Open Closed Principle)

> 클래스는 확장에는 열려있어야 하며, 수정에는 닫혀있어야 한다
> 
- 기능 추가 요청 시
    - 클래스 확장을 통해 손쉽게 구현
    - 확장에 따른 클래스 수정은 최소화
    - 위를 적용하는 설계 기법
- 추상화 사용을 통한 관계 구축을 권장하는 것을 의미
    - 즉, 다형성과 확장을 가능케 하는 객체지향의 장점을 극대화하는 기본적인 설계 원칙

## LSP (Liskov Substitution Principle)

> 자식 타입은 언제나 부모 타입으로 교체할 수 있어햐 한다
> 
- 다형성 원리를 이용하기 위한 원칙
- 부모 메서드의 오버라이딩을 조심스럽게 따져가며 해야함
    - 부모클래스와 동일한 수준의 선행 조건을 기대하고 사용하는 프로그램 코드에서 예상치 못한 문제 발생 가능

## ISP (Interface Segregation Principle)

> 인터페이스를 각각 사용에 맞게끔 잘게 분리해야 한다
> 
- 인터페이스의 단일 책임을 강조
- 인터페이스 분리를 통해 설계하는 원칙
- 인터페이스를 사용하는 클라이언트 기준으로 분리
    - 클라이언트의 목적과 용도에 적합한 인터페이스만을 제공하는 것이 목표
- 주의점
    - 한번 인터페이스를 분리하여 구성 후, 나중에 문언가 수정사항이 생겨서 또 인터페이스들을 분리하는 행위 X

## DIP (Dependency Inversion Principle)

> 어떤 Class를 참조해서 사용해야 하는 상황이 생긴다면, 그 Class를 직접 참조하는 것이 아니라, 그 대상의 상위 요소(추상 클래스 or 인터페이스)로 참조하라는 원칙
> 
- 구현 클래스에 의존하지 말고, 인터페이스에 의존하라
- 변하기 쉬운 것 또는 자주 변화하는 것에 의존 X
- 변화하기 어려운 것에 의존하라는 것

3. JVM

## JVM (Java Virtual Machine)

> 자바 프로그램이 운영체제(OS)에 종속되지 않고 어디서든 실행될 수 있도록(Write Once, Run Anywhere) 바이트 코드를 해석하고 실행하는 가상의 컴퓨팅 엔진
> 

나의 한줄 정리

- 자바 파일을 컴파일하여 생성된 바이트코드를 운영체제에 상관없이 기계어로 변환시켜주는 엔진

### JVM의 역사

- C/C++의 경우, 운영체제나 CPU아키텍처에 따라 각각 빌드해야 하고, 코드를 따로 작성해야 했음
- 자바는 Write Once, Run Anywhere 철학을 세우며 플랫폼 독립적으로 실행 가능
- JVM이 플랫폼 독립성이 가능하도록 핵심적인 역할 수행

### 클래스 로더 (Class Loader)

> JVM 내로 클래스 파일(*.class)을 동적으로 로드하고, 링크를 통해 배치하는 작업을 수행하는 모듈
> 

→ 로드된 바이트코드들을 엮어서 JVM 메모리 영역인 Runtime Data Areas에 배치

클래스를 메모리에 올리는 로딩 기능은 한번에 메모리에 올리지 않고, 애플리케이션에서 필요한 경우 동적으로 메모리에 적재

#### 동작 과정

1. Loading : 클래스 파일을 가져와서 JVM의 메모리에 로드한다
2. Linking : 클래스 파일을 사용하기 위해 검증하는 과정이다
    1. Verifying : 읽어들인 클래스가 JVM 명세에 명시된 대로 구성되어 있는지 검사한다
    2. Preparing : 클래스가 필요로 하는 메모리에 할당한다
    3. Resolving : 클래스의 상수 풀 내 모든 심볼릭 레퍼런스를 다이렉트 레퍼런스로 변경한다
3. Initialization : 클래스 변수들을 적절한 값으로 초기화한다 (staic 필드들을 설정된 값으로 초기화 등)

### 실행 엔진 (Execution Engine)

> 클래스 로더를 통해 런타임 데이터 영역에 배치된 바이트 코드를 명령어 단위로 읽어서 실행
> 

바이트 코드 : 기계가 바로 실행할 수 있는 언어 X, 가상머신이 이해할 수 있는 중간 레벨로 컴파일 된 코드

실행 엔진은 바이트 코드를 JVM 내부에서 기계가 실행할 수 있는 형태로 변경해줌

#### 구성

인터프리터 (Interpreter)

- 바이트 코드 명령어를 하나씩 읽어서 해석하고 바로 실행
- JVM 내부에서는 디폴트로 인터프리터 방식으로 바이트코드 실행
- 같은 메소드 여러번 호출 시, 매번 해석하고 수행해야 됨
    - 전체적인 속도가 느림

JIT 컴파일러 (Just-In-Time Compiler)

- 인터프리터 단점 보완을 위해 도입된 방식
- 반복되는 코드 발견시, 바이트 코드 전체를 컴파일하여 Native Code로 변경
    - 인터프리팅하지 않고 캐싱해 둠
    - 발견시 바로 네이티브 코드로 직접 실행
- 컴파일된 네이티브 코드를 실행함 → 실행 속도가 빠름
- But, 바이트코드를 Native Code로 변환하는 데에도 비용이 소모됨
    - 인터프리터 방식을 사용하다가 일정 기준 넘어가면 JIT 컴파일 방식으로 명령어 수행

GC (Garbage Collector)

- Heap 메모리 영역에서 더는 사용되지 않는 메모릴 자동으로 회수
- 개발자가 따로 메모리를 관리하지 않아도 됨
- But, GC가 실행되는 시간은 정해져 있지 않음
    - Full GC가 발생할 경우, GC를 제외한 모든 스레드가 중지
        - 장애 발생 가능

### 런타인 데이터 영역

> JVM의 메모리 영역으로, 자바 애플리케이션을 실행할 때 사용되는 데이터들을 적재하는 영역
> 

<img width="1116" height="599" alt="image (6)" src="https://github.com/user-attachments/assets/da471718-6be4-482a-8871-644086ae6fea" />

구성은 위와 같다. 이때 메서드 영역과 힙 영역은 모든 스레드가 공유하는 영역이고, 스택 영역, PC 레지스터, 네이티브 메서드 스택은 각 스레드마다 생성되는 개별 영역이다.

#### 구성

메서드 영역

- JVM이 시작될 때 생성되는 공간
- 바이트 코드를 처음 메모리 공간에 올릴 때, 초기화되는 대상을 저장하기 위한 메모리 공간
- 프로그램이 종료될 때까지 저장
- 정적 필드와 클래스 구조만을 갖고 있다

힙 영역

- JVM이 관리하는 프로그램 상에서 데이터를 저장하기 위해 런타임 시 동적으로 할당하여 사용하는 영역
    - new 연산자로 생성되는 클래스와 인스턴스 변수, 배열 타입 등 참조 타입이 저장되는 곳
- 힙의 참조 주소는 스택이 갖고 있음
    - 해당 객체를 통해서만 힙 영역에 있는 인스턴스를 핸들링 할 수 있음
- 참조하는 변수나 필드가 없을 경우
    - GC를 실행시켜 힙 영역에서 자동으로 제거
    - GC 수행을 위해 세부적으로 나뉜 영역
        - Young Generation
            - Eden
            - Survivor 0 / Survivor 1
        - Old Generation
        - Permanent

스택 영역

- 임시적으로 사용되는 변수나 정보들이 저장되는 영역
    - int, long, boolean 등 기본 자료형
- 메서드 호출 시 각각의 스택 프레임(그 메서드만을 위한 공간) 생성
    - 메서드 안에서 사용되는 값들 저장
    - 호출되는 메서드의 매개변수, 지역 변수, 리턴 값, 연산 시 일어나는 값들을 임시 저장
- 메서드 수행 끝날시 프레임별로 삭제
- 기본 타입 변수는 스택 영역에 값을 직접 가짐
- 참조타입 변수는 힙 영역이나 메서드 영역의 객체 주소를 가짐

PC 레지스터

- 스레드가 시작될 때 생성
- 현재 수행중인 JVM 명령어 주소를 저장하는 공간

네이티브 메서드 스택

- 실제 실행할 수 있는 기계어로 작성된 프로그램을 실행시키는 영역
- 자바 이외의 언어(C, C++, 어셈블리 등)로 작성된 네이티브 코드를 실행하는 공간
- 사용되는 메모리 영역으로는 일반적인 C 스택 사용

### JNI (Java Native Interface)

> 자바가 다른 언어로 만들어진 애플리케이션과 상호작용할 수 있도록 인터페이스를 제공하는 프로그램
> 

JVM이 Native Method를 적재하고 수행할 수 있도록 함

### 네이티브 메서드 라이브러리

- C, C++로 작성된 라이브러리를 칭함
- 헤더가 필요하면, JNI가 이 라이브러리를 로딩해 실행
