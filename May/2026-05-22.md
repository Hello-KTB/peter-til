# 1. Spring MVC

> MVC 패턴으로 만들어진 자바 기반의 웹 프레임워크
> 

<img width="860" height="573" alt="ㅡㅍㅊ" src="https://github.com/user-attachments/assets/79039d7b-b710-47d3-8571-924a8ca31ac2" />

흐름

1. DispatcherServlet이 모든 웹 브라우저로부터의 요청을 받는다.
2. DispatcherServlet은 HandlerMapping으로 부터 주어진 request를 처리할 수 있는 Handler객체를 가져온다.
3. 가져온 Handler를 실행시킬 수 있는 HandlerAdapter객체를 가져온다.
4. 만약 해당 Controller를 처리할 Handler객체에 적용할 interceptor가 존재한다면 모든 interceptor객체의 preHandle메소드를 호출한다.
5. HandlerAdapter객체를 통해 실제 컨트롤러의 메소드를 실행 후 ModelAndView를 얻는다.
6. 만약 해당 Controller를 처리할 Handler객체에 적용할 interceptor가 존재한다면 모든 interceptor객체의 postHandle메소드를 호출한다.
7. DispatcherServlet은 5번 과정에서 얻은 ModelAndView를 통해 view name을 ViewResolver에게 전달하여 응답에 필요한 View객체를 얻어온다.
8. DispatcherServlet은 7번 과정에서 얻은 View객체에 5번 과정에서 얻은 ModelAndView의 Model을 파라미터로 넘겨주어 render메소드를 호출하여 페이지 렌더링을 수행한다.
9. DispatcherServlet은 렌더링된 페이지를 response로 사용자에게 리턴한다.

## 1.1. MVC (Model View Controller)

> Model, View, Controller 세 가지 역할로 분할된 디자인 패턴
> 

<img width="2208" height="1568" alt="easyMVC" src="https://github.com/user-attachments/assets/590c2788-50c9-4157-844c-736011a88d7e" />

MVC 구조를 간단하게 표현하면 위와 같다. 

기존에는 역할을 분리되어 있지 않았습니다. 사용자 인터페이스 코드, 다양한 데이터 렌더링 로직, 데이터베이스에서 데이터 가져오는 코드 모두 같은 파일에 작성되어 있었습니다.

이로 인해서 애플리케이션 관리 및 디버깅이 어려웠습니다. 이러한 문제를 해결하기 위해 트뤼그베 렌스카우가 1979년에 MVC를 제안했습니다

### 1.1.1. Model

> 애플리케이션 데이터, 비즈니스 로직을 다룬다
> 

비즈니스(소프트웨어 공학 측면)란 “소프트웨어가 해결해야 하는 현실 세상의 문제”를 의미한다. 즉 해당 소프트웨어, 애플리케이션이 존재하는 이유가 비즈니스이다. 

예를 들어 SNS는 미디어 시청, 댓글 + 공감 + 공유를 통한 소통이 SNS의 비즈니스이다.

비즈니스 로직이란 “소프트웨어가 현실 세계의 문제를 해결하는 방법을 구체적으로 구현한 것”이라고 정의가 가능하다.

**역할**

- 데이터 관리 : CRUD 작업
- 비즈니스 규칙 시행
- 뷰와 컨트롤러에 상태 변경 사항 알림

### 1.1.2. View

> UI 로직을 다룬다
> 

**역할**

- 특정 형식으로 사용자에게 데이터 렌더링(표시)
- UI 표시
- 모델이 변경될 때 디스플레이 업데이트

### 1.1.3. Controller

> View와 Model를 상호간에 연결 시킨다
> 

**역할**

- 사용자 요청을 전달 받고 해석
- 사용자 행동에 따른 모델 업데이트
- 적절한 UI 선택 및 디스플레이

# 2. Dispatcher Servlet

> Spring MVC에서 front controller 역할을 하는 핵심 구성 요소이다.
> 

디스패처는 영어로 ‘보내는 사람’ 또는 ‘배차원’을 뜻한다. 서블릿은 사용자의 요청에 맞게 동적으로 결과물을 만드는 자바 프로그램이다.

디스패처 서블릿은 서블릿의 일종으로, HTTP 요청을 가장 먼저 받아서 적절한 컨틀로러에 전달하는 역할을 한다. 또한 핸들러 매핑과 뷰 해석을 포함한 응답 생성 프로세스 관리를 합니다.

정리하자면

- 수신 요청을 적절한 컨틀롤러 라우팅
- 뷰 리졸버, 핸들러 매핑, 컨버터, 예외 처리기 등 다른 구성 요소에 작업 위임
- MVC 스택의 여러 부분 사이에서 조정자 역할 수행

## 2.1. Front Controller

> 애플리케이션 자원에 대한 모든 요청은 단 하나의 핸들러로 다루며 요청에 적절한 핸들러를 반환하는 디자인 패턴이다.
> 

프론트 컨트롤러라고 불리는 이유는 요청 처리를 한 곳으로 집중시킨 후에 핸들러로 전달하기 때문이다.

### 2.1.1. Helper

> View 또는 컨트롤러가 처리를 완료하도록 돕는 역할
> 

헬퍼는 뷰에 필요한 데이터를 수집하고 이 중간 모델을 저장하는 책임을 가지며, value bean이라고도 불린다.

위 헬퍼 함수들을 활용해서 프론트 컨트롤러의 전달 메커니즘을 구현했다.

# 3. 레이어드 아키텍처

> 시스템을 책임과 변경 이유에 따라 여러 계층으로 분리해, 각 계층이 정해진 역할만 수행하도록 구성하는 구조
> 

레이어드 아키텍처는 시스템을 이해할 때 “이 기능은 어디에 속하는가”를 계층의 책임으로 판단하게 만들고, 코드가 어디에 존재해야 하는지를 역할 기준으로 결정할 수 있도록 합니다.

### - MVC 패턴의 한계

실제 프로그램은 복잡함. 요청이 오면 DB에 접근하여 요청에 따른 데이터를 반환하거나 저장, 삭제해야 하고, 단순한 기능만 있는 것이 아니기 때문에 요청에 맞는 데이터를 처리해서 화면에 출력하는 로직이 구현되어야 함.

### - MVC 패턴과 차이점이 무엇이냐?

MVC는 웹 요청과 응답을 어떻게 처리할지에 초점을 맞춤 패턴

레이어드 아키텍처는 코드를 어떻게 역할별로 분리할지에 대한 구조

- MVC **패턴은 사용자 인터페이스**의 로직을 구성하는 데에만 초점을 맞춥니다 .
- **3계층 아키텍처는** 더 광범위한 문제를 다룸.
    - **애플리케이션 전체의 코드를 체계적으로 구성하는 것에 관한 것**

## 3.1. Controller (Presentation layer)

> 스프링 부트 애플리케이션의 진입점 역할
> 

컨트롤러는 사용자의 요청을 가장 먼저 받는 계층으로, 요청에 맞는 곳으로 안내하는 역할을 한다.

**역할**

- 사용자와 가장 가까운 계층
- 사용자와 상호작용
- Spring MVC 객체를 말하며, 디스패치 컨트롤러, 컨트롤러, 보, 모델이 포함됨

## 3.2. Service (Business layer)

> 애플리케이션의 핵심 비즈니스 로직을 포함
> 

실제 비즈니스 로직이 구현되는 곳이다. “회원가입시 중복 이메일 체크”같은 규칙들이 여기서 구현된다.

**역할**

- 실제 비즈니스 로직을 수행하는 컴토넌트로 트랜잭션 및 기능을 수행함
- 컨트롤러에서 요청을 보내면 DAO(data access layer)를 이용해 실제로 비즈니스 로직을 수행함
- 보통 하나의 비즈니스 로직은 하나의 트랜잭션으로 동작(ACID 특징)함

## 3.3. Repository (Persistence layer)

> 데이터베이스 상호 작용 및 데이터 접근 로직 담당
> 

데이터베이스와의 통신을 담당합니다. SQL쿼리나 데이터 접근을 캡슐화해서 서비스 계층이 데이터베이스 구조를 알 필요 없게 만든다.

**역할**

- 데이터베이스에 연동되어 데이터의 저장과 조회를 담당
- DB에 값을 저장하거나 가져오기 위해 JDBC, MyBatis, JPA 등을 사용해 구현한 DAO임

DAO **(Data Access Object)** : DB에 접근하는 Java 객체

DTO **(Data Transfer Object)** : 계층간 데이터 교환을 위한 Java Bean으로, 로직을 가지지 않는 데이터 객체임

- 관심사 분리
- 보안성 강화

## 3.4. 흐름

<img width="769" height="532" alt="레이어드" src="https://github.com/user-attachments/assets/19125350-c22a-4985-94de-82477100bf3c" />

1. 클라이언트 요청
2. 컨트롤러 계층에서 DispatchServlet이 HandlerMapping을 통해 Controller에게 클라이언트의 요청을 알려줌
3. 컨트롤러는 클라이언트 요청 처리를 서비스 계층에게 요구함.
    1. 넘겨줄 데이터가 있을 경우 Domain Object에 담음
4. 클라이언트 요청을 적절히 처리한 후 데이터베이스 저장 혹은 데이터를 꺼내기 위해 리포지토리 계층에 DAO에 요청함
    1. 비즈니스 로직 수행에 필요한 데이터가 있으면 Domain Object에서 가져옴
    2. 리포지토리 계층으로 넘겨줄 데이터가 있으면 Domain Object에 저장
5. 데이터베이스에 저장하기 위해 필요한 데이터를 DO에서 가져오거나, 넘겨줄 데이터가 있으면 DO에 저장
6. 모든 처리가 끝나면 컨트롤러는 클라이언트 요청이 처리된 데이터와 사용할 뷰 정보를 DO에서 가져와 ModelAndView에 담음.
7. ModelAndView 객체를 디스패처 서블릿에 넘김
8. Dispatcher 서블릿에서 뷰리졸버를 통해 뷰를 선택하고 클라이언트에게 요청이 처리된 데이터를 화면에 출력
