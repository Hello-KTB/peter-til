# 1. NoSQL

> Not Only SQL의 약자로, SQL만을 사용하지 않는 여러 유형의 데이터베이스
> 

## 1-1. 왜 알아야 하는가?

데이터의 형식은 다채로워지고, 사용자가 데이터를 작성하면서 동시에 많은 양이 작성되고, 기존 스키마들은 규칙이 너무 강하고, 사용자가 늘면서 빠르게 확장해야 하는데, 기존 RDB만으로는 한계가 있음.

관계형 DB의 한계

- 정규화된 테이블 구조
    - 일관성 보장, 관계 지향적
    - 그러나 유연하지 못함
- 트랜잭션
    - 원자성을 보장
    - 그러나 동시 처리성이 낮음
- 디스크 기반
    - 수직 확장에 의존하는 테이블을 영원히 저장
    - 그러나 확장성이 낮음

위 관계형 DB의 한계에서 벗어나서 아래와 같은 기능들이 필요했음

- 유연한 데이터 구조
    - 스키마에서 자유롭게 관계가 아닌 Doc, Key-Value, Graph 등
- 높은 동시 처리성
    - JOIN과 트랜잭션이 아닌 단순 조회 성능을 빠르게
- 높은 확장성
    - 수평 확장에 최적화된 가용성과 분할이 가능

이러한 이유들로 인해서 NoSQL이 등장하게 됐다.

## 1-2. NoSQL 유형별 정리

### a. 키-값 저장소 (Key-Value Store)

> 각 키에 하나의 값이 매핑되는 가장 단순한 형태의 데이터 저장 방식
> 

#### 대표적인 예시

- Redis, AEROSPIKE

#### 동작 방식

- 쓰기 : 키를 해싱하여 데이터 저장 위치 결정
- 읽기 : 키를 입력받아 데이터를 검색
- 샤딩 : 해시 함수를 사용해 데이터를 여러 노드에 분산 저장

#### 장단점

장점

- 매우 빠른 읽기/쓰기 속도
    - 인메모리 구조
    - 해시 테이블 기반
- 구조 단순, 수평 확장 용이함

단점

- 데이터 구조가 단순해서, 복잡한 쿼리나 검색이 어려움
- value 내부 구조를 DB가 이해하지 못함

<aside>
💡

#### 인메모리

메모리(RAM)

- 데이터 날아감 (휘발성)
- 속도 빠름
- 용량 적음
- 가성비 안 좋음

메모리를 쓰기 좋은 경우

- 데이터가 휘발되도 크게 지장이 없음
- 자주 접근되어서 속도에 많이 예민
- 저장되는 데이터가 복잡하지 않고, 작은 데이터
- 적은 용량으로도 서비스가 가능한

Key-Value Store

- Key랑 Value만 저장해서 데이터가 작음
- 자주 접근하는 데이터라서 속도가 매우 중요
- 세션은 모든 서비스에서 접근 → 느려지면 전체가 느려짐
- 저장하는 값들이 없어지더라도 크게 문제 없음
- 세션, 토큰, 설정 듣등 안 날아가면 좋지만, 날아가도 서비스에 큰 영향을 주지 않음

그래서 Key-Value Store에 인메모리 형식이 많음

</aside>

#### 주 사용처

- 세션, 캐시 토큰, 사용자 설정 같은 곳
- 많이 써야하고, 많이 읽혀지는 곳 (속도에 민감한 것들)

### b. 문서 저장소 (Document Oriented Databases)

> JSON, XML과 같은 문서 형식을 사용하여 데이터를 저장
> 

#### 대표적인 예시

- MongoDB, CouchDB

#### 동작 방식

- 쓰기 : 고유 ID로 문서를 저장
- 읽기 : ID 또는 특정 조건(필드 값)을 기준으로 문서를 검색
- 인덱스 : 특정 필드에 대해 인덱스를 생성하여 조회 속도를 최적화

#### 장단점

장점

- 구조가 자유로워 스키마 변경이 유연
- 문서 단위로 조회, 수정 가능
- 쿼리 검색 유연

단점

- JOIN이 어려움 → 복잡한 관계 데이터는 비효율적
- 데이터 중복 허용

#### 주사용처

- 콘텐츠 관리, 블로그, 게시판, 카탈로그, 채팅 시스템
- 속성의 수정이 많거나, 관계성이 낮은 데이터

### c. 컬럼 기반 저장소 (Column-Family Store)

> 컬럼 단위로 데이터를 저장하고 관리하여, 대량의 데이터를 빠르게 조회하고 분석할 수 있음
> 

#### 대표적인 예시

- Cassandra, HBASE

#### 동작 방식

- 쓰기 : RowKey와 Column 기준으로 데이터를 저장
- 읽기 : 특정 RowKey 또는 Column 기반으로 데이터 검색
- 샤딩 : RowKey를 기준으로 데이터 분산

#### 장단점

장점

- 대용량 데이터, 빅데이터 처리 적합
- 컬럼 단위 조회 최적화 → 읽기 성능 좋음

단점

- 설계가 복잡함. 스키마 잘못 설계하면 비효율
- 단순 조회/저장 외 복잡 쿼리는 어려움

#### 주 사용처

- 로그 수집, 분석, 시계열 데이터, 추천 시스템
- 속성의 수정이 많거나, 관계성이 낮은 데이터

### d. 그래프 데이터베이스 (Graph Database)

> 데이터를 노드와 엣지로 표현하여, 객체 간의 관계를 중심으로 데이터를 저장하고 조회
> 

#### 대표적인 예시

- Neo4j

#### 동작 방식

- 쓰기 : 데이터는 노드와 간선으로 저장
- 읽기 : 노드와 관계를 탐색
- 인덱스 : 노드 및 간선에 대한 인덱스를 생성하여 탐색 속도 향상

#### 장단점

장점

- 관계 기반 조회 최적화
- 소셜 네트워크, 추천 시스템에서 효율적

단점

- 트랜잭션/대용량 처리 복잡
- 수평 확장이 어려움(관계를 유지해야함)

#### 주 사용처

- 소셜 그래프, 추천 엔진, 지식 그래프

# 2. 데이터베이스 확장

> 데이터베이스를 물리적 또는 논리적으로 분산시키는 기술
> 

데이터베이스 확장은 부하 분산과 시스템의 확장성 향상을 목표로 한다

## 2-1. 왜 사용하는가?

데이터와 사용자가 급격히 증가하는 시스템에서는 기존의 단일 서버 데이터베이스로는 처리 한계에 도달하기 쉬움

→ 시스템의 무중단 운영과 효율적인 자원 활용을 위해 데이터베이스 확장이 필수

데이터베이스 확장을 통해 얻는 이점은

- 데이터 관리와 접근성 개선
- 시스템 장애에 대한 내성 갖춤

등의 이점이 있다

## 2-2. 데이터베이스 확장 종류

### Partitioning(파티셔닝)

> 논리적으로 하나의 거대한 테이블이나 인덱스를 관리하기 쉽고 성능이 좋은 작은 물리적 조각(파티션)으로 나누는 데이터베이스 관리 기법
> 

#### 수직(Vertical) 파티셔닝
<img width="577" height="430" alt="파티셔닝2" src="https://github.com/user-attachments/assets/076a2a5b-71d5-4252-affa-f389e5fb3736" />

> 테이블을 열(Column) 기준으로 분리하여 자주 접근하는 데이터 그렇지 않은 데이터를 나눔
> 

장점

- 조회가 잦은 데이터에 대한 I/O 감소
- 테이블 잠금, 캐싱 효율 증가

단점

- 조인 필요도가 늘어서 쿼리 복잡도 증가
- 2개 테이블 동시 적용 트랜잭션 시 관리 어려움

#### 수평(Horizontal) 파티셔닝 (또는 샤딩)
<img width="790" height="446" alt="파티셔닝1" src="https://github.com/user-attachments/assets/c9182ff6-5ee9-4b12-9561-67808360d53c" />

> 데이터를 행(row) 단위로 나누어 여러 테이블 또는 여러 DB에 분산 저장하는 방식
> 

테이블 구조는 동일하지만, 저장되는 행위 범위가 서로 다름

목적

- 대용량 테이블에서 **읽기·쓰기 부하 분산**
- 단일 DB 서버의 **성능 한계 극복**
- 특정 범위 데이터만 조회하도록 하여 **스캔 비용 감소**

장점

- 많이 작성되는 경우, 쓰기 성능 증가
- 특정 파티션 별로 처리하기 좋음
- 아카이빙, 백업이 쉬움

단점

- 인덱스 관리 힘듬
- 데이터 불균형
- 파티션간 쿼리 검색이 어려움
- 트랜잭션 어려움

### Replicaion(복제)

> **하나의 데이터베이스에 저장된 데이터를 여러 노드로 복사하여 유지하는 기술**
> 

#### 장단점

장점

- 고가용성 제공
- 읽기 부하 분산
- 장애 발생 시 빠른 복구 가능

단점

- 데이터 동기화로 인한 문제 발생
- 스토리지 비용 증가
- 대역폭 요구 사항 증가

### Sharding(샤딩) vs Horizontal Partitioning

같은 의미로 사용되곤 하나, 차이점이 있다

- 수평 분할은 같은 데이터베이스 내에서 하나의 큰 테이블을 쪼개 분산 저장하는 기법
- 샤딩은 하나의 큰 테이블을 쪼개 다른 데이터베이스에 분산 저장하는 기법

# 3. 서버 캐시

> 웹 서버가 데이터를 빠르게 제공하기 위해 자주 사용되는 정보를 임시로 저장하는 장소
> 

## 3-1. 왜 사용하는가?

웹 사이트의 속도를 높이고 서버 부하를 줄여 UX를 개선할 수 있기 때문

트래픽이 점점 증가하면 처리해야 하는 용량 또한 늘어난다. 그런데 많은 클라이언트가 똑같은 데이터를 요청을 하는데 일일이 데이터베이스에 요청을 한다면 너무 비효율적이다. 

자주 조회되는 데이터를 미리 올려둔다면 데이터베이스를 거치지 않고 서버에서 바로 요청을 처리할 수 있는데 이를 ‘캐싱’이라고 한다.

## 3-2. 서버 캐시 유형

### a. 로컬 캐시

> 각 서버 인스턴스에 독립적으로 존재하며, 서버의 리소스를 사용하여 데이터를 캐싱한다
> 

장점

- 데이터 접근 속도 빠름
- 추가적인 네트워크 지연 없음

단점

- 스케일 아웃(수평 확장, 즉 서버 대수 늘리기) 시, 일관성 유지 힘듬
- 각 서버 캐시가 독립적으로 작동

### b. 로컬 캐시

> 여러 서버 인스턴스 간에 공유되며, 네트워크를 통해 접근 가능한 별도의 캐시 서버에서 데이터를 관리한다
> 

장점

- 데이터 일관성과 공유
- 동일한 캐시 데이터 사용

단점

- 네트워크 지연 가능성
- 로컬에 비해 상대적으로 느림
