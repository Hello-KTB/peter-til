# 1. Namespace (네임스페이스)

!image (1).png.png)

## 핵심 개념

> 하나의 쿠버네티스 클러스터 안에서 리소스를 목적이나 팀별로 구분하여 관리하는 논리적인 공간
> 

네임스페이스는 클러스터를 물리적으로 나누는 기능이 아니다. 하나의 클러스터 안에서 논리적으로 공간을 구분한다.

> 사무실 비유: 같은 건물 안에 개발팀·디자인팀·기획팀이 있을 때, 각 팀에 독립된 공간을 주는 것. "회의실"이라는 이름은 같지만 각 팀의 회의실은 서로 다른 리소스다.
> 

## 네임스페이스가 필요한 이유

네임스페이스 없이 하나의 클러스터에 dev·staging·production 환경을 모두 올리면:

- 쿠버네티스에서 같은 종류의 리소스는 동일한 이름을 가질 수 없어 충돌 발생
- `api-server`라는 파드가 개발용인지 운영용인지 구분 불가
- 개발자가 운영 리소스를 실수로 삭제하거나 수정할 가능성이 높아짐

```
Kubernetes Cluster
├── dev Namespace        → api-server Pod, database Service
├── staging Namespace    → api-server Pod, database Service
└── production Namespace → api-server Pod, database Service
```

## 네임스페이스의 핵심 역할 4가지

### 1. 리소스를 논리적으로 구분

관련된 리소스를 하나의 그룹으로 묶어 관리한다. 팀 규모에 따라 나누는 기준이 달라진다.

| 규모 | 클러스터 구성 | 네임스페이스 기준 |
| --- | --- | --- |
| 소규모 팀 | 단일 클러스터 | 환경별 (dev, stag, prod) |
| 대규모 팀 | 환경별 클러스터 분리 | 팀·서비스 단위 (frontend, backend, data) |

### 2. 리소스 이름 범위 제공

같은 네임스페이스 안에서는 같은 종류의 리소스 이름이 중복될 수 없다. 다른 네임스페이스라면 동일한 이름의 리소스를 생성할 수 있다.

```
dev Namespace        → Pod/api-server (가능)
production Namespace → Pod/api-server (가능, 서로 다른 리소스)
dev Namespace        → Pod/api-server + Pod/api-server (불가, 동일 네임스페이스 중복) 
```

### 3. 명령어 범위 구분

```bash
kubectl get pods              # 현재 네임스페이스(default)
kubectl get pods -n dev       # dev 네임스페이스만
kubectl get namespaces        # 네임스페이스 목록
kubectl apply -f pod.yaml -n dev
```

### 4. 정책 적용 단위

| 정책 | 역할 |
| --- | --- |
| ResourceQuota | 네임스페이스 전체가 사용할 수 있는 CPU, 메모리, 파드 개수 총량 제한 |
| LimitRange | 개별 컨테이너·파드의 리소스 범위 설정 |
| 접근 권한 (RBAC) | 특정 사용자나 팀이 특정 네임스페이스만 관리하도록 구성 |
| NetworkPolicy | 네임스페이스 또는 파드 사이의 네트워크 통신 제한 |

## 오해하기 쉬운 것들

**1. 클러스터를 물리적으로 나누지 않는다.**

네임스페이스는 논리적 구분이다. CPU·메모리·디스크 같은 실제 자원은 여전히 공유된다. 노드에 문제가 생기면 네임스페이스만으로 격리되지 않는다.

**2. 네임스페이스만으로 네트워크가 차단되지 않는다.**

AWS VPC Subnet과 달리, 네임스페이스가 달라도 파드 간 통신은 기본적으로 가능하다. 쿠버네티스 보안 사고의 흔한 패턴이 여기서 발생한다. 네임스페이스 간 통신을 제한하려면 CNI의 NetworkPolicy를 별도로 설정해야 한다.

**3. 네임스페이스만으로 접근 권한을 나눌 수 없다.**

네임스페이스를 분리해도 다른 팀의 네임스페이스에 접근이 가능하다. 접근 권한 분리는 RBAC으로 별도 설정해야 한다.

## 기본 네임스페이스

```bash
kubectl get namespaces
```

| Namespace | 역할 |
| --- | --- |
| `default` | 네임스페이스를 지정하지 않은 리소스가 기본으로 생성되는 공간 |
| `kube-system` | DNS, kube-proxy 등 쿠버네티스 시스템 컴포넌트가 실행되는 공간 |
| `kube-public` | 클러스터 전체에서 공개적으로 읽을 수 있는 정보에 사용되는 공간 |
| `kube-node-lease` | 각 노드의 상태 확인을 위한 Lease 오브젝트가 저장되는 공간 |

## 구조적 특징

- 네임스페이스는 **중첩할 수 없다.** `production > backend > payment` 같은 계층 구조가 불가능하다.
- 하나의 리소스는 **하나의 네임스페이스에만** 속할 수 있다.

## 실무 사용 기준

| 원칙 | 내용 |
| --- | --- |
| 세세하게 나누지 않는다 | 파드마다 네임스페이스를 만들지 않는다. 팀·서비스·환경 단위로 나눈다 |
| 명명 규칙 공유 | 이름만 보고 목적을 알 수 있게 (`payment-dev-ns`, `team-a-ns`). 회사 단위로 규칙 통일 |
| default 사용 금지 | default 네임스페이스에 앱을 올리면 관리가 어렵고 다른 정책들과 분리되지 않는다 |
| 현재 NS 확인 필수 | 명령어 실행 전 `-n` 옵션으로 대상 네임스페이스를 반드시 명시한다 |

> 🚨 **네임스페이스 삭제 주의:** `kubectl delete ns dev` 실행 시 내부의 파드·서비스·시크릿 등 모든 리소스가 함께 삭제된다.
>

# 2. ResourceQuota

## 핵심 개념

> 하나의 Namespace에서 요청할 수 있는 CPU·메모리와 생성할 수 있는 쿠버네티스 리소스의 총량을 제한하는 정책
> 

네임스페이스는 클러스터를 논리적으로만 분리하므로, 자원은 여전히 공유된다. ResourceQuota 없이는 특정 팀이나 파드가 클러스터 자원을 독점할 수 있다.

> 비유: 팀별 예산. 팀 전체 예산(총량)을 미리 제한해서 개발팀이 회사 예산 전부를 가져가지 못하게 한다.
> 

## ResourceQuota가 없으면 생기는 문제

```
Worker Node (CPU: 8 Core, Memory: 16Gi)
├── team-a Pod → 7 Core 요청
├── team-b Pod → 1 Core 요청
└── team-c Pod → 배치 불가 (Pending 상태)
```

team-a가 자원 대부분을 가져가면 team-c는 아무리 요청해도 파드가 배치되지 않는다.

## ResourceQuota 제한 대상

| 대상 | 예시 |
| --- | --- |
| 컴퓨팅 자원 | CPU requests/limits 합계, Memory requests/limits 합계 |
| 오브젝트 수 | 파드 개수, 서비스 개수, ConfigMap 개수, PVC 개수 등 |

## ResourceQuota와 Pod Requests·Limits의 관계

```
requests / limits    → 각 컨테이너가 얼마나 요청하고 사용할 것인가
ResourceQuota        → Namespace 전체에서 requests / limits의 합계를 어디까지 허용할 것인가
```

| 구분 | Pod requests·limits | ResourceQuota |
| --- | --- | --- |
| 적용 범위 | 개별 컨테이너·파드 | 네임스페이스 전체 |
| 주요 목적 | 스케줄링 기준과 실행 상한 설정 | 누적 요청량과 오브젝트 수 제한 |
| 초과 시점 | 실행 중 제한 또는 스케줄링 실패 | 리소스 생성·수정 요청 단계에서 거부 |

## YAML 구조

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "2"
    requests.memory: "2Gi"
    limits.cpu: "4"
    limits.memory: "4Gi"
    pods: "30"
```

## 중요한 동작 특성

**ResourceQuota는 실제 사용량이 아닌 선언된 requests·limits 합계를 기준으로 작동한다.**

실제 CPU 사용량이 1.2 vCPU여도, 파드에 선언된 requests 합계가 4 vCPU라면 Quota 4 vCPU를 다 쓴 것으로 간주한다.

**ResourceQuota가 있는 네임스페이스에 requests·limits 없는 파드를 배포하면 거절된다.**

Quota는 선언값의 합산으로 계산하므로, 값이 없는 파드는 계산이 불가능하여 배치 자체를 막는다. 이 문제를 해결하기 위해 LimitRange를 함께 사용한다.

## 언제 사용하는가

| 상황 | 목적 |
| --- | --- |
| 여러 팀이 하나의 클러스터 공유 | 특정 팀이 자원을 독점하지 못하도록 |
| 환경별 자원 제한 | dev에 prod보다 적은 자원 할당 |
| 오브젝트 무한 생성 방지 | 데드락으로 인한 파드 폭증 같은 상황의 최후 방어선 |

# 3. LimitRange

## 핵심 개념

> 특정 Namespace에서 생성되는 개별 컨테이너나 Pod의 requests와 limits에 기본값, 최솟값, 최댓값을 적용하는 정책
> 

```
Namespace 정책 체계

ResourceQuota  → Namespace 전체 총량 제한
LimitRange     → 개별 컨테이너의 기본값·최솟값·최댓값 관리
```

> 비유: ResourceQuota가 팀 전체 예산이라면, LimitRange는 개인별 결제 한도. 팀 예산이 1,000만 원이어도 신입 인턴이 800만 원짜리 장비를 혼자 결제하지 못하게 한다.
> 

## LimitRange가 필요한 이유

ResourceQuota만 있으면 컨테이너 하나가 네임스페이스 전체 총량을 독점할 수 있다.

```
Namespace CPU request 예산: 4

Pod A → Container A: request 4  (전체 독점)
남은 예산: 0
```

LimitRange로 컨테이너 하나의 최솟값·최댓값을 제한한다.

```
컨테이너 하나의 CPU request
─ 최소: 100m
─ 최대: 1
```

## LimitRange 기능

| 기능 | 설명 |
| --- | --- |
| 기본값 적용 | requests나 limits를 생략한 컨테이너에 기본값 자동 적용 |
| 최솟값 제한 | 지나치게 작은 request를 선언하지 못하도록 제한 |
| 최댓값 제한 | 하나의 컨테이너가 지나치게 큰 limit을 선언하지 못하도록 제한 |
| 비율 제한 | request와 limit의 차이가 지나치게 커지지 않도록 제한 |
| PVC 제한 | 개별 PVC가 요청할 수 있는 스토리지 용량 범위 제한 |

## YAML 구조

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: team-a-limitrange
  namespace: team-a
spec:
  limits:
    - type: Container          # Container / Pod / PVC
      min:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "1"
        memory: "1Gi"
      defaultRequest:
        cpu: "250m"
        memory: "256Mi"
      default:
        cpu: "500m"
        memory: "512Mi"
      maxLimitRequestRatio:
        cpu: "2"
        memory: "2"
```

| 필드 | 역할 |
| --- | --- |
| `min` | 개별 리소스가 요청해야 하는 최소 기준 |
| `max` | 개별 리소스에 설정할 수 있는 최대 기준 |
| `defaultRequest` | request를 생략했을 때 적용되는 기본값 |
| `default` | limit을 생략했을 때 적용되는 기본값 |
| `maxLimitRequestRatio` | limit이 request의 몇 배까지 가능한지 제한 |

## ResourceQuota vs LimitRange

| 구분 | ResourceQuota | LimitRange |
| --- | --- | --- |
| 적용 범위 | 네임스페이스 전체 | 개별 컨테이너·파드·PVC |
| 주요 목적 | 전체 리소스 총량 제한 | 개별 리소스 범위 및 기본값 제한 |
| 기본값 적용 | 불가 | 가능 |
| 초과 시 | 생성·수정 요청 거부 | 생성·수정 요청 거부 |

## 중요한 동작 특성

- LimitRange는 **실제 사용량을 실시간으로 제한하지 않는다.** 스케줄링 시점에 선언값을 검사하는 용도다. 이미 배포된 파드는 LimitRange를 변경해도 자동으로 수정되지 않는다.
- 네임스페이스당 LimitRange는 **하나만** 만드는 것이 권장된다. 여러 개를 만들면 기본값이 어떻게 적용되는지 예측하기 어려워진다.

# 4. ConfigMap

## 핵심 개념

> 애플리케이션 코드와 일반 설정값을 분리하여, 동일한 컨테이너 이미지를 환경별로 다르게 실행할 수 있게 해주는 쿠버네티스 리소스
> 

| 환경 | API 주소 | 로그 레벨 |
| --- | --- | --- |
| 개발 | `https://dev-api.example.com` | `debug` |
| 테스트 | `https://test-api.example.com` | `info` |
| 운영 | `https://api.example.com` | `warn` |

쿠버네티스는 여러 서비스가 동시에 동작하며, 파드가 어느 노드에 뜰지 예측할 수 없다. 300대 서버 × 30개 서비스의 환경 변수 파일을 수동으로 관리하는 것은 불가능하다. ConfigMap은 설정값을 쿠버네티스 리소스로 중앙 관리하는 방법이다.

## ConfigMap을 사용하는 이유

- **코드와 환경 분리** — 동일한 이미지로 환경별 다른 설정 적용
- **중앙 관리** — 설정이 etcd에 저장되어, 어느 노드에 파드가 배치되든 kubelet이 API Server를 통해 값을 가져옴
- **파일 마운트 방식 지원** — 볼륨으로 마운트하면 ConfigMap 변경 시 일정 시간 후 파일이 갱신됨 (단, 앱이 다시 읽어야 반영)

## 저장하는 데이터

ConfigMap에는 **민감하지 않은** 설정값을 저장한다. `kubectl get configmap -o yaml`로 값이 그대로 보이기 때문에 민감한 값은 Secret을 사용해야 한다.

```
ConfigMap → LOG_LEVEL, SERVER_PORT, API_ENDPOINT, Nginx 설정 파일
Secret    → DB_PASSWORD, JWT_SECRET, API Key
```

## YAML 구조

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: team-a
data:
  LOG_LEVEL: "info"
  SERVER_PORT: "3000"
  default.conf: |
    server {
      listen 80;
      location / {
        proxy_pass http://backend;
      }
    }
```

ConfigMap의 최대 크기는 1MiB다. 그 이상은 PV/PVC나 S3 같은 외부 저장소를 사용한다.

## 파드에 전달하는 방법 3가지

### 1. 개별 환경 변수 (`env`)

```yaml
env:
  - name: APP_MESSAGE
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: MESSAGE
```

### 2. 전체 환경 변수 (`envFrom`)

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

| 구분 | env | envFrom |
| --- | --- | --- |
| 전달 범위 | 필요한 Key만 선택 | 모든 Key 전달 |
| 이름 변경 | 가능 | 기본적으로 ConfigMap Key 그대로 사용 |
| 권장 상황 | 일부 값만 필요한 경우 | ConfigMap 전체를 사용하는 경우 |

### 3. 파일 마운트 (볼륨)

```yaml
containers:
  - volumeMounts:
      - name: config-volume
        mountPath: /etc/app-config
volumes:
  - name: config-volume
    configMap:
      name: web-config
```

## 환경 변수 vs 파일 마운트

| 구분 | 환경 변수 | 파일 마운트 |
| --- | --- | --- |
| 적합한 설정 | 짧고 단순한 값 | 여러 줄의 설정 파일 |
| 사용 예 | 포트, 로그 레벨, API 주소 | Nginx, Redis, 앱 설정 파일 |
| 변경 반영 | 실행 중 자동 반영 안 됨. 파드 재시작 후 적용 | 일정 시간 후 파일 갱신. 단, 앱이 다시 읽어야 실제 반영 |

## 다른 방법들과의 비교

| 방법 | 문제점 |
| --- | --- |
| Pod YAML에 직접 작성 | 설정이 파드 정의에 종속. 재사용·공유 불가 |
| 컨테이너 이미지에 포함 | 설정 변경 시 이미지 재빌드·재배포 필요 |
| AWS Parameter Store 등 외부 시스템 | CSP 종속. 배포 프로세스와 분리됨 |

# 5. Secret

## 핵심 개념

> 민감한 데이터를 안전하게 저장하고 Pod에 전달하기 위해 설계된 키-값 쌍 기반의 리소스
> 

ConfigMap이 일반 설정값을 담는다면, Secret은 비밀번호·API Key·인증서처럼 민감한 값을 담는다. 분리하는 이유는 **데이터 성격을 명확히 구분하기 위해서**다. 모든 값을 Secret에 넣으면 운영자가 무엇이 민감한 값인지 파악하기 어려워지고, 수천 개의 설정값을 제대로 관리하기 힘들어진다.

| 종류 | 저장 위치 |
| --- | --- |
| DB 주소, 포트, 로그 레벨, API 엔드포인트 | ConfigMap |
| DB 비밀번호, JWT 서명 키, OAuth Client Secret, TLS 인증서 | Secret |

## Secret 기본 구조

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
type: Opaque
stringData:
  DB_USERNAME: admin
  DB_PASSWORD: password1234
```

| 필드 | 설명 |
| --- | --- |
| `type` | Secret의 용도와 데이터 형식 |
| `data` | Base64로 직접 인코딩한 값을 입력 |
| `stringData` | 평문으로 작성하면 저장 시 자동으로 Base64 인코딩됨 |

## Secret 타입

| 타입 | 용도 |
| --- | --- |
| `Opaque` | 일반 KV 데이터. DB 비밀번호, API Key, JWT 서명 키 등 |
| `kubernetes.io/tls` | TLS 인증서 + 개인 키. 주로 Ingress에서 사용 |
| `kubernetes.io/dockerconfigjson` | Private Registry 접근 시 인증 정보 |

## 파드에 전달하는 방법

### 1. 환경 변수

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: database-secret
        key: DB_PASSWORD
```

### 2. 파일 마운트

```yaml
volumeMounts:
  - name: secret-volume
    mountPath: /etc/app-secret
    readOnly: true
volumes:
  - name: secret-volume
    secret:
      secretName: database-secret
```

## 🔥 Secret은 사실 Secret이 아니다

Base64는 **암호화가 아니라 인코딩**이다. Secret도 etcd에 저장되는데, etcd의 저장 시 암호화(Encryption at Rest)가 기본값이 아니다. 즉, 별도 설정 없이는 Secret 값이 etcd에 평문에 가깝게 저장된다.

| 한계 | 내용 |
| --- | --- |
| Base64 | 인코딩일 뿐, 암호화가 아님 |
| etcd 암호화 | 별도로 Encryption at Rest를 설정해야 함 |
| 접근 권한 | kubectl 권한이 있으면 Base64 디코딩으로 평문 확인 가능 |
| 비밀번호 교체 | 자동 Rotation이 기본 지원되지 않음 |

## 실무에서의 Secret 사용

실무에서는 쿠버네티스 Secret 그 자체보다 외부 비밀 관리 시스템과 연동하는 방식을 선호한다.

```
AWS Secrets Manager / Vault
          ↓
External Secrets Operator
          ↓
Kubernetes Secret
          ↓
Pod
```

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: database-external-secret
spec:
  secretStoreRef:
    name: aws-secret-store
    kind: SecretStore
  target:
    name: database-secret
  data:
    - secretKey: DB_PASSWORD
      remoteRef:
        key: production/database
        property: password
```

> 🚨 **Secret YAML을 Base64 상태라도 Git에 커밋해서는 안 된다.**
>

# 6. 전체 정리

| 개념 | 핵심 |
| --- | --- |
| Namespace | 하나의 클러스터 안에서 리소스를 논리적으로 구분하는 공간. 물리적 격리나 네트워크 차단은 아님 |
| ResourceQuota | 네임스페이스 전체의 CPU·메모리·오브젝트 수 총량을 제한하는 정책 |
| LimitRange | 개별 컨테이너·파드의 requests·limits 기본값·최솟값·최댓값을 관리하는 정책 |
| ConfigMap | 민감하지 않은 설정값을 KV 형태로 저장해 파드에 환경 변수 또는 파일로 전달하는 리소스 |
| Secret | 비밀번호·API Key·인증서 등 민감한 값을 저장하는 리소스. Base64는 암호화가 아님 |
| Namespace 오해 1 | 네임스페이스가 달라도 자원(CPU·메모리)은 공유됨 |
| Namespace 오해 2 | 네임스페이스가 달라도 파드 간 네트워크 통신은 기본적으로 가능. 차단은 NetworkPolicy 필요 |
| Namespace 오해 3 | 접근 권한 분리는 네임스페이스만으로 불가. RBAC 별도 설정 필요 |
| ResourceQuota 계산 | 실제 사용량이 아닌 선언된 requests·limits 합계 기준. 선언값 없는 파드는 배치 거부 |
| LimitRange 적용 시점 | 스케줄링 시점에 선언값 검사. 이미 실행 중인 파드에는 소급 적용 안 됨 |
| ConfigMap 변경 반영 | 환경 변수 방식은 파드 재시작 후 적용. 볼륨 마운트 방식은 파일 갱신 후 앱이 다시 읽어야 반영 |
| Secret 실무 | etcd 암호화 설정 + RBAC + External Secrets Operator(Vault, AWS SM 연동) 조합 권장 |
