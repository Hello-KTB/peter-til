# 1. CI (Continuous Integration)

## 핵심 개념

> 개발자가 작성한 코드를 자동으로 통합 및 테스트하여 코드의 품질을 지속적으로 유지하는 개발 프로세스
> 

CI는 "여러 개발자의 코드 변경"을 자주, 하나의 기준 코드에 통합하는 것을 의미한다. 단순한 도구가 아니라 **팀의 개발 방식 + 자동화 체계**다.

---

## CI가 없을 때 무슨 문제가 발생하는가

개발자들이 각자 기능을 오랫동안 개발하다가 마지막에 한 번에 합치는 방식을 사용하면 아래와 같은 문제가 생긴다.

```
커머스 팀 예시
- A → 결제
- B → 주문
- C → 회원 정책 (DB 스키마 변경)
- D → 쿠폰 정책
→ 며칠 뒤 한 번에 합치면?
```

- 같은 파일의 같은 부분을 수정한 경우
- A가 바꾼 DTO가 다른 영역에 문제를 일으키는 경우
- 의존성 충돌
- C가 DB 스키마를 변경했는데 다른 서비스가 모르는 경우

더 큰 문제는 "언제", "누구의 커밋" 때문에 "어떻게" 문제가 발생했는지 추적하기가 매우 어렵다는 것이다.

| 문제 | CI가 해결하는 방식 |
| --- | --- |
| 개발자가 로컬에서만 테스트함 | 공통된 Runner 환경에서 자동 검증 |
| 병합 후 빌드 실패 발견 | PR 또는 main 병합 직후 자동 빌드 |
| 테스트를 빼먹음 | 테스트 실행을 병합 조건으로 설정 |
| 코드 리뷰만으로 오류를 찾으려 함 | 자동 테스트와 정적 분석을 함께 실행 |
| 누가 언제 깨뜨렸는지 모름 | 커밋·PR 단위의 실행 로그와 결과 제공 |
| 배포 직전에 여러 문제를 한꺼번에 발견 | 작은 변경 단위로 빠르게 실패 발견 |

---

## CI를 구성하는 원칙

### 1. 하나의 코드 기준 베이스

```
main  → 항상 배포가 가능한 상태를 목표로 하는 "기준이 되는 브랜치"
dev   → 개발자들이 작업을 수행하는 브랜치
feature → 특정 기능을 개발하는 브랜치

main → dev로 브랜치를 나누고
dev에서 feature/login, feature/payment, feature/coupon으로 분기
→ dev에 합치는 과정으로 수행
```

### 2. 변경 사항을 "자주" 통합

- 개발자가 너무 오랫동안 다른 사람의 코드와 분리된 상태로 작업하면 안 된다.
- 큰 기능을 4주 뒤에 한 번에 합치려 하면 CI 과정이 복잡해지고, 개발자들은 본능적으로 CI를 피하게 된다.

**올바른 변경 단위 기준**

- 로그인 API 형식이 수정됐다 → 통합
- 특정 예외 처리 추가 → 통합
- Dockerfile 개선 → 통합

**피해야 하는 변경 단위**

- 인증 + 결제 + 주문 + 쿠폰 기능을 하나의 PR에 다 넣기
- 리팩토링 + 기능 추가를 같은 PR에 넣기 (리팩토링은 전역 영향, 기능 추가는 특정 도메인 영향)

### 3. 재현 가능한 빌드

개발자 노트북에서는 빌드가 되는데 CI 서버에서는 안 되는 경우가 흔하다. Secret 관리 문제, 멱등성 없는 테스트 코드, 로컬 의존성 사용 등이 원인이다.

| 항목 | 역할 |
| --- | --- |
| `pom.xml`, `build.gradle` | Java 의존성과 빌드 설정 |
| `package.json`, `package-lock.json` | Node.js 의존성과 버전 고정 |
| `Dockerfile` | 컨테이너 실행 환경 정의 |
| `docker-compose.yml` | 여러 컨테이너 구성 정의 |
| `.github/workflows/*.yml` | GitHub Actions 자동화 정의 |
| 테스트 코드 | 기대 동작 정의 |
| `.env.example` | 설정 구조 공유 |

### 4. 자동으로 테스트를 돌려야 한다

CI에서 기대하는 바는 단순히 빌드가 되는 것이 아니다. 테스트 코드 실행, 의존성 테스트가 "자동"으로 이뤄져야 한다. 개발자들은 수동 통합을 미루기 때문이다.

---

## PR → CI 흐름

| 시점 | 목적 |
| --- | --- |
| Pull Request 생성·수정 시 | 병합 전에 위험한 변경을 발견 |
| main 병합 후 | 실제로 통합된 최종 코드 상태를 다시 검증 |
| 배포 직전 | 배포할 결과물이 정상인지 최종 확인 |

PR에서도 CI를 하고, main에서도 CI를 하는 이유: 같은 코드처럼 보여도 **실제 통합된 최종 상태**를 다시 검증하기 위해서다.

---

## CI 품질 게이트

| 단계 | 필수 여부 | 이유 |
| --- | --- | --- |
| 컴파일·빌드 성공 | 필수 | 실행 불가능한 코드는 병합하면 안 됨 |
| 단위 테스트 통과 | 필수 | 핵심 로직 회귀 방지 |
| 통합 테스트 통과 | 가능하면 필수 | DB·Redis·외부 연동 오류 확인 |
| PR 리뷰 승인 | 팀 상황에 따라 | 설계·가독성·의도 검토 |
| 정적 분석 | 점진적 도입 | 코드 규칙과 잠재 문제 탐지 |
| 보안 검사 | 점진적 도입 | 알려진 취약점 탐지 |
| E2E 테스트 | 핵심 기능만 | 느린 테스트의 비용 관리 |

## 실무적으로 CI 잘하기

### 1. CI는 "빠르고 + 신뢰할 수 있어야" 한다

CI 결과까지 30분이 걸리면 개발자는 다른 일을 하고, 실패를 늦게 발견하고, 이미 실패한 CI 위에 다른 커밋이 쌓인다. 결국 PR 병합이 느려지고 CI를 무시하거나 우회하게 된다.

| 구분 | 실행 시점 | 예시 |
| --- | --- | --- |
| 빠른 검사 | 모든 PR Push | 컴파일, 단위 테스트, 포맷 검사 |
| 중간 검사 | PR 생성·병합 | 통합 테스트, Docker 이미지 빌드 |
| 느린 검사 | main 병합 후 또는 야간 | 전체 E2E, 부하 테스트, 전체 보안 스캔 |

### 2. 깨진 테스트를 방치하지 않는다

코드는 그대로인데 외부 환경에 따라 테스트 결과가 달라지는 테스트(Flaky Test)의 원인은 다음과 같다.

- 이미 어떤 데이터가 있다고 가정하는 경우 (데이터 의존)
- `LocalDateTime` 같은 현재 시간에 의존하는 경우
- 외부 API(카카오 지도 등)에 의존하는 경우
- 병렬 실행 시 데이터가 충돌하는 경우

"핵심 기능이 아닌걸"이라고 자기합리화하며 퀄리티 게이트 목록에서 제외하는 것은 피해야 한다.

### 3. Secret + 권한을 최소화

CI Runner는 보통 외부 환경(GitHub Actions의 경우 GitHub 서버)에서 실행된다. SSH `.pem` 키나 AWS 배포 권한을 과하게 등록하면, GitHub 계정이 탈취됐을 때 해커가 CI Runner를 통해 서버에 접근할 수 있다.

---

## CI 정리

| 구분 | 핵심 내용 |
| --- | --- |
| **CI란?** | 여러 개발자의 변경 사항을 자주 통합하고, 자동 빌드·테스트로 문제를 빠르게 발견하는 개발 방식 |
| **왜 필요한가?** | 각자 로컬에서는 정상이어도, 코드를 합치면 충돌·컴파일 오류·환경 차이·테스트 누락 문제가 생길 수 있기 때문 |
| **핵심 흐름** | `Push / PR → 빌드 → 테스트 → 결과 확인 → 성공 시 병합` |
| **CI의 목적** | 오류를 없애는 것이 아니라, **운영 배포 전에 오류를 발견**하는 것 |

# 2. 테스트 코드

## 핵심 개념

> 기대하는 동작이 실제로 실행되는가? 를 코드로 검증하는 과정
> 

---

## 테스트 코드의 역할

| 역할 | 설명 |
| --- | --- |
| 기능 검증 | 현재 기능이 요구사항대로 동작하는지 확인 |
| 회귀 방지 | 새 기능을 추가하거나 리팩터링한 뒤, 기존 기능이 깨졌는지 확인 |
| 요구사항 문서 | "이 기능은 어떤 입력에서 어떤 결과를 내야 하는가"를 코드로 남김 |
| 변경 안전성 확보 | 코드를 수정할 때 어디까지 영향이 있는지 빠르게 확인 |
| 설계 피드백 | 테스트하기 너무 어려운 코드라면 책임이 너무 많거나 의존성이 과도하게 얽혀 있을 가능성을 발견 |

## 테스트 종류

| 종류 | 확인 대상 | 특징 | CI 적용 우선순위 |
| --- | --- | --- | --- |
| 단위 테스트 (Unit Test) | 함수, 클래스, 서비스 로직 | 빠르고 원인 추적이 쉬움 | 매우 높음 |
| 통합 테스트 (Integration Test) | DB, Redis, API, 여러 모듈의 연결 | 실제 환경 문제를 더 잘 발견 | 높음 |
| E2E 테스트 (End-to-End Test) | 사용자의 전체 흐름 | 실제 사용자 경험과 가까움 | 선택적·핵심 시나리오 |
| 정적 분석 (Static Analysis) | 코드 규칙, 잠재 오류 | 실행 전 코드 품질 검사 | 높음 |

---

## 좋은 테스트 코드 작성 방법

### 1. 동작을 검증한다

단순히 메서드가 호출됐는지가 아니라, **기대하는 결과가 나오는지**를 검증해야 한다.

```java
// ❌ 메서드 호출 여부만 확인
@Test
void 회원가입을_실행한다() {
    userService.signUp("test@example.com", "password");
    verify(userRepository).save(any());
}

// ✅ 실제 동작 결과를 검증
@Test
void 정상적인_이메일과_비밀번호로_회원가입하면_회원이_저장된다() {
    // given
    String email = "test@example.com";
    String password = "password123!";

    // when
    UserResponse response = userService.signUp(email, password);

    // then
    assertThat(response.email()).isEqualTo(email);
    assertThat(userRepository.existsByEmail(email)).isTrue();
}
```

### 2. 하나의 중요한 동작만을 검증한다

회원가입 + 로그인 + 게시글 작성 + 댓글 작성을 하나의 테스트에 넣지 않는다. 각각 독립된 테스트로 분리한다.

### 3. 테스트는 서로 독립적이어야 한다

```
테스트 A가 회원 데이터를 생성
→ 테스트 B가 그 데이터가 존재한다고 가정
→ 테스트 B만 단독 실행하면 실패
```

이런 테스트는 CI에서 실행 순서가 바뀌거나 병렬 실행되면 결과가 달라진다.

- 각 테스트는 필요한 데이터를 직접 준비한다.
- 각 테스트는 실행 후 다른 테스트에 영향을 남기지 않는다.
- 테스트 순서가 바뀌어도 결과가 같다.

---

## 테스트 코드 작성 방법 — Given-When-Then

| 구분 | 의미 | 질문 |
| --- | --- | --- |
| Given | 테스트 준비 | 어떤 상황인가? |
| When | 실행 | 무엇을 실행했는가? |
| Then | 검증 | 무엇이 일어나야 하는가? |

```java
@Test
void 주문_금액이_0원이하면_예외가_발생한다() {
    // given
    Long userId = 1L;
    Long productId = 10L;
    int quantity = 0;

    // when & then
    assertThatThrownBy(
        () -> orderService.createOrder(userId, productId, quantity)
    ).isInstanceOf(InvalidOrderQuantityException.class);
}
```

## 테스트 대상 선정 우선순위

모든 코드를 다 테스트할 수는 없다. 중요한 코드부터 우선순위를 정해야 한다.

| 우선순위 | 대상 | 예시 |
| --- | --- | --- |
| 매우 높음 | 핵심 비즈니스 규칙 | 주문 가능 여부, 결제 금액 계산, 권한 검증 |
| 매우 높음 | 장애 시 피해가 큰 로직 | 중복 결제 방지, 재고 차감, 포인트 차감 |
| 높음 | 입력 검증과 예외 처리 | 잘못된 요청, 권한 없음, 중복 데이터 |
| 높음 | 복잡한 조건문과 계산 로직 | 할인 정책, 등급 정책, 상태 전이 |
| 중간 | 외부 시스템 연동 | Redis, DB, 메시지 큐, 외부 API |
| 낮음 | 단순 DTO, Getter, Setter | 단순 데이터 전달 객체 |
| 낮음 | 프레임워크 자동 설정 | Spring Boot 기본 설정, 단순 Configuration |

## TDD에 대하여

> Test Driven Development: 구현 코드를 작성하기 전에 테스트 코드를 먼저 작성하고, 테스트 코드를 통과하는 구현 코드를 작성하는 개발 방법론
> 

**장점** — 요구사항을 코드로 먼저 정의하고, 자연스럽게 작은 단위 개발이 된다.

**단점**

- 내가 실패할 것 같은 사항을 예측할 수 있는가? (예: soft delete된 이메일 처리를 예상 못하면 테스트 코드 자체에 구멍이 생긴다)
- 테스트 커버리지 80%라 해도 코드가 안전하다고 착각할 수 있다.
- 테스트를 "통과만 하는" 코드를 작성하게 된다. 문제를 내는 것도 나, 푸는 것도 나이기 때문이다.

---

## 테스트 코드 커버리지

- 목적이 커버리지 숫자를 올리는 것이 되면 안 된다.
- 실패를 먼저 하고, 그 부분에 대한 테스트 코드를 자세하게 작성하는 것을 반복하면 알아서 커버리지가 넓어진다.
- 5년차 코드 프로젝트도 커버리지가 20%인 경우가 있다.

---

## 테스트 코드 정리

| 구분 | 핵심 내용 |
| --- | --- |
| 테스트 코드란? | 앞으로 변경이 되어도 고장나지 않아야 하는 기능에 대한 검증 코드 |
| 좋은 테스트 | 중요한 비즈니스에 대한 "동작"을 검증, 테스트끼리 독립적, 같은 코드면 항상 같은 결과 |
| 작성 방법 | Given-When-Then 구조로 작성 |
| 테스트 우선순위 | 단위 테스트를 가장 많이, DB·Redis 등은 통합 테스트, E2E는 핵심 시나리오에만 |

# 3. CD (Continuous Delivery / Deployment)

## 핵심 개념

> 코드가 자동화된 테스트를 통과하면 운영 환경까지 자동으로 배포되는 소프트웨어 배포 프로세스
> 

CI가 "이 코드가 정상적으로 작동하는가?"를 확인한다면, CD는 확인한 코드를 실제 서버나 사용자에게 어떻게 전달할 것인가의 문제다.

---

## CI가 끝난 뒤 남는 작업

테스트가 성공했다고 해서 사용자에게 자동으로 제공되는 것은 아니다. 다음 작업이 남아 있다.

```
운영 서버 접속
→ 새 버전 준비
→ 기존 서비스 교체
→ 환경 변수 설정
→ 새 버전이 동작하는지 확인
→ 문제가 있으면 이전 버전으로 복구
```

이 "배포" 과정을 매 번 사람이 직접 수행하면 느리고 실수하기 좋은 구조가 된다.

| 문제 | 실제 상황 |
| --- | --- |
| 배포 절차가 사람마다 다름 | 어떤 개발자는 `git pull` 후 실행하고, 다른 개발자는 이미지만 교체 |
| 운영 서버를 잘못 조작 | 개발 서버가 아닌 운영 서버에서 테스트 명령 실행 |
| 테스트한 코드와 배포한 코드가 다름 | 테스트 이후 다른 커밋을 받아 배포 |
| 환경 설정 누락 | `.env`, 포트, DB 주소, API Key 등을 빠뜨림 |
| 배포 이력이 불명확 | 현재 운영 서버에 어떤 버전이 배포되었는지 모름 |
| 장애 발생 시 복구가 느림 | 이전 버전 이미지나 배포 방법을 다시 찾아야 함 |
| 배포 중 서비스 중단 | 기존 컨테이너를 종료한 뒤 새 컨테이너를 실행 |

---

## CD의 흐름

| 단계 | 하는 일 | 예시 |
| --- | --- | --- |
| CI | 코드 품질 검증 | 빌드, 테스트, 정적 분석 |
| Artifact 생성 | 배포 가능한 결과물 생성 | `.jar`, Docker 이미지, `dist/` |
| Registry 저장 | 결과물을 저장하고 배포 대상에 전달 | Docker Hub, Amazon ECR |
| Deploy | 서버 또는 플랫폼에 새 버전 반영 | EC2, ECS, Kubernetes |
| Health Check | 새 버전이 실제로 정상 동작하는지 확인 | `/health` API 호출 |
| Monitoring | 배포 이후 장애 여부 확인 | 로그, 에러율, CPU, 응답 시간 |
| Rollback | 문제가 발생하면 이전 안정 버전으로 복구 | 이전 이미지 재배포, 트래픽 전환 |

---

## Artifact

> CI를 통과하고 나서 실제로 배포할 수 있는 결과물
> 
- Spring → `.jar`
- Docker → Image
- React, Vue → `dist/`

**왜 굳이 Artifact를 별도로 보관하는가?**

운영 서버에서 직접 빌드하지 않기 위해서다. 운영 서버는 환경이 다를 수 있고, 30대의 서버가 다 동일한 시간에 만들어진 게 아니기 때문이다. **Build once → Deploy many times.**

GitHub Actions는 Step별로 Artifact를 자동 공유하지 않기 때문에, CI에서 만든 `.jar`나 Docker 이미지를 CD 단계에서 받아오려면 별도 Artifact 저장소나 Registry에 올려야 한다.

---

## CD의 두 가지 의미

| 구분 | Continuous Delivery | Continuous Deployment |
| --- | --- | --- |
| 한국어 표현 | 지속적 전달 | 지속적 배포 |
| 테스트·빌드 | 자동 | 자동 |
| 이미지 생성·저장 | 자동 | 자동 |
| 스테이징 배포 | 자동 | 자동 |
| 운영 배포 | 승인 후 실행 | 자동 실행 |
| 핵심 가치 | 안정성, 통제 | 속도, 자동화 |
| 적합한 환경 | 금융, 공공, 대기업, 게임 서버 (베타 테스트) | 빠른 배포와 피드백이 중요한 서비스 |

---

## Health Check와 Rollback이 필요한 이유

Docker 컨테이너가 실행 중이어도 내부에서 에러가 발생 중일 수 있다. "컨테이너가 뜬다 ≠ 서비스가 정상이다". 항상 백엔드에 헬스체크 API를 만들어야 한다.

Rollback은 자동화돼야 한다. 새 버전 배포 후 Health Check 실패 시 이전 버전 이미지를 가져와 다시 실행하는 스크립트가 있어야 한다.

---

## CD 정리

| 항목 | 핵심 내용 |
| --- | --- |
| CD | CI에서 검증한 결과물을 운영 환경에 안전하고 반복 가능하게 반영하는 프로세스 |
| CI와의 차이 | CI는 코드 품질 검증, CD는 검증된 결과물의 배포와 운영 반영 |
| CD가 필요한 이유 | 수동 배포의 실수, 배포 지연, 환경 차이, 복구 어려움을 줄이기 위해 |
| Continuous Delivery | 운영 배포 직전까지 자동화하고, 최종 배포는 승인 후 진행 |
| Continuous Deployment | 테스트와 조건을 통과하면 운영 환경까지 자동 배포 |
| Artifact | 배포 가능한 결과물. Docker 환경에서는 Docker 이미지 |
| Health Check | 컨테이너 실행 여부가 아니라 서비스가 실제로 정상 동작하는지 확인 |
| Rollback | 새 버전 장애 시 이전 안정 버전으로 되돌리는 작업 |

# 4. GitHub Actions

## 핵심 개념

> GitHub 저장소에서 이벤트가 발생했을 때 빌드, 테스트, 배포 같은 작업을 자동으로 실행하는 CI/CD 플랫폼
> 

---

## 왜 사용하는가

코드 Push부터 배포까지의 과정을 수동으로 하면 작업 누락, 환경 차이, 속도 저하 문제가 생긴다. GitHub Actions는 저장소 안에서 특정 이벤트(Push, PR, 릴리즈 등)를 트리거로 CI/CD 작업을 자동 실행할 수 있다.

| 구분 | CI에서 하는 일 | CD에서 하는 일 | GitHub Actions에서의 구현 |
| --- | --- | --- | --- |
| 목적 | 코드가 정상인지 검증 | 검증된 코드를 배포 | YAML 워크플로우 작성 |
| 대표 작업 | 테스트, 린트, 빌드 | Docker 이미지 Push, EC2/ECS 배포 | Job과 Step으로 단계 구성 |
| 실행 시점 | PR 생성, Push | `main` 병합, 태그 Push | `on:` 이벤트 설정 |
| 실패 시 | PR 병합 차단 가능 | 배포 중단 또는 롤백 | Job 실패 처리 |

---

## GitHub Actions 핵심 구성 요소

| 구성 요소 | 한 줄 설명 | 예시 |
| --- | --- | --- |
| **Event** | 워크플로우를 시작시키는 GitHub 이벤트 | `push`, `pull_request`, `workflow_dispatch` |
| **Workflow** | 자동화 전체 흐름을 정의한 YAML 파일 | `.github/workflows/ci.yml` |
| **Job** | 워크플로우 안의 독립 실행 작업 단위 | `test`, `build`, `deploy` |
| **Step** | Job 안에서 순서대로 실행되는 한 단계 | 코드 내려받기, 의존성 설치, 테스트 |
| **Action** | 특정 기능을 재사용하기 위해 만든 자동화 코드 조각 | `actions/checkout`, `actions/setup-node` |
| **Runner** | Job이 실제로 실행되는 컴퓨터 또는 가상 머신 | `ubuntu-latest`, Self-hosted Runner |

---

## 1. Event

```yaml
on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - dev
```

| Event | 사용 사례 |
| --- | --- |
| `push` | main 브랜치 병합 후 배포 |
| `pull_request` | PR 생성 시 테스트, 린트, 빌드 검증 |
| `workflow_dispatch` | GitHub 화면에서 수동 실행 |
| `schedule` | 매일 새벽 보안 검사, 정기 배치 작업 |
| `release` | 릴리스 생성 시 패키지 배포 |
| `issues` | 이슈 생성 시 Slack 또는 Discord 알림 |

보통 이벤트는 PR 검증, 운영 배포, 테스트 배포, PR 머지를 **전부 분리해서** 사용한다.

---

## 2. Workflow

워크플로우는 코드로 작성하기 때문에 변경 이력을 관리할 수 있고, 누가 실행해도 같은 결과가 나온다.

```
my-project/
├── src/
├── .github/
│   └── workflows/
│       ├── ci.yml
│       └── cd.yml
```

---

## 3. Runner

```yaml
runs-on: ubuntu-latest
```

| Runner 유형 | 설명 | 적합한 상황 |
| --- | --- | --- |
| GitHub-hosted Runner | GitHub가 관리하는 임시 실행 환경 | 일반적인 CI, 테스트, 빌드 |
| Self-hosted Runner | 회사 또는 개인이 직접 설치·운영하는 Runner | 내부망 접근, 사내 서버 배포, 특수 장비 사용 |

**중요**: Job마다 깨끗하게 비어있는 실행환경이 새롭게 만들어진다. 이전 실행의 의존성, 코드, 생성한 파일은 다음 Job에 공유되지 않는다.

GitHub Actions Runner에서 EC2에 접근하려면 GitHub는 외부 인터넷, EC2는 Private Subnet에 있기 때문에 SSH 포트 오픈 + IP 대역 설정 또는 Self-hosted Runner 설치가 필요하다.

---

## 4. Job

```yaml
jobs:
  test:
    runs-on: ubuntu-latest

  build:
    needs: test        # test가 완료된 뒤 실행
    runs-on: ubuntu-latest

  deploy:
    needs: build
    runs-on: ubuntu-latest
```

| 특징 | 설명 |
| --- | --- |
| 기본 실행 방식 | Job들은 기본적으로 병렬 실행 |
| 실행 환경 | 각 Job은 별도 Runner에서 실행 |
| 파일 공유 | Job 간 파일은 자동 공유되지 않음 |
| 실행 순서 제어 | `needs:`를 사용 |
| 실패 처리 | 선행 Job이 실패하면 후속 Job은 기본적으로 실행되지 않음 |

**Job을 너무 잘게 쪼개지 말 것.** Job은 각각 별도 Runner에서 실행되므로, 결과 파일을 공유하려면 별도 설정(Artifact)이 필요하다.

---

## 5. Step

```yaml
steps:
  - name: Checkout repository
    uses: actions/checkout@v6

  - name: Install dependencies
    run: npm ci

  - name: Run tests
    run: npm test
```

---

## 6. Action

자주 사용되는 기능을 미리 정의해둔 재사용 가능한 자동화 코드다.

| Action | 역할 |
| --- | --- |
| `actions/checkout` | GitHub 저장소 코드를 Runner로 내려받음 |
| `actions/setup-node` | Node.js 설치 및 설정 |
| `actions/setup-java` | Java 설치 및 설정 |
| `actions/cache` | 의존성 캐시 저장 및 복구 |
| `docker/login-action` | Docker Hub 또는 Container Registry 로그인 |
| `docker/build-push-action` | Docker 이미지 빌드 및 Push |
| `actions/upload-artifact` | 빌드 결과물 업로드 |
| `actions/download-artifact` | 다른 Job에서 빌드 결과물 다운로드 |

---

## Job 간 데이터 공유 — Cache vs Artifact

| 구분 | Cache | Artifact |
| --- | --- | --- |
| 목적 | 속도 향상 | 결과물 전달 및 보관 |
| 대표 대상 | npm, Gradle, Maven 의존성 | `.jar`, `dist/`, 테스트 리포트 |
| 다음 Job 전달 | 가능하지만 목적이 다름 | 가능 |
| 예시 | npm 캐시 | 빌드된 프론트엔드 결과물 |

```yaml
# Artifact 업로드
- name: Upload build result
  uses: actions/upload-artifact@v4
  with:
    name: frontend-build
    path: dist/

# Artifact 다운로드
- name: Download build result
  uses: actions/download-artifact@v4
  with:
    name: frontend-build

# 캐시 사용 (setup-node 내장)
- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: npm
```

---

## GitHub Actions 실제 CI 예시

```yaml
name: Node.js CI

on:
  pull_request:
    branches:
      - main
  push:
    branches:
      - main

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - name: Checkout repository
        uses: actions/checkout@v6

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run lint
        run: npm run lint --if-present

      - name: Run tests
        run: npm test

      - name: Build application
        run: npm run build --if-present
```

## GitHub Actions 정리

| 개념 | 핵심 |
| --- | --- |
| GitHub Actions | GitHub 이벤트를 기준으로 개발·운영 작업을 자동화하는 CI/CD 플랫폼 |
| Workflow | `.github/workflows/*.yml`에 정의하는 자동화 전체 흐름 |
| Event | 워크플로우 실행 조건 |
| Job | 독립된 실행 작업 단위 |
| Step | Job 안에서 순서대로 실행되는 단계 |
| Action | 재사용 가능한 자동화 코드 |
| Runner | Job이 실제로 실행되는 환경 |
| `run` | 쉘 명령어 직접 실행 |
| `uses` | Action 호출 |
| `needs` | Job 실행 순서 제어 |
| Cache | 의존성 다운로드 속도를 높이는 기능 |
| Artifact | 빌드 결과물 또는 리포트를 전달·보관하는 기능 |

---

## 전체 흐름 요약

```
CI 실패 → CD 실패 → 운영이 안정적이지 않다 → 옵저빌리티가 안 나온다 → 서비스 퀄리티가 떨어진다
```

| 단계 | 핵심 |
| --- | --- |
| CI | 코드를 자주 병합하고, 자동 빌드·테스트·정적 분석으로 문제를 운영 전에 발견 |
| 테스트 코드 | CI 자동화의 실질적인 검증 수단. 중요 비즈니스 로직 중심으로 독립적으로 작성 |
| CD | CI가 검증한 결과물을 자동화된 절차로 운영 환경에 안전하게 배포 |
| GitHub Actions | Event → Workflow → Job → Step → Action → Runner 구조로 CI/CD를 코드로 정의 |
