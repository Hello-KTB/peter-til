# 1. Controller (컨트롤러)

## 핵심 개념

> 클러스터의 현재 상태를 지속적으로 모니터링하고, 사용자가 정의한 목표 상태와 일치하도록 조치를 취하는 자동화된 관리 루프
> 

컨트롤러 없이 파드를 직접 생성하면 파드가 사라졌을 때 운영자가 직접 다시 만들어야 한다. 컨트롤러는 이 수동 관리 문제를 해결한다.

```
파드 직접 생성
    ↓ 파드 장애 또는 삭제
사라진 상태로 유지 → 운영자가 직접 재생성

Controller 사용
    ↓ 파드 장애 또는 삭제 감지
새로운 파드 자동 생성 → 사용자가 지정한 상태 유지
```

현업에서는 파드를 직접 생성하지 않는다. Deployment, StatefulSet, Job, CronJob 같은 컨트롤러를 통해 파드를 관리한다.

## 원하는 상태와 현재 상태

> 컨트롤러를 이해하려면 Desired State(원하는 상태)와 Current State(현재 상태)를 알아야 한다.
> 

**Desired State:** 운영자가 YAML 파일에 선언한 목표 상태. `spec.replicas: 3`은 파드를 3개 만들라는 일회성 명령이 아니라, 앞으로도 계속 3개를 유지하라는 선언이다.

**Current State:** 클러스터에 실제로 존재하는 상태. 원하는 상태와 다르면 컨트롤러가 감지해 조정한다.

```
원하는 상태: Pod 3개
현재 상태: Pod 2개
    ↓ Controller가 차이 감지
Pod 1개 생성
    ↓
현재 상태: Pod 3개
```

> 에어컨 비유: 사용자가 희망 온도 24도를 설정하면 에어컨이 현재 온도를 계속 감시하며 자동으로 동작한다. 컨트롤러도 동일하게 원하는 상태를 유지하려고 지속적으로 현재 상태를 확인하고 조정한다.
> 

## 컨트롤러의 핵심 역할

### 1. 원하는 상태 유지

`spec.replicas: 3`은 선언적 명령이다. 파드가 하나 삭제되면 컨트롤러가 제어 루프로 감지하고 다시 원하는 상태로 맞춘다.

### 2. Auto Healing (자동 복구)

```
Pod A / Pod B / Pod C (정상)
    ↓ Pod B 삭제
Pod A / Pod C
    ↓ Controller가 부족한 파드 감지
Pod D 생성
    ↓
Pod A / Pod C / Pod D (원하는 상태 복구)
```

쿠버네티스는 파드를 수리하지 않는다. 삭제하고 새로 만든다.

### 3. 자동 확장·축소

replicas 숫자를 변경하면 컨트롤러가 자동으로 파드를 늘리거나 줄인다.

### 4. 선언적 관리

명령형 방식은 상황에 따라 운영자가 직접 명령을 내린다. 선언형 방식은 원하는 최종 상태만 적으면 이후의 생성·삭제·복구는 컨트롤러가 알아서 처리한다.

## 컨트롤러 YAML 구조

```yaml
spec:
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:          # Pod Template: 새 파드 생성 시 사용하는 설계도
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

| 구성 요소 | 역할 |
| --- | --- |
| `replicas` | 유지할 파드 수 |
| `selector` | 컨트롤러가 관리할 파드를 찾는 조건 |
| `template` | 새로운 파드를 만들 때 사용하는 설계도 |

컨트롤러는 모든 파드를 관리하지 않는다. selector에 정의된 라벨과 일치하는 파드만 관리한다.

## 컨트롤러가 직접 수행하는 것과 요청하는 것

컨트롤러는 모든 작업을 직접 수행하지 않는다. API Server를 통해 클러스터 상태를 확인하고, 필요한 리소스 생성·수정·삭제를 "요청"한다.

```
사용자 → YAML 적용 → API Server → etcd 상태 저장
                                        ↑
Controller → API Server에 상태 조회
Controller → API Server에 파드 생성 요청
API Server → Scheduler → 배치 노드 결정
API Server → kubelet → 컨테이너 생성
```

## 컨트롤러 종류

| Controller | 주요 목적 |
| --- | --- |
| ReplicaSet | 지정한 수의 동일한 파드 복제본 유지 |
| Deployment | ReplicaSet을 관리하며 배포·업데이트·롤백 수행 |
| StatefulSet | 고유한 이름과 스토리지가 필요한 상태 기반 앱 관리 |
| DaemonSet | 조건을 만족하는 각 노드에 파드를 실행 |
| Job | 완료를 목적으로 하는 일회성 작업 실행 |
| CronJob | 정해진 일정에 따라 Job을 반복 실행 |

모든 컨트롤러의 기본 원리는 동일하다.

```
원하는 상태 선언 → 현재 상태 확인 → 두 상태 비교 → 차이가 있으면 조정
```

## 파드 직접 생성 vs 컨트롤러 사용

| 구분 | 파드 직접 생성 | 컨트롤러로 파드 관리 |
| --- | --- | --- |
| 파드 삭제 시 | 그대로 사라짐 | 새로운 파드 자동 생성 |
| 복제본 유지 | 지원하지 않음 | 지정한 수량 유지 |
| 확장·축소 | 파드를 직접 추가·삭제 | 목표 수량만 변경 |
| 장애 복구 | 운영자가 직접 처리 | 컨트롤러가 자동 처리 |
| 운영 적합성 | 단순 테스트·학습 | 지속적으로 운영할 애플리케이션 |

# 2. ReplicaSet

## 핵심 개념

> 라벨 셀렉터로 관리할 파드를 찾아, 사용자가 지정한 개수의 파드가 항상 실행되도록 유지하는 Controller
> 

```
원하는 상태: Pod 3개
    ↓ Pod 하나 삭제
현재 상태: Pod 2개
    ↓ ReplicaSet이 차이 감지
새로운 Pod 1개 생성
    ↓
현재 상태: Pod 3개
```

## ReplicaSet을 사용하는 상황 — Stateless Application

ReplicaSet은 라벨·셀렉터로 파드를 찾아 replicas 숫자와 비교만 한다. 각 파드가 독립적으로 동일한 역할을 수행하는 **Stateless Application(WAS 등)** 에 적합하다.

## YAML 구조

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-replicaset
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
```

## 라벨 사용 시 주의점

**기존 파드도 관리 대상이 될 수 있다.** 컨트롤러는 라벨만 보기 때문에, ReplicaSet을 만들기 전에 존재하던 파드라도 셀렉터 조건이 일치하면 관리 대상에 포함된다. 컨트롤러가 삭제될 때 관리 중인 파드도 함께 삭제되므로 주의해야 한다.

## ReplicaSet의 한계

ReplicaSet은 **복제본 수 유지에만 관심**을 둔다. 이미지 버전을 변경해도 이미 실행 중인 파드는 자동으로 업데이트되지 않는다. 새롭게 만들어지는 파드만 새 버전을 사용한다.

애플리케이션 운영에는 복제본 수 유지 외에 다음이 필요하다.

- 새로운 버전 배포
- 기존 파드와 새 파드의 점진적 교체
- 이전 버전으로 롤백
- 배포 이력 관리

이런 기능을 추가한 것이 **Deployment**다.

```
Deployment   → 배포 관련 관리
    └── ReplicaSet → 복제본 수 관리
            └── Pod → 실제 컨테이너 실행
```

## 자주 헷갈리는 개념들

| 오해 | 실제 동작 |
| --- | --- |
| ReplicaSet이 파드를 수리한다 | 수리하지 않는다. 삭제하고 새 파드를 생성한다 |
| 파드가 부족할 때만 동작한다 | 초과 시에도 동작한다. 복제본 수를 정확히 맞춘다 |
| Probe와 같은 역할을 한다 | Probe는 컨테이너 레벨 복구, ReplicaSet은 파드 레벨 복구. 보통 함께 사용한다 |
| 트래픽을 분산한다 | 트래픽 분산은 Service의 역할이다. ReplicaSet은 복제본 수만 관리한다 |

# 3. Deployment

## 핵심 개념

> ReplicaSet을 관리하여 파드의 개수뿐 아니라 애플리케이션의 배포, 업데이트, 롤백까지 자동으로 관리하는 상위 Controller
> 

ReplicaSet은 복제본 수 유지는 가능하지만, 배포 작업을 편리하게 처리하기 어렵다. Deployment는 다음 문제를 해결한다.

| 운영 문제 | Deployment의 해결 방법 |
| --- | --- |
| 파드를 여러 개 유지해야 함 | ReplicaSet을 통해 복제본 유지 |
| 새로운 버전을 배포해야 함 | 새로운 ReplicaSet 생성 |
| 서비스 중단을 줄여야 함 | RollingUpdate로 순차 교체 |
| 배포에 문제가 발생함 | 이전 Revision으로 롤백 |
| 배포 진행 상태를 확인해야 함 | Rollout 상태 제공 |
| 이전 버전 기록이 필요함 | 이전 ReplicaSet을 Revision으로 보관 |

## Deployment 생성 흐름

```bash
kubectl apply -f web-deployment.yaml
```

```
Deployment: web-deployment
    └── ReplicaSet: web-deployment-7f8b9c
            ├── Pod: web-deployment-7f8b9c-a1b2c
            ├── Pod: web-deployment-7f8b9c-d3e4f
            └── Pod: web-deployment-7f8b9c-g5h6i
```

## YAML 구조

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
```

ReplicaSet YAML과 구조가 거의 동일하다. `kind: Deployment`로 선언하는 것이 핵심이다.

## 업데이트 동작 방식

이미지 버전을 변경하고 `kubectl apply`를 실행하면, Deployment가 Pod Template 변경을 감지하고 **새로운 ReplicaSet을 생성**한다.

```
기존 ReplicaSet: nginx:1.27
신규 ReplicaSet: nginx:1.28
    ↓
새 RS 확장 + 기존 RS 축소 (반복)
    ↓
배포 완료
```

**Pod Template이 변경된 경우에만 새 ReplicaSet이 생성된다.** `replicas` 수 변경은 기존 ReplicaSet을 유지하고 복제본 수만 조정한다.

Pod Template 변경으로 인정되는 항목:

- 컨테이너 이미지
- 환경 변수
- Pod Label
- ConfigMap·Secret 참조
- Volume 설정
- Probe 설정
- resources requests·limits

# 4. Deployment 배포 전략

## 핵심 개념

> Deployment는 RollingUpdate와 Recreate 두 가지 배포 전략을 제공한다.
> 

| 전략 | 동작 |
| --- | --- |
| `RollingUpdate` | 기존 파드와 새로운 파드를 점진적으로 교체 |
| `Recreate` | 기존 파드를 모두 삭제한 후 새로운 파드 생성 |

## RollingUpdate

> 기존 파드를 한 번에 모두 종료하지 않고, 새로운 파드로 조금씩 교체하는 배포 전략
> 

```
v1  v1  v1
    ↓ 새 파드 하나 생성
v1  v1  v1  v2
    ↓ 기존 파드 하나 제거
v1  v1  v2
    ↓ 반복
v2  v2  v2
```

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
```

| 옵션 | 의미 |
| --- | --- |
| `maxSurge` | 업데이트 중 replicas를 초과해서 추가로 생성할 수 있는 파드 수. `replicas: 3`, `maxSurge: 1`이면 최대 4개까지 허용 |
| `maxUnavailable` | 업데이트 중 사용 불가 상태를 허용하는 최대 파드 수. `replicas: 3`, `maxUnavailable: 1`이면 최소 2개는 항상 사용 가능해야 함 |

### RollingUpdate 동작 예시

```
초기: v1 RS = 3개, v2 RS = 0개
    ↓ v2 파드 1개 생성 (maxSurge: 1 → 최대 4개 허용)
v1: 3, v2: 1
    ↓ v2 준비 완료 → v1 파드 1개 제거 (maxUnavailable: 1 기준)
v1: 2, v2: 1
    ↓ 반복
v1: 1, v2: 2 → v1: 0, v2: 3
    ↓ 배포 완료
```

### RollingUpdate는 항상 무중단인가?

서비스 중단을 **줄이는** 전략이지, 무조건 무중단이 보장되지는 않는다. 진짜 무중단이 되려면 추가로 필요한 것들:

- 새 파드가 정상 실행될 때까지 트래픽을 차단하는 **Readiness Probe** 설정
- 기존 버전과 새 버전이 동시에 동작할 수 있는 **DB 스키마 호환성**
- 클라이언트(특히 모바일 앱)에서 v1·v2 API 동시 지원

## Recreate

> 기존 파드를 전부 삭제한 뒤 새로운 파드를 생성하는 배포 전략. 서비스 중단이 발생한다.
> 

```yaml
spec:
  strategy:
    type: Recreate
```

```
v1  v1  v1
    ↓ 기존 파드 모두 삭제
-   -   -
    ↓ 새 파드 생성
v2  v2  v2
```

**Recreate를 선택하는 경우:**

- 두 버전이 동시에 실행되면 안 되는 애플리케이션 (라이브 게임 서버 등)
- 동일 리소스에 대한 동시 접근이 허용되지 않는 경우
- 개발·테스트 환경에서 빠른 교체가 필요한 경우

## RollingUpdate vs Recreate

| 구분 | RollingUpdate | Recreate |
| --- | --- | --- |
| 기존 파드 처리 | 점진적으로 삭제 | 모두 먼저 삭제 |
| 새 파드 생성 | 점진적으로 생성 | 기존 삭제 후 생성 |
| 서비스 중단 가능성 | 상대적으로 낮음 | 높음 |
| 버전 공존 | 배포 중 공존 | 공존하지 않음 |
| 주요 사용 환경 | 일반적인 운영 환경 | 개발·테스트 또는 특수한 앱 |

## Deployment 상태 확인

```bash
kubectl get deployment

NAME             READY   UP-TO-DATE   AVAILABLE   AGE
web-deployment   3/3     3            3           10m
```

| 항목 | 설명 |
| --- | --- |
| `READY` | 준비된 파드 수 / 원하는 파드 수 |
| `UP-TO-DATE` | 최신 Pod Template으로 생성된 파드 수 |
| `AVAILABLE` | 사용 가능한 상태의 파드 수 |

## 실무에서 Deployment 사용 시 주의사항

| 원칙 | 내용 |
| --- | --- |
| Stateless 앱에 사용 | WAS, 프론트 서버, 인증 서버 등 Stateless 앱은 반드시 Deployment 사용 |
| `latest` 태그 금지 | 어떤 버전이 배포됐는지 추적 불가. Semantic Version(`v1.0.3`) 또는 이미지 digest 사용 |
| Probe와 함께 사용 | 새 파드가 준비되기 전 트래픽 유입 방지를 위해 Readiness Probe 필수 |
| 배포 상태 확인 | YAML 변경이 성공해도 배포가 실패할 수 있다. `kubectl rollout status deployment/web-deployment`로 확인 |
| 이전 RS가 남아 있음 | 업데이트 후 기존 ReplicaSet이 바로 삭제되지 않는다. 롤백을 위한 Revision으로 보관된다 |

# 5. 전체 정리

| 개념 | 핵심 |
| --- | --- |
| Controller | 현재 상태를 원하는 상태와 일치시키는 자동화 관리 루프. API Server를 통해 리소스 생성·수정·삭제를 "요청"한다 |
| Control Loop | 원하는 상태 확인 → 현재 상태 확인 → 비교 → 차이가 있으면 조정. 이 반복을 Reconciliation이라 한다 |
| Desired State | `spec.replicas: 3` 같이 운영자가 YAML에 선언한 목표 상태. 일회성 명령이 아닌 지속적 유지 선언 |
| ReplicaSet | 라벨·셀렉터로 파드를 찾아 지정한 복제본 수를 유지하는 컨트롤러. 배포·업데이트 기능 없음 |
| Deployment | ReplicaSet을 관리하며 배포·업데이트·롤백까지 자동화하는 상위 컨트롤러. 실무에서 Stateless 앱의 기본 단위 |
| Pod Template | 컨트롤러가 새 파드를 생성할 때 사용하는 설계도. Template 변경 시 새 ReplicaSet 생성 |
| RollingUpdate | 기존 파드와 새 파드를 점진적으로 교체하는 배포 전략. `maxSurge`·`maxUnavailable`로 속도 조절 |
| Recreate | 기존 파드 전부 삭제 후 새 파드 생성. 서비스 중단 발생. 두 버전이 공존하면 안 되는 앱에 사용 |
| Probe + Deployment | Readiness Probe 없이 RollingUpdate하면 준비 안 된 파드로 트래픽이 유입될 수 있다 |
| ReplicaSet vs Probe | ReplicaSet은 파드 레벨 복구(파드가 사라지면 새 파드 생성), Probe는 컨테이너 레벨 복구(컨테이너 재시작). 보통 함께 사용 |
