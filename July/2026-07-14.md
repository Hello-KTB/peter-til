# 1. Pod (파드)

## 핵심 개념

> 하나 이상의 컨테이너를 그룹화하여 실행 환경과 네트워크 자원, 스토리지를 공유하는 쿠버네티스의 가장 작은 배포 단위
> 

쿠버네티스에서는 컨테이너를 워커 노드에 직접 배포하지 않는다. 컨테이너를 파드라는 실행 단위로 감싸고, 파드를 워커 노드에 배치한다.

## 파드가 필요한 이유

Docker처럼 컨테이너를 직접 배포하면 안 될까? 컨테이너가 하나일 때는 동작할 수 있다. 하지만 **최소 실행 단위가 2개 이상의 컨테이너**인 경우 문제가 생긴다.

예를 들어 백엔드 동작에 반드시 `backend-container`와 `json-parser-container`가 함께 필요하다고 가정하면:

| 노드 | 남은 자원 | 배치 결과 |
| --- | --- | --- |
| Worker Node A | 200MB | backend-container (180MB) 배치 |
| Worker Node B | 300MB | json-parser-container (50MB) 배치 |

이렇게 두 컨테이너가 다른 노드에 흩어지면, 백엔드 역할을 제대로 수행할 수 없다. 자동 배치가 이루어지려면 **"최소한 이것들이 함께 있어야 동작한다"는 단위**가 필요하다. 이것이 파드다.

## 파드와 컨테이너의 관계ㅎ

```
Cluster
└── Worker Node
    └── Pod
        └── Container(s)
```

파드 자체는 애플리케이션을 실행하지 않는다. 내부 컨테이너가 실제 애플리케이션을 실행하고, 파드는 쿠버네티스의 관리 단위가 된다. 실무에서는 파드 하나에 컨테이너 하나를 두는 경우가 가장 많다.

## 파드를 사용해서 얻는 것

같은 파드 안의 컨테이너들은 다음을 공유한다.

- 네트워크 (IP 주소, 포트 공간)
- 볼륨 (스토리지)
- 생명주기

컨테이너 간 통신 중 가장 빠른 방법은 localhost 통신이다. 같은 파드 안의 컨테이너들은 `localhost`로 서로 통신할 수 있다. 단, 포트는 겹칠 수 없다.

## 파드의 네트워크

**1. 파드마다 IP가 할당된다.**

쿠버네티스에서는 파드별로 독립적인 IP를 할당한다.

**2. 같은 파드의 컨테이너는 IP를 공유한다.**

하나의 파드에 여러 컨테이너가 있으면, 동일한 네트워크 공간을 사용한다. 즉 같은 파드 내 컨테이너 A가 8080을 쓰면 컨테이너 B는 8080을 사용할 수 없다.

## 파드 볼륨

파드에는 내부 컨테이너 전부가 접근할 수 있는 볼륨을 연결할 수 있다.

```
메인 컨테이너 (BE)
    └── 요청 처리 후 볼륨에 로그 작성
헬퍼 컨테이너 (Sidecar)
    └── 주기적으로 볼륨의 로그를 읽어 중앙 로그 저장소로 전송
```

이처럼 볼륨을 매개로 메인 컨테이너와 헬퍼 컨테이너가 데이터를 공유하는 패턴이 중앙 집중형 로깅 시스템의 기본 구조다.

# 2. 파드 유형

## 핵심 개념

> 파드는 컨테이너 구성 방식에 따라 단일 컨테이너 파드와 멀티 컨테이너 파드(사이드카 패턴)로 나뉜다.
> 

## Pod 유형 1 — 단일 컨테이너 (가장 일반적)

실무에서 가장 흔하고, 쿠버네티스의 장점을 가장 잘 살리는 구조다.

```
frontend-pod
└── frontend-container

backend-pod
└── backend-container

database-pod
└── database-container
```

**왜 FE, BE, DB를 하나의 파드에 넣지 않는가?**

쿠버네티스의 배포·확장 단위는 파드다. 하나의 파드에 여러 역할을 넣으면 두 가지 문제가 생긴다.

| 문제 | 내용 |
| --- | --- |
| 장애 파악 어려움 | 어느 컨테이너에서 문제가 발생했는지 구분하기 힘들다 |
| 독립적 확장 불가 | BE만 10개 필요해도 FE까지 10개로 늘어나 불필요한 자원이 낭비된다 |

```
# 필요한 구성
FE Container → 3개
BE Container → 10개

# application-pod(FE+BE 혼합) 방식이라면
FE Container → 10개  ← 7개 낭비
BE Container → 10개
```

## Pod 유형 2 — 멀티 컨테이너 (사이드카 패턴)

비즈니스 로직 컨테이너는 하나만 두고, 보조 기능 컨테이너(로깅, 포맷팅 등)를 함께 넣는 패턴이다.

**멀티 컨테이너 파드 주의 사항:**

- 네트워크 공간과 볼륨을 공유하므로 포트 충돌과 볼륨 충돌에 주의
- **생명주기가 항상 같다.** 트래픽 스파이크 시 파드가 빠르게 늘고 줄어야 할 때, 헬퍼 컨테이너가 외부 의존성으로 인해 시작/종료가 느리면 전체 파드의 시작과 종료가 지연된다

# 3. 🔥 파드는 일시적인 리소스다 🔥

## 핵심 개념

> 파드는 영구적으로 유지되지 않는다. 언제든지 삭제되고, 언제든지 다시 만들어질 수 있다.
> 

파드가 종료되는 대표적인 상황:

- 사용자가 직접 삭제
- 워커 노드 장애 발생
- 컨테이너 반복 장애
- 상위 관리 리소스에서 새 파드로 교체
- 노드 유지 보수
- Auto Scaling으로 처리량 감소 시 파드 축소

쿠버네티스는 파드를 가축처럼 다룬다. 장애가 나면 고치려 하지 않고 그냥 죽인 다음 새로 만든다.

## 새로 생성된 파드는 이전 파드와 완전히 다른 존재다

같은 이미지, 같은 라벨, 같은 규칙을 적용해도 새로 만들어진 파드는 이전 파드와 전혀 다른 존재다.

| 속성 | 변경 여부 |
| --- | --- |
| Pod 고유 식별자 | 변경됨 |
| IP 주소 | 변경됨 |
| 실행되는 워커 노드 | 달라질 수 있음 |
| 내부 볼륨 (임시 쓰기 레이어) | 초기화됨 |

> 🚨 **주의 사항**
> 
> - **파드 내부에 중요한 데이터를 저장하면 안 된다.**
> - **파드 IP를 고정값으로 요청 주소에 쓰면 안 된다.** (파드가 재생성되면 IP가 바뀐다)

# 4. 파드 YAML 구조

## 핵심 개념

> 쿠버네티스의 대부분의 리소스는 YAML 파일로 관리한다. 파드 역시 YAML로 원하는 상태를 선언한다.
> 

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: express-pod

spec:
  containers:
    - name: express-container
      image: adapterz/k8s-pod:latest
      ports:
        - containerPort: 3000
```

## YAML 필드 설명

| 필드 | 역할 |
| --- | --- |
| `apiVersion` | 쿠버네티스 API 버전 (Pod는 `v1`) |
| `kind` | 리소스 종류 (`Pod`, `Deployment` 등) |
| `metadata` | 리소스를 식별하는 정보 (이름, 라벨 등) |
| `spec` | 파드가 어떤 모습으로 실행되어야 하는지 정의 |
| `containers` | 파드 내부에서 실행할 컨테이너 목록 |
| `containers.name` | 컨테이너 이름 |
| `containers.image` | 컨테이너가 사용할 이미지 |
| `containers.ports` | 컨테이너가 노출하는 포트 정보 |

# 5. Label (라벨)

## 핵심 개념

> 쿠버네티스 오브젝트에 붙이는 키-값 형태의 이름표
> 

EC2 태그는 없어도 서비스가 동작하지만, 쿠버네티스에서 라벨은 리소스 관리의 핵심이다.

```yaml
app: community
env: production
tier: backend
version: v1
```

## 라벨을 사용하는 이유

> 쿠버네티스는 리소스를 동적으로 생성한다. 동적으로 생성된 리소스들은 IP와 식별자가 고정되지 않는다. 그래서 이름이 아닌 속성으로 리소스를 관리하기 위해 라벨을 사용한다.
> 

파드 10개로 스케일 아웃하면 IP도 10개로 늘어나고, 예측하거나 고정할 수 없다. 그래서 "express 서비스의 백엔드 컨테이너 중 v1인 파드"처럼 조건으로 리소스를 찾으려면 미리 라벨을 붙여 두어야 한다.

## 실무에서 자주 쓰는 라벨

| 라벨 키 | 용도 | 예시 |
| --- | --- | --- |
| `app` | 어떤 애플리케이션에 속하는지 | `app: payment`, `app: auth` |
| `tier` | 애플리케이션 내 계층 | `tier: frontend`, `tier: backend`, `tier: data` |
| `env` | 실행 환경 | `env: dev`, `env: staging`, `env: production` |
| `version` | 버전 | `version: v1`, `version: 1.0.1` |

## 라벨 구성 및 적용

라벨은 파드뿐 아니라 모든 쿠버네티스 오브젝트(Node, Service, ConfigMap, Secret, Namespace 등)에 붙일 수 있다.

```yaml
metadata:
  labels:
    env: production
    app: community
```

## 실무에서 라벨 잘 쓰기

| 원칙 | 내용 |
| --- | --- |
| 명확한 이름 | `type` 같은 모호한 이름 대신 의미가 명확한 키를 사용. 라벨은 팀 단위로 공유되며 다른 팀의 라벨도 같이 보인다 |
| 일관된 규칙 | `app` / `application` / `service` 중 하나를 팀 전체가 통일해서 사용 |
| 안정적인 값만 | `cpu-usage`나 `instance-id`처럼 자주 변하는 값은 라벨로 쓰지 않는다 |

# 6. Selector (셀렉터)

## 핵심 개념

> 라벨을 기준으로 조건에 맞는 쿠버네티스 오브젝트를 선택하는 방법
> 

라벨이 "리소스에 붙이는 이름표"라면, 셀렉터는 "그 이름표를 기준으로 리소스를 고르는 필터"다.

```yaml
# 라벨 부착
metadata:
  labels:
    app: community
    tier: backend

# 셀렉터로 선택
selector:
  app: community
  tier: backend
```

## 셀렉터를 사용하는 이유

라벨과 동일한 이유다. 파드가 재생성되면 이름과 IP가 바뀌기 때문에 특정 식별자로 고정할 수 없다. 셀렉터는 라벨 조합으로 리소스를 선택하므로, 파드가 교체되어도 동일한 역할의 파드를 계속 가리킬 수 있다.

```
파드 재생성
    ↓
이름, IP 변경
    ↓
라벨은 동일하게 유지
    ↓
셀렉터가 새로운 파드를 자동으로 선택
```

## 라벨과 셀렉터 비교

| 구분 | 역할 | 예시 |
| --- | --- | --- |
| Label | 리소스에 속성을 부착 | `app=community` |
| Selector | 속성을 기준으로 리소스를 선택 | `app=community`인 파드 선택 |

## 셀렉터 동작 예시

| Pod | Label |
| --- | --- |
| Pod A | `app=community`, `tier=frontend` |
| Pod B | `app=community`, `tier=backend` |
| Pod C | `app=community`, `tier=backend` |
| Pod D | `app=payment`, `tier=backend` |

```yaml
selector:
  app: community
  tier: backend
```

```
Pod A → 선택되지 않음 (tier=frontend)
Pod B → 선택됨
Pod C → 선택됨
Pod D → 선택되지 않음 (app=payment)
```

## 셀렉터의 주요 특징

- **라벨 기반 선택** — 이름이나 IP가 아닌 속성으로 선택
- **동적 갱신** — 조건에 맞는 리소스가 생성·삭제되면 선택 결과도 자동으로 갱신
- **AND 조건** — 여러 조건을 함께 쓰면 모두 만족하는 리소스만 선택
- **리소스 연결에 핵심** — Service가 파드를 찾을 때 셀렉터를 기본으로 사용

# 7. 전체 정리

| 개념 | 핵심 |
| --- | --- |
| Pod | 쿠버네티스의 최소 배포 단위. 하나 이상의 컨테이너를 묶어 네트워크와 스토리지를 공유 |
| 단일 컨테이너 파드 | 실무에서 가장 일반적인 구조. 역할별로 분리하여 독립적 확장 가능 |
| 사이드카 패턴 | 메인 컨테이너 + 보조 컨테이너(로깅 등). 생명주기가 항상 같음에 주의 |
| 파드의 일시성 | 파드는 언제든 삭제·재생성됨. 내부에 데이터 저장 금지, IP 고정 사용 금지 |
| YAML | 파드를 포함한 모든 쿠버네티스 리소스는 YAML로 원하는 상태를 선언 |
| Label | 쿠버네티스 오브젝트에 붙이는 키-값 이름표. 동적 리소스를 속성으로 관리하기 위해 사용 |
| Selector | 라벨을 기준으로 리소스를 선택하는 필터. 파드가 재생성되어도 동일 역할의 리소스를 자동으로 가리킴 |
