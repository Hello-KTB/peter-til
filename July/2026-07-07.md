# 1. 무중단 배포 (Zero Downtime Deployment)

## 핵심 개념

> 사용자의 입장에서 서비스 중단 없이 애플리케이션을 업데이트하거나 배포하는 방식
> 

---

## 중단 배포가 문제가 되는 이유

기본적인 배포 방식은 아래와 같다.

```bash
기존 서버 종료 → 새 코드 배포 → 새 서버 실행

docker compose down
docker compose pull
docker compose up -d
```

기존 컨테이너가 종료된 뒤 새 컨테이너가 실행될 때까지 요청을 처리할 서버가 없다. 이 시간을 **다운타임**이라고 부른다.

| 개념 | 설명 |
| --- | --- |
| 다운타임 | 서비스가 정상적으로 요청을 처리하지 못하는 시간 |
| 중단 배포 | 기존 버전을 종료하고 새 버전을 실행하는 방식 |
| 무중단 배포 | 서비스 요청을 계속 처리하면서 새 버전으로 전환하는 배포 방식 |

무중단 배포는 "서버를 멈추지 않는다"는 의미가 아니다. 배포 전략에 따라 서버나 컨테이너가 중단될 수 있지만, 그 중단이 서비스의 요청 처리를 끊지 않는 형태를 띤다.

> 새 버전을 먼저 준비하고, 준비가 완료된 뒤 트래픽을 전환한다. 정상 작동이 확인되면 기존 버전을 종료한다.
> 

---

## 무중단 배포가 꼭 필요한가?

중단 배포가 적합한 서비스도 있다. 게임 서버(대규모 업데이트), 은행(메이저 버전 변경 시 검증 필수) 등은 중단을 선택하기도 한다.

무중단 배포가 필요한 서비스 유형은 지속적으로 유저가 들어와야 하는 서비스들이다.

- 커머스, SaaS, API 서비스, 실시간 서비스
- 글로벌 트래픽을 받는 서비스 (KR → EN, JP, CN 확장 시)

---

## 좋은 배포의 요구사항

| 요구사항 | 설명 |
| --- | --- |
| **가용성** | 배포 중에도 사용자가 서비스를 이용할 수 있어야 함 |
| **안정성** | 새 버전이 정상인지 확인한 뒤 트래픽을 받아야 함 |
| **롤백 가능성** | 문제가 생기면 이전 버전으로 빠르게 돌아갈 수 있어야 함 |
| **관측 가능성** | 오류율, 응답 시간, CPU, 메모리 등을 확인할 수 있어야 함 |
| **자동화** | 사람의 수동 작업과 실수를 줄여야 함 |
| **재현성** | 누가 배포해도 동일한 절차와 결과가 나와야 함 |

---

## 무중단 배포의 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| 다중 인스턴스 또는 다중 컨테이너 | 기존 버전과 새 버전을 동시에 실행 |
| 로드밸런서 / 리버스 프록시 | 사용자 요청을 정상 서버로 분산 |
| 헬스 체크 | 새 버전이 실제 요청을 받을 준비가 되었는지 확인 |
| 트래픽 전환 정책 | 기존 버전과 새 버전 사이의 요청 비율을 조절 |
| 롤백 전략 | 새 버전에 문제가 생기면 이전 버전으로 복귀 |
| 모니터링 | 배포 후 오류율·응답 시간·리소스 상태 확인 |
| CI/CD 파이프라인 | 빌드·테스트·배포 과정을 자동화 |

---

## 기존 요청은 어떻게 처리하나? — Graceful Shutdown

새 버전으로 트래픽을 전환한 뒤 기존 서버를 종료할 때, 아래처럼 처리 중인 요청이 있을 수 있다.

- 파일 업로드 / 대용량 다운로드
- 결제 요청
- 외부 API 요청 대기 중
- WebSocket 연결

이 때 필요한 개념이 **Connection Draining / Graceful Shutdown**이다. 기존 서버에는 새 요청이 가지 않지만, 이미 처리 중인 요청을 마무리할 시간을 주는 방식이다. ECS, EKS 같은 AWS 관리형 서비스에서는 기본으로 300초 정도 설정돼 있다.

```
1. 새 버전 실행
2. 새 버전 헬스 체크 통과
3. 새 버전에 트래픽 전달 시작
4. 기존 버전에는 새 요청 전달 중단
5. 기존 요청 완료 대기 (Graceful Shutdown)
6. 기존 버전 종료
```

---

## 무중단 배포 시 고려해야 하는 사항

### 1. 애플리케이션은 가능하면 Stateless하게 설계해야 한다

서버 메모리에 사용자 상태를 저장하면 서버가 교체될 때 문제가 발생한다.

| 상태 데이터 | 일반적인 저장 위치 |
| --- | --- |
| 사용자 로그인 세션 | Redis |
| 사용자 데이터 | MySQL, PostgreSQL 등 DB |
| 업로드 파일 | S3, EFS, Object Storage |
| 캐시 | Redis, Memcached |
| 메시지 | Kafka, RabbitMQ, SQS |

### 2. 데이터베이스 변경은 무중단 배포에서도 문제가 많이 발생한다

무중단 배포 중 V1, V2가 동시에 실행 중이기 때문에 둘 다 사용자 요청을 정상적으로 처리해야 한다.

```
V1: users 테이블의 nickname 컬럼 사용
V2: nickname 컬럼 제거, display_name 컬럼 사용

올바른 순서:
1. display_name 컬럼 추가
2. V2가 nickname, display_name 모두 처리하도록 개발
3. 데이터 마이그레이션
4. 모든 서버를 V2로 전환 + V2 안정성 확인
5. nickname 컬럼 제거
```

nickname 컬럼을 먼저 제거하면 V1이 응답을 못하고, display_name에 데이터가 아직 채워지지 않은 상태가 된다. 이 경우 전날 DB 스냅샷으로 복구해야 하는데, 그 사이의 데이터는 유실된다.

### 3. 롤백 ≠ "배포 실패 시", 롤백 = "지표가 불안정"

헬스 체크를 통과했어도 지표가 불안정하면 롤백해야 한다.

| 관측 항목 | 확인 이유 |
| --- | --- |
| HTTP 5xx 비율 | 서버 오류 증가 여부 |
| 응답 시간 p95, p99 | 일부 사용자 요청 지연 여부 |
| CPU / 메모리 | 리소스 부족 여부 |
| DB 커넥션 수 | DB 과부하 여부 |
| 컨테이너 재시작 횟수 | 애플리케이션 비정상 종료 여부 |
| 핵심 비즈니스 지표 | 결제, 주문, 로그인 등의 성공률 확인 |

### 4. 무중단 배포는 실행보다 롤백 계획이 더 중요하다

Blue/Green, Rolling 같은 배포 방식에 꽂히기 쉽지만, 인프라를 다루는 포지션에서는 "안정성"과 "관측성"이 핵심이다. 무중단으로 어떻게 배포하느냐보다 문제가 생겼을 때 어떻게 안정적으로 롤백하느냐가 더 중요하다.

---

## 무중단 배포 전략 비교

| 전략 | 핵심 개념 | 특징 |
| --- | --- | --- |
| **Blue/Green** | 두 환경을 준비하고 트래픽을 한 번에 전환 | 빠른 전환, 빠른 롤백 |
| **Rolling** | 기존 인스턴스를 순차적으로 새 버전으로 교체 | 구조가 비교적 단순, 비용 절감 |
| **Canary** | 일부 사용자에게만 새 버전을 먼저 제공 | 실사용 환경에서 위험 최소화 |

---

## 무중단 배포 정리

| 항목 | 핵심 내용 |
| --- | --- |
| 무중단 배포 | 사용자가 서비스를 이용하는 동안 새 버전으로 전환하는 배포 방식 |
| 해결하려는 문제 | 배포 중 발생하는 다운타임, 요청 실패, 사용자 불편 |
| 핵심 원칙 | 새 버전을 먼저 준비하고, 정상 확인 후 트래픽을 전환 |
| 필수 요소 | 다중 인스턴스, 로드밸런서·프록시, 헬스 체크, 롤백, 모니터링 |
| 기존 요청 처리 | Connection Draining, Graceful Shutdown으로 완료 대기 |
| 대표 전략 | Blue/Green, Rolling, Canary |

# 2. Blue/Green Deployment

## 핵심 개념

> 두 개의 독립된 환경(블루, 그린)을 운영하며, 트래픽을 새로운 버전으로 전환해 서비스 중단 없이 배포와 롤백이 가능한 배포 방식
> 

---

## Blue, Green은 항상 이전 버전과 새 버전을 의미하는가?

아니다. Blue/Green은 버전 번호를 고정하는 개념이 아니다.

```bash
# 현재
app-blue  # v1.0.1 → 트래픽을 받고 있는 환경

# 배포 시작
app-green # v1.0.2 → 대기 중인 환경

# 다음 배포
app-blue  # v1.0.3 → 다시 대기 환경이 됨
```

**트래픽을 받고 있는 환경**과 **대기 중인 환경**, 이 두 개의 환경을 동시에 운영하면서 분리하는 것이 핵심이다.

---

## 장점

### 1. 빠른 롤백

새 버전에 문제가 생기면 대기 중인 이전 버전으로 바로 롤백할 수 있다. 특별한 코드를 치는 것이 아니라 Nginx의 프록시 패스를 Green → Blue로 옮기고 `nginx -s reload`만 하면 끝이다.

### 2. 배포 구조가 간단

현재 환경 ↔ 신규 환경이 분리되어 있어 배포 과정이 다른 무중단 배포 방식에 비해 단순하다.

### 3. 장애 영향 최소화

사전에 충분히 검증하고 롤백이 용이하기 때문에 서비스 영향을 최소화할 수 있다.

---

## 단점

### 1. 리소스 비용이 크다

Blue가 EC2 10대라면 Green도 EC2 10대가 필요하다. 배포 시점에 서버가 20대 운영되는 셈이다.

### 2. 이중 운영 위험

Blue, Green 둘 다 일정 시간 유지해야 한다. 배포 스크립트에서 Green 안정화 완료 후 Blue를 삭제하는 작업을 빠뜨리면 이중으로 리소스를 계속 사용하게 된다.

### 3. DB 변경이 어렵다

V1, V2가 동시에 같은 DB를 바라보기 때문에 스키마 변경 시 호환성 문제가 발생한다.

---

## Blue/Green 배포 시 실무에서 실수하는 포인트

**1. Green이 실행되자마자 트래픽 전환**
Green이 실행됐다 ≠ Green이 정상 작동한다. 반드시 헬스 체크를 통과한 뒤 트래픽을 전환해야 한다.

**2. 트래픽 전환 후 Blue를 바로 종료**
헬스 체크 통과 ≠ 안정성. 지표가 정상적으로 나오는지 일정 시간 관측한 뒤 종료해야 한다.

**3. 롤백 기준을 미리 정의하지 않음**
어떤 상황에, 어떤 지표가 어떤 수치에 닿으면 롤백할지를 미리 정의하고 코드로 작성해야 한다. HTTP 5xx 비율 5% 초과 등 기준점을 지표마다 설정해 두어야 한다.

**4. Blue와 Green의 설정이 다름**
환경 변수, 리소스 설정(CPU, Docker 네트워크), 권한(IAM, Role)이 서로 다르면 같은 이미지라도 동작이 달라진다.

---

## Blue/Green이 유리한 상황

- 결제, 주문처럼 장애 영향이 큰 서비스
- API 변경 위험이 큰 배포
- 신규 기능 릴리즈
- 대규모 리팩터링
- 인프라 설정 변경
- 공통적으로: 롤백이 필요할 수 있고, 한다면 빠르게 해야 하는 상황

---

## Blue/Green 정리

| 항목 | 핵심 내용 |
| --- | --- |
| Blue | 현재 운영 중이거나 롤백 가능한 안정 환경 |
| Green | 새 버전을 배포하고 검증하는 환경 |
| 핵심 원리 | 새 버전을 먼저 준비한 뒤 트래픽만 전환 |
| 핵심 장점 | 빠른 롤백, 낮은 다운타임, 분리된 사전 검증 |
| 핵심 단점 | 배포 중 이중 리소스 비용, DB 호환성 문제 |

# 3. Rolling Deployment

## 핵심 개념

> 서비스를 구성하는 여러 인스턴스를 한 번에 종료하지 않고, 일부씩 새 버전으로 교체하여 서비스 가용성을 유지하는 배포 전략
> 

---

## 롤링을 사용하는 이유

> 인프라를 두 배로 준비하지 않더라도 배포 중 서비스의 처리 용량을 유지하기 위해
> 

Blue/Green은 Blue 10대 + Green 10대가 필요하지만, Rolling은 V1 10대에서 9대 → 8대로 줄이면서 V2를 1대씩 늘린다.

Rolling 배포를 직접 구현하는 것은 난이도가 있기 때문에 AWS ECS, Kubernetes, EKS 같은 관리형 서비스에서 제공하는 기능을 사용하는 경우가 일반적이다.

---

## 롤링 배포의 두 가지 방식

| 방식 | 핵심 | 특징 |
| --- | --- | --- |
| **In-place 방식** | 기존 인스턴스를 하나씩 종료한 뒤 같은 자리에서 새 버전 실행 | 추가 자원이 적게 듦 |
| **Side-by-side 방식** | 새 인스턴스를 먼저 추가한 뒤 기존 인스턴스를 제거 | 처리 용량 유지에 유리 |

| 비교 항목 | In-place | Side-by-side |
| --- | --- | --- |
| 새 버전 실행 시점 | 기존 서버를 제거한 뒤 실행 | 새 서버를 먼저 추가 |
| 추가 리소스 | 거의 필요 없음 | 일시적으로 필요 |
| 배포 중 처리 용량 | 감소할 수 있음 | 비교적 유지 가능 |
| 배포 안정성 | 상대적으로 낮음 | 상대적으로 높음 |
| 롤백 속도 | 이전 버전을 재배포해야 함 | 기존 버전이 남아 있을 수 있음 |
| 적합한 환경 | 소규모·리소스 제한 환경 | 트래픽이 많고 안정성이 중요한 환경 |

---

## 장점

**1. 인프라 비용 절감** — Blue/Green에 비해 동시에 유지해야 하는 리소스가 적다.

**2. 점진적 배포** — 변경 영향을 점진적으로 전달하기 때문에, 새 버전에 문제가 생겨도 일부 인스턴스에만 영향이 간다.

---

## 단점

**1. 배포 시간이 길다** — Blue/Green은 Green 준비가 되면 바로 전환이지만, Rolling은 교체해야 하는 인스턴스가 많을수록 전체 완료까지 시간이 걸린다.

**2. V1, V2가 동시에 혼재** — 배포 중 V1과 V2가 동시에 요청을 처리한다. 클라이언트 v2가 server v1에 응답을 받는 상황이 생길 수 있기 때문에 API Versioning(`/api/v1/`, `/api/v2/`)이 필요하다.

**3. 롤백 속도가 느리다** — 이미 10대 중 8대가 V2로 교체됐다면 V1으로 롤백할 때 8대를 다시 만들어야 한다.

---

## Blue/Green vs Rolling 비교

| 비교 항목 | Blue/Green | Rolling Deployment |
| --- | --- | --- |
| 배포 방식 | 환경을 두 개 준비 후 트래픽 전환 | 기존 인스턴스를 순차 교체 |
| 트래픽 전환 | 보통 한 번에 전환 | 인스턴스 교체 과정에서 자연스럽게 분산 |
| 추가 리소스 | 배포 중 상당히 필요 | 설정에 따라 일부만 필요 |
| 배포 속도 | 전환 자체는 빠름 | 전체 완료까지 시간이 걸릴 수 있음 |
| 롤백 속도 | 매우 빠름 | 이전 버전 재배포가 필요할 수 있음 |
| V1·V2 혼재 | 전환 전후로 비교적 분리 가능 | 배포 중 혼재 상태가 일반적 |

---

## Rolling 정리

| 항목 | 핵심 내용 |
| --- | --- |
| Rolling Deployment | 기존 인스턴스를 일부씩 새 버전으로 교체하는 배포 방식 |
| 핵심 목표 | 배포 중에도 일정 수 이상의 서버가 요청을 처리하도록 유지 |
| 핵심 흐름 | V1 일부 제외 → V2 실행 → Health Check → V2 등록 → 다음 V1 교체 |
| In-place 방식 | 기존 서버를 하나씩 새 버전으로 교체, 추가 리소스가 적음 |
| Side-by-side 방식 | 새 서버를 먼저 추가한 뒤 기존 서버 제거, 용량 유지에 유리 |
| 롤백 | 이전 버전을 다시 순차 배포하는 방식이 일반적 |

# 4. Canary Deployment

## 핵심 개념

> 새 버전을 전체 사용자에게 한 번에 배포하지 않고, 일부 사용자 또는 일부 트래픽에만 먼저 노출해 실제 운영 환경에서 검증한 뒤 점진적으로 확대하는 배포 전략
> 

---

## Canary vs Rolling — 목적이 다르다

- Rolling 배포는 **인프라 교체 전략**
- Canary 배포는 **사용자 영향 범위를 제어하는 전략**

| 구분 | Rolling Deployment | Canary Deployment |
| --- | --- | --- |
| 핵심 목적 | 서버·Pod를 순차적으로 새 버전으로 교체 | 새 버전의 위험을 작은 사용자 집단에서 먼저 검증 |
| 기준 | 인스턴스 교체 순서 | 트래픽 비율 또는 사용자 그룹 |
| 새 버전 노출 | 새 인스턴스가 준비되면 자연스럽게 요청을 받음 | 의도적으로 일부 요청만 전달 |
| 배포 판단 | 새 인스턴스가 정상인지 확인 | 오류율·응답 시간·핵심 기능 지표를 보고 확산 여부 판단 |
| 대표 질문 | "몇 대씩 교체할까?" | "처음에 몇 %에게 노출할까?" |

---

## 트래픽 비율 제어

단순히 V1 90%, V2 10%로 트래픽을 나누면 문제가 생길 수 있다.

- 웹 브라우저는 강제할 수 있지만, 설치형 앱·프로그램은 클라이언트 버전을 강제할 수 없다.
- `client v2 → server v1`으로 응답을 받는 상황이 생길 수 있다.

---

## 유저 그룹 고정 — A/B Test

특정 유저를 고정해서 새로운 버전을 보여주는 방식을 **A/B Test**라고 한다. 아래 기준으로 유저를 분리할 수 있다.

- device type / OS version / client version
- 성별(F/M) / 연령대
- `user_id % 3` 등 ID 기반 분할

---

## Bake Time

카나리 트래픽을 유지하면서 새 버전의 실제 운영 지표를 관찰하는 시간이다. "10분 보고 넘어가자"처럼 짧게 설정하면 안 되고, 충분한 시간 동안 지표를 확인한 뒤 전체 확산 여부를 판단해야 한다.

## 전략 비교 총정리

| 비교 항목 | Blue/Green | Rolling | Canary |
| --- | --- | --- | --- |
| 핵심 목적 | 빠른 전환과 롤백 | 인프라 순차 교체 | 실사용 위험 최소화 |
| 트래픽 전환 | 한 번에 전환 | 인스턴스 교체에 따라 분산 | 비율 또는 유저 그룹으로 제어 |
| 추가 리소스 | 두 배 필요 | 일부만 필요 | 설정에 따라 다름 |
| 롤백 속도 | 매우 빠름 | 느림 | 비율 줄이면 비교적 빠름 |
| V1·V2 혼재 | 비교적 분리 가능 | 배포 중 혼재 | 의도적으로 혼재 |
| 적합한 상황 | 결제·주문처럼 장애 영향이 큰 서비스 | 리소스를 아끼면서 점진적으로 교체 | 새 기능을 실사용 환경에서 먼저 검증 |
