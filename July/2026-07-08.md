# 1. ECR (Elastic Container Registry)

## 핵심 개념

> Docker 이미지를 AWS 안에 안전하게 저장하고, ECS/EKS/EC2 같은 실행 환경에서 가져다 쓸 수 있게 해주는 컨테이너 이미지 저장소
> 

AWS 서비스이기 때문에 얻는 것: IAM 권한 제어, 이미지 보안 취약점 스캔, ECS·EKS 같은 AWS 서비스와의 연동, 이미지 수명주기(Life Cycle) 관리.
(ECS = 컨테이너 실행환경 관리형 서비스, EKS = 쿠버네티스 마스터 관리형 서비스)

## 이미지 / 레지스트리 / 리포지토리 / 태그

| 용어 | 설명 |
| --- | --- |
| Image | 애플리케이션 실행에 필요한 코드·라이브러리·설정을 묶은 실행 패키지 |
| Registry | 이미지를 저장하는 저장소 (ECR, Docker Hub, GitHub Container Registry) |
| Repository | 특정 이미지를 이름 기준으로 버전을 모아두는 공간. Registry 내의 폴더 같은 개념 (예: `backend` 리포지토리 → backend 이미지들을 모음) |
| Tag | 같은 이미지에서 버전을 구분 (`latest`=가장 최근, `1.0.0`=버전 태그, 커밋 SHA 태그) |

**ECR 이미지 주소 구조**

```
123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/my-backend:v1.0.0
└─ AWS 계정 ID    └─ 리전            └─ 리포지토리 이름  └─ 태그명
```

## ECR을 왜 사용하는가

> 컨테이너 이미지를 AWS 환경 안에서 안전하게 저장하고, AWS 서비스가 빠르게 가져와 실행할 수 있도록 하기 위해
> 

ECR은 AWS 종속 서비스라, AWS 서비스만 쓰는 환경에선 연동성이 매우 좋다. (외부 접근 시 IAM 권한 부여 필요. 멀티 클라우드라면 고려사항이 달라짐.)

### 1) Docker Image 보관

"각 인스턴스에서 직접 `git pull` → `docker build` 하면 되지 않나?"라는 접근의 한계:

```bash
# EC2 A
git pull origin
docker build . -t 1.0.0
```

- EC2가 300대라면 각각 접속해 빌드하거나, 빌드 이미지를 SCP로 300대에 전달해야 함 → 번거롭고 실수 가능성↑
- 300대가 전부 같은 환경이라는 보장이 없음
- 이미지는 변경 이력이 추적 가능해야 함(빌드·성공 내역 관리 → **롤백**). 300대에 개당 800MB 이미지 내역을 다 남길 수는 없음

→ Registry는 회사 내부 이미지를 관리할 때 사용. 내부 이미지엔 외부 노출 금지 정보가 있어 공유·권한 관리가 필요.

### 2) AWS 컴퓨팅 리소스(ECS/EC2/EKS)와 연결

- ECR은 AWS 내부 서비스와 연결이 편하고 **비용이 저렴**하다. (AWS 내부 네트워크 통신 비용 < 외부 네트워크 비용)
- 예: 1.2GB 이미지를 Private Subnet의 EC2(WAS)가 NAT Gateway로 받으면 컴퓨팅+네트워크 비용이 든다.

### 3) 보안 스캔

- ECR은 자동으로 보안 취약점 스캔 — Basic Scanning(업로드 시 자동), AWS Inspector(전용 취약점 조사 서비스)
- 실무 CI/CD에서는 PR 시점과 main 병합 시점 작업이 다름. 배포 태그가 아니면 Basic, **배포 태그면 Inspector까지 함께** 돌리는 식.

## 실무에서 ECR 사용 방식

개발자가 직접 push하지 않고 **CI/CD 파이프라인에서 자동으로** 사용한다.

```yaml
name: Deploy
on:
  push:
    branches: ["main"]
jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-region: ap-northeast-2
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-ecr-role
      - name: Login to Amazon ECR
        run: |
          aws ecr get-login-password --region ap-northeast-2 \
            | docker login --username AWS --password-stdin \
              123456789012.dkr.ecr.ap-northeast-2.amazonaws.com
      - name: Build image
        run: docker build -t my-backend:${{ github.sha }} .
      - name: Tag image
        run: |
          docker tag my-backend:${{ github.sha }} \
            123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/my-backend:${{ github.sha }}
      - name: Push image
        run: docker push 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/my-backend:${{ github.sha }}
```

**EC2에서 가져오기(pull & run)**

```bash
aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin \
    123456789012.dkr.ecr.ap-northeast-2.amazonaws.com

docker pull 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/my-backend:20260708-a1b2c3d
docker run -d --name my-backend -p 8080:8080 \
  123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/my-backend:20260708-a1b2c3d
```

## ECR 사용 시 주의할 점

| # | 주의점 | 내용 |
| --- | --- | --- |
| 1 | `latest`만 쓰지 않기 | 논리적으론 "최근 이미지"지만 어떤 버전을 배포 중인지 모를 수 있음. 여러 개발자가 동시 작업하면 최신 = 내 마지막 빌드라는 보장이 없음. → 명명 규칙/리포지토리 분리(`dev-${sha}`, `prod-${sha}`, `prod-${version}-${sha}`) |
| 2 | ECR은 "서비스" = 돈이 나간다 | 저장한 이미지 용량만큼 과금. CI/CD 돌 때마다 1.2GB급 이미지가 쌓임. (실제 사례: 4년 운영에 운영·개발·스테이징 이미지 총 5TB, 월 20만 원대) → **Life Cycle 정책**으로 N일 후 삭제 / 최근 N개만 보관 / 태그별 분리 |
| 3 | IAM 권한을 분리 | ECR 권한은 크게 push / pull. 전체 권한을 다 주지 말고 — 실행 서버(EC2·ECS)는 pull, CI/CD 서버(GitHub Runner)는 push |
| 4 | ECR 로그인은 영구가 아니다 | Docker Hub와 달리 ECR CLI 로그인 토큰 유효시간은 12시간. CI/CD 스크립트에는 항상 ECR 로그인 단계를 넣어야 함 |

## Private Subnet에서 ECR 접근

Private Subnet은 인터넷 연결이 없고, ECR은 VPC 안에 없는 AWS 서비스라 통신이 필요하다.

| 방법 | 특징 |
| --- | --- |
| NAT Gateway | 가능하지만 비용 발생. AWS 서비스인데 굳이 외부 인터넷을 경유 |
| VPC Endpoint | NAT·인터넷망 없이 AWS 내부망으로 통신 (권장) |

## ECR 정리

| 핵심 | 설명 |
| --- | --- |
| ECR | AWS에서 제공하는 컨테이너 이미지 저장소 |
| 저장 대상 | Docker 이미지, OCI 이미지, OCI 호환 아티팩트 |
| 주요 역할 | 이미지를 저장하고 ECS/EKS/EC2/Fargate에서 가져와 실행하게 함 |
| 실무 사용 위치 | CI/CD 파이프라인의 빌드 결과물 저장소 |

# 2. CodeDeploy

## 핵심 개념

> AWS에서 제공하는 자동화된 애플리케이션 배포 서비스
> 

"어떤 방식으로, 어떤 서비스에서, 어떤 순서로 배포할지"를 AWS 안에서 (반)자동화해주는 서비스. 대신 설정할 것이 많다.

## 기존 CI/CD 순서 (CodeDeploy 없이)

1. 코드 푸시
2. GitHub Actions 러너에서:
    1. 코드 pull
    2. 테스트 (생략 가능)
    3. 도커 빌드
    4. ECR Registry에 push
    5. **SSH로 배포 대상 서버에 직접 접속** ← 여기가 문제
    6. `docker pull`
    7. `docker run -d --name ~~`

## CodeDeploy를 쓸 때 좋아지는 점

### 1) 서버가 여러 대일 때 반복 문제가 사라진다

- 배포 대상이 EC2 10대, 1000대라면 SSH 접속 → 도커 유무 확인 → 설치 → 실행을 반복해야 함. 병렬 처리도 직접 구성해야 함.
- **동적으로 생성되는 VM(Auto Scaling Group)** 상황에선 더 심각: 기존 2대는 IP를 알아도, 스케일로 늘어난 8대의 IP는 배포 시점에 알기 어렵다(IP는 VM 생성 시 할당; aws cli로 가져올 수는 있음).
- → **Deployment Group**(Target Group 같은 개념)으로 그룹 기준 배포.

### 2) 배포 실패 시 자동 대응 강화

- 헬스 체크·메트릭 기반으로 배포 실패 시 롤백. 실패 시 어떻게 할지·어떤 이미지로 롤백할지를 설정으로 관리.

## CodeDeploy 구조

| 구성 요소 | 설명 |
| --- | --- |
| Application | CodeDeploy의 배포 단위 (백엔드 서비스, 프론트엔드 서비스 등) |
| Deployment Group | 어디에 배포할지 정하는 그룹. EC2를 직접 지정하지 않고 보통 **태그**로 지정 (예: `app=was`, `env=prod`). 서버를 목록이 아니라 태그 조합으로 관리 → EC2 만들 때 태그 설정 필수 |
| Revision | 배포할 결과물(버전). 대상에 따라 EC2 → S3 zip, ECS → Task Definition + AppSpec |
| AppSpec | 어떻게 배포를 진행할지 알려주는 배포 설명서 (기존 GitHub Actions yml 역할) |
| Deployment Configuration | 배포를 어떤 속도·방식으로 할지 (배포 전략) |

**AppSpec 예시 (hooks)**

```yaml
hooks:
  BeforeInstall: 기존 앱 정리
  ApplicationStart: 새 앱 실행
  ValidateService: 정상 실행 확인
```

**Deployment Configuration — 배포 전략**

- 전략: Blue/Green, 롤링 (대상마다 지원 전략이 다름)
- `AllAtOnce`: 한 번에 전부 / `OneAtATime`: 한 대씩 / `HalfAtATime`: 절반씩

## GitHub Actions vs CodeDeploy

| 구분 | GitHub Actions | CodeDeploy |
| --- | --- | --- |
| 성격 | 범용 자동화 도구 | AWS 배포 자동화 서비스 |
| 주 사용 | 테스트·빌드·스크립트 실행·외부 도구 연결 | EC2/ECS/Lambda 배포 관리 |
| 배포 전략 | 직접 구현해야 함 | AWS 배포 전략을 설정으로 사용 |
| AWS 연동 | Credentials 설정 필요 | AWS 서비스와 네이티브 연동 |
| 적합한 사용 | 간단한 배포, 전체 워크플로우 제어 | AWS 리소스 대상 안정적 배포 |

**실무에서는 둘을 함께 사용**: GitHub Actions로 Git 트리거 기반 CI + 이미지 빌드 → CodeDeploy로 AWS 배포.

## 단점

| # | 단점 | 내용 |
| --- | --- | --- |
| 1 | 설정이 많고 분리되어 있다 | 시간이 많이 듦. CD.yml, IAM, Role, AppSpec(배포 절차), Deployment Group(대상), Agent, ECR·S3까지 설정 필요 |
| 2 | Agent 문제 | EC2에 CodeDeploy Agent를 설치해야 하고, Agent가 항상 실행 중이어야 배포됨 → 관리 포인트 증가 (Agent 설치된 AMI를 쓰기도 함) |

## 장점

- 배포 전략을 직접 구현하지 않아도 됨(표준화)
- 배포 타이밍 조절을 직접 설정하지 않아도 됨
- EC2 같은 동적 자원에 배포하기 편함

## 언제 CodeDeploy를 선택하는가

1. EC2 배포를 표준화하고 싶다 (수동 SSH 배포는 실수 위험이 커서 피하고 싶다)
2. 여러 EC2가 동적으로 생성·삭제되는 환경
3. AWS 중심으로 CD가 동작한다
4. 배포 전략을 더 다양하게 선택하고 싶다

## CodeDeploy 퀴즈

- **Q1.** EC2에 CodeDeploy Agent가 필요한 이유 → ① EC2 내부에서 CodeDeploy 지시를 받아 파일을 내려받고 배포 스크립트를 실행하기 위해
- **Q2.** AppSpec 파일의 역할 → ② 배포할 파일 위치와 배포 단계별 실행 스크립트를 정의하는 파일
- **Q3.** "CodeDeploy = 무중단 배포 자동 보장"이 부정확한 이유 → ② 무중단 여부는 배포 대상 구조·로드밸런서·헬스 체크·배포 전략 등에 따라 달라지기 때문

# 3. 과제 관점 메모

- 예산이 적어도(EC2 1~2대, GitHub Actions Self-hosted Runner) 정답이 정해진 게 아니라 **시나리오 기반 설계**를 해야 한다.
    - 예: 100만 MAU / 1000만 MAU 가정
    - 제약(월 서버비 10만 원)은 현재의 선택 이유일 뿐, 아키텍처는 **확장 가능하게** 설계하고 트래픽 증가 시 대응 방안(ASG, AZ 확장 등)을 함께 고려.
- "아는데 안 쓰는 것"과 "몰라서 못 쓰는 것"의 차이는 크다. A를 선택하려면 B·C·D를 공부하고 A를 고른다.
- 공유할 때: "저는 이렇게 했고, 그 기술의 특징이 이러이러하기 때문에 이렇게 했다"라고 근거와 함께 공유. (데일리 스크럼은 문제와 해결 방법을 공유하는 자리)

# 4. 전체 흐름 정리

```
코드 push
  └─ GitHub Actions (CI)
       ├─ 코드 pull / 테스트 / 도커 build
       └─ ECR에 이미지 push  ────────────────┐
                                          │
              (배포)                       ▼
       CodeDeploy (CD) ── Deployment Group(태그) 대상에
       AppSpec 절차대로 ECR 이미지를 pull & run
       ├─ 배포 전략: AllAtOnce / OneAtATime / HalfAtATime / Blue-Green
       └─ 헬스 체크 실패 시 롤백
```

| 개념 | 핵심 |
| --- | --- |
| ECR | 빌드된 컨테이너 이미지를 AWS 안에 저장·관리하는 레지스트리 (CI 결과물 저장소) |
| CodeDeploy | 저장된 이미지를 대상 서버에 표준화된 전략으로 자동 배포하는 CD 서비스 |
| 함께 쓰는 이유 | GitHub Actions로 빌드·push(CI), CodeDeploy로 AWS 리소스에 안정 배포(CD) |
