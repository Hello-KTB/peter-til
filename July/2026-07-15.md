# 1. Service (서비스)

## 핵심 개념

> 파드 집합에 대한 네트워크 엔드포인트를 생성하고, 클러스터 내부 또는 외부에서 해당 파드들에 안정적으로 접근할 수 있도록 지원하는 쿠버네티스 리소스
> 

파드는 IP가 계속 바뀌고, 언제든 생성·삭제된다. 클라이언트나 내부 서비스가 특정 파드의 IP로 직접 접근하는 것은 불가능하다. 서비스는 이런 파드들 앞에서 오래 유지되는 가상의 IP와 DNS 이름을 제공한다.

> 회사 사내 내선 번호 비유: 사원이 퇴사·입사할 때마다 번호가 바뀌면 연락하기 힘드니, 개발팀 대표번호(서비스)로 전화한다. 누가 받든 연결은 된다.
> 

## 서비스의 기본 역할 — 내부 연결

서비스를 "외부 요청을 받는 것"으로 오해하기 쉽지만, 서비스의 기본 역할은 **클러스터 내부에서 변경되는 파드들에게 안정적으로 접근하게 하는 것**이다.

```
frontend Pod
    ↓ backend-service (http://backend-service:8080)
ClusterIP Service
    ├── backend Pod A (10.244.1.10)
    ├── backend Pod B (10.244.2.15)
    └── backend Pod C (10.244.2.16)
```

파드가 교체되어 IP가 바뀌어도 `backend-service:8080`만 부르면 된다. 쿠버네티스 서비스는 일관된 DNS 이름을 제공하므로, 클러스터 내부 트래픽 전달에 IP 주소 대신 서비스 이름을 사용한다.

## 서비스 핵심 역할 4가지

### 1. 안정적인 접근 주소 제공

서비스를 선언하면 클러스터 내부에서 사용할 수 있는 가상 IP와 DNS 이름이 만들어진다.

```bash
# 같은 네임스페이스
http://backend-service:8080

# 다른 네임스페이스
http://backend-service.default:8080

# 서비스 DNS 전체 구조
[서비스명].[네임스페이스].svc.cluster.local
```

### 2. 여러 파드를 하나의 대상으로 추상화

개별 파드 IP를 몰라도 서비스 이름 하나로 접근할 수 있다.

```
backend-a: 10.244.1.10
backend-b: 10.244.2.15
backend-c: 10.244.2.16
        ↓
backend-service:8080  (클라이언트는 이것만 알면 됨)
```

### 3. 대상 파드 변경을 자동 반영

셀렉터 조건에 맞는 파드가 새로 생성되면 자동으로 서비스 대상에 포함되고, 삭제되거나 조건이 맞지 않으면 자동으로 제외된다.

### 4. 기본 로드밸런싱

서비스로 들어온 트래픽이 여러 파드로 분산된다. 단, **L4 수준(IP + Port)** 로드밸런싱이다. URL 경로 기반 분산(`/api/users → A`, `/api/auth → B`)은 Ingress나 API Gateway 같은 L7 리소스가 담당한다.

## 서비스 동작 구조

```
1. Pod에 Label을 붙임
2. Service에 Selector를 작성함
3. Selector와 일치하는 Pod를 찾음
4. 해당 Pod의 IP를 EndpointSlice에 기록함
5. Service로 들어온 트래픽을 해당 Pod로 전달함
```

### EndpointSlice

서비스가 현재 연결할 수 있는 실제 파드 IP 목록을 저장하는 리소스다.

```
Service: backend-service (10.99.101.3)

EndpointSlice:
- 10.244.1.10
- 10.244.2.15
- 10.244.2.16
```

## 서비스 YAML 구조

```yaml
apiVersion: v1
kind: Service
metadata:
  name: community-service
spec:
  selector:
    app: community
    tier: backend
  ports:
    - protocol: TCP
      port: 80        # 서비스가 요청을 받는 포트
      targetPort: 3000  # 파드 컨테이너가 사용하는 포트
```

```
Client
   │ community-service:80
   ▼
Service (port: 80)
   │ targetPort: 3000
   ▼
Pod (containerPort: 3000)
```

`targetPort`는 파드 YAML의 `containerPort`와 반드시 일치해야 한다.

# 2. Service 타입

## 핵심 개념

> 서비스는 접근 범위와 목적에 따라 ClusterIP, NodePort, LoadBalancer 세 가지 타입으로 나뉜다.
> 

| 타입 | 접근 범위 | 주요 사용 목적 |
| --- | --- | --- |
| ClusterIP | 클러스터 내부 | 내부 애플리케이션 간 통신 |
| NodePort | 노드 IP + 포트로 외부 접근 | 실습 또는 제한된 외부 노출 |
| LoadBalancer | 클라우드 LB를 통한 외부 접근 | 클라우드 환경의 외부 서비스 |

## ClusterIP (기본값)

클러스터 내부에서만 접근할 수 있는 타입. 타입을 명시하지 않으면 자동으로 ClusterIP가 된다.

```yaml
spec:
  type: ClusterIP
  selector:
    app: community
    tier: backend
  ports:
    - port: 8080
      targetPort: 3000
```

ClusterIP는 사설 IP 대역(`10.x.x.x`, `172.x.x.x`, `192.x.x.x`)을 사용하므로 외부에서 직접 접근이 불가능하다. `frontend → backend`, `backend → database` 같은 내부 통신에 사용한다.

## NodePort

각 노드에 특정 포트를 열어 클러스터 외부에서 서비스에 접근할 수 있게 하는 타입.

```yaml
spec:
  type: NodePort
  ports:
    - port: 80
      targetPort: 3000
      nodePort: 31000   # 외부에서 접근하는 포트 (30000~32767)
```

```
사용자 → WorkerNodeIP:31000 → NodePort → Service → Pod:3000
```

외부에서는 `http://노드IP:31000`으로 접근한다. 실습·테스트 환경에는 적합하지만 운영 환경에는 적합하지 않다. 퍼블릭 IP와 포트를 직접 노출해야 하고, 보안·TLS·포트 충돌 등 관리 문제가 많다.

## LoadBalancer

클라우드 제공자의 외부 로드밸런서를 연결해 서비스를 외부에 노출하는 타입. EKS 같은 관리형 쿠버네티스 환경에서 주로 사용한다. kubeadm으로 직접 설치한 환경에서는 클라우드와 연결되지 않아 동작하지 않는다.

```
Internet → Cloud Load Balancer (ALB) → Service → Pod A / Pod B
```

## 서비스 타입 선택 기준

```
클러스터 내부 통신인가?
    ├── Yes → ClusterIP
    └── No
         ├── 간단한 실습·임시 노출 → NodePort
         └── 클라우드 외부 노출 → LoadBalancer (EKS)
```

## 서비스가 하지 않는 일

서비스는 **파드를 생성하지 않는다.** 만들어진 파드 중 조건에 맞는 파드에게 트래픽을 전달하는 역할만 한다. 파드를 만드는 것은 Deployment, ReplicaSet, kubelet의 역할이다.

서비스는 **URL 경로로 라우팅하지 않는다.** `/api → backend-service`, `/admin → admin-service` 같은 처리는 L7 리소스인 Ingress나 API Gateway가 담당한다.

## 실무 팁

| 상황 | 확인 포인트 |
| --- | --- |
| 서비스가 동작하지 않음 | 서비스 자체보다 EndpointSlice와 CoreDNS/LocalDNS 파드 상태를 먼저 확인 |
| 요청이 실패함 | `targetPort`(서비스)와 `containerPort`(파드)가 일치하는지 확인 |
| Selector 변경 시 | 조건이 맞는 파드 수가 충분한지 확인. 변경 직후 처리량이 급감할 수 있음 |
| NodePort | 운영 환경에서는 사용하지 않는다. Ingress나 API Gateway를 사용 |

# 3. Probe (프로브)

## 핵심 개념

> 컨테이너의 상태를 주기적으로 진단하는 메커니즘. kubelet이 컨테이너 안의 애플리케이션 상태를 주기적으로 검사하고, 결과에 따라 컨테이너를 재시작하거나 Service 트래픽에서 제외한다.
> 

컨테이너가 Running 상태라고 해서 정상 처리가 가능한 것은 아니다. 데드락, 스레드 고갈, 무한 루프, DB 연결 끊김 등 다양한 이유로 컨테이너가 실행 중이어도 요청을 처리하지 못할 수 있다.

## 프로브가 필요한 이유

쿠버네티스가 파드에게 물어봐야 하는 질문은 세 가지다.

| 확인해야 하는 상태 | 질문 |
| --- | --- |
| 시작 상태 | 애플리케이션이 정상적으로 시작되었는가? |
| 생존 상태 | 애플리케이션이 멈추지 않고 계속 동작하고 있는가? |
| 준비 상태 | 지금 사용자 요청을 받아도 되는가? |

프로브는 이 확인 작업을 kubelet이 자동으로 수행하게 한다. 수동 모니터링 대신 상태 점검을 자동화하여 대응 속도를 높인다.

### Kubelet과 프로브의 관계

프로브는 컨테이너 안에 설치된 별도 프로그램이 아니다. 워커 노드에 상주하는 kubelet이 주기적으로 컨테이너에 요청을 보내는 것이 프로브다.

```
kubelet → 프로브 요청 → 컨테이너 응답 여부 확인
                          │
               응답 O → 정상 유지
               응답 X → kubelet이 재시작 명령
```

## 프로브 진단 방법 3가지

모든 프로브 타입은 다음 세 가지 방법 중 하나로 진단한다.

| 방법 | 동작 | 정상 판단 기준 |
| --- | --- | --- |
| `httpGet` | 특정 URL 경로로 HTTP 요청 전송 | 응답 코드 2xx (200~299) |
| `tcpSocket` | 특정 포트에 TCP 연결 시도 | 연결 성공 |
| `exec` | 컨테이너 내부에서 명령어 실행 | 종료 코드 0 |

## 프로브 종류

### 1. Liveness Probe — 생존 확인, 데드락 감지

앱이 겉으로는 살아 있지만 실제로는 멈춰 있는 상태(데드락, 무한 루프 등)를 감지해 컨테이너를 재시작한다.

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5   # 컨테이너 시작 후 첫 점검까지 대기 시간
  periodSeconds: 10         # 점검 주기
  failureThreshold: 3       # 연속 실패 횟수 초과 시 재시작
```

**구현 시 주의사항:**

로직을 단순하게 유지한다. 프로브 엔드포인트에서 DB 쿼리나 복잡한 연산을 하면 점검 자체가 리소스 낭비가 된다. 단순히 200 OK를 리턴하는 경량 엔드포인트로 설계한다.

**Flapping(플래핑) 방지:**

주기가 너무 짧으면 앱이 잠깐 바빠서 응답이 느렸을 때 정상 컨테이너를 죽였다 살리는 플래핑이 발생한다. 플래핑이 생기면 가용성과 처리량이 크게 저하된다.

| 설정 | 권장값 |
| --- | --- |
| `initialDelaySeconds` | 앱 부팅 시간보다 여유 있게 |
| `failureThreshold` | 3~5회 (1~2회는 플래핑 위험) |
| `periodSeconds` | 10~30초 |
| `timeoutSeconds` | p95 응답 시간 × 3~5 |

### 2. Readiness Probe — 준비 확인, 트래픽 제어

컨테이너가 요청을 받을 준비가 되어 있는지 판단한다. 준비가 안 된 것으로 판단하면 해당 파드를 Service의 EndpointSlice에서 제거해 트래픽이 유입되지 않도록 한다.

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
```

Readiness Probe가 없으면 **무중단 배포가 불가능하다.** 롤링 업데이트 시 새로운 버전의 파드가 준비 상태가 된 이후에 서비스에 올라가야 유저가 에러를 겪지 않는다. Auto Scaling 시에도 새로 추가된 파드가 준비된 이후에 트래픽을 받아야 한다.

### 3. Startup Probe — 초기화 보호

초기화가 오래 걸리는 컨테이너에서 Liveness Probe의 오작동을 막는 용도로 사용한다.

**문제 상황:** Spring Boot 앱이 초기화에 3분이 필요한데 Liveness Probe가 10초마다 3번 실패하면 재시작을 한다. 그러면 초기화 도중 컨테이너가 무한 재시작된다(False Failure).

**Startup Probe 역할:** 앱이 초기화되는 동안 Liveness Probe가 동작하지 않도록 막아준다.

## 프로브 타입 비교

| 구분 | Startup | Liveness | Readiness |
| --- | --- | --- | --- |
| 목적 | 초기화 완료 확인 | 생존 확인 (데드락 감지) | 트래픽 처리 준비 확인 |
| 실패 시 행동 | Liveness 차단 유지 | 컨테이너 재시작 | 서비스 목록에서 제외 |
| 비유 | 출근 준비 중 방해 금지 | 심장 박동 확인 | 영업 준비 완료 확인 |

## 파드 종류별 프로브 선택 기준

| 파드 종류 | Startup | Liveness | Readiness | 핵심 전략 |
| --- | --- | --- | --- | --- |
| Frontend | X | HTTP (`/`) | HTTP (`/`) | 단순하게 (켜지면 바로 투입) |
| Backend (WAS) | O (느리다면) | HTTP (`/live`) DB 체크 금지 | HTTP (`/ready`) DB 체크 필수 | 살아있는 것과 준비된 것을 분리 |
| Database | O | TCP / CMD (보수적) | CMD (`SELECT 1`) | 신중하게 (재시작은 최후의 수단) |

# 4. QoS Class

## 핵심 개념

> Pod의 CPU·메모리 Requests와 Limits 설정을 기준으로 Kubernetes가 Pod를 자동 분류하고, 노드 자원이 부족할 때 어떤 Pod를 우선 보호하거나 퇴출할지 판단하는 기준
> 

QoS Class는 사용자가 이름으로 직접 설정하는 것이 아니다. Pod에 작성한 CPU·메모리 설정을 보고 쿠버네티스가 자동으로 결정한다.

## QoS Class가 필요한 이유

하나의 워커 노드에서 여러 파드가 자원을 함께 사용한다. 자원이 부족해지면 모든 파드를 계속 실행하지 못하는 상황이 생긴다. 무작위로 종료하면 비즈니스적으로 중요한 파드가 먼저 죽을 수 있다.

QoS Class는 중요한 파드를 상대적으로 보호하고, 자원을 많이 쓰는 파드를 식별해 노드 전체가 멈추기 전에 일부 파드를 퇴출하여 내구성을 높인다. 서비스의 중요도를 나타내는 것이 아니라, **리소스 설정에 따른 보호 수준 분류 체계**다.

# 5. Requests와 Limits

## 핵심 개념

> Requests는 파드 실행을 위해 쿠버네티스에 요청하는 최소 자원이고, Limits는 컨테이너가 사용할 수 있는 최대 자원 한도다.
> 

```yaml
resources:
  requests:
    cpu: "250m"     # CPU 코어의 25%
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "1Gi"
```

**Requests:** 스케줄러가 파드를 어느 노드에 배치할지 판단할 때 사용한다. 적어도 requests에 적힌 자원량 이상이 남아 있는 노드에 배치한다.

**Limits:** 배치된 파드가 노드 자원을 사용할 때의 최대치. CPU와 Memory는 동작이 다르다.

| 리소스 | Limit 초과 시 동작 |
| --- | --- |
| CPU | 컨테이너를 종료하지 않고 CPU 사용을 제한(Throttling) |
| Memory | OOM Kill — 컨테이너가 종료될 수 있음 |

CPU는 사용량을 줄일 수 있지만, 메모리는 한 번 할당되면 해제하기 어렵기 때문이다.

# 6. QoS Class 종류

## Guaranteed — 가장 강하게 보호

모든 컨테이너의 CPU·메모리 Request와 Limit이 동일하게 설정된 파드.

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "500m"     # requests와 동일
    memory: "512Mi" # requests와 동일
```

스케줄러는 Request만큼 자원을 확보할 수 있는 노드에만 배치하고, Limit도 동일하므로 실행 중 추가 자원을 사용할 수 없다. 노드 자원 부족 상황에서 상대적으로 가장 강하게 보호된다.

결제·인증처럼 안정성이 최우선인 서비스, 장애 시 비즈니스에 심각한 영향을 주는 파드에 적합하다.

## Burstable — 유연한 자원 활용

일부 자원은 보장받되, 노드에 여유가 있으면 요청량보다 더 많은 자원을 사용할 수 있는 파드. Guaranteed 조건을 충족하지 않으면서 Request나 Limit 중 하나라도 설정되어 있으면 Burstable로 분류된다.

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "1Gi"
```

평상시에는 Request 기준으로 실행하고, 노드에 여유가 있으면 Limit까지 자원을 더 가져다 쓴다. Guaranteed보다 자원 활용이 유연하고, BestEffort보다는 보호받는다.

Spring, Node.js API 같은 일반 WAS에 적합하다. 트래픽에 따라 자원 사용량이 달라지는 서비스들이 여기에 해당한다.

## BestEffort — 남는 자원만 사용

CPU·메모리 Requests와 Limits를 모두 설정하지 않은 파드. 자원 요청이 없으므로 스케줄러는 어느 노드든 배치할 수 있고, 노드의 남는 자원을 자유롭게 쓴다.

```yaml
spec:
  containers:
    - name: app
      image: nginx:1.27
      # resources 설정 없음
```

노드 자원 부족 시 가장 먼저 퇴출된다. 테스트 파드, 일회성 디버깅 파드, 실패해도 재시도하면 되는 통계성 작업 등에 적합하다.

## QoS Class 비교

| 구분 | Guaranteed | Burstable | BestEffort |
| --- | --- | --- | --- |
| Requests | 모든 컨테이너에 설정 | 일부 또는 전체 설정 | 설정하지 않음 |
| Limits | 모든 컨테이너에 설정 | 일부 또는 전체 설정 | 설정하지 않음 |
| Request = Limit | CPU·Memory 모두 동일 | 서로 다르거나 일부 누락 | 해당 없음 |
| 추가 자원 사용 | Limit 이상 불가 | 여유가 있으면 Limit까지 가능 | 남는 자원 사용 |
| 자원 부족 시 보호 | 상대적으로 높음 | 중간 | 상대적으로 낮음 |
| 주요 용도 | 결제·인증 등 핵심 시스템 | 일반 WAS | 테스트·디버깅 |

# 7. 파드 퇴출 (Eviction)

## 핵심 개념

> 노드를 안정적으로 유지하기 위해 kubelet이 실행 중인 파드를 노드에서 종료하는 것. 전체 파드가 죽기 전에 미리 자원을 확보하는 메커니즘이다.
> 

```
노드 자원 부족 감지
    ↓
불필요한 이미지·종료된 컨테이너 정리
    ↓
자원 부족 지속
    ↓
퇴출 대상 Pod 선정 → Pod 종료
    ↓
노드 자원 확보 → API Server 보고
    ↓
종료된 파드 재스케줄링 → 다른 노드로 배치
```

**퇴출 트리거 자원:** 메모리 부족, 디스크 공간 부족(컨테이너 이미지·로그 포함), PID 고갈

**실제 퇴출 판단 순서:**

1. 실제 사용량이 Request를 초과했는가 (Guaranteed 파드는 상대적으로 보호)
2. Pod Priority가 낮은가
3. Request 대비 현재 자원 사용량이 더 적은 파드를 우선 퇴출

# 8. 전체 정리

| 개념 | 핵심 |
| --- | --- |
| Service | 변경되는 파드 앞에 안정적인 접근 주소(가상 IP + DNS)를 제공하고 트래픽을 전달하는 리소스 |
| ClusterIP | 클러스터 내부 전용 서비스. 타입을 명시하지 않으면 기본값 |
| NodePort | 노드 IP + 포트로 외부 노출. 실습용. 운영 환경에서는 사용하지 않음 |
| LoadBalancer | 클라우드 LB를 연결해 외부에 서비스 노출. EKS 등 관리형 환경에서 사용 |
| EndpointSlice | 서비스와 연결된 실제 파드 IP 목록을 저장하는 리소스 |
| Probe | kubelet이 컨테이너 상태를 주기적으로 검사하는 메커니즘 |
| Liveness Probe | 데드락·무응답 감지 → 컨테이너 재시작 |
| Readiness Probe | 트래픽 처리 준비 확인 → 미준비 시 서비스에서 제외. 무중단 배포의 핵심 |
| Startup Probe | 초기화 시간이 긴 앱에서 Liveness의 오작동(False Failure) 방지 |
| Requests | 파드 배치를 위한 최소 자원 요청. 스케줄러가 노드 선택 시 사용 |
| Limits | 컨테이너가 사용할 수 있는 최대 자원. 초과 시 CPU는 Throttling, Memory는 OOM Kill |
| QoS Class | Requests·Limits 설정에 따라 자동 분류되는 파드 보호 수준 |
| Guaranteed | Request = Limit. 가장 강하게 보호. 결제·인증 등 핵심 서비스에 적합 |
| Burstable | Request만 설정하거나 Request ≠ Limit. 일반 WAS에 적합 |
| BestEffort | Requests·Limits 미설정. 자원 부족 시 가장 먼저 퇴출. 테스트·디버깅용 |
| Eviction | 노드 자원 부족 시 kubelet이 파드를 종료해 자원을 확보하는 메커니즘 |
