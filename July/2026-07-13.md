# 1. Kubernetes (쿠버네티스)

!image.png

## 핵심 개념

> 여러 서버에서 실행되는 많은 컨테이너를 자동으로 배치하고, 감시하고, 복구하고, 확장하기 위한 컨테이너 오케스트레이션 플랫폼
> 

Docker가 "컨테이너를 만들고 실행하는 도구"라면, 쿠버네티스는 "여러 서버에서 많은 컨테이너를 관리하는 도구"다. 컨테이너 수십 개까지는 사람이 직접 관리할 수 있지만, 수백 개가 넘어가면 배치·복구·확장을 수동으로 처리하기 불가능해진다.

## 애플리케이션 실행 방식의 변화

| 방식 | 특징 | 문제점 |
| --- | --- | --- |
| 물리 서버 | 한 서버에 모든 앱 설치 | 한 앱 장애 → 전체 영향, 라이브러리 충돌, 확장 어려움 |
| 가상 머신 | 물리 서버 자원을 나누어 앱별 독립 OS | OS마다 자원 소모가 크고 이미지도 무거움, 부팅 느림 |
| 컨테이너 | 호스트 OS 커널을 공유하여 앱 단위 격리 | 컨테이너가 많아지면 여러 서버에 걸친 운영이 어려움 |

## Docker만으로 해결 안 되는 문제

컨테이너가 수백 개로 늘어나면 사람이 직접 관리할 때 세 가지 핵심 문제가 생긴다.

**문제 1. 컨테이너가 죽으면 누가 다시 실행하나?**

컨테이너는 앱 에러, 메모리 부족, 네트워크 장애 등 다양한 이유로 종료된다. 예를 들어 173개 컨테이너 중 어떤 것이 어느 서버에서 왜 죽었는지 사람이 일일이 파악하고 재시작하기란 불가능하다.

**문제 2. 새 컨테이너를 어느 서버에 띄워야 하나?**

| 서버 | CPU 사용률 | 메모리 사용률 |
| --- | --- | --- |
| Server A | 85% | 80% |
| Server B | 30% | 40% |
| Server C | 55% | 60% |

단순히 자원이 남는 서버를 고르는 것만이 아니다. 해당 컨테이너가 필요한 자원, 네트워크 가용성, 가용성 분산 정책 등을 종합적으로 고려해야 한다.

**문제 3. 특정 서버 자체가 장애를 일으키면?**

서버 B 전체가 죽으면, 그 서버에서 실행 중이던 컨테이너들에 대한 요청이 모두 끊긴다. 남은 서버의 자원 현황을 파악하고 컨테이너를 재배치하는 작업이 즉시 이루어져야 한다.

## 쿠버네티스가 해결하는 것

- 컨테이너를 자동으로 실행·배치
- 클러스터 내 서버 자원을 실시간 모니터링
- 컨테이너 자원 사용량 실시간 모니터링
- 서버 자원에 맞춰 컨테이너 자동 배치
- 서버 에러 발생 시 컨테이너 자동 재배치
- 처리량에 따라 컨테이너 수를 자동으로 늘리거나 줄임
- 롤링 업데이트 지원
- 35대 서버에 일일이 접속하지 않고 중앙에서 관리

## 핵심 개념 3가지

쿠버네티스를 이해하려면 세 가지 개념이 핵심이다.

### 1. 선언적 관리 (Declarative Management)

> 작업 방법을 하나씩 명령하는 것이 아니라, 최종적으로 원하는 상태를 정의하는 방식
> 

| 방식 | 설명 |
| --- | --- |
| 명령형 | 운영자가 서버에 접속해서 실행 → 확인 → 실패 시 대응을 직접 수행 |
| 선언형 | "백엔드 앱이 3개 실행되면 좋겠어"라고 상태만 정의. 쿠버네티스가 알아서 맞춤 |

### 2. 원하는 상태 (Desired State)

사용자가 정의한 상태(앱 3개, 메모리 500MB, 특정 이미지 사용)와 현재 실제로 실행 중인 상태를 쿠버네티스가 지속적으로 비교한다.

### 3. 지속적인 상태 조정 (Reconciliation Loop)

```
1. 원하는 상태 확인
2. 현재 상태 확인
3. 두 상태 비교
4. 차이가 있으면 수정
5. 다시 상태 확인 → 반복
```

이 자동화된 반복 조정이 쿠버네티스 운영의 핵심이다.

# 2. 쿠버네티스 아키텍처

## 핵심 개념

> 쿠버네티스 클러스터는 "두뇌" 역할의 Control Plane과 "손발" 역할의 Worker Node로 구성된다.
> 

```
Kubernetes Cluster
├── Control Plane
├── Worker Node 1
├── Worker Node 2
└── Worker Node 3
```

클러스터를 구성하는 각 서버는 모두 **Node**라고 부른다. Node는 물리 서버, 가상 머신, EC2 등 다양하게 구성할 수 있다.

---

# 3. Control Plane

## 핵심 개념

> 클러스터 전체의 상태를 관리하고, 파드 배치를 결정하는 중앙 제어 영역
> 

```
Control Plane
├── kube-apiserver
├── etcd
├── kube-scheduler
└── kube-controller-manager
```

## 구성 요소

### kube-apiserver — 클러스터의 중앙 출입구

> 쿠버네티스 클러스터로 들어오는 모든 관리 요청의 중앙 출입구
> 

사용자가 `kubectl` 명령을 내리면 워커 노드로 직접 전달되지 않는다. 모든 요청은 API Server를 거친다.

역할

- 사용자 요청 수신
- 사용자 인증 및 권한 확인
- 요청 내용 검증
- 내부 구성 요소 간 통신 중계
- 클러스터 상태 변경 및 조회

### etcd — 클러스터의 데이터베이스

> 클러스터의 설정, 상태를 저장하는 "분산" key-value 저장소
> 

etcd에는 쿠버네티스가 필요로 하는 모든 상태 정보가 저장된다.

- 노드 목록과 상태
- 실행 중인 앱과 실행해야 할 앱의 수
- 현재 상태 / 원하는 상태
- 각종 설정 및 정책 정보

**etcd 데이터가 손실되면 쿠버네티스 클러스터는 정상 작동이 불가능하다.** 운영 환경에서는 반드시 백업, 다중화(고가용성), 접근 제한을 적용해야 한다. etcd는 애플리케이션용 DB가 아닌, 쿠버네티스 자체의 상태 저장소다.

### kube-scheduler — 파드 배치 결정자

> 새로운 파드를 어느 워커 노드에 배치할지 결정하는 구성 요소
> 

스케줄러가 고려하는 정보는 다음과 같다.

| 고려 항목 | 설명 |
| --- | --- |
| Node 자원 | CPU, 메모리 현재 사용량 |
| 파드 요구 자원 | 컨테이너가 요청한 CPU, 메모리 |
| Node 상태 | 정상 여부 |
| 배치 조건 | "BE 컨테이너와 떨어져야 한다", "Nginx와 항상 같이 있어야 한다" 등 |
| 스토리지 조건 | 특정 스토리지 필요 여부 |

스케줄러는 컨테이너를 **직접 실행하지 않는다.** 실행할 노드를 **결정만** 한다.

### kube-controller-manager — 상태 조정자

> 현재 상태를 원하는 상태로 맞추는 여러 제어 기능을 실행하는 구성 요소
> 

```
원하는 상태: 3개
현재 상태:  2개
→ kube-controller-manager가 감지
→ 부족한 파드 1개 생성 요청
```

클러스터 상태를 지속적으로 확인하고, 차이가 발생하면 필요한 작업을 실행한다.

# 4. Worker Node

## 핵심 개념

> 실제 애플리케이션(파드/컨테이너)이 실행되는 서버
> 

```
Worker Node
├── kubelet
├── Container Runtime
├── kube-proxy
└── 파드 (애플리케이션 실행 단위)
```

## 구성 요소

### kubelet — 워커 노드의 에이전트

> 각 워커 노드에서 애플리케이션 실행 상태를 관리하고, Control Plane에 보고하는 에이전트
> 

```
API Server
   ↓ 실행해야 할 내용 전달
kubelet
   ↓
Container Runtime
   ↓
Container 실행
```

역할

- API Server와 통신
- 실행해야 하는 작업 확인
- Container Runtime에 작업 요청
- 컨테이너 및 앱 상태 점검
- Node 상태 보고
- 문제 발생 컨테이너 재시작

### Container Runtime — 실제 컨테이너 실행자

> 컨테이너 이미지를 가져오고, 실제 컨테이너 프로세스를 실행하는 소프트웨어
> 

쿠버네티스 자체는 컨테이너를 직접 실행하지 않는다. Container Runtime에 실행을 위임한다.

```
kubelet
   ↓ 실행 요청
Container Runtime (containerd 등)
   ↓
Image 다운로드 → Container 생성 및 실행
```

대표적인 Container Runtime은 `containerd`, `CRI-O`다. 쿠버네티스에서 도커 이미지를 사용한다고 해서 Docker(데스크탑)를 설치할 필요는 없다. 컨테이너를 실행할 수 있는 런타임만 있으면 동작한다.

### kube-proxy — 네트워크 트래픽 관리

> 워커 노드에서 네트워크 트래픽 전달 규칙을 관리하는 구성 요소
> 

클러스터 내 여러 노드에 분산된 컨테이너 간 통신, 특히 노드 간 통신이 가능하도록 각 워커 노드의 네트워크 규칙을 관리한다. 단, kube-proxy만으로 모든 네트워킹이 해결되지는 않으며 CNI 플러그인과 함께 동작한다.

### Pod — 쿠버네티스의 최소 실행 단위

> 쿠버네티스가 컨테이너를 실행하고 관리하는 가장 작은 배포 단위
> 

쿠버네티스는 컨테이너를 직접 다루지 않고, **Pod**라는 단위로 관리한다.

```
Cluster
└── Worker Node
    └── Pod
        └── Container
```

하나의 파드에는 하나 이상의 컨테이너가 들어갈 수 있다. 같은 파드 안의 컨테이너들은 네트워크(IP, localhost), 스토리지, 생명주기를 공유한다.

```
Pod
├── Main Container (BE)
└── Helper Container (JSON Exporter)
```

# 5. 쿠버네티스를 왜 사용하는가

## 핵심 개념

> 애플리케이션의 배포, 확장, 감시, 장애 복구를 자동화하여 운영 복잡성을 줄이기 위해 사용한다.
> 

## 장점

### 1. 자동 복구 (Auto Healing)

컨테이너가 종료되거나 문제가 생기면 자동으로 다시 실행한다.

```
컨테이너 장애 → 장애 감지 → 컨테이너 재시작
```

운영자가 직접 재시작할 필요 없고, 서비스 가용성이 높아진다. 단, **쿠버네티스가 잘못된 코드나 설정을 수정하는 것이 아니다.** 원하는 수의 컨테이너를 유지할 뿐이다.

> 쿠버네티스는 컨테이너를 "가축"처럼 다룬다. 죽으면 새로 만든다. 애완동물처럼 이름을 붙이고 하나하나 돌보는 방식이 아니다.
> 

### 2. 자동 배치 (Auto Scheduling)

etcd에 저장된 노드 상태와 앱 요구사항을 기반으로, 새 파드를 적절한 노드에 자동으로 배치한다.

```
Node A: 자원 부족
Node B: 자원 충분
Node C: 장애 상태
→ 새 Pod는 Node B에 자동 배치
```

### 3. 확장성 (Scalability)

원하는 상태의 수를 바꾸면 쿠버네티스가 알아서 컨테이너를 늘리거나 줄인다. 트래픽 변화에 따른 자동 확장(HPA)도 지원한다.

### 4. 선언적 관리

원하는 상태를 YAML 파일로 정의해 관리하면, 어떤 클라우드나 환경에서도 동일하게 재현할 수 있다. AWS, GCP, NCP 등 CSP에 종속되지 않는다.

### 5. 일관된 운영 환경

YAML로 정의된 운영 환경은 어디서든 동일하게 동작한다.

## 단점

### 1. 높은 학습 난이도

쿠버네티스를 제대로 사용하려면 Linux, Container, OS, Network, Storage, 보안, Cloud, 분산 시스템 등 여러 영역의 지식이 필요하다. 소규모 팀이 도입하면 앱 개발보다 쿠버네티스 관리에 더 많은 시간이 들 수 있다.

### 2. 복잡한 운영 구조

Control Plane, Worker Node, etcd, Container Runtime, CNI, CoreDNS, Storage, Monitoring, Logging, 대시보드, 인증 등 구성 요소 자체의 관리 포인트가 상당하다.

### 3. 장애 분석 난이도

사용자 요청이 외부 네트워크 → CNI → Worker Node → kube-proxy → LocalDNS → Pod → Container → Application → Database의 여러 레이어를 거치기 때문에 장애 원인 파악이 어렵다. 중앙 집중형 로깅·모니터링 시스템이 필수이며 이는 추가 관리 포인트와 비용으로 이어진다.

### 4. 높은 비용

고가용성 구성을 갖추려면 최소 EC2 기준 약 9대 이상이 필요하다. QPS 3000 이하의 서비스라면 EC2만으로 충분한 경우가 많다.

### 5. 작은 서비스에는 의미 없음

운영 자동화를 통해 얻는 이득이 쿠버네티스 운영으로 생기는 워크로드보다 커야 도입 의미가 있다. 팀 규모, 배포 빈도, 트래픽 변화, 비용을 종합적으로 고려해야 한다.

# 6. CNI와 Pod 네트워킹

## 핵심 개념

> 쿠버네티스는 Pod에 IP를 부여하고 서로 통신할 수 있는 네트워크를 직접 구현하지 않는다. 이를 담당하는 것이 CNI 플러그인이다.
> 

## Pod도 IP 주소가 필요하다

| 구분 | 예시 | 의미 |
| --- | --- | --- |
| Node IP | `192.168.10.10` | EC2 또는 물리 서버의 실제 네트워크 IP |
| Pod IP | `10.244.1.5` | 쿠버네티스 내부에서 Pod에 할당된 IP |

Node끼리는 서로의 IP를 알고 있다. 하지만 기존 네트워크 장비는 Pod IP를 알지 못한다. 이 문제를 해결하기 위해 CNI 플러그인을 사용한다.

## CNI (Container Network Interface)

> 컨테이너 네트워크를 설정하고 제거하는 방법을 정의한 표준 규격 인터페이스
> 

CNI는 "컨테이너끼리 이렇게 통신하자"는 약속이고, CNI 플러그인은 그 약속의 실제 구현체다.

**CNI를 사용하는 이유:**

쿠버네티스가 AWS, GCP, NCP, 온프레미스 등 모든 네트워크 환경을 직접 지원하면 CSP 종속 문제가 생긴다. CNI로 표준 인터페이스만 정의하고, 환경별 구현은 플러그인에 맡김으로써 쿠버네티스는 순수한 오케스트레이션 역할에 집중할 수 있다.

대표적인 CNI 플러그인: `Flannel`, Calico, Cilium

---

# 7. Flannel

## 핵심 개념

> Flannel은 여러 노드에 있는 Pod들이 서로 통신할 수 있도록 Pod 네트워크를 구성하는 CNI 플러그인이다.
> 

## 노드별 Pod 네트워크 대역 할당

Flannel은 노드마다 독립된 Pod IP 대역을 할당한다.

| 노드 | 할당된 Pod 네트워크 |
| --- | --- |
| Node A | `10.244.1.0/24` |
| Node B | `10.244.2.0/24` |
| Node C | `10.244.3.0/24` |

## Flannel 주요 역할

| 역할 | 설명 |
| --- | --- |
| 노드별 Pod 대역 관리 | 각 노드가 사용할 Pod IP 대역을 구분 |
| Pod 네트워크 구성 | Pod가 네트워크에 연결될 수 있도록 인터페이스와 경로 구성 |
| 노드 간 통신 경로 제공 | 서로 다른 노드의 Pod끼리 통신할 수 있도록 연결 |
| 캡슐화 | VXLAN으로 Pod 패킷을 Node 간 전송 가능한 패킷으로 감쌈 |

## 같은 노드 vs 다른 노드의 통신

같은 노드 내의 Pod끼리는 노드 내부 가상 네트워크를 통해 통신할 수 있다. 문제는 **다른 노드에 있는 Pod 간의 통신**이다. 이를 해결하기 위해 Flannel은 VXLAN 방식을 사용한다.

---

# 8. VXLAN

## 핵심 개념

> VXLAN은 Pod 패킷을 Node 간에 전달할 때, UDP 패킷 안에 한 번 더 감싸는 터널링 기술이다.
> 

Pod가 보내려는 원본 패킷을 Node 간 이동이 가능한 외부 패킷으로 **캡슐화(Encapsulation)** 한다.

## VXLAN 패킷 전달 과정

`Node A의 Pod A(10.244.1.5)` → `Node B의 Pod B(10.244.2.5)`로 요청하는 경우:

**1. Pod 패킷 생성**

```
Inner Packet
출발지: 10.244.1.5
목적지: 10.244.2.5
```

**2. Node A에서 캡슐화**

10.244.2.5가 Node B 소속임을 파악하고, 원본 패킷을 UDP 패킷으로 감쌈.

```
Outer Packet
출발지 Node: 192.168.10.10 (Node A)
목적지 Node: 192.168.10.20 (Node B)
프로토콜: UDP / 목적지 포트: 8472
```

**3. 물리 네트워크 전송**

물리 네트워크는 Pod IP를 몰라도 된다. Outer Packet의 Node B IP만 알면 전달된다.

**4. Node B에서 캡슐 제거**

UDP 포트 8472로 수신 → VXLAN 헤더 제거 → 내부 패킷(10.244.1.5 → 10.244.2.5) 확인

**5. 목적지 Pod로 전달**

Node B 내부에서 원래 목적지 Pod에게 패킷 전달

> 택배 비유: Pod의 원본 패킷은 도착지가 `10.244.2.5`로 적힌 소포. 일반 배송망은 이 주소를 모르므로, Flannel이 이 소포를 `Node B (192.168.10.20)`로 적힌 큰 박스에 넣어 보낸다. Node B가 받으면 박스를 뜯어 내부 소포를 Pod에 전달한다.
> 

## 왜 UDP를 사용하나 (TCP over TCP 문제)

VXLAN이 UDP를 사용하는 이유는 원래 보내는 패킷이 이미 TCP이기 때문이다.

**TCP over TCP 문제 (TCP Meltdown):**

겉포장(터널)까지 TCP를 쓰면, 네트워크가 잠깐 느려질 때 Inner TCP와 Outer TCP가 각자 재전송을 시도한다. 안 그래도 막힌 네트워크에 패킷이 폭발적으로 쏟아져 완전히 마비된다.

| 역할 | 프로토콜 | 이유 |
| --- | --- | --- |
| 원본 데이터 (Inner) | TCP | 신뢰성, 순서 보장, 재전송 처리 |
| 터널 전송 (Outer) | UDP | 단순 운반, 오버헤드 최소화 |

터널(Flannel/UDP)은 A에서 B로 빠르게 전달하는 역할만 하면 된다. 중간에 문제가 생기면 Inner TCP가 알아서 재전송한다. 트럭 기사(UDP)가 택배 상자 안의 물건 상태까지 걱정할 필요가 없다.

# 9. kubectl

## 핵심 개념

> 쿠버네티스 API Server에 명령을 전달하는 CLI 도구. 클러스터 리소스 조회, 생성, 삭제, 디버깅 등 모든 관리 작업을 수행한다.
> 

사용자가 kubectl 명령을 내리면 직접 워커 노드로 가는 것이 아니라, Control Plane의 kube-apiserver로 전달된다.

## 기본 명령어 구조

bash

```bash
kubectl[동작][리소스][리소스 이름][옵션]
# 예시 kubectl get pods -o widekubectl describe pod express-pod -o wide -l app,env
```

## 리소스 축약어

| 전체 이름 | 축약형 | 의미 |
| --- | --- | --- |
| `pods` | `po` | Pod |
| `nodes` | `no` | Node |
| `services` | `svc` | Service |
| `namespaces` | `ns` | Namespace |
| `deployments` | `deploy` | Deployment |

## 주요 명령어

### 리소스 조회

```bash
kubectl get pods
kubectl get nodes
kubectl get svc

# 가장 많이 쓰는 옵션: 노드 IP, 할당 노드 등 상세 정보 포함
kubectl get pods -o wide
```

### 리소스 상세 조회 (디버깅)

```bash
# 파드가 제대로 안 뜨거나 계속 죽을 때 주로 사용
kubectl describe pod express-pod
```

### 로그 출력

```bash
kubectl logs express-pod

# 컨테이너가 재시작된 경우 이전 로그 확인
kubectl logs express-pod --previous

# CrashLoopBackOff: 파드를 만들자마자 계속 깨져서 루프에 걸린 상태
```

### 리소스 생성

```bash
# apply: 동일한 이름의 리소스가 있으면 변경분만 반영 (주로 사용)
# create: 동일한 이름의 리소스가 있으면 충돌 오류 발생
kubectl apply -f pod.yaml
```

`apply`를 위주로 사용한다. `create`는 이미 존재하는 리소스에 적용하면 충돌이 발생하지만, `apply`는 변경된 내용만 반영한다.

### 리소스 삭제

```bash
kubectl delete -f pod.yaml       # YAML 파일 기준 삭제
kubectl delete pod express-pod   # 이름으로 삭제
kubectl delete pods -l app=community  # 라벨로 삭제
```

### 컨테이너 내부 접속

```bash
kubectl exec -it express-pod -- sh
```

자주 쓰는 명령어를 alias로 등록하면 타이핑을 크게 줄일 수 있다.

```bash
cat <<EOF>> ~/.zshrc
alias ka='kubectl apply --recursive -f'

alias kgv='kubectl get pvc -o wide'
alias kgpa='kubectl get pods -o wide -A'
alias kgpw='kubectl get pods -o wide -w'
alias kgpaw='kubectl get pods -o wide -A -w'

alias kcn='kubectl create deployment nginx --image=nginx'
alias krb='kubectl run busybox --image=busybox --restart=Never -- sleep 1d'
EOF
```

# 10. 전체 정리

| 개념 | 핵심 |
| --- | --- |
| Kubernetes | 수많은 컨테이너를 여러 서버에서 자동으로 배치·감시·복구·확장하는 컨테이너 오케스트레이션 플랫폼 |
| Cluster | 쿠버네티스가 관리하는 서버(Node)와 리소스의 집합 |
| Control Plane | 클러스터 전체 상태를 관리하고 파드 배치를 결정하는 중앙 제어 영역 |
| kube-apiserver | 모든 요청이 거치는 중앙 출입구. 인증·검증·상태 변경 처리 |
| etcd | 클러스터의 모든 상태와 설정을 저장하는 분산 KV 저장소 |
| kube-scheduler | 새 파드를 어느 노드에 배치할지 결정하는 구성 요소 |
| kube-controller-manager | 현재 상태를 원하는 상태로 맞추기 위한 제어 루프 실행 |
| Worker Node | 실제 컨테이너(파드)가 실행되는 서버 |
| kubelet | 워커 노드에서 실행 상태를 관리하고 Control Plane에 보고하는 에이전트 |
| Container Runtime | kubelet의 요청을 받아 실제 컨테이너를 실행하는 소프트웨어 (containerd 등) |
| kube-proxy | 워커 노드의 네트워크 트래픽 전달 규칙 관리 |
| Pod | 쿠버네티스가 관리하는 최소 실행 단위. 하나 이상의 컨테이너를 포함 |
| CNI | 컨테이너 네트워크 설정 표준 인터페이스. 구현체(플러그인)가 실제 네트워크 처리 |
| Flannel | 노드별 Pod 네트워크 대역을 관리하고 노드 간 통신 경로를 제공하는 CNI 플러그인 |
| VXLAN | Pod 패킷을 UDP로 캡슐화하여 다른 노드로 전달하는 터널링 기술 |
| 선언적 관리 | 작업 방법이 아니라 원하는 상태를 정의. 쿠버네티스가 현재 상태와 비교해 자동으로 조정 |
| kubectl | kube-apiserver에 명령을 전달하는 CLI 도구. `get`, `describe`, `logs`, `apply`, `delete`, `exec` 등으로 클러스터 전체를 관리 |
